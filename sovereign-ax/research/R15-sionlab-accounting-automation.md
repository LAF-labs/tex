# R15. 시온랩(SION.LAB) 회계 자동화: 무엇을 어떻게 하고, 우리가 배울 점

> 조사일: 2026-11-05 · 요청: yulmu(대표) · 출처: [회계 자동화 솔루션 페이지](https://www.sionlab.co.kr/solutions/automation/accounting-automation)와 같은 사이트의 공개 페이지(구축 사례 1, API 상품 3, 블로그 25편, 이용약관, 개인정보처리방침). 글 목록은 부록 A.
> **검증 수준**: 공개 웹페이지만 읽었다. 문의·상담 신청·회원가입·폼 제출은 하지 않았다. 페이지는 HTML을 받아 본문 텍스트로 바꿔 읽었고, 접힌 FAQ 답은 페이지 DOM에서 읽었다. 블로그는 전체 100편 가운데 회계·홈택스·인증·운영과 관련된 25편만 읽었다. 나머지 75편(ERP·챗봇·OCR·부동산 등)은 읽지 않았으므로, "언급 없음"은 **읽은 페이지에 없다**는 뜻이다. 날짜는 페이지 메타데이터(`datePublished`, UTC)를 한국 시간으로 바꾼 값이다. 25편 모두 2026-11-04에 마지막으로 수정됐다. 시온랩 내부 구현은 공개 글에서 드러난 것만 적었고, 드러나지 않은 것은 **(추정)**으로 표시했다.
> **용도**: 경쟁사 평가가 아니다. 같은 문제(홈택스 발급·자료 수집, 사람 검토 경계)를 다른 사업 모델로 푸는 곳에서 화면 문구, 예외 처리, 운영 절차를 배울 것이 있는지 본다.

## 핵심 10줄

1. **시온랩은 제품을 파는 곳이 아니라 맞춤 개발(SI)과 API 중개를 하는 개발사다.** 회계 자동화 페이지는 "구축 상담" 랜딩이고, 가격은 공개하지 않으며 견적제다. 같은 사이트에서 주문·재고·OCR·챗봇·크롤링·설비 연동 자동화도 판다.
2. **대상 업무**: 세금계산서 발행(거래 확정 → 사업자번호·금액 검증 → 홈택스 발행 요청 → 승인번호 회수), 홈택스 매출·매입 매일 수집, 계정과목 추천과 부가세·종소세 신고 자료 집계, 법인카드·기업계좌 내역 수집, 월말 마감 상태 관리. 기존 엑셀·시트·ERP는 그대로 두고 "반복 구간만" 옮긴다는 것이 중심 문구다.
3. **회계 구축 사례는 자체 프로토타입이다.** 사례 페이지가 "자체 기획·설계 프로토타입입니다. 화면과 성과 수치는 예시입니다"라고 밝힌다. 성과표(전표 입력 85% 절감 등)도 예시다. 공개 자료로는 실제 고객 운영 사례를 확인할 수 없었다.
4. **기술**: 사례 스택은 Next.js·TypeScript·PostgreSQL·OpenAI API다. 홈택스 연동 방식(RPA, 스크래핑, 인증서 위치)은 공개하지 않고 "상담 단계에서 확인"으로 미룬다. API 상품 페이지는 수집 방식을 "홈택스에서 조회한 결과를 수집해 단일 스키마로 정규화"라고 쓰고, 흐름을 "SIONLAB API 게이트웨이를 거쳐 원천 기관으로 전달"이라고 그린다. 서버 쪽에서 원천을 조회하는 중개형으로 보인다(추정).
5. **사람 개입 지점은 우리와 거의 같은 말로 정해 두었다.** "신고·지급·외부 제출의 승인 책임은 담당자에게", "추천값과 확정값을 따로 저장하고 확정한 것만 반영", "자동화는 자료를 모아 차이를 보여 주는 데까지". 다른 점은 하나다. 발행은 **거래 확정이 곧 트리거**이고, 건마다 승인하는 단계가 따로 없다.
6. **예외 처리 원칙도 우리 설계와 겹친다.** 응답이 끊긴 발행은 다시 발행하지 않고 기존 발행부터 조회하고, 부분 성공은 보존하고 실패 건만 재처리하며, 일시 오류와 입력 오류를 나누고, 재시도에 상한을 둔다. 우리가 이미 정한 것들(02 §4, 08 §11, D03 §6)을 밖에서 다시 확인한 셈이다.
7. **우리에게 없는 디테일이 몇 가지 있다.** ① 거래처 상태 **조회 실패를 폐업과 구분해 '확인 불가'로 둔다** ② 진위확인과 상태조회는 다른 기능이라고 나눈다 ③ 내보내는 파일 안에 사업자·기간·행 수·합계를 적어 범위를 다시 대조한다 ④ 원본의 공급가액·세액·합계 세 값을 따로 보관하고, 합계가 맞지 않는 행은 보류하며, 같은 거래를 다시 받아도 행이 늘지 않게 한다 ⑤ OCR은 필드마다 위험이 다르다고 보고 검증 규칙을 달리 둔다.
8. **법·운영 리스크는 "확인하라"고만 쓴다.** "홈택스 이용 조건에서 자동 조회를 어디까지 허용하는지 확인", "원천 공개 여부와 수집 방식, 법적 검토는 상담 접수 후 타당성 회신 단계에서"처럼 고객이 확인할 항목으로 적는다. 국세청과의 관계, 인증서 위임 계약, 세무사법은 읽은 페이지에 언급이 없다. 사이트 이용약관은 웹사이트·상담·뉴스레터만 다루고, 자동화 서비스 약관은 없다.
9. **콘텐츠 운영이 눈에 띈다.** 대표 명의로 블로그 글 100편을 올렸다(읽은 글 가운데 가장 이른 것은 2026-04-01). 글마다 "프로토타입이며 실제 고객 성과가 아님", "2026년 10월 7일 조회", "로컬 시연 자료 검증, 급여 지급 아님"처럼 **범위와 확인 날짜를 본문에 적는다.** 세무사법 광고 규정(R5 #8, R13 #4) 때문에 대외 문구를 다듬어야 하는 우리에게 참고가 된다.
10. **배울 점 상위 3개(제안, 사용자 확인 전)**: ① 거래처 상태에 '확인 불가'를 더해 세 상태로 나누고, 등록 단계에서도 휴·폐업은 멈추지 않고 경고한다(08 §4·§8·§11, 02 §4) ② 세무사 꾸러미 엑셀에 범위 표지(사업자번호·기간·시트별 행 수·합계)를 넣고, 매출·매입 행은 승인번호 기준으로 중복을 없애고 공급가액·세액·합계 불일치를 표시한다(02 §17, ADR-032) ③ 대외 문구 허용 사전에 "자료를 모아 차이를 보여 주는 데까지", "신고와 판단은 사장님과 세무사가"류 경계 문장과 "확인 날짜·범위 표기" 규칙을 넣는다(D11 §8, R13 §2.4, 01 §8). §5에 상세가 있다.

## 1. 무엇을 자동화하는가

### 1-A. 대상 업무

### 1-B. 대상 고객

- 회계 자동화 구축: 직원 10인 미만 중소사업자(사례 기준), 세무사무소(설계 시나리오), 엑셀·시트로 거래를 관리하는 사업자. [W-accounting], [B-tax-office]
- API 상품: ERP·경영관리·세무 SaaS, 핀테크·여신 심사, 세무대리인. 홈택스 매입/매출 API에는 "세무대리 전용" 수임처 총액 집계 엔드포인트가 있다. [API-58]

### 1-C. 가격과 도입 방식

- **가격 비공개, 견적제.** 견적 변수로 월 처리 건수, 사업자 수, 프로그램 연결 방식, 거래 양식 종류, 승인·복구 절차를 든다. [B-tax-invoice-automation], [솔루션]
- 구축 흐름: 무료 설계 제안 → 화면·필드·승인 규칙 초안 → 연결안과 시작 순서. "지금 쓰는 엑셀과 양식을 보내 주시면 설계 초안으로 회신". [솔루션]
- API 상품: 상담 → 2~5영업일 안에 타당성·범위 회신(원천 공개 여부·수집 방식·법적 검토) → 응답 스키마 합의 → 인증키 발급·연동·검수. 키 하나로 모든 상품을 부르고 호출량은 상품별로 집계한다. [API-58], [B-api-market]
- 인계: "계약 종료 시 소스코드·계정·운영 권한을 회사 명의로 넘기고", 작은 변경은 사내 담당자가 AI 코드 에이전트로 처리하게 셋업한다. [솔루션 FAQ]
- 랜딩 도구: "한 달 몇 시간을 쓰는가" 계산기(건수 × 건당 분)와 고민 체크박스("세금계산서를 한 건씩 끊다 보면 오후가 다 갑니다" 등). 고른 항목이 상담 신청서에 담긴다. [솔루션]

## 2. 어떻게 하는가

### 2-A. 기술 방식

| 항목 | 드러난 사실 | 출처 |
|---|---|---|
| 방식 선택 원칙 | 공식 API가 있으면 API, 없으면 "이용약관과 권한 범위 안에서" 화면 자동화(RPA), 비정형 입력은 AI가 후보를 만들고 사람이 승인. "한 방식으로 전부 해결하려 하지 않는다" | [B-rpa-api-ai] |
| 회계 사례 스택 | Next.js, TypeScript, Tailwind CSS, OpenAI API, PostgreSQL. 사례 분류 태그는 "RPA" | [W-accounting] |
| 로그인 필요 소스 | 금융 데이터 파이프라인 예시 코드에 `SeleniumCollector("운용사포털", credentials)`가 "로그인 필요 소스"로 나온다. 소스별 수집기가 따로 실패하게 나눈다. 회계 쪽 홈택스 연결에 같은 방식을 쓰는지는 밝히지 않았다 | [B-finance-data] |
| 홈택스 API 상품 | "홈택스에서 조회한 결과를 수집해 단일 스키마로 정규화", "11개 서브 API를 병렬로 호출". 공식 오픈API가 아니라 조회 결과를 수집하는 방식으로 보인다. 어디서(고객 PC/시온랩 서버) 실행하는지는 밝히지 않았다. 흐름도가 "SIONLAB API 게이트웨이 → 원천 기관"이므로 서버 쪽 실행으로 보인다(추정) | [API-58], [API-137] |
| 휴폐업 조회 | 블로그는 국세청 공식 OpenAPI(사업자등록정보 진위확인 및 상태조회)를 쓰라고 안내하고, 자사 상품도 함께 소개한다. 자사 상품에는 **대표자 주민등록번호**로 사업자 상태를 조회하는 엔드포인트가 있다 | [B-business-status], [API-25] |
| AI의 자리 | 계정과목 추천(신뢰도 임계값 미만은 검토 대기), OCR 후보 추출. 발행·수집 실행에는 AI를 쓴다는 언급이 없다 | [W-accounting], [B-ocr] |
| 정규화 계층 | 응답을 표준 envelope(status, data, error, meta)로 감싸고, 부분 실패는 `error.partial`로 알린다. 외부 키 회전·만료를 중개 쪽에서 처리한다 | [B-orchestration] |

### 2-B. 로그인·인증수단 처리

- 발급 인증수단 종류(사업자범용·전자세금계산서용 공동인증서, 전자세금용 금융인증서, 사업자용 간편인증, 발급용 보안카드)를 공개 가이드로 정리했다. 우리 02 §2의 목록과 같다. [B-e-tax-guide]
- 자동 발행에 쓰는 인증 방식은 **공개하지 않는다**: "연결 전에 인증서를 어디에 두고 누가 관리할지, 담당자가 바뀌면 어떻게 넘길지를 먼저 정합니다. 구체적인 인증 방식은 사업자 환경에 따라 상담 단계에서 함께 확인합니다." [솔루션 FAQ], [B-daily-sync]
- 상담 폼에서 비밀을 받지 않는다고 여러 곳에 적었다: "인증서·비밀번호는 문의에 첨부하지 않습니다", "인증서나 비밀번호를 문의폼으로 보내실 필요는 없습니다". [솔루션], [B-tax-invoice-automation]
- 인증 만료를 멈춤의 주원인으로 본다: "인증 수단이 만료되면 조회도 함께 멈춥니다", "비밀번호가 바뀌거나 담당자가 바뀌면 수집이 멈추므로 관리자와 변경 시 알릴 사람을 정합니다". 유지보수 계약에 "인증 만료·수집 중단의 발견·연락·복구 담당"을 적으라고 권한다. [B-wetax], [B-card-sales], [B-api-cost]
- 비밀번호 잠금을 경고한다: 주민등록증 진위확인은 발급일자 입력 오류가 5회 쌓이면 잠기므로 "자동으로 계속 재시도하면 고객의 신분증을 잠기게 만들 수 있다". [B-gov24-id]

| 지점 | 시온랩 표현 | 출처 |

### 2-D. 운영 방식(실패·재시도·기록)

- 운영 점검 12항목: 작업 ID, 상태 구분, 중복 실행 방지, 일시 오류·입력 오류 구분, 재시도 상한, 실패 건만 재처리, 실패·지연·**인증 만료** 알림 대상, 알림에 작업 ID와 다음 행동, 담당자 부재 시 대체 경로, 조회·수정·재시도·승인 권한 분리, 재실행 기록, **로그에 개인정보·인증 정보 남기지 않기**. [B-ops-checklist]
- 재시도: 회복 가능한 오류만 간격을 늘려 재시도하고, 권한 부족·잘못된 입력은 사람에게 보낸다. 운영 지표는 성공률보다 지연 작업 수, 같은 오류 반복 수, 평균 복구 시간, 수동 개입 이유를 본다. [B-ops-checklist]
- 일괄 발급: 요청 전체 상태와 문서별 상태를 따로 두고, 상태는 대기·처리 중·성공·재시도 가능 실패·종단 실패의 다섯 가지다. 화면에 "전체 10건 중 성공 9건, 재시도 가능 1건"처럼 보여 준다. [B-property-retry]
- 응답이 끊긴 발행: "바로 다시 발행하지 않고 기존 발행 결과부터 확인". [B-tax-invoice-automation], [솔루션]
- 상태조회 실패: "조회 실패를 폐업으로 처리해서는 안 됩니다. 인증 오류, 호출 제한, 네트워크 실패는 '확인 불가' 상태로 분리". 결과는 "특정 시점에 국세청이 제공한 정보"이므로 응답과 **확인 시각**을 함께 저장한다. 등록 때 휴·폐업이면 "자동 거절 대신 담당자 확인". [B-business-status]
- 회계 반영: 원본 식별자와 공급가액·세액·합계 세 값, 적용한 변환 규칙을 함께 보관한다. 같은 거래를 다시 넣으면 기존 행에 잇고(새 행 0개), 공급가액+세액≠합계인 행은 보류한다(예시: 80,000 + 8,000 ≠ 88,001). [B-hometax-import]
- 다사업자: 문서번호만으로 중복을 판정하면 다른 사업자의 같은 번호가 덮인다. 사업자 식별값과 문서번호를 함께 키로 쓰고, **내보내는 파일 안에도 사업자·기간을 적고** 행 수·합계로 범위를 대조한다. [B-multi-business]
- OCR: 원본 위치·후보값·신뢰도·엔진 버전을 저장한다. 사업자번호는 체크 규칙과 원본 대조, 금액은 합계·세액 교차검증, 날짜는 허용 범위처럼 **필드마다 검증을 달리 둔다**. "신뢰도는 정답일 확률과 같지 않습니다". [B-ocr]
- 마감 확정: 노임대장 마감은 화면 계산 함수와 DB가 같은 현장·월의 합계를 따로 구해 맞을 때만 확정한다. [B-construction-payroll]

## 3. 법·운영 리스크를 어떻게 다루는가

| 주제 | 읽은 페이지에서 확인한 것 | 언급 없음(읽은 범위) |
|---|---|---|
| 포털 이용약관 | "홈택스 이용 조건에서 자동 조회를 어디까지 허용하는지 확인"(고객 확인 항목), "카드사마다 이용 조건이 다르므로", "위택스 이용 조건에서", "API가 없다면 이용약관과 권한 범위 안에서 화면 자동화가 가능한지 확인". 등기소 상품도 "공식 서비스의 이용 조건, 인증, 수수료, 자동화 허용 범위를 별도로 확인" | 홈택스 약관 조항의 해석, 시온랩 자신의 판단 |
| 법적 검토 시점 | API 상품: "원천 공개 여부와 수집 방식, 법적 검토는 상담 접수 후 타당성 회신 단계에서 확인" | 검토 결과, 검토 주체 |
| 인증서 위임 | "인증서를 어디에 두고 누가 관리할지"를 고객과 정한다고만 쓴다 | 위임 계약, 보관 위치, 시온랩 직원 접근 여부 |
| 국세청 관계 | 휴폐업은 국세청 공식 OpenAPI를 안내한다 | 국세청 협의·허가, 안티 스크래핑 차단(R5 #9), 국세기본법 개정안 |
| 세무사법 | "회계 자동화는 신고 판단을 대신하는 일이 아닙니다", "신고와 납부, 세법 해석이 필요한 판단은 담당자가 확인" | 세무사법·세무대리 광고 규정의 직접 언급 |
| 개인정보 | 4대보험 명부·신분증·연말정산 자료는 고유식별정보이므로 "정보주체 동의와 법적 근거… 법률 검토를 받아야", "대조에만 필요하다면 번호를 그대로 저장하지 않는 설계도 가능", "사업자 자료만 필요하다면 개인 묶음은 아예 넣지 않는 편이 안전" | 국외 이전(OpenAI API 사용 시) |
| 성과 표시 | 프로토타입·데모 수치마다 "예시이며 실제 고객 성과가 아님"을 붙인다. 측정하지 않은 절감액을 더하지 말라고 쓴다 | — |
| 자사 약관 | 사이트 이용약관(2026-04-14 시행)은 웹사이트·상담·뉴스레터만 다룬다. 개인정보처리방침의 수집 항목은 문의·교육·뉴스레터·접속 기록(GA)이다 | 자동화 서비스·API 이용약관, 장애·오발행 책임 |

정리: 시온랩은 법적 판단을 **고객이 확인할 항목**으로 넘기고, 자사가 정한 해석은 공개하지 않는다. 맞춤 개발이라 책임 범위를 계약마다 정하는 구조로 보인다(추정). 우리는 한 플랜 구독 제품이라 같은 방식을 쓸 수 없다. 약관·화면 문구·공문 질의로 우리가 먼저 정해야 한다(R13).

## 5. 배울 점

모든 항목은 **(제안, 사용자 확인 전)**이다. 영향받는 문서를 함께 적었다.

### 5-A. 지금 Phase 1에 반영할 만한 것

**P1-1. 거래처 상태를 세 가지로 나눈다: 계속·휴·폐업 / 확인 불가 / 아직 조회 안 함** (제안, 사용자 확인 전)
- 근거: [B-business-status]. 조회 실패(키 오류, 호출 제한, 네트워크)를 폐업으로 읽으면 멀쩡한 거래처에 발급을 막게 되고, 반대로 성공으로 읽으면 확인 없이 발급하게 된다.
- 우리 현재: 08 §8 D-02 상태 열은 "계속·휴업·폐업 + 마지막 확인일"뿐이고, 조회 실패 때의 문구가 08 §11에 없다. 08 §4 O-02는 등록 때 휴·폐업이면 "등록을 멈춘다"고 하는데, 08 §11 발급 단계는 [그래도 진행] [취소]다. 두 곳의 처리가 다르다.
- 제안: 배지는 "확인 불가 · 국세청 조회 실패(시각)"로 두고 [다시 확인]을 붙인다. 발급 직전 재확인이 실패하면 초안 카드에 경고 줄만 두고 발급은 막지 않는다. 등록 단계의 휴·폐업도 멈추지 않고 경고와 사용자 확인으로 바꿔 §11과 맞춘다(폐업 거래처에 수정세금계산서를 낼 일이 있다).
- 덧붙여 용어: 공공데이터포털 서비스에서 **진위확인**(사업자번호·개업일자·대표자명 일치)과 **상태조회**(계속·휴·폐업·과세유형)는 다른 기능이다. 우리 배지는 상태조회 결과이므로 02 §4와 08 §4의 "진위확인 결과를 배지로"를 "상태조회 결과"로 고친다.
- 영향: 08 §4(O-02)·§8(D-02)·§11, 02 §4, design/16-error-taxonomy(조회 실패 코드).

**P1-2. 세무사 꾸러미 엑셀에 범위 표지와 행 정합성 표시를 넣는다** (제안, 사용자 확인 전)
- 근거: [B-multi-business], [B-hometax-import]. 합계만 맞고 범위가 틀린 파일(다른 기간·다른 사업자 행 포함)은 합계 대조로 못 잡는다.
- 제안: ① 첫 시트 "표지"에 사업자번호·상호·기간·생성 시각·시트별 행 수와 공급가액·세액 합계를 적는다. 세무사가 받은 파일만 보고 범위를 확인할 수 있다. ② 매출·매입 행은 (사업자번호, 승인번호)를 키로 중복을 없앤다. [최신화]나 H-02를 다시 돌려도 행이 늘지 않는다. ③ 공급가액·세액·합계를 각각 열로 두고(02 §17 제안 "별도 열"과 같은 방향), 공급가액+세액≠합계인 행은 "빠진 것" 시트에 "금액 확인 필요"로 올린다. 판단이 아니라 산술 차이 표시다.
- 영향: 02 §17(내보내기), ADR-032, ADR-034 결정 7(표준 서식), 08 §3 D-05·D-07.

**P1-3. 종이 증빙 OCR에 필드별 검증 규칙을 둔다** (제안, 사용자 확인 전)
- 근거: [B-ocr]. 같은 신뢰도라도 금액 오인식과 상호 오인식은 영향이 다르다.
- 제안: 사업자번호는 체크디지트 검증, 금액은 공급가액+세액=합계 검사(세금계산서), 날짜는 이번 달 ±범위 검사를 하고, 통과하지 못한 필드만 사장님 확인 칸으로 강조한다. 원본 사진·읽은 후보·확정값을 따로 저장한다(02 §17의 "읽어 낸 값은 사장님이 확인"을 구체화).
- 영향: 02 §17(종이 증빙), ADR-032 조건, 08 §10 P-08, 모바일 트랙.

**P1-4. 문의·진단 내보내기 화면에 "비밀은 보내지 마세요" 문구** (제안, 사용자 확인 전)
- 근거: 시온랩은 상담 폼 세 곳에 "인증서·비밀번호는 문의에 첨부하지 않습니다"를 적었다([솔루션], [B-tax-invoice-automation]).
- 제안: 진단 내보내기(D12 §5)와 문의 메일 안내에 "인증서 파일, 인증서·홈택스 비밀번호, 보안카드 번호는 문의에 적거나 첨부하지 마세요. 저희는 이것을 묻지 않아요"를 고정한다. 누출 스캐너가 지우는 것과 별개로, 사용자가 스스로 붙이는 것을 막는 문구다. 사칭 피싱 예방 문구로도 쓴다.
- 영향: design/12-observability-ops §5, 08 §9(설정의 도움말·문의), D11 §8.

**P1-5. 대외 문구에 경계 문장과 범위·확인일 표기 규칙을 넣는다** (제안, 사용자 확인 전)
- 근거: 시온랩은 경계를 기능이 아니라 문장으로 반복한다. "회계 자동화는 신고 판단을 대신하는 일이 아닙니다", "자동화는 자료를 모아 차이를 보여 주는 데까지입니다", "목표는 전문가를 빼는 것이 아니라 전문가가 검토할 대상을 선명하게 만드는 것". 수치·도식마다 "예시", "로컬 시연 자료", "2026년 10월 7일 조회"를 붙인다([B-boundaries], [B-construction-payroll], [B-card-sales]).
- 제안: R13 §2.4의 허용 사전 후보로 "사장님 PC에서 발급하고 모아서 세무사에게 넘겨요. 신고와 세금 판단은 세무사가 해요"류 문장을 올린다(우리 문장으로 새로 쓰고, 시온랩 문장을 옮기지 않는다). 랜딩·도움말의 기한·인증수단 같은 사실 문구에는 "(2026-11 국세청 안내 기준)"처럼 기준일을 붙이는 규칙을 둔다. 성과 수치는 실측 전에는 쓰지 않는다(§5-C 참고).
- 영향: design/11-security §8(대외 문구 점검표), R13 §2.4, 01 §8.

**P1-6. 인증 만료·변경을 '조용한 멈춤'의 첫 원인으로 보고 판 카드로 올린다** (제안, 사용자 확인 전)
- 근거: [B-wetax], [B-card-sales], [B-api-cost]. 수집이 멈춘 이유가 대부분 인증서 만료·비밀번호 변경이다.
- 우리 현재: 인증서 만료 임박·만료는 판(M-02)에 표시한다(08 §11). 홈택스 비밀번호가 바뀐 경우(보안카드 경로)는 실행 중 "비밀번호 오류"로만 드러난다.
- 제안: 보안카드 사용자의 홈택스 비밀번호 오류가 한 번 나면, 다음 실행을 기다리지 않고 판에 "금고의 홈택스 비밀번호를 확인해 주세요" 카드를 남긴다. 세무사 꾸러미 준비 알림 전(매달 초)에 인증수단 상태를 한 번 점검해 판에 올린다.
- 영향: 08 §5(M-02)·§11, 02 §17(알림), ADR-033.

### 5-D. 이미 같은 결론인 것(재검토 불필요)

응답 끊김 시 재발급 금지(02 §4), 승인 뒤 값이 바뀌면 승인 무효(ADR-027 `cardHash`·`actionHash`), 일시 오류 재시도 상한(D03 §6), 비밀번호 오류 뒤 재입력 금지(08 §11, D-19), 로그에 비밀·개인정보 없음(D12 §5), 납세증명 등 유효기간 재발급 알림(02 §6), 정부24 비자동화와 후처리(ADR-011)에 대응되는 "기관 이용 조건 확인" 원칙.
