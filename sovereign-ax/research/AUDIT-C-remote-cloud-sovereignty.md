### 0.2 전제

- 인프라는 과제 전제대로 **AWS 서울 리전 + OpenAI**로 본다. 설계 문서에는 "S3 호환·PostgreSQL·KMS/HSM·국내 리전"(D07:10-11, D09:12, D01:145)만 있고 AWS라는 이름은 없다.
- 공격자 모델은 R4 §1.1(R4:37-40)을 따른다. 릴레이·블롭·메타데이터 서버는 기밀성 면에서 신뢰하지 않는다(Dolev–Yao). 게이트웨이와 공급사는 반신뢰다. 여기에 **우리 운영자(내부자)**, **계정 탈취자(이메일 장악)**, **분실 폰 습득자**, **외국 법역의 강제 제출**을 별도 공격자로 둔다.
- REVIEW-B가 이미 지적했고 설계에 반영된 항목(Kv 인증 봉인, 기기 범위 토큰, 블롭 키 객체 분리, 레지스트리 단조 버전·만료 등)은 다시 올리지 않았다. **반영이 빠졌거나 부분 반영인 것**만 "REVIEW-B X 미반영"으로 표시했다.
- 이미 잔여 위험으로 인정된 항목은 완화가 모자랄 때만 올리고 **[기존 인정]**으로 표시했다.
- 외부 사실(Noise·HPKE 성질, iOS/Android 백업 동작, CLOUD Act 등)은 감사자 지식으로 보강했다. 확인하지 못한 것은 **(확인 필요)**로 적었다.
- 심각도: Critical = 설계대로 만들면 핵심 약속이 깨짐 / High = 현실적 공격으로 서류·비밀·신원이 새거나 사용자 명의 비가역 행위가 일어남 / Medium = 조건부 악용·과장·심층 방어 결손 / Low = 위생·정합성. 비용: 설계만 / Phase 1 / Phase 2(리모트·클라우드 구현 단계).

## 2. 발견 상세

### C-01 [High] 페어링의 신뢰 앵커가 서버가 준 무서명 기기 목록이다

1. **위치**: D08:46(폰: "`Sd`가 내 계정의 데스크톱 기기 목록에 있음"), D08:49(PC: "`Sm`이 폰이 계정에 직접 등록한 기기 키 목록"), D08:50(`PAIR_OK`에 `AIK_pub`), D08:53(단어 코드 대체 경로), D09:23·30(기기 등록), R4:252(원래 권고: AIK 서명 없는 기기 목록 항목 거부), REVIEW-B C-7.
2. **공격 시나리오**
   - 공격자: 피해자 이메일을 장악한 사람, 또는 계정 DB를 고칠 수 있는 내부자.
   - 단계: ① 공격자가 자기 PC에서 디바이스 플로우(또는 이메일 2차 확인)로 피해자 계정에 데스크톱을 등록한다. 이제 공격자 `Sd'`가 피해자 계정 기기 목록에 있다. ② "보안 점검을 위해 앱으로 이 QR을 스캔하세요"라는 메일이나 원격 지원 화면으로 공격자 PC의 QR을 보여 준다. 앱 내 스캐너는 어느 화면의 QR이든 읽는다. ③ 폰 검사 3(D08:46)이 서버 목록을 보고 통과한다. ④ 폰에 6자리가 뜨면 피싱 페이지가 "앱에 표시된 6자리를 여기에 입력하세요"라고 요구한다. "PC에 입력" 설계는 그 PC가 공격자 것일 때 아무것도 막지 못한다. ⑤ `PAIR_OK`의 `AIK_pub`는 폰이 처음 받는 값이므로(TOFU) 공격자 AIK가 그대로 핀 고정된다. ⑥ 이후 공격자 PC는 `human.request{kind:secret, secretKind:portal_password|security_card, origin:"www.hometax.go.kr"}`를 보내 폰에서 포털 비밀번호·보안카드 칸 값을 받아 낸다. 폰은 공격자 `Kv`로 봉인하므로 공격자가 연다. 승인 카드와 `file.offer`로 가짜 서류도 보낼 수 있다.
   - 내부자 변형: 계정 탈취 없이 서버 응답만 바꿔 "그 `Sd'`는 이 계정 소속"이라고 답한다.
3. **현재 통제**: 광학 QR(PSK), 폰의 `rs==Sd` 검사, 계정 기기 목록 대조(양방향), 6자리 PC 입력, 룸 1회용·120초, 앱 내 스캐너만.
4. **구멍**: 양방향 대조는 모두 **서버가 정직하고 계정이 안전하다는 전제**에 선다. 기기 목록에 AIK 서명이 없다(R4:252 권고가 D08에서 빠짐). 첫 페어링에서 폰에는 계정 신원의 독립 앵커가 없다. 6자리 코드는 "QR 사진 + 내부자" 조합은 막지만(사용자가 자기 폰의 숫자를 넣으므로), 공격자 PC로 유도하는 원격 피싱은 막지 못한다. 단어 코드 대체 경로(D08:53)에서는 폰이 `Sd`를 서버 목록에서 고르므로 더 약하다.
5. **권고**
   - D08 §4에 넣을 문장: "계정 기기 목록의 모든 항목은 `AIK`가 서명한 `DeviceListEntry{device_id, role, Sx, Vx, registered_at, list_version}`이다. 폰과 PC는 AIK 서명이 없거나 `list_version`이 이미 본 값보다 낮은 목록을 거부한다."
   - 계정 신원 고정: "계정의 `AIK_pub`는 첫 데스크톱 설치 때 1회 등록하고, 교체는 옛 AIK 서명 + 7일 공지 지연 + 모든 기기·이메일 알림으로만 한다. 폰은 페어링 때 서버가 준 `AIK_pub`와 `PAIR_OK`의 `AIK_pub`가 같을 때만 진행한다." 이렇게 하면 계정 탈취자는 자기 AIK로 목록을 서명할 수 없다. 내부자가 첫 페어링 시점의 `AIK_pub`까지 속이는 경우는 남으므로 잔여 위험으로 적는다.
   - 신규 데스크톱 경고: "`registered_at`이 24시간 이내인 데스크톱과 페어링하려 하면 폰이 전면 경고('이 PC는 오늘 등록되었습니다')를 띄우고, 기존 기기와 이메일에 알린다."
   - SAS 화면 문구: PC가 아닌 웹페이지·전화 상대가 숫자를 요구하면 입력하지 말라는 경고를 **폰** 화면의 6자리 옆에 둔다(사용자가 실제로 보는 곳).
   - REVIEW-B C-7 미반영분 반영: QR·SAS 창에 `setContentProtection(true)`, `PAIR_OK`에서 `KEK_N` 전달을 분리해 PC의 Hello 확인이 있는 별도 단계("이 폰에서 서류 열람 허용")로 둔다.
   - 정책 상수: `pairing.newDesktopWarnHours = 24`, `pairing.aikChangeDelayDays = 7`.
   - ADR-007 개정 필요(신뢰 앵커 서술).
6. **심각도**: High(계정 탈취 또는 내부자 + 사회공학 전제. 결과는 포털 비밀번호·보안카드 탈취와 가짜 승인 화면).
7. **비용**: 설계만(문장·스키마) + Phase 2(기기 목록 서명 구현).

### C-02 [High] 7일 삭제 유예가 새로 등록한 기기의 서명으로 우회된다

1. **위치**: D09:29("기기 서명이 있는 삭제 요청만 유예 없이 즉시"), D09:30("새 기기 등록은 기존 기기 또는 이메일 2차 확인"), D09:63(`DELETE /v1/blobs/{id}` 즉시), REVIEW-B E-5.
2. **공격 시나리오**: 이메일 장악자가 ① 매직링크로 로그인, ② 디바이스 플로우로 자기 PC를 등록하고 "이메일 2차 확인"을 같은 메일함에서 누른다, ③ 이 기기의 키로 서명한 대량 삭제·계정 삭제를 보낸다. 유예 없이 즉시 삭제된다. 블롭 API도 즉시 삭제다.
3. **현재 통제**: 7일 유예, 기기 서명 예외, 디바이스 플로우 승인 화면.
4. **구멍**: "기기 서명"이 어느 기기인지(나이·AIK 인증 여부) 조건이 없다. 이메일 2차 확인은 매직링크와 **같은 요소**라 추가 요소가 아니다. 블롭 `DELETE`가 유예 대상인지도 불명이다.
5. **권고**
   - D09 §2 수정 문장: "유예 없는 즉시 삭제는 `AIK`로 서명된 요청만 허용한다(AIK는 복구 문구에서 파생되어 데스크톱에만 있다). 등록 7일 미만 기기의 서명, 계정 세션만 있는 요청은 모두 7일 유예 대상이다. 블롭·메타데이터의 대량 삭제(1일 10건 초과)도 같다."
   - "새 기기 등록은 (a) 기존 AIK 인증 기기의 승인 또는 (b) 이메일 확인 + 72시간 대기 + 모든 기존 기기 알림 중 하나다. 패스키가 등록된 계정은 이메일만으로 기기를 추가할 수 없다."
   - 정책 상수: `account.deleteGraceDays = 7`, `device.newDeviceCoolingDays = 7`, `device.emailOnlyAddDelayHours = 72`.
6. **심각도**: High. 로컬 원본이 있으면 재업로드로 회복되지만, PC 분실과 겹치면 영구 손실이다.
7. **비용**: 설계만.

### C-03 [High] 메타데이터 API·조회 에이전트·블롭 조회가 계정 세션만으로 열린다

1. **위치**: D09:62(`GET /v1/blobs/{id}` "계정 소유 확인 후"), D09:69(`GET /v1/docs`), D09:75(조회 에이전트 입력), D08:110(블롭 "기기 토큰"), D01:39(모바일 `query`).
2. **공격 시나리오**: 이메일 장악자가 모바일 앱이나 API로 로그인하면 페어링 없이 ① 조회 에이전트로 "보관된 서류 전부 알려줘"를 묻고, ② `GET /v1/docs`로 계정의 doc_type·발급일·만료일·크기를 전부 받고, ③ 블롭 암호문과 wDEK를 내려받아 둔다(복구 문구를 나중에 피싱하면 C-21과 결합해 전부 연다).
3. **현재 통제**: D08은 블롭에 "기기 토큰"을 말하지만 D09 API 명세는 계정 단위다. 메타데이터 API·조회 에이전트에는 기기 조건이 없다.
4. **구멍**: 문서 간 불일치로 구현자가 계정 세션만으로 열 가능성이 크다. 메타데이터는 평문이라 계정 세션 = 메타데이터 전체 공개다.
5. **권고**
   - D09 §5·§6·§7 공통 문장: "블롭·메타데이터·조회 에이전트 API는 **AIK 인증서가 있는 기기**의 기기 범위 토큰(요청마다 기기 키 서명, DPoP 방식)만 받는다. 계정 세션만 있는 클라이언트는 구독·기기 관리 화면만 쓸 수 있다."
   - 이메일 로그인 직후의 새 폰은 페어링(=PC의 AIK가 인증서 발급) 전에는 조회 에이전트를 쓸 수 없다고 02 §8과 온보딩에 적는다.
6. **심각도**: High(공공 AX 맥락에서 메타데이터 자체가 민감, C-09 참조).
7. **비용**: Phase 2.

### C-04 [Medium] 디바이스 플로우 피싱(REVIEW-B E-5 미반영)

1. **위치**: D09:28·30.
2. **공격 시나리오**: 공격자가 자기 PC에서 디바이스 플로우를 시작해 받은 `user_code`를 "소버린 AX 보안 인증 코드" 문자로 보낸다. 피해자가 정식 승인 페이지에 코드를 넣으면 공격자 PC가 계정 토큰을 얻는다. 이것이 C-01·C-02의 입구다.
3. **현재 통제**: 승인 화면에 기기명·위치·코드 표시, 새 기기 등록 시 기존 기기 또는 이메일 2차 확인.
4. **구멍**: RFC 8628 디바이스 플로우는 원래 입력 장치가 없는 기기용이다. 브라우저가 있는 데스크톱에는 필요 없고, 피싱 표면만 늘린다. 위치 표시는 공격자가 같은 도시 VPN을 쓰면 무력하다.
5. **권고**: D09 §2를 "데스크톱 로그인은 RFC 8252 루프백 리디렉트 + PKCE. 디바이스 플로우는 쓰지 않는다"로 바꾼다. 남겨야 한다면 `user_code` 수명 5분, 승인은 **이미 페어링된 폰의 푸시 승인**으로만 한다.
6. **심각도**: Medium.
7. **비용**: Phase 1.

### C-05 [High] 모바일 키가 iCloud·Google 백업에 실려 다른 기기로 복원될 수 있다

1. **위치**: D08:33·38(모바일이 받는 키: `KEK_N`, `K_meta`, `K_audit`, 기기 키 `Sm`·`Vm`·`Km`·`Qm`·`Lm`), D08:51("폰은 키를 생체 바인딩 저장소로 이동"), D01:36("장기 키 보관(Secure Enclave/Keystore)"), D05:86(macOS만 `ThisDeviceOnly` 명시), R4:465(SecureStore: iOS 재설치 후 잔존, Android 자동 백업 제외 필요).
2. **공격 시나리오**: Apple ID 또는 Google 계정을 장악한 공격자가 피해자 폰의 기기 백업을 자기 폰에 복원한다. Keychain 항목의 접근성 클래스가 `...ThisDeviceOnly`가 아니면 암호화 백업에 포함되어 새 기기로 옮겨진다. 래핑된 키 링 파일(앱 문서 폴더)도 백업에서 제외하지 않으면 같이 온다. 결과는 피해자 폰과 같은 `Sm`·`Vm`·`KEK_N`이다. 피해자 PC와 IK 세션을 맺고, 블롭을 열고, 승인에 서명한다.
3. **현재 통제**: "생체 바인딩 저장소"라는 문장 하나. Expo SecureStore의 기본 접근성은 `WHEN_UNLOCKED`(ThisDeviceOnly 아님)로 알고 있다(확인 필요).
4. **구멍**: 모바일 쪽 접근성 클래스·백업 제외·Android `allowBackup`/`dataExtractionRules`가 명세에 없다. D01:36의 "Secure Enclave에 장기 키 보관"은 사실과 다르다. SE는 P-256만 지원하므로 X25519·Ed25519 키는 SE가 보호하는 AES 키로 래핑해야 한다(R4:467).
5. **권고**
   - D08 §3 또는 신설 "모바일 저장 규칙" 표: 모든 키·토큰은 `keychainAccessible = WHEN_PASSCODE_SET_THIS_DEVICE_ONLY` + `requireAuthentication`. 래핑 키 링·캐시 DB·복호 캐시 파일은 iOS `NSURLIsExcludedFromBackupKey`, Android `android:allowBackup="false"`와 `dataExtractionRules`로 클라우드 백업·기기 간 이전 모두 제외. 재설치 후 Keychain 잔존 시 키를 지우고 재페어링을 요구.
   - D01:36을 "X25519·Ed25519 키는 SE/StrongBox가 보호하는 래핑 키로 암호화해 저장(키 자체는 SE에 들어가지 않음)"으로 정정.
   - 기기 등록 시 App Attest(iOS)·Play Integrity(Android) 증명을 서버가 확인해 변조 앱·에뮬레이터 등록을 줄인다. 경계가 아니라 신호라고 적는다.
6. **심각도**: High.
7. **비용**: 설계만 + 스파이크(SP-1).

### C-06 [High] 분실·탈옥 폰 하나로 사용자 명의 발급·유출이 가능하다

1. **위치**: D08:19(승인 서명은 소프트웨어 Ed25519, SE는 선택), D08:82·85(`cmd.run`, `gate.response`), D08:110(기기 해제는 PC에서), D03:66, REVIEW-B C-6.
2. **공격 시나리오**: 잠금이 풀린 폰을 습득했거나 탈옥 폰에서 `Vm`을 빼낸 공격자가 PC가 켜져 있는 시간에 `cmd.run(hometax.invoice.issue, {거래처: 공격자 회사, 금액, 이메일: 공격자 주소})`를 보낸다. PC는 게이트 카드를 같은 폰으로 보내고 공격자가 승인한다. 사용자 명의의 전자세금계산서가 발급되고 PDF가 공격자 메일로 간다. 서류 조회(`query.*`)와 `file.offer`로 등본도 받아 간다. 피해자가 밖에 있어 PC에 갈 수 없으면 폐기할 수단이 없다.
3. **현재 통제**: 생체 인증 후 서명(소프트웨어 키는 OS 생체 게이트에 의존), 플레이북 화이트리스트, 카드 렌더링은 PC 신뢰값, PC에서 기기 해제.
4. **구멍**: 승인 키가 기본적으로 추출 가능하다. 원격 비가역 행위의 상한·새 거래처 제한이 없다. 원격에서 일어난 발급을 PC·이메일로 알리는 규칙이 없다. 서버 측 긴급 정지 경로가 없다(폐기는 AIK = PC 전용).
5. **권고**
   - D08 §2·§6: "비가역 효과(`issue_document`·`send`·`sign`)의 원격 승인은 SE/StrongBox P-256 키(`Px`, 사용자 존재 필요)로만 한다. 하드웨어 키가 없는 폰은 조회·캡차·시작 동의만 하고 비가역 승인은 PC 로컬에서만 한다." `gate.response.sigAlg`를 비가역 카드에서 `p256` 필수로.
   - 정책 상수(policy.schema에 `remote` 블록 신설): `remote.irreversiblePerDay = 5`, `remote.newCounterpartyRequiresLocal = true`(처음 쓰는 거래처·이메일 수신자는 원격 승인 불가), `remote.notifyOnIrreversible = ["desktop","email"]`.
   - D08 §9 신설 문장: "계정 웹에서 '기기 긴급 정지'를 누르면 서버는 해당 기기의 블롭·메타데이터·릴레이·푸시 토큰을 즉시 정지한다(서버 측 조치, AIK 서명 폐기 전까지 임시). 남용을 막기 위해 긴급 정지는 정지만 할 수 있고 재활성화는 AIK가 한다."
   - 폰 앱 잠금(앱 진입 시 생체)과 백그라운드 30초 후 재잠금을 명시.
6. **심각도**: High(사용자 명의 비가역 행위).
7. **비용**: Phase 2.

### C-07 [High] KEK 회전이 실제로 회수하는 것이 거의 없다

1. **위치**: D08:28(`KEK_N = HKDF(RK, "kek/blob/vN")`), D08:110("KEK를 N+1로 회전해 재래핑 … 블롭 재암호화 없이"), D08:111("옛 RK 파생 키는 재래핑 후 폐기"), D07:144-145, D08:88(`file.offer`가 wDEK를 폰에 직접 보냄), REVIEW-B C-3(f)·C-4.
2. **공격 시나리오**
   - 폐기 폰: 폰은 `KEK_N`을 갖고 있고, 동기화·`file.offer`로 받은 wDEK들을 이미 캐시했다. DEK는 회전해도 바뀌지 않으므로 `KEK_N`으로 옛 wDEK를 풀면 DEK가 나오고, 서버 접근(유출·내부자·백업)으로 얻은 암호문을 영구히 연다.
   - 문구 유출·PC 도난: `KEK_{N+1}`, `KEK_{N+2}`…도 같은 RK에서 결정적으로 나온다. "옛 KEK 폐기"는 RK를 가진 사람에게 의미가 없다.
3. **현재 통제**: 서버 측 기기 토큰 무효화, 재래핑, PC 분실 시 새 문구 발급(D08:111).
4. **구멍**: 문서가 재래핑을 회수 수단처럼 쓴다. 실제 보호는 "서버 접근 통제"뿐인데 그렇게 적혀 있지 않다. 새 문구를 발급해도 블롭 재암호화 단계가 없다(R4:274 "문구 유출 → 블롭 재암호화"가 빠짐).
5. **권고**
   - D08 §9에 넣을 정직한 문장: "KEK 회전은 아직 wDEK를 받지 않은 문서에 대해서만 폐기 기기의 접근을 막는다. 폐기 전에 기기가 받은 wDEK의 문서는 블롭을 재암호화하지 않으면 계속 열 수 있다. 서버 쪽 방어는 기기 토큰 무효화(접근 통제)다."
   - 절차를 둘로 나눈다: (a) 폰 분실 = 토큰 무효화 + KEK 회전 + **선택형 재암호화**(최근 90일 또는 민감 doc_type부터), (b) 문구 유출·PC 도난 = 새 문구(RK′) + AIK′ 전환(폰 승인) + **전체 재암호화 필수**.
   - KEK 버전에 무작위성을 섞는다: `KEK_N = HKDF(RK, "kek/blob/vN" ‖ salt_N)`이고 `salt_N`은 PC가 만든 32B 난수로 AIK 서명 레코드에 둔다. 이것만으로는 RK 유출을 막지 못하므로(레코드가 서버에 있음) 주목적은 버전 간 분리이며, RK 유출 대응은 여전히 RK 교체라고 적는다.
   - 폰에는 문서 단위로 필요할 때만 wDEK를 내려받게 하고 대량 동기화하지 않는다(폐기 시 노출 범위 축소).
6. **심각도**: High.
7. **비용**: 설계만(문장) + Phase 2(재암호화 기능).

### C-08 [Medium] "키 우선 삭제"가 DB 백업 때문에 성립하지 않는다

1. **위치**: D07:139(wDEK는 인덱스 레코드에 저장), D07:144·148("키를 먼저 지우면 백업 사본은 복호 불가"), D09:104(블롭 백업 30일), R4:437(키 객체는 백업에서 제외 권고).
2. **공격 시나리오**: 사용자가 등본을 삭제한다. PostgreSQL 자동 백업·스냅샷(RDS류는 최대 35일 보존 설정이 흔하다)과 S3 버전에 wDEK와 블롭이 함께 30일 남는다. 그 사이 사용자 문구가 유출되거나 백업이 반출되면 "삭제된" 서류가 열린다.
3. **현재 통제**: 삭제 순서(wDEK → 블롭), 백업 30일 내 소거.
4. **구멍**: 키 객체와 블롭이 같은 운영자·같은 계정의 백업에 함께 있으므로 "키 우선 삭제"의 효과는 라이브 저장소에서만 성립한다. "키-객체 분리"가 주는 보장은 **회전·삭제의 편의**이지 기밀성 분리가 아니라는 점도 적혀 있지 않다.
5. **권고**: D07 §6에 "wDEK 테이블은 DB 백업에서 제외하거나 별도 짧은 보존(≤ 7일) 저장소에 둔다. 문서 삭제의 암호적 완료 시점은 'wDEK 백업 보존 만료 시점'이며 투명성 페이지에 이 날짜를 표시한다"를 넣는다. "키-객체 분리는 같은 운영자 안의 분리이며, 기밀성은 KEK(클라이언트 전용)에서 온다"를 명시한다. 보존표(D09 §10)에 "wDEK 백업" 행을 추가한다.
6. **심각도**: Medium.
7. **비용**: 설계만.

### C-09 [High] 메타데이터 인덱스로 세대원 수·거래량·체납·고용 변동을 추정할 수 있다

1. **위치**: D07:126-133(`doc_type, issued_at, expires_at, bytes, client_updated_at, profile_slot`, `doc_id UUID`), D09:22(slot 1 = 개인, slot 2 = 사업자 고정), 02:89-90("10월 세금계산서 몇 건 발급했지?"), R4:403·411(크기 필드 없음·doc_type 옵트인 권고), REVIEW-B D-2.
2. **공격 시나리오**(내부자·서버 침해·CLOUD Act 제출 대상자 모두): 
   - `resident_copy`의 정확한 `bytes`는 쪽수·세대원 행 수에 비례하므로 **세대원 수**가 추정된다.
   - `tax_invoice`의 월별 건수와 `bytes`(품목 행 수)로 거래량·매출 리듬이 보인다.
   - `national_tax_cert` 정기 갱신이 끊기면 체납 정황(체납 시 발급 불가).
   - `nhis_eligibility` 반복은 고용 변동, `building_register`·`localtax_item_cert`는 부동산 정황, `insure4_cert`는 직원 존재.
   - `client_updated_at`(초 단위)과 UUIDv7 계열 `doc_id`는 사용 시각을 드러낸다.
   - 계정 이메일과 결합하면 실명 개인의 생활 사건 연표가 된다.
3. **현재 통제**: 상호·사업자번호·금액·파일명 미보관, doc_type 열거형.
4. **구멍**: R4의 최소화 권고(크기 필드 삭제, Padmé, 월 단위, doc_type 옵트인)와 REVIEW-B D-2가 반영되지 않았다. D07:133과 D11:40의 "종류도 서버는 모른다"는 D09:22와 doc_type 때문에 사실이 아니다.
5. **권고**
   - D07 §5 서버 스키마를 `{account_id, slot_token(계정별 무작위), doc_id(UUIDv4), doc_type, issued_month, expires_on, blob_id, rev, kek_ver, sig}`로 줄인다. `bytes`·`client_updated_at`·`issued_at`(일)은 삭제, 블롭은 Padmé 패딩.
   - doc_type별 서버 노출 옵트인: 기본 ON은 만료 추적 대상(`national_tax_cert`, `localtax_cert`, `sme_cert`, `biz_registration_cert`), 기본 OFF는 `tax_invoice`, `nhis_eligibility`, `resident_copy/abstract`, `building_register`, `land_register`, `localtax_item_cert`. 꺼진 종류는 블롭만 올라가고 인덱스 행이 없다(조회 에이전트가 답하지 못한다고 UI에 표시).
   - 02 §8의 "세금계산서 몇 건" 예시를 "옵트인 시"로 고친다.
   - D07:133·D11:40·02:102의 "종류를 모른다/안다" 서술을 하나로 정정한다(상충 X-05).
   - 정보량 계산(어떤 질문에 어떤 필드가 필요한가)을 ADR로 남긴다: ADR-006 개정.
6. **심각도**: High(공공 AX·주권 맥락에서 서버 평문의 핵심).
7. **비용**: 설계만.

### C-10 [High] 조회 에이전트가 계정 메타데이터 행을 국외 모델로 보낸다

1. **위치**: D09:75("해당 계정의 메타데이터 행들(서버가 조회해 Terra 프롬프트에 포함)"), D09:76(열거형 변환 → 결정적 조회 → 템플릿, Terra `query_agent` 툴셋), D04:150(`list_documents(filter)`), 03:143, D11:77(국외이전 고지 항목에 메타데이터 없음).
2. **공격 시나리오**: ① 정상 동작만으로 계정의 doc_type·날짜 행이 OpenAI(미국·EU·UAE 처리)로 가고 `safety_identifier`로 계정별로 묶인다(C-23). ② `list_documents(filter)`의 필터에 모델이 `account_id`·`profile_slot`을 넣을 수 있게 구현되면 프롬프트 인젝션(사용자 질문)으로 다른 계정 행을 읽는다. ③ 질문은 "모바일에서 마스킹 후 전송"인데 모바일에는 사용자 사전(상호·대표자·거래처, D06:51)이 없으므로 이름이 그대로 나간다. ④ "폰이 복호화·마스킹한 요약 요청"(D09:76)은 서류 **본문 파생물**을 국외로 보낸다.
3. **현재 통제**: 열거형 질의, 템플릿 응답, 대화 로그 비저장.
4. **구멍**: D09 §7 안에서 "행을 프롬프트에 넣는다"와 "열거형으로 바꿔 서버가 조회한다"가 충돌한다. 열거형 방식이면 행을 모델에 보낼 이유가 없다. 계정 격리 규칙과 모바일 마스킹 사전 동기화가 명세에 없다. 국외이전 고지에 "메타데이터 행"과 "본문 요약"이 빠졌다.
5. **권고**
   - D09 §7 대체 문장: "모델에는 사용자 질문(마스킹본)만 보낸다. 모델은 `query_kind`와 파라미터(`doc_type` 열거값, 날짜 범위)만 돌려준다. 서버는 **인증 토큰에서 얻은 `account_id`로만** 조회하고, 결과를 템플릿에 채운다. 메타데이터 행은 어떤 경우에도 모델 입력에 들어가지 않는다." Terra `query_agent` 툴셋은 삭제하거나 행이 아닌 열거값만 반환하는 도구로 줄인다.
   - "본문 요약"은 PC 켜짐 + PC의 마스킹 계층(사용자 사전 포함) 경유로만 하고, PC 꺼짐 상태에서는 제공하지 않는다. 폰 마스킹을 쓸 경우 PC가 사용자 사전을 `Lx` 암호화 상태로 폰에 동기화한다는 규칙을 둔다.
   - D11 §6 국외이전 항목에 "조회 질문, (옵트인) 서류 요약 마스킹본"을 추가한다.
6. **심각도**: High.
7. **비용**: 설계만.

### C-11 [Medium] `prompt_cache_key`가 D09에서 계정 공유로 남았다

1. **위치**: D09:41(`pb:<playbookId>:v<major>:shard<n>`, "계정 접두 없음, D04 §2.1"), D04:51(계정별 격리 `acct:<HMAC>:…`, "D09와 일치"), ADR-009:11, REVIEW-B E-2.

5. **권고**: D09:41을 `prompt_cache_key = acct:<HMAC(K_cache, accountId)>:pb:<playbookId>:v<major>`로 고치고, 게이트웨이는 응답의 `cached_tokens`를 클라이언트에 그대로 넘기지 않고 계량에만 쓴다는 문장을 추가한다.
6. **심각도**: Medium.
7. **비용**: 설계만.

### C-12 [Medium] 서버 인덱스 스키마에 `wDEK`·`sig`·`rev`가 없고 `K_meta`가 대칭이다

1. **위치**: D07:126-130(서버 DDL), D07:139·142(wDEK·서명 레코드는 인덱스에 저장), D09:68("D07 §5 필드만 허용, 추가 필드 400"), D08:30(`K_meta` 대칭 키, 폰에 전달), R4:390·402·405(Vd 서명 + `rev` 단조), REVIEW-B C-3(d).
2. **공격 시나리오**: ① 스키마대로 만들면 wDEK를 저장할 곳이 없어 구현이 흔들리거나 임의 필드가 생긴다. ② 서명·`rev`가 없으면 서버(또는 침해자)가 만료일을 바꾸거나 옛 레코드로 롤백해도 클라이언트가 모른다. 조회 에이전트와 만료 알림이 틀린 날짜를 말한다. ③ `K_meta`는 대칭이고 폰에 있으므로, 폐기된 폰(또는 그 키를 뺀 사람)은 영구히 유효한 레코드를 만들 수 있다.
3. **현재 통제**: "K_meta로 서명"이라는 한 줄(D07:142).
4. **구멍**: 스키마·API 규칙과 봉투 설명이 서로 맞지 않는다. 대칭 MAC은 "누가 썼는지"를 증명하지 못한다.
5. **권고**: D07 §5 DDL에 `wdek BYTEA, kek_ver SMALLINT, rev BIGINT, sig BYTEA`를 추가하고, D09 §6의 허용 필드 목록을 갱신한다. 레코드 무결성은 `Sign_Vd(canonical{doc_id, blob_id, doc_type, issued_month, expires_on, wdek, kek_ver, rev})`로 바꾸고 폰에는 `K_meta`를 주지 않는다(폰은 `Vd`로 검증). 클라이언트는 문서별 최고 `rev`를 저장하고 낮은 값을 거부한다.
6. **심각도**: Medium.
7. **비용**: 설계만.

### C-13 [Low] dedup HMAC 키 `K_idx`

1. **위치**: D07:36(`HMAC(user_index_key, sha256)`), D07:134·146, D08:29, REVIEW-B D-6.
2. **공격 시나리오**: PC 악성코드나 문구 유출로 `K_idx`가 새면, 서버 쪽에 있는 dedup 토큰으로 "이 계정이 이 파일을 갖고 있는가"를 확인하는 공격과 저엔트로피 가변 필드 대입(R4:417-418)이 다시 가능해진다. `K_idx`는 버전이 없어 회전도 안 된다.
3. **현재 통제**: 서버는 `K_idx`를 모른다.
4. **구멍**: 도메인 분리 문자열(`"SAX-idx-v1"`)·절단 길이·버전이 없다. 재발급 서류는 발급번호가 달라 중복 이득도 작다. `user_index_key`와 `K_idx`가 같은지 명시가 없다.
5. **권고**: 서버 `dedup_token`을 삭제하고 로컬 `sha256 → blob_id` 매핑으로 중복을 판단한다(R4 §6.3-3). 남긴다면 `HMAC(K_idx_v, "SAX-idx-v1"‖sha256)[:16]` + 버전 필드, RK 교체 시 재계산.
6. **심각도**: Low.
7. **비용**: 설계만.

### C-14 [Medium] 릴레이 운영자의 실시간 결합 [기존 인정]

1. **위치**: D08:7("계정과 우편함의 연관을 모른다"), D08:50·102, D09:47·51, R4:317·328, REVIEW-B C-5.
2. **공격 시나리오**: 운영자(또는 릴레이를 장악한 침해자)는 저장소를 합치지 않아도 ① 같은 WSS 연결에서 제시되는 기기 인증 토큰(계정 연결)과 우편함 토큰, ② 페어링 룸 발급(계정 토큰으로 인증, D08:44) 직후 같은 IP에서 시작되는 우편함 첫 접속, ③ 우편함 생성 시 남용 방지용 인증, ④ 데스크톱의 상시 연결 IP와 폰의 이동통신 IP가 같은 우편함에서 만나는 패턴으로 계정↔우편함↔가정·사무실 IP↔폰 위치(통신사 IP 대역 수준)를 실시간으로 잇는다. 데스크톱 온라인 시간은 근무 패턴이다.
3. **현재 통제**: 분리 저장, IP 30일 삭제, "영지식이라 부르지 않는다"(D09:47).
4. **구멍**: D09:47은 "두 저장소를 합치면"이라고 써서 위험을 저장소 병합으로 좁힌다. D08:7은 아직 "모른다"고 쓴다(상충 X-17). R4가 권고한 회전 솔트 IP 해시(R4:328)가 빠졌다.
5. **권고**
   - D08:7·D09:47 공통 문장: "릴레이는 내용과 키를 보지 못한다. 계정과 우편함의 연결은 분리 저장·접근 통제·짧은 보존으로 줄이지만, 운영자는 연결 시점·IP 상관으로 언제든 연결할 수 있다."
   - 접속 IP는 평문 저장 대신 일 단위 회전 솔트 HMAC으로만 레이트리밋에 쓰고, 평문 IP는 법정 접속기록 대상인 운영자 접근 로그에만 둔다.
   - 기기 인증(남용 방지)은 별도 연결·별도 엔드포인트로 일 1회 익명 토큰을 받아 쓰는 구조를 Phase 3 과제로 둔다(Privacy Pass 계열, SP-10).
6. **심각도**: Medium(인정됐으나 서술이 축소됨).
7. **비용**: 설계만.

### C-15 [Medium] 푸시 깨우기 경로

1. **위치**: D09:49("토큰 → 기기 매핑만, 우편함 ID 미포함"), D08:47(`msg3`에 푸시 토큰), D08:105, D01:126(`main → mobile(push)`), D08:110(폐기 절차에 푸시 토큰 없음).
2. **공격 시나리오**: 깨우기를 보내려면 (a) 릴레이가 우편함→푸시 토큰을 알거나 (b) PC가 계정 인증으로 클라우드에 "내 폰을 깨워라"를 요청해야 한다. (a)면 우편함이 APNs/FCM 토큰으로, 즉 Apple ID·Google 계정 신원으로 이어진다. (b)면 계정→푸시 토큰 매핑이 있고, 푸시 시각과 우편함 fetch 시각으로 계정↔우편함이 이어진다. 어느 쪽이든 Apple·Google은 깨우기 시각(=사용자 PC가 승인을 요구한 시각)을 본다. 미국 정부가 푸시 알림 메타데이터를 Apple·Google에 요구해 온 사실이 2023년 공개되었다(Apple은 이후 법원 명령을 요구한다고 밝힘).
3. **현재 통제**: 내용 없는 깨우기, iOS 알림 푸시 + NSE.
4. **구멍**: 명세대로는 구현할 수 없다. iOS 알림 푸시의 일반 문구("새 알림이 있습니다")는 Apple에 보인다. 기기 폐기 절차에 푸시 토큰 삭제가 없다.
5. **권고**: D09 §4에 실제 구조를 적는다: "깨우기는 (b) 방식. PC가 기기 범위 토큰으로 `POST /v1/wake{device_id}`를 호출하고, 서버는 `device_id → 암호화된 푸시 토큰`(별도 키)만 갖는다. 우편함 ID는 이 경로에 없다. 운영자는 깨우기 시각과 우편함 접속 시각으로 둘을 연결할 수 있다." 깨우기 속도 제한(기기당 분당 3, 시간당 20), 폐기 시 푸시 토큰 즉시 삭제, 처리방침에 APNs(Apple Inc., 미국)·FCM(Google LLC, 미국)을 수탁·국외이전으로 기재.
6. **심각도**: Medium.
7. **비용**: Phase 2.

### C-16 [Medium] 우편함 능력 토큰을 핸드셰이크 해시 `h`에서 파생한다

1. **위치**: D08:50(`tok_read, tok_write = HKDF(h, 컨텍스트‖device_id)`), R4:167·315.
2. **공격 시나리오**: Noise의 `h`는 공개값(임시 공개키·암호문)을 해시한 것이고, XXpsk0에서는 `MixKeyAndHash(psk)` 때문에 PSK를 모르는 사람에게만 비밀이다. 설계는 QR 사진 유출을 위협으로 인정한다(D08:124-125). 릴레이 운영자(모든 핸드셰이크 바이트를 본다)가 QR 사진(`ps`)도 얻으면 `h`를 다시 계산해 우편함 토큰과 `mbx_id`를 얻는다. 내용은 Noise·HPKE라 못 열지만, 큐를 비우거나(삭제) 우편함 쓰기로 폰을 사칭한 깨우기·DoS를 만들고, 서버 측 "토큰 해시만 저장" 방어가 무의미해진다. Noise 명세도 `h`는 채널 바인딩용이며 비밀 키로 쓰라고 하지 않는다(감사자 이해, 문구는 확인 필요).
3. **현재 통제**: 토큰 해시만 저장, 기기 범위.
4. **구멍**: 비밀이어야 하는 능력 토큰의 비밀성이 "QR이 새지 않았다"에 의존한다. 폐기 후 "우편함 토큰 재발급"(D08:110)의 파생 방법도 없다.
5. **권고**: D08:50 수정: "`mbx_id`, `tok_read`, `tok_write`는 PC가 CSPRNG로 만든 32B 난수이며 수립된 Noise 전송 채널 안의 `PAIR_OK`로 전달한다. 재발급도 라이브 세션 안에서 같은 방식으로 한다." `h`는 SAS와 채널 바인딩에만 쓴다. S-6 암호 리뷰 범위에 추가.
6. **심각도**: Medium.
7. **비용**: 설계만.

### C-17 [Medium] 오프라인 의도 봉투(72시간 큐)

1. **위치**: D08:94-98, 스키마 remote-envelope 전체(`ttl` 최대 86,400, `cmd.run.inputs`는 자유 `object`, Intent 정의 없음), D08:103(우편함 50건), REVIEW-B C-6.
2. **공격 시나리오**
   - 와이어 형식: HPKE aad인 `pair_id‖seq‖exp`를 수신자가 알려면 평문으로 같이 보내야 하는데 형식이 정해져 있지 않다. 평문이면 릴레이가 `pair_id`(우편함 재발급 후에도 그대로인 안정 식별자), 의도 개수(`seq`), 만료 시각을 본다.
   - 비밀 유입: `inputs`가 자유 객체라 사용자가 메모 칸에 비밀번호를 적거나, 플레이북 입력 스키마의 비밀 성격 필드가 큐로 들어가도 스키마가 막지 않는다. "큐에 비밀 금지"가 문장에만 있다.
   - 승인 피로: 분실 폰이나 공격자가 우편함 50건을 채우면 PC 부팅 직후 승인 요청 50개가 쏟아진다.
   - 시작 게이트: 드레인 후 "새 gate.request"가 실행 시작 전인지 비가역 직전인지 정해지지 않았다(REVIEW-B C-6 미반영). 후자면 PC가 켜지자마자 사람 없이 로그인·화면 조작이 시작된다.
   - `Q_D` 신선도: PC가 7일 넘게 꺼져 있으면 유효한 `Q_D`가 없다. 릴레이가 옛 번들을 내밀 수도 있다.
   - 72시간 창 안의 위협: 악성 릴레이가 보존 정책을 어기고 암호문을 장기 보관하면 `Q_D` 개인키가 유출될 때 최대 약 10일 창(D08:95)의 의도(거래처·금액 포함)가 열린다.
3. **현재 통제**: 서명 후 HPKE, `seq` 윈도, `exp`, `cmd_id` 영속, 큐 → 새 승인, 무응답 폐기.
4. **구멍**: 위와 같다. `action_hash`를 폰이 큐 시점에 어떻게 계산하는지(아직 readback 전) 불명이다.
5. **권고**
   - 스키마에 `intent-envelope.schema`(또는 CDDL) 신설: 바깥은 `{v, kind:"ENV", enc, ct}`만 평문, `pair_id`·`seq`·`exp`는 HPKE 평문 안에 넣고 aad는 고정 컨텍스트 `"SAX-env-v1"‖mbx_epoch`로 바꾼다. 안쪽 `Intent`의 `inputs`는 플레이북 입력 스키마를 참조하며 `x-secret: true` 필드는 금지, 문자열 최대 200자.
   - `action_hash`는 "의도 해시(intent_hash)"로 이름을 바꾸고 실행 시 게이트의 `actionHash`와 다르다고 명시.
   - D08 §7: "드레인한 의도는 먼저 **시작 게이트**(새 챌린지, 카드에 `iat`과 'N시간 전 요청' 표시)를 통과해야 실행을 시작하고, 비가역 단계에서 다시 커밋 게이트를 받는다(D10 `semi_auto`와 같은 구조)."
   - 정책 상수: `queue.maxIntentsPerPair = 5`(50 → 5), 드레인 결과는 카드 1장으로 묶어 표시, `queue.ttlHours = 72`.
   - 폰은 `valid_to`가 지난 `Q_D`로 봉인하지 않고 "PC가 오래 꺼져 있어 예약할 수 없습니다"를 표시한다. `Q_D` 번들 `seq` 최고값을 저장해 낮은 번들을 거부한다.
6. **심각도**: Medium.
7. **비용**: 설계만.

### C-18 [Medium] `rotate.static`으로 정상 기기를 몰아낼 수 있다

1. **위치**: D08:62(`ROTATE_STATIC{Sx', Sign_Vx}`), 스키마 `rotate.static{newStatic, sig}`.
2. **공격 시나리오**: 폰의 `Sm`·`Vm`과 우편함 토큰을 뺀 공격자(C-05·C-06)가 IK 세션을 맺고 `rotate.static`으로 자기 새 정적키를 등록한다. PC는 새 키만 받고 진짜 폰의 옛 `Sm` 핸드셰이크는 버린다. 사용자는 "앱이 연결이 안 된다"로 보고 재페어링하기 전까지 공격자가 유일한 폰이 된다.
3. **현재 통제**: `Vx` 서명.
4. **구멍**: 정적키 교체에 AIK 인증서 재발급·사용자 확인·알림이 없다. 서명 입력의 컨텍스트 문자열도 정해지지 않았다.
5. **권고**: "폰의 정적키 교체는 PC가 새 `Cert_M`을 AIK로 재발급할 때만 유효하며, PC 화면 또는 폰 생체 확인 후에만 적용하고, 모든 기기에 알린다. 서명 입력은 `"SAX-rotate-v1"‖pair_id‖from‖old_static‖new_static‖ts`." PC 정적키 교체는 폰에서 생체 확인 후 핀 갱신.
6. **심각도**: Medium.
7. **비용**: 설계만.

### C-19 [Medium] 데스크톱 장기 키 연산 주체가 정해지지 않았다

1. **위치**: D05:21("기기 장기 키(`Sx`,`Vx`,`Qx`) 사용 주체: 금고"), D05:49(`VaultAPI.crypto`에 `noiseStatic()` 공개키만, DH·서명·HPKE 개봉 메서드 없음), D01:25(엔진이 `net/egress`로 릴레이 통신), D03:168-170.
2. **공격 시나리오**: 구현자가 Noise 세션을 엔진(`net/egress`)에서 돌리려면 `Sd` 개인키가 엔진에 와야 한다. 그러면 엔진 RCE(포털 화면·PDF 경유) 한 번으로 `Sd`·`Vd`·`Q_D`가 유출되고, 공격자는 PC를 영구히 사칭해(폰 입장에서 진짜 PC) 승인 카드·비밀 요청을 보낼 수 있다.
3. **현재 통제**: "금고가 사용 주체"라는 표의 한 칸.
4. **구멍**: 인터페이스에 연산이 없어 결국 키를 넘기는 구현으로 흐르기 쉽다.
5. **권고**: `VaultAPI.crypto`에 `noiseDH(remotePub, ctx)`, `signVd(purpose, msg)`, `hpkeOpen(enc, ct, info, aad)`를 추가하고 "장기 개인키는 금고 밖으로 나가지 않는다. 금고는 용도 문자열 허용 목록에 있는 연산만 수행하고 호출 횟수를 감사 로그에 남긴다"를 넣는다. 금고가 오라클이 된다는 한계(침해 엔진이 연산을 요청할 수 있음)를 D05 §1의 정직한 범위에 추가한다.
6. **심각도**: Medium.
7. **비용**: 설계만.

### C-20 [Medium] 기기 인증서 수명과 폐기 신선도

1. **위치**: D08:50(`Cert_M{…, not_after}` 값 없음), D08:61·81(`deviceListVersion`), R4:251(90일), REVIEW-B C-3(e).
2. **공격 시나리오**: 서버(내부자)가 폐기 목록 갱신을 다른 기기에 숨기면, 폐기된 폰의 인증서가 계속 유효하게 보인다. 수명이 없으면 영구히 유효하다.

4. **구멍**: `not_after` 값, 버전 불일치 시 행동이 정해지지 않았다.
5. **권고**: `Cert.not_after = 발급 + 90일`, PC 온라인 시 자동 갱신. "`hello`의 `deviceListVersion`이 서로 다르면 양쪽은 더 높은 버전의 AIK 서명 목록을 상대에게 요청해 적용하기 전까지 비가역 승인과 비밀 요청을 처리하지 않는다." 폰은 30일 넘게 목록 갱신이 없으면 경고.
6. **심각도**: Medium.
7. **비용**: 설계만.

### C-21 [High] 복구 문구 피싱·부분 유출, 복구 지연·알림 부재

1. **위치**: D08:26(BIP39 12단어 → RK → AIK·KEK·K_idx…), D08:112-113, R4:91·271(`K_chk` key-check 센티넬), R4:276(UX 원칙), ADR-006:18.
2. **공격 시나리오**
   - 피싱: 가짜 "복구 키트 점검" 웹페이지, 가짜 상담원, 가짜 앱이 12단어를 받는다. 문구 하나로 AIK(계정 신원: 기기 인증서·폐기 목록 서명)와 모든 KEK가 나온다. 이메일까지 장악하면 새 기기에서 "기존 데이터 복구"를 실행해 전부 연다. 이메일이 없어도 서버 침해·내부자·CLOUD Act 제출로 얻은 암호문을 연다.
   - 부분 유출: 사진에 12단어 중 9개가 찍히면 남은 3단어는 2^33 경우라 블롭 하나의 wDEK로 몇 분 안에 맞춘다(센티넬이 없어도 가능).
   - 정상 기기의 사용자는 공격자가 복구한 사실을 모른다.
3. **현재 통제**: 128비트 엔트로피, 서버 에스크로 없음, 온보딩 안내.
4. **구멍**: 복구에 지연·알림·기존 기기 승인이 없다. R4의 `key-check` 센티넬(오타 검출)과 UX 원칙(3단어 재입력, 화면 캡처 차단)이 D08에 빠졌다. "우리는 어떤 경우에도 복구 문구를 묻지 않는다"는 대외 문구가 없다.
5. **권고**
   - D08 §9 신설 "복구 절차": "문구로 새 기기를 복구하면 (1) 모든 기존 기기와 이메일에 즉시 알리고 (2) 72시간 동안 블롭 다운로드·AIK 서명 작업(기기 추가·폐기·삭제)을 보류하며 (3) 기존 AIK 인증 기기가 승인하면 즉시 해제한다. 기존 기기가 하나도 없으면 72시간 대기 후 진행한다."
   - `K_chk = HKDF(RK, "key-check")`와 `AEAD(K_chk, "SAX-RK-OK")` 센티넬을 D08 §3에 추가(오타 검출용, 128비트라 오프라인 대입 이득 없음).
   - 문구 입력은 앱 안에서만, 웹 입력 칸을 만들지 않는다고 명시. 대외 문구 점검표(D11 §8)에 "소버린 AX는 복구 문구를 묻지 않습니다" 추가.
   - 선택 기능: SLIP-39 2-of-3 분산(R4:276)을 Phase 2 후보로 D14에 등록. REVIEW-B C-4 ④의 서버 지분 혼합(2SKD 변형)은 "문구만 훔친 사람"을 막으므로 ADR로 검토한다(계정 서버를 신뢰 경로에 넣는 대가를 함께 적는다).
6. **심각도**: High.
7. **비용**: 설계만 + Phase 2.

### C-22 [Medium] AIK 개인키가 데스크톱 키체인에 상주한다

1. **위치**: D08:38("RK는 상주시키지 않고 파생 키만 저장"), D05:22, REVIEW-B C-4 ③.
2. **공격 시나리오**: 같은 OS 사용자 권한 악성코드가 한 번 실행되면 AIK·KEK_N·K_idx를 가져간다. AIK는 회전에 새 문구가 필요하므로 계정 신원이 장기간 공격자 손에 있다(기기 인증서 발급, 폐기 목록 위조).
3. **현재 통제**: 키체인, 정직한 범위 문구(같은 사용자 악성코드는 막지 못함).
4. **구멍**: RK를 상주시키지 않는 이득이 AIK 상주로 상쇄된다. AIK는 자주 쓰지 않는 키라 사용자 존재 결박이 가능한데 그렇게 적혀 있지 않다.
5. **권고**: "AIK 개인키는 Windows Hello/Touch ID 결박 래핑 키로 암호화해 저장하고 사용할 때마다 사용자 존재를 확인한다(기기 추가·폐기·삭제·KEK 회전 때만 쓰임)." 무인 데몬은 AIK를 쓰지 않는다고 명시.
6. **심각도**: Medium(영역 B와 겹침).
7. **비용**: Phase 2.

### C-23 [Medium] 게이트웨이 재식별 [기존 인정]

1. **위치**: D09:36(접근 로그 "계정 ID 해시"), D09:39(계량 90일 원본), D09:41·D04:214(`safety_identifier = HMAC(서버 비밀, 계정 ID)[:32]`), D04:210(`X-Device-Id`), ADR-009:12, REVIEW-B E-4.
2. **공격 시나리오**: ① 운영자는 서버 비밀로 `safety_identifier`를 계정에 되돌린다. OpenAI는 같은 값으로 한 사용자의 모든 마스킹 프롬프트를 무기한 묶는다. 마스킹 잔여 정보(희귀 업종 표현, 지역명 일부)를 모으면 재식별 가능성이 오른다. 미국에서 OpenAI에 제출 명령이 오면 이 값 단위로 묶인 기록이 나가고, 우리 쪽 대응표로 실명이 된다. ② "계정 ID 해시"는 계정 ID 전체를 아는 운영자에게 가명일 뿐이다. ③ 계량(계정·기기·플레이북 ID·시각)은 "누가 언제 등본을 뗐는지"를 90일간 재구성한다.
3. **현재 통제**: 계량 원본 90일 → 일 단위 집계, 처리방침 고지, 본문 무저장.
4. **구멍**: `safety_identifier`의 서버 비밀 보관 위치·회전이 없다. 계량을 결제용(계정 연결)과 운영 통계용(계정 비연결)으로 나누지 않았다.
5. **권고**
   - `safety_identifier = HMAC(K_sid, accountId ‖ yyyymm)[:32]`(월 회전), `K_sid`는 KMS, 게이트웨이 외 접근 불가. 공급사의 남용 추적이 월 단위로 끊긴다는 대가를 적는다.
   - 계량 분리: 결제 레코드 = `{account, month, tokens, cost}`만, 운영 통계 = `{bundle, playbook, latency, outcome}`은 계정·기기 ID 없이. 호출 단위 계정 연결 레코드는 결제 대사 기간(35일)만.
   - 접근 로그의 계정 식별자를 일 회전 키 HMAC으로.
6. **심각도**: Medium(인정됐으나 완화 부족).
7. **비용**: 설계만.

### C-24 [Medium] 게이트웨이 내부자의 번들·툴셋·응답 변조

1. **위치**: D09:37-38, D04:38(`bundleId@ver+digest`, 불일치 409), D04:210-211(게이트웨이가 질문·도구·`text.format` 주입, 응답 원문 반환), ADR-009:9.
2. **공격 시나리오**: 내부자가 게이트웨이 배포본을 바꿔 ① `screen_state_v2` 응답에서 `blocked`·`security_warning` 확률을 낮춰 차단 신호를 숨긴다(사용자가 포털 제재를 받음), ② Terra 툴셋에 엔진이 모르는 도구나 developer 지시를 넣는다, ③ 모든 마스킹 프롬프트를 몰래 기록한다. 클라이언트가 보낸 `bundleDigest`는 게이트웨이가 비교하므로 악의적 게이트웨이는 비교를 건너뛰면 된다.
3. **현재 통제**: 서버 정의 번들, 화이트리스트, 무저장 검증 수단(로그 스키마·탐지기·외부 점검·산출물 해시 공개).
4. **구멍**: `bundleDigest`가 일관성 장치일 뿐 무결성 장치가 아니라는 점, 게이트웨이가 모델 출력 무결성의 신뢰 지점이라는 점이 적혀 있지 않다. 배포 산출물 해시 공개는 "실제로 돌고 있는 것"을 증명하지 못한다.
5. **권고**: D04 §7에 "게이트웨이는 모델 출력의 무결성에 대해 신뢰 지점이다. 엔진은 응답을 비신뢰 입력으로 다룬다: 결과 매핑·임계값은 **로컬 번들 정의**로 계산하고, Terra 응답의 도구 호출은 로컬 툴셋 정의에 없는 이름·스키마면 버린다. `bundleDigest` 409는 배포 불일치 감지용이다"를 넣는다. 게이트웨이가 공급사로 보낸 요청의 질문 목록 해시를 응답에 실어 클라이언트가 로컬 번들과 대조하게 한다(악의적 게이트웨이는 속일 수 있음을 함께 적음). 차단 신호는 모델 외 결정적 신호(차단 안내 URL·문구 사전)도 함께 본다는 규칙을 D03에 연결.

### C-26 [High] 레지스트리: split-view·버전 인플레이션·동결 창·키 폐기 채널

1. **위치**: D09:82-87, D11:89(서명 키 유출 대응), D12:35(긴급 보수화 1인), policy.schema:10-11(`monotonic`, `expiresAt` ≤ 14일).
2. **공격 시나리오**
   - split-view: 정적 호스팅이라도 서버(또는 CDN·내부자)는 요청자별로 다른 `index.json`을 줄 수 있다. 특정 사용자에게만 서명된 옛·다른 패키지를 주어도 투명성 로그가 없어 아무도 모른다.
   - 버전 인플레이션: 서명 키가 유출되면 공격자는 `version = 2^53-1`(또는 `monotonic` 최대치) 인덱스·정책을 서명해 뿌린다. 클라이언트는 최고 버전을 저장하므로 이후 정상 인덱스를 **영구히 거부**한다. 롤백 방어가 잠금 공격이 된다. 앱 업데이트로 키를 바꿔도 버전 상태를 초기화하는 규칙이 없다.
   - 동결 창: 공격자가 서명한 악성 인덱스는 `expires`(≤ 14일)까지 유효하다. "인덱스 즉시 동결"(D11:89)은 우리가 발행을 멈추는 것일 뿐 이미 퍼진 서명본을 무효화하지 못한다. 정책 만료 14일은 제재 후 긴급 보수화를 막는 네트워크 차단(동결)에 14일 창을 준다.
   - 2인 승인: "CI에서 사람 승인(2인) 후 서명"을 CI 기능으로 구현하면 CI 관리자 1인이나 CI 공급사 침해가 KMS 서명 권한을 쓴다.
   - 긴급 1인 정책(D12:35)은 정책 서명 키가 1인 통제로 쓰인다는 뜻이다.
3. **현재 통제**: Ed25519, 플레이북·정책 키 분리·핀 고정, KMS/HSM, 단조 버전, 만료 ≤ 14일, 만료 시 전 포털 `postprocess`, 내장 eTLD+1·origin 허용 목록.
4. **구멍**: 위 다섯 가지. 피해 반경 제한(내장 허용 목록)은 좋지만 가용성·준수 상태(잘못된 정책)를 공격받는다.
5. **권고**
   - 투명성: "모든 서명 인덱스·정책은 추가 전용 로그(Merkle, RFC 9162 형식)에 먼저 기록하고, 클라이언트는 포함 증명 없는 인덱스를 거부한다. 폰과 PC는 `hello`에 본 인덱스 헤드 해시를 교환해 서로 다르면 경고한다." 외부 증인(witness) 1곳 이상을 Phase 2에.
   - 버전 상한: "새 인덱스의 `version`은 저장된 값보다 크고 `+1000` 이하여야 한다. 서명 키 세대(`key_epoch`)가 바뀌면 버전 비교는 새 세대 안에서만 한다." policy.schema에 `keyEpoch`(정수) 추가.
   - 키 폐기 채널: 오프라인 루트 키가 서명한 `revoked_keys.json`(만료 24시간)을 따로 배포하고, 클라이언트는 폐기된 키의 서명을 즉시 거부한다.
   - 정책 만료 단축: `policy.expiresAt ≤ 72시간`(패키지 인덱스는 14일 유지). 만료 시 보수 정책은 그대로.
   - 긴급 키 제한: "1인 긴급 서명 키로 서명한 정책은 현재 정책보다 **엄격하게 보수적인** 경우(`portalMode` 하향만, 모든 상한 ≤ 현재값)에만 클라이언트가 받는다." 클라이언트가 단조 보수성을 검사.
   - 서명 의식: 2인 승인은 CI 밖, HSM 쿼럼(m-of-n 스마트카드)으로 강제한다(C-27).
6. **심각도**: High.
7. **비용**: 설계만 + Phase 1(로그·폐기 채널).

### C-27 [Medium] 서명 키 운영(KMS/HSM)

3. **권고**: D11 §7에 위 6개 시나리오별 표(탐지 신호·즉시 조치·사용자 통지·복구)를 추가한다. policy.schema에 `remote: {minProtocolVersion, disabledFeatures[]}`를 넣고 서명 배포로 즉시 적용한다. 피해 범위 문장을 §3 "운영자가 볼 수 있는 것" 표로 대체한다.
4. **심각도**: Medium.
5. **비용**: 설계만.

(형식상 (2) 공격 시나리오와 (3) 현재 통제는 구멍 목록에 함께 적었다.)

### C-32 [Low] 기기·프로필 상한 우회

1. **위치**: D09:23·27, 02:103, REVIEW-C B-07.
2. **공격 시나리오**: 세무대리 성격의 사용자가 이메일을 여러 개 만들어 계정을 늘리거나, 기기 해제·재등록을 반복한다. 서버는 프로필의 실제 신원(사업자번호)을 모르므로 슬롯 2에 사업자를 번갈아 넣어도 알 수 없다.
3. **현재 통제**: 슬롯·기기 수 상한, 로컬 이중 강제.
4. **구멍**: "구조적으로 차단"(02:103)은 과장이다.
5. **권고**: 02:103을 "한 계정 안의 대리 사용을 어렵게 한다. 다계정은 막지 못한다"로 고친다. 기기 등록·해제 이력 상한(30일에 데스크톱 3회·모바일 5회)과 결제 수단 단위 계정 수 경고를 둔다. 신원 확인 없이 다계정을 막을 수 없음을 잔여 위험으로 적는다.
6. **심각도**: Low.
7. **비용**: 설계만.

### C-33 [Low] Rekey·상태 영속·서명 컨텍스트(REVIEW-B C-8 미반영)

1. **위치**: D08:62(1시간 또는 2^20 메시지 Rekey), D08:60, D08:75.
2. **내용**: 시간 기반 Rekey는 양쪽 시점이 달라 전송 중 메시지 복호 실패를 낳는다. IK msg1 타임스탬프 최고값의 디스크 영속, 폰 재설치 시 `seq` 초기화 처리, 용도별 서명 컨텍스트 표가 없다.
3. **권고**: Rekey는 `ctr`가 2^20의 배수일 때 양쪽이 결정적으로 하거나 outer 헤더에 1비트 epoch를 둔다. 타임스탬프·`seq` 상태를 pair별로 영속하고 재페어링 시 epoch를 올린다. 서명 용도 표: `SAX-approve-v1`, `SAX-env-v1`, `SAX-qbundle-v1`, `SAX-rotate-v1`, `SAX-ckpt-v1`, `SAX-devlist-v1`, `SAX-revoke-v1`.
4. **심각도**: Low / **비용**: 설계만.

### C-34 [Low] 양자 이후 "지금 저장, 나중에 해독"

1. **위치**: D08:16-17, R4:75.
2. **내용**: 의도 봉투(거래처·금액)와 IK 세션은 X25519만 쓴다. 릴레이 운영자나 국외 망 관찰자가 암호문을 장기 보관하면 미래에 열릴 수 있다. 페어링은 QR PSK가 섞여 영향이 작다.
3. **권고**: 블롭 헤더처럼 HPKE·Noise 협상에 알고리즘 식별자를 두고, X-Wing(ML-KEM-768 + X25519) 하이브리드 전환 경로를 ADR로 예약한다. 의도 봉투에는 거래처 식별값 대신 로컬 거래처 ID 참조를 우선 쓴다.
4. **심각도**: Low / **비용**: 설계만.

## 4. 데이터 주권: 데이터가 국외 또는 외국 법인 통제 아래 놓이는 지점

### 4.1 법적 배경(감사자 지식, 법률 의견 아님)

- **미국 CLOUD Act**(18 U.S.C. §2713): 미국 관할의 통신·원격 컴퓨팅 서비스 제공자는 데이터가 어느 나라에 저장되어 있든 "소유·보관·통제" 중인 데이터를 미국 영장·제출 명령에 따라 내야 한다. AWS 서울 리전 데이터도 대상이 될 수 있다. 한국과 미국 사이의 CLOUD Act 행정협정 체결 여부는 확인 필요하다. FISA 702의 2026년 이후 재승인 상태도 확인 필요하다.
- E2EE 암호문은 제출되어도 키가 없으면 열리지 않는다. 그러나 **평문 메타데이터·계정·로그는 그대로 제출 대상**이다.
- 국내 CSP로 옮겨도 국내 법(형사소송법 영장, 통신비밀보호법 등)에 따른 제출은 남는다. 주권은 "누구의 법이 미치는가"의 문제이지 "아무도 볼 수 없음"이 아니다.
- 개인정보보호법 제28조의8: 처리위탁·보관도 국외 이전이다(R4:623).

### 4.2 지점별 표

열 "NCP+국산 모델 이전 후"는 인프라를 네이버클라우드(국내 CSP)로, 모델을 국내 리전에서 처리되는 국산 모델로 옮겼을 때를 말한다. **사라짐** = 해당 국외·외국 법인 지점이 없어짐, **남음** = 그대로, **바뀜** = 형태가 바뀌어 남음.

- **이전으로 사라지는 지점**: 1~10, 17, 19(국내·자체 선택 시). 서버 평문(계정·메타데이터·로그)과 모델 전송이 외국 법인 통제에서 빠진다. 이것이 가장 큰 이득이다.
