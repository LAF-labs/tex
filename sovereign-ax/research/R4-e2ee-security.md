## 3. 키 계층 (복구 문구 포함)

```
복구 문구 (BIP39 영어 12단어 = 128비트 엔트로피 E)   ← 종이/비밀번호 관리자. 서버 미보관
        │  HKDF-SHA256(ikm=E, salt="SAX-RK-v1")
        ▼
 RK (256비트 루트 키)  — 데스크톱(주 기기) OS 키체인. 필요하면 문구로 재생성
  ├─ HKDF("aik")          → AIK  : Ed25519 계정 신원 키 (기기 인증서·폐기 목록·키 전환 서명)
  ├─ HKDF("kek/blob/vN")  → KEK_N: 파일별 DEK 래핑 키 (모바일에도 전달, 생체 보호 저장)
  ├─ HKDF("idx/hmac")     → K_idx: 메타데이터 키드 태그. 서버 비공개
  ├─ HKDF("meta/sig")     → K_meta: 인덱스 레코드 무결성(모바일 검증용으로 전달 가능)
  ├─ HKDF("key-check")    → K_chk: "키가 맞는지" 확인용 AEAD 센티넬
  └─ HKDF("audit")        → K_audit: 감사 로그 체크포인트 MAC (폰과 공유)

기기별 랜덤 키 (복구 문구와 무관, 기기 밖으로 나가지 않음)
  ├─ Sx : X25519 정적키 (Noise IK/XX 전용)
  ├─ Vx : Ed25519 서명키 (승인·체크포인트·비동기 봉투)
  ├─ Qx : X25519 inbox 키 (HPKE 수신용, 7일 단위 로테이션 [제안])
  ├─ Lx : 로컬 저장소 래핑 키 (SecureStore/Keystore, 생체 바인딩)
  └─ Px : (모바일, 선택) SE/StrongBox P-256 승인 서명키 — 추출 불가, 데스크톱이 ECDSA로 검증

파일별
  └─ DEK_f (256비트 랜덤) ── XChaCha20-Poly1305 ──> wDEK_f (KEK_N으로 래핑)
```

| 규칙 | 근거 |
|---|---|
| DEK는 파일마다 새로 생성하고, 서로 다른 사용자 간에 공유하지 않는다 | Google KMS 권고 [S55] |
| KEK 회수는 "DEK를 새 KEK로 재래핑한 뒤 옛 KEK 폐기". 재래핑은 DEK의 암호 기간을 초기화하지 않는다 | OWASP Key Management [S56] |
| 모든 키는 컨텍스트 문자열로 도메인을 분리한다 | libsodium `crypto_kdf` 설명 [S7] |
| 모바일은 RK·AIK 개인키를 갖지 않는다. 받는 것은 `KEK_N`, `K_meta`, `K_audit` | 최소 권한. 폰 분실 피해를 "열람 가능 범위"로 한정 |
| 서버·릴레이는 RK 파생 키를 하나도 갖지 않는다 | 비밀 경계(03 §4) |
| 계정 인증(이메일 OTP 등)과 암호 키는 완전히 분리한다. 비밀번호에서 키를 만들지 않는다 | 1Password는 비밀번호 + Secret Key를 섞는 2SKD로 서버 저장 검증자를 크래킹 불가로 만든다 [S49b]. 우리는 비밀번호 인증 자체를 없애 같은 효과를 더 단순하게 얻는다 |

## 4. 프로토콜 흐름

### 4.0 패턴 선택 근거 (XX vs IK vs KK vs XK)

Noise 명세의 "페이로드 보안 속성" 표(수신 인증 0–2, 기밀성 0–5)가 선택의 기준이다 [S1 §7.7].

| 패턴 | 메시지 | 송신자 인증 | 기밀성(Destination) | 우리에게 의미 |
|---|---|---|---|---|
| XX | `-> e` / `<- e, ee, s, es` / `-> s, se` | 0 / 2 / 2 | 0 / 1 / 5 | 사전 지식 0. 정적키가 암호화되어 전송되므로 신원 은닉에 유리하나, **누구의 키인지는 앱이 별도로 확인해야 한다**(Noise §14 "Authentication") |
| IK | `<- s` … `-> e, es, s, ss` / `<- e, ee, se` | 1 / 2 | 2 / 4 | 1번 메시지 페이로드는 **재전송 가능·전방 비밀성 약함**(기밀성 2). 2번 메시지부터 강해진다 |
| KK | `-> s` `<- s` … `-> e, es, ss` / `<- e, ee, se` | 1 / 2 | 2 / 4 | IK와 같은 약점. 양쪽 정적키를 사전에 알아야 해서 키 분실 시 복구 경로가 없다 |
| XK | `<- s` … `-> e, es` / `<- e, ee` / `-> s, se` | 0 / 2 / 2 | 2 / 1 / 5 | 응답자 정적키를 사전에 알 때 가장 엄격. 3번째 메시지에서 개시자 정적키를 숨긴 채 전달 |

선택:

1. **페어링 = XXpsk0.** 폰이 QR로 데스크톱 정적키 `Sd`를 이미 안다는 점에서 이론상 XK 계열(XKpsk3)이 더 엄격하다. 그러나 후보 라이브러리(`noise-handshake`)는 psk0만 지원하고 XK에 psk를 붙이는 형태를 지원하지 않는다 [S64]. XXpsk0에 "폰은 수신한 `rs`가 QR의 `Sd`와 같은지 검사" 규칙을 더하면 응답자 인증은 XK와 같은 효과를 낸다. PSK를 첫 메시지(psk0)에 섞으면 PSK 없는 관찰자는 `e` 이후의 모든 바이트를 해독할 수 없다(Noise §9.4 [S1]).
2. **상시 세션 = IK.** 양쪽이 서로의 정적키를 알고 있으므로 1.5 왕복이 필요한 XX는 불필요하다. IK는 2메시지 완료이며 WireGuard가 같은 계열(`Noise_IKpsk2_25519_ChaChaPoly_BLAKE2s`)을 쓴다 [S29]. KK도 가능하나 후보 라이브러리에 없고 이득이 작다.
3. **IK 1번 메시지에는 명령을 싣지 않는다.** 표의 기밀성 2는 재전송과 수신자 키 사후 유출에 취약하다. 대신 WireGuard 방식으로 **단조 증가 타임스탬프**만 싣고(응답자가 정적키별 최댓값을 보관하고 이하를 버림) 핸드셰이크 재전송으로 정상 세션이 끊기는 것을 막는다 [S29 §5.1].
4. **일방향 패턴(N/K/X)은 오프라인 큐에 쓰지 않는다.** 기밀성이 2 수준(수신자 정적키 유출 시 과거 메시지 해독, 재전송 가능)이라서다. 오프라인은 §4.4의 HPKE 봉투로 처리한다.
5. 정적키는 Noise 전용으로만 쓰고 같은 해시(BLAKE2b)로 고정한다. 서명·HPKE에는 다른 키를 쓴다 [S1 §14 "Static key reuse"].

### 4.1 QR 페어링 (데스크톱 ↔ 모바일, 릴레이는 비신뢰)

**QR 페이로드** (바이너리 모드. URL 형식을 쓰지 않는다 — OS 기본 카메라가 앱을 열어 피싱에 쓰이는 경로를 막는다. MSC4108도 같은 이유로 독자 바이너리 형식을 쓴다 [S2 보안 고려 표]):

| 필드 | 크기 | 내용 |
|---|---|---|
| 매직·버전 | 5B | `SAXP` + `0x01` |
| 의도 | 1B | 새 폰 추가 / 복구 후 재페어링 (MSC4388의 intent 바이트와 유사 [S3]) |
| 릴레이 | 1+n B | 호스트명. 앱이 허용 도메인 목록과 대조 |
| room_id | 16B | 1회용 임시 룸(랜덤) |
| Sd | 32B | 데스크톱 X25519 정적 공개키 |
| ps | 32B | 1회용 PSK. **비밀**. 로그·클립보드·화면 공유 금지 |
| exp | 4B | 만료 UTC epoch (기본 120초 [제안]) |

합계 약 100~140바이트라 QR 용량에 여유가 있다(QR은 버전 1–40, 최대 177×177 모듈 [S48]). 사진·화면 공유로 `ps`가 새는 경우를 가정해 아래 4·6·8단계를 둔다.

**사전 조건**: 폰은 이메일 OTP로 로그인한 직후 자기 `Sm`, `Vm`(공개키만)을 계정에 "미승인 기기"로 등록한다. 데스크톱의 `Sd`, `Vd`는 최초 설치 때 계정에 등록되어 있다.

**흐름**

1. [데스크톱] 사용자가 "기기 추가"를 누른다. OS 사용자 존재 확인(Windows Hello/Touch ID)을 거친다. 데스크톱은 `room_id`, `ps`, `exp`를 만들고 클라우드 API(계정 토큰)에서 **1회용 룸**을 발급받는다. 룸은 정원 2, TTL 120초, 계정 ID를 룸 레코드에 남기지 않는다.
2. [데스크톱] QR을 화면에 표시하고 룸에서 응답자(Responder)로 대기한다. 룸 생성은 계정당 시간당 5회 등으로 제한한다 [제안].
3. [모바일] 앱 내부 스캐너로만 스캔한다. 검사: ① `exp` 미경과, ② 릴레이 호스트가 허용목록에 있음, ③ **`Sd`가 내 계정의 데스크톱 기기 목록에 있음**(클라우드 API 조회, 없으면 중단). ③은 "공격자가 자기 데스크톱의 QR을 피해자 폰이 스캔하도록 유도하는 원격 피싱"을 막는다 (Matrix MSC4108도 같은 위협을 별도 절로 다룬다 [S2]).
4. [모바일→데스크톱] `Noise_XXpsk0_25519_ChaChaPoly_BLAKE2b`, 개시자=모바일, `psk=ps`, prologue=`"SAX-pair-v1" ‖ room_id ‖ 릴레이 호스트 ‖ exp`(prologue가 다르면 핸드셰이크가 실패한다 [S1 §6]).
   - msg1 `psk, e` — 페이로드 없음
   - msg2 `e, ee, s, es` — 페이로드: 데스크톱 기기 인증서(`Vd`, 역할)
   - 폰은 수신한 `rs == Sd` 를 확인하고 아니면 중단한다
   - msg3 `s, se` — 페이로드: 기기 이름·플랫폼·`Vm`·푸시 토큰
5. [양쪽] 핸드셰이크 해시 `h`(채널 바인딩에는 `ck`가 아니라 `h`를 쓰라는 것이 Noise의 지침 [S1 §11.2, §14])로 SAS를 계산한다: `SAS = u32(HKDF-SHA256(ikm=h, info="SAX-SAS-v1", L=4)) mod 10^6`. 폰은 6자리를 크게 표시한다.
6. [데스크톱] 입력창이 열리고 사용자는 **폰에 표시된 6자리를 PC에 직접 입력**한다(단순 "일치합니다" 버튼으로 만들지 않는다 — MSC4388도 체크코드를 생성 측 기기에 입력하게 한다 [S3]). 3회 실패 또는 TTL 경과 시 룸을 폐기한다. 동시에 데스크톱은 폰의 `Sm`이 **같은 계정에 폰이 직접 등록한 기기 키 목록**에 있는지 확인한다(QR이 유출된 공격자는 계정 로그인 없이는 통과하지 못한다).
7. [데스크톱] 성공하면 AIK로 폰의 기기 인증서 `Cert_M = Sign_AIK{device_id, Sm, Vm, role, not_after}`를 발급하고, **이미 수립된 Noise 전송 채널** 안에서 `PAIR_OK{Cert_M, AIK_pub, 기기 목록 버전, KEK_N, K_meta, K_audit}`를 보낸다. 같은 채널에서 영구 우편함 ID·토큰을 만든다: `mbx_id`, `tok_read`, `tok_write` = HKDF(`h`, 컨텍스트별). 릴레이는 페어링 룸과 영구 우편함의 연관을 알 수 없다.
8. [양쪽] `ps`, 임시키, 룸을 폐기한다. 서로의 `Sx`, `Vx`, 인증서, 카운터 상태를 보관한다. 폰은 키를 생체 인증 바인딩 저장소로 옮긴다(§7).

**왜 이 구조가 안전한가 (분석)**

| 공격 | 막는 요소 |
|---|---|
| 릴레이/네트워크 MITM | 폰이 `Sd`(QR로 인증된 광학 채널)와 응답자 정적키를 대조 → 사칭 불가. PSK 없이는 msg1 이후를 해독·참여 불가 |
| 두 세션을 중계해 SAS를 맞추려는 브리징 MITM | 폰이 데스크톱을 인증하므로 폰 쪽 세션을 공격자가 만들 수 없다 → 20비트 SAS로 충분(대안: ZRTP·Matrix의 해시 커밋먼트 SAS 42비트 [S4, S20]). 이 판단은 [제안·분석]이며 페어링 검토 시 형식 검증 대상 |
| QR 사진·어깨너머 → 공격자가 먼저 접속 | PC가 폰의 SAS를 요구하고 계정 기기 목록을 대조한다. 공격 세션의 SAS는 폰의 SAS와 다르고, 폰은 룸이 소진되어 실패 화면을 본다 (MSC4108의 "shoulder-surfing" 시나리오와 동일 구조 [S2]) |
| 핸드셰이크 재전송 | 응답자가 새 임시키를 내고 `ps`·`s`를 모르는 재전송자는 완료 불가. 룸은 1회용·120초 |
| 원격 피싱 | 3단계 계정 기기 목록 대조 + "내 PC 화면의 QR만 스캔하세요" 경고 |
| QR 데이터 재사용 | 룸 소진·만료, 임시 `ps` |

**QR을 스캔할 수 없을 때(카메라 고장·권한 거부 등)의 대체 경로**: 8–9개 BIP39 단어(88–99비트)를 `ps`로 직접 입력하는 방식이 Keybase KEX의 `W`와 같다 [S36]. 짧은 코드(16비트)로 PAKE(SPAKE2)를 쓰는 Magic Wormhole 방식은 "코드당 추측 1회"가 전제이며 서버 DoS에 취약하다고 스스로 밝힌다 [S37c]. 우리는 새 프리미티브를 추가하지 않고 88비트 단어 코드를 권한다.

### 4.2 상시 세션 (재접속) · 키 교체

1. [모바일] WSS 연결 후 우편함 `tok_write`/`tok_read` 토큰을 제시한다(§5.2). 데스크톱이 온라인이면 릴레이가 두 소켓을 이어 준다.
2. `Noise_IK_25519_ChaChaPoly_BLAKE2b`, 개시자=모바일, prologue=`"SAX-session-v1" ‖ pair_id`. msg1 페이로드는 **단조 타임스탬프 8바이트뿐**. 데스크톱은 ① `Sm`이 페어링 목록·미폐기 상태인지, ② 타임스탬프가 정적키별 최댓값보다 큰지 확인하고 아니면 **무응답으로 버린다**(오류 신호가 오라클이 되지 않도록).
3. 전송 키가 만들어지면 방향별 `n=0`부터 시작한다. 첫 메시지 `HELLO{기기 목록 버전, 비동기 seq 최고값}`.
4. **키 교체**: ① 연결(재접속)마다 새 핸드셰이크 → 임시키가 새로 생기므로 전방 비밀성; ② 연결 중에는 `Rekey()`를 **1시간 또는 2^20 메시지마다**(둘 중 먼저) 양방향 호출 [제안]. Noise의 `Rekey()`는 `n`을 초기화하지 않으므로 2^64−1 한도 전에 새 핸드셰이크가 필요하다 [S1 §11.3]. 참고: WireGuard는 UDP VPN이라 120초/2^60 메시지마다 재협상한다 [S29 §6]. 우리는 저빈도 제어 채널이라 완화했다.
5. **정적키 교체(연 1회 또는 의심 시)**: 라이브 세션 안에서 `ROTATE_STATIC{신규 Sx', 서명=Vx}`를 보내 상대가 핀을 갱신한다. 둘 다 오프라인에서 키를 잃은 경우는 재페어링이다.
6. **종료**: 인증된 `CLOSE` 메시지를 보내 끝난다. 스트림 절단 방지는 애플리케이션 책임이라고 Noise가 명시한다 [S1 §14 "Session termination"].

### 4.3 메시지 프레이밍·논스

릴레이가 보는 바깥 헤더와 암호화되는 안쪽 구조를 분리한다.

```
outer = ver(1B) ‖ kind(1B: HS / DATA / ENV) ‖ ctr(8B, DATA만, 평문) ‖ len(2B)
DATA  = outer ‖ ChaCha20-Poly1305(k_tx, nonce = 0x00000000 ‖ LE64(ctr), ad = outer, pt = pad(inner))
inner = 결정적 CBOR { t:타입, id:UUIDv7, seq, ts, ttl, body }
pad   = ISO/IEC 7816-4 로 버킷 {256, 512, 1K, 4K, 16K, 64K−오버헤드}까지  [libsodium sodium_pad]
```

| 항목 | 규칙 |
|---|---|
| Noise 전송 메시지 한도 | 65,535바이트. 더 큰 것은 분할. **PDF·이미지는 릴레이로 보내지 않고** 블롭 저장소로 올리고 릴레이에는 `blob_id`와 래핑된 DEK만 보낸다(03 §8.6과 일치) |
| 카운터 | 명시 `ctr`(8B)를 헤더에 실어 **수신 측이 슬라이딩 윈도(1024)로 중복·순서 역전을 걸러낸다**(Noise §11.4가 허용하는 `SetNonce` 방식 [S1], WireGuard·IPsec 윈도 [S29, S25]). 릴레이가 재전달·역전해도 윈도 밖이면 버린다 |
| 논스 | Noise 내부는 **카운터 논스만**. 랜덤 논스 금지. 키 하나당 반복 금지(RFC 8439) [S17] |
| 블롭·DEK 래핑·로컬 저장 | XChaCha20-Poly1305 랜덤 24B 논스 [S5] |
| 크기 은닉 | 패딩 버킷으로 길이 유출을 줄인다. 큰 파일은 Padmé(최대 +12%) [S61] |
| 도메인 분리 | 서명·MAC 입력에는 항상 컨텍스트 문자열(`"SAX-approve-v1"` 등)과 `pair_id`, 방향을 포함. 방향별 키가 달라 반사(reflection) 공격도 무효 |
| 키 커밋먼트 | Poly1305 계열 AEAD는 키 커밋을 제공하지 않으므로, 하나의 암호문을 여러 키로 시험하는 서버 측 오라클을 만들지 않는다 [미검증: 별도 문헌 확인 필요] |

### 4.4 오프라인 큐와 "릴레이가 재전송 오라클이 되지 않게" 하는 법

**원칙**: 비밀(인증서 비번·OTP·보안카드·캡차 답)은 큐에 넣지 않는다. 큐는 "PC 켜지면 실행" 같은 **의도(intent)** 만 담는다.

**봉투 흐름**

1. 각 기기는 `Qx`(X25519 HPKE 수신키)를 7일마다 새로 만들고 `{Qx, valid_from, valid_to, seq}`를 `Vx`로 서명해 우편함의 "번들 슬롯"(최신 1개만)에 게시한다. 개인키는 `valid_to` + 큐 TTL 동안만 보관 후 삭제한다 → 전방 비밀성 창 ≈ 로테이션 7일 + 큐 TTL 3일 [제안]. Signal X3DH가 서명된 프리키를 주기적으로 교체하고 이전 키를 지연 메시지 처리용으로만 잠시 보관하는 것과 같은 논리다 [S33].
2. 폰이 `Intent{pair_id, from, to, seq, iat, exp, cmd_id, playbook_id, inputs, action_hash}`를 만든다 → Ed25519 서명(`Vm`) → HPKE Base 봉인(`pkR=Q_D`, info=`"SAX-env-v1"`, aad=`pair_id ‖ seq ‖ exp`) → 우편함 업로드(TTL 72시간, 최대 50건 [제안]). 서명 안에 수신자 ID를 넣어 "서명 후 암호화"의 재포장 문제를 막는다.
3. 데스크톱 부팅 → IK 세션 수립 → 큐 드레인. 각 봉투: ① HPKE 개봉 실패 → **조용히 폐기**, ② 서명 검증, ③ `exp` 미경과·`seq`가 윈도 안에서 미사용·`cmd_id` 미실행, ④ 화이트리스트 플레이북, ⑤ 통과해도 **즉시 실행하지 않고** 대기 요청 카드를 만들어 §4.5의 새 챌린지로 승인받는다(비가역 단계).
4. 데스크톱은 `ACK{seq}`를 게시하고 서버는 봉투를 지운다. 수신 상태(`max_seq`, 비트맵, 처리한 `cmd_id`)는 **디스크에 영속**한다(재시작 후 재전송 방어).

**방어 계층**

| 공격 | 통제 | 근거 |
|---|---|---|
| 옛 세션 암호문을 새 세션에 재전송 | 세션 키가 연결마다 새로움 → 복호 실패 | Noise 임시키 [S1] |
| 세션 안 재전송·순서 역전 | `ctr` 윈도 | [S1 §11.4, S25] |
| 핸드셰이크 1번 재전송 | 단조 타임스탬프 + 정적키별 최댓값 | WireGuard [S29] |
| 봉투 재전송 | `seq` 윈도 + `exp` + `cmd_id` + 영속 상태. HPKE 자체는 재전송을 막지 않는다 | RFC 9180 §9.7.3 [S19], X3DH §4.2–4.3 [S33] |
| 재전송으로 비가역 실행 | 큐 → **실행이 아니라 새 승인**. 승인은 데스크톱이 방금 만든 1회용 챌린지에 묶임(§4.5) | [제안] |
| 재전송의 관찰 가능한 반응(오라클) | 실패는 모두 무응답·정상 처리와 시간 차이 최소화, 오류 코드 없음, 우편함당 실패 횟수 상한 후 연결 종료 | [제안] |
| 릴레이의 삭제·지연 | `ACK`/재전송, 폰 UI에 "대기 중" 상태와 만료 표시 | |
| 반사·방향 혼동 | 방향별 키·서명 컨텍스트에 `from/to` | |

### 4.5 승인(user_gate)·비밀·캡차/OTP 중계

1. 데스크톱이 비가역 단계 직전 `APPROVAL_REQUEST{req_id, card, action_hash, challenge(32B 랜덤), exp(120초)}`를 생성한다. **카드 텍스트는 데스크톱이 신뢰 계획값에서 렌더링**한 것이며 폰은 표시만 한다(03 §8.4의 "로컬 화면에도 동일 표시"와 일치).
2. 폰은 생체 인증 후 `Sign("SAX-approve-v1" ‖ pair_id ‖ req_id ‖ challenge ‖ action_hash ‖ decision)`를 `APPROVAL_RESPONSE`로 보낸다. 서명키는 소프트웨어 `Vm`(Ed25519)이 기본이고, SE/StrongBox의 P-256 키 `Px`로 두면 키 추출이 불가능해 더 강하다(§7, Apple SE는 P-256만 지원 [S42]).
3. 데스크톱은 챌린지 일치·`exp`·서명·`action_hash`를 검증한다. 로컬에서 먼저 승인되면 폰 카드는 닫는다(둘 중 하나 승인).
4. **비밀 입력**(`NEED_SECRET{req_id, kind, exp}` → `SECRET{req_id, value}`)은 라이브 IK 세션에서만 오간다. 폰은 비밀을 디스크·로그·클립보드에 쓰지 않고, 데스크톱은 `Uint8Array`로 받아 사용 직후 0으로 덮는다. 큐 금지.
5. **캡차/OTP**: 데스크톱이 캡차 이미지를 `CAPTCHA_IMAGE{req_id}`로 보내면 사용자가 폰에서 직접 푼다(02 §12 "캡차는 사용자가 직접 푼다"와 일치). 답은 `req_id`에 묶여 TTL(120초)이 지나면 폐기된다. OTP는 일회용이므로 재전송 가치가 거의 없고, `req_id` 불일치는 무시한다.

**지연 목표**: `05-access-and-detection.md` §3-1의 "10초 핸드오프"를 지키려면 폰이 이미 세션을 갖고 있거나(포그라운드), 알림 푸시 → 사용자가 탭 → IK 핸드셰이크(2메시지) 순서로 이어져야 한다. iOS 백그라운드에서는 무음 푸시에 의존할 수 없으므로(§5.4) 캡차·승인 알림은 반드시 **알림 푸시 + 탭**으로 설계한다 [제안]. 핸드셰이크 지연은 스파이크 S-1에서 측정한다.

### 4.6 기기 분실·폐기

1. 사용자가 데스크톱(또는 복구 문구로 복구한 새 기기)에서 "기기 폐기" → `Revoke{device_id, version+1}`을 **AIK로 서명**해 서버·남은 기기에 배포한다. 서버는 해당 기기의 토큰·푸시 등록·블롭 다운로드 권한을 즉시 무효화한다(서버 측 방어 심층화).
2. 폐기된 폰이 이미 받은 `KEK_N`을 가지고 있으므로 **KEK 버전을 올려 모든 DEK를 재래핑**한다(블롭 재암호화는 불필요) [S56b]. 이미 내려받은 평문 사본은 회수할 수 없다 → 앱 캐시는 항상 `Lx`로 암호화, 일정 시간 후 자동 삭제.
3. 인증서 수명은 90일 [제안]. 갱신은 데스크톱이 온라인일 때 이루어진다. 서버가 폐기 소식을 숨겨도 인증서가 만료되도록 하는 장치다.
4. 계정 서버가 임의로 기기를 추가하지 못하게, 모든 기기는 **AIK 서명이 없는 기기 목록 항목을 거부**한다. Matrix의 교차 서명(MSK→SSK→기기 키)을 단일 주 기기 구조로 단순화한 것이다 [S4].

### 4.7 다기기 검증: Signal·Matrix·Keybase·1Password·Tailscale와 우리의 선택

| 시스템 | 새 기기 추가 방식 | 검증·신뢰 | 우리가 가져온 것 |
|---|---|---|---|
| Signal | 새 기기가 임시 "provisioning 주소"와 Curve25519 공개키를 QR로 표시 → 주 기기가 스캔하면 새 기기 공개키로 암호화한 provisioning 메시지(공유 키, 계정 정보, **1회용 링크 토큰**) 전송. 기기마다 별도 키, 발신자가 기기별로 암호화 [S31]. Sesame가 기기별 세션 레코드를 관리 [S32] | 링크 토큰이 "주 기기의 허락"을 증명. 서버는 내용을 못 봄 | 기기 인증서 개념, 기기별 독립 키, 이력 이전 시 **1회용 대칭키를 provisioning 메시지로** 전달 [S31] |
| Matrix | 교차 서명 키 3종(MSK/SSK/USK)이 기기 키를 서명 [S4]. SAS(해시 커밋먼트, 이모지 7개=42비트 또는 13비트 숫자 3개), QR 검증(양쪽 마스터 키 + 랜덤 비밀) [S4]. QR 로그인은 MSC4108/4388: 임시 X25519 + HPKE Base, 2자리 체크코드, 비신뢰 랜데뷰 서버, 4KB 페이로드 상한 [S2, S3] | 사용자가 대역 외(사람 눈)로 확인 | QR 구조, 체크코드를 생성 측에 입력, 랜데뷰 DoS 통제, 서명된 기기 목록 |
| Keybase | 기존 기기가 새 기기를 프로비저닝. 오프라인 비밀 `W`(BIP39 단어 8–9개 88/99비트 또는 QR)로 서버를 경유한 메시지를 인증·암호화(NaCl SecretBox), 모바일은 scrypt N=2^10으로 완화 [S36] | `W`를 아는 쪽만 참여 | 단어 코드 대체 경로, 모바일 KDF 비용 완화 |
| Magic Wormhole | SPAKE2 PAKE + 중개 "메일박스". 코드는 1회용이라 공격자의 추측은 1회 [S37a] | 기본 코드 16비트 → 1/65536 확률 MITM, 서버 DoS 취약점을 문서가 인정 [S37c] | 메일박스·네임플레이트 개념, DoS 완화 후보(PoW, IP 해시 로테이션) |
| 1Password | 비밀번호 + 128비트 Secret Key(34자) → 2SKD, 새 기기는 add-device 링크/QR + 비밀번호 [S49a, S49b] | Secret Key는 1Password도 복구 불가 | 서버가 가진 것으로 크래킹 불가능한 구조, 비상 키트 UX |
| Tailscale | 코디네이션 서버는 "공개키 사서함", 개인키는 기기 밖으로 나가지 않음. DERP는 이미 암호화된 WireGuard 패킷을 맹목 중계 [S38] | 노드 키 공개 목록 | 릴레이는 사서함·맹목 중계 모델 |

→ 우리 선택은 Signal(QR + 1회용 토큰) + Matrix(QR, 체크코드, 서명된 기기 목록) + Keybase(88비트 단어 대체 경로)의 조합이며, 키 계층(AIK/KEK)은 1Password·Proton 사례를 따른다.

### 4.8 복구 절차 (서버 에스크로 없음)

| 시나리오 | 절차 | 결과 |
|---|---|---|
| 모든 기기 분실, 문구 보관 | ① 새 앱에서 이메일 OTP 로그인 → "기존 데이터 복구" ② 12단어 입력 → RK 파생 ③ 서버의 `key-check` 센티넬(`AEAD(K_chk, "SAX-RK-OK")`)을 복호해 **키 일치를 확정**(BIP39 체크섬은 4비트뿐이라 보조) ④ AIK 서명된 기기 목록·폐기 목록 검증 ⑤ 새 기기 인증서 발급 ⑥ 이전 기기 폐기 ⑦ 인덱스·블롭 복호 | 서류 복구. **인증서·비밀번호·로컬 DB는 복구 대상 아님**(비밀 경계 원칙) → 재등록 안내 |
| 문구 분실, 데스크톱 정상 | "복구 문구 재발급" → 새 RK′ → DEK 재래핑, AIK 전환 선언을 옛 AIK로 서명해 폰의 신뢰 승계. 옛 문구가 유출됐다면 블롭 자체를 새 DEK로 재암호화 | 정상 운영 |
| 문구와 모든 기기 분실 | 복구 불가를 가입 시 고지. Apple ADP·1Password·Signal도 동일하게 "운영자가 복구 불가"를 전제 [S35, S49a, S50] | 서류 영구 손실. 서버 평문 메타데이터만 남음 |
| 문구 유출 | 유출자가 서버 암호문을 확보하면 전부 해독 가능 → 즉시 RK 교체 + 블롭 재암호화 | 사고 절차 문서화 필요 |

**UX 원칙**: ① 가입 직후가 아닌 "첫 서류 백업 ON" 직전에 문구를 보여 준다. ② 3개 임의 단어 재입력 확인. ③ 인쇄용 "복구 키트" PDF(문구 + 안내, QR 없음). ④ 화면 캡처 방지·클립보드 비활성(권고). ⑤ 90일마다 "문구를 아직 가지고 계신가요?" 리마인더. ⑥ 선택 기능: SLIP-39 Shamir 분산(예: 2-of-3, 대표자·세무 담당·금고) [S53] — 핵심 기능은 아니고 Phase 2 후보이며 기본 UX를 해치지 않는 옵션으로 둔다.

### 4.9 감사 로그 해시 체인

```
entry_i  = { seq=i, ts, actor_device, event, summary(비밀 제외), prev=H_{i-1} }
H_i      = BLAKE2b-256( canonical(entry_i) )         // prev가 entry에 포함되므로 체인
checkpoint_k = Sign_Vd{ seq, H_seq, ts }             // 100건 또는 1시간마다 [제안]
```

| 항목 | 설계 |
|---|---|
| 앵커링 | 체크포인트를 **폰에 푸시**(E2E 채널)하고, 사용자가 허용하면 서버에는 `(seq, H, ts)` 32바이트급만 "증인"으로 올린다(03 §7의 "감사 로그 요약 통계 옵트인"과 같은 수준) |
| 한계 | 해시 체인만으로는 **끝부분 절단·전체 재작성**을 막지 못한다. Schneier–Kelsey는 장애 종료와 정상 종료를 구분하는 "비정상 종료 메시지" 및 키 진화(전방 안전 MAC)로 이를 보완한다 [S62a]. Crosby–Wallach는 서명된 커밋먼트와 일관성 증명으로 "서로 다른 시점에 다른 이야기를 하는 로거"를 검출한다 [S62b] |
| 선택 강화 | `K_audit`로 항목 MAC 키를 매 항목 `A_{j+1}=H(A_j)`로 진화시키고 이전 키 삭제(데스크톱 침해 이후에도 과거 항목 위조 불가). 검증자는 폰 [S62a] |
| 확장 | 증명 크기를 줄이려면 Merkle 트리의 포함·일관성 증명(RFC 9162 §2.1) [S26] |
| 내용 | OWASP 로깅 지침: 비밀·세션 토큰·불필요한 민감정보는 제외하거나 마스킹·해시하고 변조 탐지를 넣는다 [S56d]. 03 §11의 "입력값 요약"은 마스킹된 값만 |
| 서버 측 접속기록 | 사용자용 감사 로그와 별개로, 개인정보처리시스템 접속기록은 법정 보관(§9 L3) |

## 5. 릴레이 서버 설계 (영지식 우편함)

### 5.1 구성과 데이터 모델

```
클라이언트 ──WSS(TLS1.3)──> Edge(레이트리밋·WAF) ──> Relay(우편함 라우팅)
                                                       ├─ 큐 저장소(암호문, TTL 만료)
                                                       ├─ 레지스트리(우편함 ID → 토큰 해시, 쿼터)
                                                       └─ 푸시 디스패처(토큰 암호화 보관)
```

| 엔티티 | 저장 필드 | 저장하지 않는 것 |
|---|---|---|
| 페어링 룸 | `SHA-256(room_id)`, 생성 시각, TTL(120초), 상태 | 계정 ID, 공개키, PSK |
| 우편함 | `mbx_id`(128비트), `SHA-256(tok_read)`, `SHA-256(tok_write)`, 번들 슬롯(서명된 `Qx`), 쿼터 소유 참조 | 평문 토큰, 기기 이름, 페어 상대 |
| 메시지 | 불투명 바이트열, 길이, 입고 시각, TTL, 순번 | 평문, 발신자 신원 |
| 푸시 등록 | 플랫폼, 푸시 토큰(저장 시 서버 키로 암호화) | 알림 내용 |

- 우편함 ID와 토큰은 페어링 핸드셰이크 해시 `h`에서 HKDF로 파생되므로 서버는 페어링 룸과 영구 우편함을 연결할 수 없다.
- **토큰 해시만 저장**하므로 DB가 유출되어도 우편함에 쓰기·읽기를 할 수 없다. Signal이 "sealed sender"에서 96비트 배달 토큰의 증명을 요구해 전송을 제한하는 것과 같은 계열의 능력 기반 접근 제어다 [S30]. Signal은 이를 통해 "발신자 신원 없이도 남용 방지"를 달성하려 했다.
- 레지스트리의 "쿼터 소유 참조(계정)"는 과금·남용 제한용이다. 데이터 평면 로그에는 쓰지 않고 접근 권한을 분리한다. 운영자가 가입 정보(이메일·IP)를 이미 알고 있어 **연결 가능성은 이론상 남는다**(LINDDUN Linking). 장기 완화책으로 Privacy Pass 계열 비연결 토큰을 검토한다 [S27: 발급자-클라이언트 비연결성이 설계 목표].

## 6. 암호화 블롭 백업

### 6.1 포맷과 흐름

**블롭 포맷 v1** (RN 라이브러리가 `crypto_secretstream`을 제공하지 않으므로 [S46], 같은 개념의 청크 AEAD를 `XChaCha20-Poly1305`로 직접 규정한다. age 명세의 STREAM 변형(64KiB 청크, 마지막 청크 표시, 파일마다 새 페이로드 키)이 참고 설계다 [S54]).

| 객체 | 내용 |
|---|---|
| **키 객체** (≈200B, 별도 객체) | `ver`, `alg_id`, `kek_ver`, `wDEK = XChaCha20-Poly1305(KEK_N, DEK, ad="SAX-dek-v1" ‖ blob_id ‖ kek_ver)`, 24B 논스 |
| **데이터 객체** | 청크 반복: `nonce(24B) ‖ ct(64KiB + 16B)`. 청크 AD = `SHA-256(헤더) ‖ 청크번호 ‖ 마지막여부`. 마지막 청크는 반드시 `final=1`이고 비어 있지 않아야 함(절단·순서 변경 검출) |
| 평문 구성 | 내부 헤더(파일명, MIME, 전체 로컬 메타, 평문 SHA-256) ‖ 파일 바이트 ‖ 패딩(Padmé) |

키 객체를 분리하면 KEK 회전 때 작은 객체만 다시 쓰면 되고(OWASP: 재래핑은 DEK를 바꾸지 않음 [S56b]), 삭제 때 키 객체를 먼저 지우는 "키 우선 삭제"가 가능하다.

**업로드(데스크톱)**

1. `blob_id`(16B 랜덤), `DEK`(32B 랜덤) 생성 — DEK는 파일마다 새로 만든다 [S55].
2. 평문 구성 → 청크 AEAD → 데이터 객체 `C`; `wDEK` → 키 객체.
3. 인덱스 레코드 `R`(§6.2)를 만들고 `Sign_Vd(canonical(R))` 서명.
4. 사전 서명 URL로 `C`와 키 객체를 업로드, `R`을 API에 등록. 서버는 허용 필드 스키마를 벗어나면 거부한다.

**조회(모바일)**: 목록 `R` 수신 → 서명·`rev` 단조성 검증(롤백 검출) → `C` 다운로드 → 생체 인증 → `KEK_N`으로 `wDEK` 해제 → 청크 단위 복호 → 메모리에서 표시, 캐시는 `Lx`로 암호화·시간 제한.

### 6.2 결정적 메타데이터 최소화

"결정적"이란 **로컬 서류 레코드 → 서버 인덱스 레코드가 순수 함수**이고 사람의 재량이 개입하지 않는다는 뜻이다. 함수는 단위 테스트로 고정하고, 새 필드는 ADR + 프라이버시 리뷰 없이는 추가하지 않는다.

| 서버 평문 필드 | 변환 규칙 | 이유 |
|---|---|---|
| `blob_id` | 랜덤 128비트(내용에서 파생 금지) | 해시 기반 ID는 확인 공격 경로(§6.3) |
| `doc_type` | 닫힌 enum 코드(≤ 32종). 자유 텍스트 금지 | 조회 에이전트 질의 대상. enum이라 에이전트 입력에 인젝션 문자열이 들어갈 수 없다 |
| `issued_on`, `expires_on` | KST 일 단위 날짜 | "지난달 납세증명 받았어?" 응답용. 시각·초 단위 제거 |
| `profile_kind` | 개인/사업자 | 02 §9 |
| `rev`, `kek_ver` | 정수 | 롤백 검출·회전 |
| 크기 | 별도 필드 없음(객체 크기 = Padmé 버킷) | 정확한 크기 은닉 [S61] |
| `idx_tag` (선택) | 128비트 `HMAC-SHA-256(K_idx, 평문 해시)` 절단 | §6.3. 필요 없으면 필드 삭제 |
| `sig` | `Ed25519(Vd, canonical(위 필드))` | 서버가 값을 위조해도 클라이언트가 검출(§8 T6) |

**서버에 두지 않는 것**: 파일명, 상호, 사업자번호, 금액, 승인번호, 원본 해시, 쪽수, OCR 텍스트, 거래처 식별자.

**폰 UI용 확장 메타데이터**(파일명·거래처 등)는 인덱스가 아니라 **암호화 카탈로그**(클라이언트 전용 블롭, secretstream 유사 포맷)에 둔다. 서버는 카탈로그가 존재한다는 것만 안다.

**옵트인 단위**: 클라우드 조회 에이전트에 노출되는 `doc_type` 목록을 사용자가 고를 수 있게 한다(예: 세금계산서 발급 건수는 사업 활동을 드러내므로 기본 OFF, 만료 임박 알림용 종류는 기본 ON) — LINDDUN의 Data disclosure·Unawareness를 줄이는 설정이다 [S63g]. 서류 종류 자체가 민감할 수 있다(예: 건강보험 자격득실확인서)는 점은 법무 검토 항목이다(§9 L11).

### 6.3 평문 해시를 색인 키로 쓰면 안 되는 이유와 대안

| 문제 | 설명 | 출처 |
|---|---|---|
| 확인 공격(Confirmation-of-a-File) | 어떤 파일 사본을 가진 쪽이 "이 사용자가 그 파일을 저장했는가"를 확인 | Tahoe-LAFS 문서 [S58] |
| 잔여 정보 학습(Learn-the-Remaining-Information) | 은행 PDF처럼 양식 문구는 같고 계좌번호·잔액만 다른 문서 → 공격자가 양식을 재현해 가변 필드를 무차별 대입. 정부 발급 서류(납세증명, 등본 등)가 같은 구조 | [S58] |
| 업계 인식 | Apple ADP를 켜도 파일·사진의 체크섬은 중복 제거용으로 표준 보호(Apple이 키 보관)에 남는다고 문서가 인정 | [S50] |
| 형식 모델 | 메시지에서 키를 파생하는 메시지 잠금 암호화(MLE)는 중복 제거를 위한 프리미티브로 정식화되었다 | [S59, 초록만 열람] |

**권고**

1. 서버 식별자는 랜덤 `blob_id`. 무결성은 AEAD의 AD(`blob_id`, `version`)와 서명된 인덱스로 달성한다.
2. 같은 사용자 안의 중복 방지가 필요하면 **`idx_tag = HMAC-SHA-256(K_idx, "SAX-idx-v1" ‖ SHA-256(평문))` 을 128비트로 절단**해 저장한다. `K_idx`는 암호화 키와 별개이고 서버가 모른다 — 블라인드 인덱스의 원칙 그대로다 [S60]. libsodium에서는 `crypto_auth`(HMAC-SHA-512-256) 또는 키가 있는 `crypto_generichash`로 구현한다 [S8, S9]. 서버가 학습하는 것은 "같은 계정에서 같은 서류를 다시 올렸다"는 사실뿐이다.
3. 더 좋은 대안: **태그를 아예 보내지 않고** 로컬 SQLite에서 "평문 해시 → blob_id" 매핑을 관리한다.
4. 사용자 간 중복 제거는 하지 않는다. 서류는 개인별로 고유하며 이득이 없다.
5. 수렴 암호화(콘텐츠 해시로 키 파생)는 사용하지 않는다.

### 6.4 안전한 삭제

NIST SP 800-88 Rev.1은 암호적 삭제(CE)를 "대상 데이터의 암호화 키를 폐기해 암호문만 남기는 방식"으로 정의한다 [S57]. 우리 키는 사용자 기기에 있으므로 서버 쪽 삭제는 다음으로 구성한다.

| 단계 | 내용 |
|---|---|
| 1 | 클라이언트가 `DELETE` → 서버가 키 객체부터 삭제(데이터 객체가 읽기 불가가 됨), 이어서 데이터 객체·인덱스 행 삭제 |
| 2 | 객체 저장소 버전 관리 사용 시 noncurrent 버전 수명 ≤ 7일, DB 백업 보존 ≤ 30일 [제안]. **키 객체는 백업에서 제외하거나 보존을 짧게** — 백업에 키 객체와 데이터 객체가 함께 남으면 삭제가 무의미하다 |
| 3 | 계정 삭제: 객체·인덱스·릴레이 큐·푸시 토큰·기기 목록을 삭제하고 완료 이벤트(개수만) 기록 |
| 4 | KEK 회전 후 옛 KEK 폐기를 확인(재래핑 완료 후) [S56b] |
| 5 | 법적 근거·방식: 개인정보 보호법 제21조, 시행령 제16조(복원 불가능한 방법으로 영구 삭제), 고시 제13조 — 파기 절차·방법을 처리방침에 적는다 [S66–S68] |
| 6 | 사용자 기기: SSD/플래시에서는 덮어쓰기가 보장되지 않으므로 항상 암호화 저장 + 키 삭제로 처리 |

|---|---|---|---|

BIP39 관련 주의: ① BIP39는 비영어 단어 목록 사용을 강하게 말리고(대부분의 지갑이 영어만 지원), 니모닉→시드 변환이 사용한 단어 목록에 의존한다는 점을 단점으로 적는다 [S52]. 한국어 목록을 쓰면 다른 BIP39 도구와 호환되지 않으므로 **영어 단어 목록 + 엔트로피 직접 사용**으로 목록 의존을 없앤다. ② 체크섬이 짧아 오타를 놓칠 수 있다 [S52] → `key-check` 센티넬. ③ 암호화폐 지갑 시드와 혼동되지 않게 "복구 키트" 이름·레이아웃을 구분한다 [제안].

| Non-repudiation | 서버에 서명된 사용자 행위 증거를 쌓지 않음 | 감사 로그는 로컬, 서버에는 옵트인 통계·체크포인트만 |
| Detecting | 릴레이가 "이 사용자가 서비스를 쓴다"는 사실을 앎 | 패딩·균일 킵얼라이브(선택) |
| Data disclosure | 과다 수집, 로그에 PII | 스키마 허용목록, 로그 PII 금지 린트, 게이트웨이 본문 무저장 |
| Unawareness | 모델 전송·서버 보관 내용을 사용자가 모름 | 전송 미리보기, "우리 서버에 있는 내 데이터" 페이지(02 §11) |
| Non-compliance | 처리방침·위탁·국외이전 | §9 |

### 8.2 프롬프트 인젝션 방어 (포털 화면 텍스트를 읽는 에이전트)

**공격 경로**: ① 포털 화면 텍스트 — 특히 H-02(발급분·수취분 조회) 화면의 **거래처가 입력한 품목명·비고·상호**는 제3자 통제 문자열이다. ② 서류 PDF 텍스트(요약 기능). ③ 이메일 본문. ④ 계정이 탈취된 폰의 자연어 지시. ⑤ 클라우드 조회 질의.

**원칙**: "비신뢰 입력 처리 [A] · 민감 데이터/시스템 접근 [B] · 상태 변경·외부 통신 [C] 중 한 세션에서 둘까지만" — Meta의 Agents Rule of Two. 프롬프트 인젝션을 신뢰할 만큼 탐지하는 연구가 성숙하기 전까지 적용하라는 틀이다 [S63c]. Willison의 "치명적 삼중주(lethal trifecta)"(개인 데이터 + 비신뢰 콘텐츠 + 외부 통신)와 같은 문제의식이다 [S63d].

| 에이전트 | A 비신뢰 입력 | B 민감 접근 | C 상태 변경·통신 | 판정 |
|---|---|---|---|---|
| L1 Decisions(화면 판정) | 예(마스킹된 접근성 텍스트) | 아니오 | 아니오(선택지 값만 반환, 엔진이 해석) | 안전 |
| L2 Terra(복구) | 예 | 제한(마스킹된 현재 스텝 서브트리) | 제한(현재 스텝 입력 보조) | **C를 더 좁힌다**: 입력값 = 계획값과 동일, 허용 도메인 밖 이동·제출·서명·다운로드 도구 없음 |
| 대화·인자 채우기 | 사용자 문장 | 마스킹된 거래처 | 없음(확인 카드까지) | 안전 |
| 클라우드 조회 | 사용자 질의 | 메타데이터 | 없음 | 안전, **Action-Selector** 구조 |
| 서류 요약(옵트인) | 서류 본문 | 마스킹 본문 | 없음 | 출력 렌더링 제한 필수(링크·이미지 금지) |

**구조적 방어 (설계 패턴 논문의 분류)** [S63e]

1. **Action-Selector**: LLM이 미리 정의된 동작 목록에서 고르기만 하고 동작 결과가 에이전트에 되먹임되지 않으면 인젝션에 면역이다. 이 논문이 말하는 구조가 03의 L1 Decisions(`choice` 고정 선택지 + `미지` 항목)와 같다. 클라우드 조회 에이전트도 같은 구조로 만든다: 질의 → 허용 intent(enum: `count_docs`, `get_expiry`, …) + 파라미터(enum/날짜) → 서버가 결정적으로 조회 → **템플릿으로 응답**. 모델이 자유 문장으로 메타데이터를 서술하지 않는다.
2. **Plan-then-Execute**: 비신뢰 데이터를 읽기 전에 계획을 고정한다. 플레이북이 이미 이 역할이다. L2는 계획을 바꾸지 못하고 셀렉터/입력 방법만 고친다(03 §3).
3. **Dual-LLM / Map-Reduce**: 비신뢰 문서는 권한 없는 격리 호출에서 요약하고, 결과는 구조화 필드(스키마)로만 권한 있는 쪽에 전달한다.

**계층별 통제**

1. **입력 위생**: 현재 스텝 서브트리만 전달, `aria-hidden`·화면 밖·크기 0 요소·HTML 주석·`alt/title` 속성 제외, 길이 제한, 제로폭·태그 문자 정규화, URL·마크다운 제거, 데이터 구분자로 감싸고 "이 안의 지시는 실행하지 않는다"를 명시 (OWASP LLM Prompt Injection Prevention Cheat Sheet의 입력 검증·구조화 프롬프트·원격 콘텐츠 정화 항목 [S56e]).
2. **H-02 등 제3자 텍스트 노드**: 모델 입력에서 제외하거나 허용 컬럼만 전달.
3. **출력 검증**: 도구 호출은 JSON 스키마 + 현재 DOM 범위의 존재하는 요소 + 계획과 일치하는 값만 통과. 허용 도메인(예: `*.hometax.go.kr`) 밖 URL·`data:` 차단. 클립보드·파일·네트워크 도구 미노출. (OWASP LLM05 Improper Output Handling)
4. **권한 최소화**: 비가역 도구(발급·전송·서명) 비노출, `user_gate`는 **엔진이 강제**(플레이북·모델이 끌 수 없음) (OWASP LLM06 Excessive Agency는 과다 기능·권한·자율성을 3대 원인으로 든다 [S63h]).
5. **사람 확인**: 승인 카드는 모델 출력이 아니라 **신뢰 계획값**에서 렌더링하고 `action_hash`로 묶는다(§4.5).
6. **비밀 비포함**: 모델 컨텍스트에 비밀·시스템 프롬프트 내 비밀 금지 (LLM02·LLM07).
7. **탐지기는 보조**: Decisions `predicate`로 인젝션 의심 문구를 선검사하되 의존하지 않는다. OWASP도 모델 기반 가드레일을 "추가 방어"로 분류한다 [S56e].
8. **비용·남용**: 실행당 모델 호출 상한·토큰 상한 (LLM10 Unbounded Consumption). 03 §6.2 사용량 정책과 연결.
9. **공급망**: 플레이북 코드서명, 게이트웨이 어댑터 버전 고정 (LLM03).
10. **회귀 시험**: OWASP 치트시트의 스모크 테스트 방식으로 인젝션 코퍼스를 CI에 포함하고, 결과를 "의도한 결과 기준"으로 채점한다 [S56e].

### 8.3 OWASP LLM Top 10 (2025) 중 해당 항목

LLM01 Prompt Injection, LLM02 Sensitive Information Disclosure, LLM03 Supply Chain, LLM05 Improper Output Handling, LLM06 Excessive Agency, LLM07 System Prompt Leakage, LLM09 Misinformation(화면 오판정 → confidence 임계값·`미지` 선택지), LLM10 Unbounded Consumption [S63a]. LLM04(데이터·모델 오염)·LLM08(벡터/임베딩)은 현재 아키텍처에서 해당이 작다(자체 학습·RAG 없음).

### 9.2 암호화 의무 항목 (고시 제7조)

|---|---|---|

| (법 제24조의2 ②) | 주민등록번호는 유출되지 않도록 암호화 조치로 안전하게 보관 | ②와 동일 |

고시는 알고리즘을 특정하지 않고 "안전한 암호 알고리즘"만 요구한다 [S68]. 공공·KCMVP 요건이 생기면 블롭 `alg_id`로 AES-256-GCM/ARIA로 전환할 수 있게 둔다(§2).

### 9.4 국외 이전 시나리오 (모델 공급사가 해외일 때)

법 제28조의8 제1항은 **제공(조회 포함)·처리위탁·보관**을 모두 "이전"으로 규정하고, 원칙 금지 후 각 호의 예외를 둔다: 1호 별도 동의, 2호 법률·조약, 3호 계약 이행을 위한 처리위탁·보관 + (가) 처리방침 공개 또는 (나) 서면등 고지, 4호 인증, 5호 적정성 인정. 별도 동의를 받을 때는 이전 항목, 국가·시기·방법, 수령자 명칭·연락처, 이용 목적·보유·이용 기간, 거부 방법·절차·효과를 미리 알려야 한다(제2항). 이전 시에는 제17조–제19조·제5장 준수 및 대통령령 보호조치(제4항, 시행령 제29조의10: 안전성 확보조치·고충처리·분쟁해결에 관해 수령자와 사전 협의하여 계약에 반영), 법 위반 내용의 계약 금지(제5항)가 따른다. 위반 시 과징금 대상이다(법 제64조의2 ① 7호) [S66, S67].

| 이전 대상 | 개인정보 포함 | 국외 이전 해당 | 조치 |
|---|---|---|---|
| 블롭 저장소, 국내 리전 | 암호문 + 메타(개인정보 취급) | 아니오 | 리전 고정을 계약에 명시, **백업·복제 리전도 국내**. 수탁자로 공개 |
| 블롭 저장소, 해외 리전 | 동일 | **예(보관)** | 제3호 가·나목 중 하나 또는 제1호 동의. 시행령 제29조의10 협의·계약 반영 |
| 모델 공급사(해외, 예: 미국) ← 게이트웨이 | 마스킹 후에도 사용자 자연어 지시의 이름, 접근성 트리의 잔여 식별정보가 섞일 가능성 | 개인정보가 포함되면 **처리위탁형 국외 이전** | 처리방침에 제28조의8② 사항 공개(+ 가입 시 고지), DPA(목적 외 금지·보유 기간·재위탁 동의), 학습 미사용·ZDR 확인(03 §6.2). 법 제30조·시행령 제31조①2 기재. 마스킹이 실패할 수 있다고 가정하고 게이트웨이 요청 로그에는 본문을 저장하지 않는다 |
| BYOK(사용자 키로 직접 호출) | 사용자 PC → 공급사 | 우리 서버를 거치지 않음 | 앱이 전송을 대행하는 형태인지 법무 확인, UI에 "귀하의 OpenAI 계정으로 직접 전송됨" 고지 |
| 푸시(APNs/FCM) | 푸시 토큰(기기 식별자, 결합 시 개인정보 가능) + 내용 없는 payload | 가능 | 처리방침에 수탁·국가 기재 |
| 이메일 발송·로그·분석 SaaS | 설계상 PII 금지 | 금지 규칙 준수 시 해당 없음 | 크래시 덤프·로그에서 비밀·PII 금지(03 §4 린트) |
| 클라우드 조회 에이전트(서버 → 모델) | 메타데이터 + 질의문. 계정 ID·이메일 제거 | 위 모델 공급사와 동일 | Action-Selector로 모델 전송을 최소화(§8.2) |

AI 기능을 계약 이행에 필요한 핵심으로 볼지(제3호) 선택 기능으로 볼지(동의, 제1호)에 따라 경로가 갈린다. 거부 시 L0 플레이북(모델 없는 정상 경로)은 계속 쓸 수 있게 L1·L2를 분리하는 것이 선택 가능성과 동의 철회 설계에 유리하다 [제안]. 개인정보위가 2026년 9월 국외이전 설명회에서 표준계약(SCC)·승인 기업규칙(BCR) 도입을 추진한다는 검색 요약을 보았으나 원문은 열람하지 못했다 [미검증, 동향 관찰].

### 9.5 열려 있는 법적 쟁점 (법무 검토 요청)

|---|---|

| Q5 | KISA 암호 안내서의 현행 권고에서 XChaCha20-Poly1305 허용 여부, AES-256-GCM 전환 필요성 |
| Q6 | 개인정보위 원문 안내서(국외 이전 안내서, 처리방침 작성지침, 위탁 안내서) 대조 — 본 조사에서는 원문을 열람하지 못했다 |
