## A. 금고·비밀 타이피스트

### A-1 [치명] ADR-005 갱신본의 `--remote-debugging-port=0`은 세 대안 중 가장 위험하다. 엔진이 넘기는 `cdpEndpoint`는 그대로 유출 경로다
- **위치**: ADR-005 결정(11:01 갱신), D03 Chrome 기동(`--remote-debugging-port=0`, `--remote-allow-origins=http://127.0.0.1`), D05 §3 `typist.fill(req:{cdpEndpoint: string, …})`, D11 T2.
- **내용**
  1. DevTools 포트는 OS 사용자 인증이 없다. 127.0.0.1에 바인딩돼도 **같은 PC의 다른 Windows 계정**(빠른 사용자 전환, 사무실 공용 PC의 직원 계정, RDS)이 접속해 로그인된 홈택스 세션을 그대로 조종하고 쿠키를 뽑을 수 있다. ADR의 근거("어차피 키체인도 같은 사용자에게 열려 있다")는 사용자 간 경계에는 해당하지 않는다.
  2. 같은 사용자 범위에서도 상황이 나빠진다. Chrome은 App-Bound Encryption으로 같은 사용자 인포스틸러의 쿠키 탈취를 막았다. 이후 인포스틸러는 원격 디버깅으로 우회했고, Chrome 136이 기본 프로필에서 디버깅 스위치를 막은 이유가 이것이다. 우리는 가장 민감한 세션(홈택스·정부24)에 그 경로를 실행 내내 열어 둔다. 포트 번호는 user-data-dir의 `DevToolsActivePort` 파일에 적혀 있고, 그 파일이 없어도 로컬 포트 스캔으로 찾을 수 있다.
  3. `--remote-allow-origins`는 브라우저 페이지가 보내는 Origin 헤더만 거른다. Origin을 보내지 않는 네이티브 클라이언트에는 아무 제한이 없다.
  4. `cdpEndpoint`를 **엔진이** 넘긴다. 침해된 엔진은 자기가 띄운 가짜 CDP 서버(localhost WS)를 가리키고, `type=password` 검사에 맞춘 응답을 꾸며 키 이벤트로 비밀을 그대로 받아 간다. 금고의 "아웃바운드 금지"는 localhost WebSocket을 막지 않는다.
  5. 기각된 (b) "엔진 중계"의 추가 위험은 이미 존재하는 A-2(엔진은 DOM에서 값을 되읽을 수 있음) 위에 파이프 버퍼 노출이 조금 더해지는 정도다. (a) 포트 개방은 실행하는 동안 모든 로컬 프로세스와 다른 사용자에게 브라우저 전권을 준다. 위험만 보면 (b)가 (a)보다 엄격히 낫다.
- **수정**
  - (권장) **(c) 금고가 Chrome을 파이프로 띄우는 단독 소유자**가 된다. 엔진에는 금고가 중계하는 CDP를 준다. 전송은 MessagePort를 쓰거나, 쓸 수 없으면 256비트 경로 토큰을 요구하는 로컬 WS 프록시로 하되 `/json` 디스커버리를 두지 않는다. 프록시 코드는 메시지 전달 + 소수의 차단 규칙이라 작다. 금고는 타이핑 구간에 엔진의 `Input.*`·`DOM.focus`·탭 전환·`Emulation.*` 명령을 보류하고 `Input.setIgnoreInputEvents(true)`로 사용자 입력을 잠깐 막는다. 이 구조는 A-6의 포커스 경쟁도 함께 푼다.
  - (차선) (b)를 택하고 "평문이 엔진 파이프를 지난다"를 정직하게 적는다.
  - 공통: `--remote-debugging-port` 사용 금지를 정책 상수로 둔다. `cdpEndpoint` 인자는 삭제한다. 매 기동 시 `about:blank`에서 `navigator.webdriver===true`를 확인해 거짓이면 자동화를 거부한다(ADR-010을 연결 방식 변경이 깨지 않게 하는 자기 점검). S6에 "다른 OS 사용자 계정에서 CDP 접속 불가"와 "엔진이 지정한 엔드포인트로 금고가 접속하지 않음"을 넣는다.

### A-2 [높음] 엔진이 침해되면 비밀은 여전히 탈취된다. T2·D08 §11의 통제 문구는 과장이다
- **위치**: D11 §2 T2 "비밀은 금고만, 타이피스트", D08 §11 "엔진 침해로 비밀 탈취 → 금고 키 이중 봉인", D00 "금고: 비밀을 평문으로 다루는 유일한 프로세스", D01 §3 "TB-1: 비밀 평문 유일".
- **내용**: 엔진은 같은 페이지의 CDP 전권을 가진다. 금고가 입력을 끝내면 엔진은 `Runtime.evaluate`나 `inputValue()`로 `.value`를 되읽을 수 있다. 미리 `Page.addScriptToEvaluateOnNewDocument`로 keydown 리스너를 심어 둘 수도 있고, 자기가 만든 `<input type=password>`를 금고에 대상으로 넘길 수도 있다(게이트 조건을 충족한다). `fillFromRemote(sessionId, stepId, element)`의 대상 요소도 엔진이 고르므로 폰에서 온 비밀도 같은 경로로 샌다(C-2). 엔진은 포털 화면, PDF, OCR, 모델 응답처럼 비신뢰 입력을 가장 많이 처리하는 프로세스다(G-4).
- **수정**: T2 통제를 다음처럼 고친다. "평문이 엔진의 힙·로그·덤프·모델 페이로드에 남지 않게 하는 **위생 장치**다. 엔진 RCE와 같은 사용자 악성코드에는 경계가 아니다. 엔진이 침해되면 그 실행 중에 입력된 비밀이 노출된다." D00·D01·D08·README에도 같은 문구를 쓴다. 실제 위험은 엔진 공격면 축소(G-4)와 A-1 권장안의 타이핑 구간 명령 보류로 줄인다.

### A-3 [높음] 보안카드 번호표를 "DB 키로 암호화해 DB에" 두면 엔진이 복호화한다
- **위치**: D05 §7 "큰 값(보안카드 전체 표)은 DB 키로 암호화해 DB에 두고 키체인에는 키만", "앱 수준 추가 키 래핑(DB 키로 2차 암호화)". 관련: D05 §3 `getDbKeyOnce()`(엔진에 DB 키 전달), D01 §2.1(엔진의 DB 읽기·쓰기).
- **내용**: 엔진은 DB 키와 DB 파일을 모두 가진다. 따라서 가장 강한 2차 인증 수단인 보안카드 전체 표를 엔진이 풀 수 있고, TB-1→TB-2 금지 규칙이 저장 계층에서 깨진다. 보안카드 표는 수백 바이트라 Credential Manager의 2,560B 상한에 걸리지 않으므로 이 우회의 전제(크기 제한)도 성립하지 않는다. "DB 키로 2차 래핑"은 DB 키가 같은 키체인에 있으므로 엔진에도, 같은 사용자 악성코드에도 효과가 없다.
- **수정**: 보안카드는 칸 단위로 키체인 항목에 저장한다. 큰 값이 정말 생기면 금고 전용 키 `K_vault`로 봉투 암호화해 **금고만 여는 파일**에 둔다. 이 키는 키체인에 두고 엔진에 넘기지 않는다. "DB 키 2차 래핑" 문구는 삭제한다. 보안카드 저장은 대화형 등급(Hello 키 결박)에서만 허용한다.

### A-4 [높음] TB-1 밖에도 평문 비밀이 머무는 경로가 있는데 문서에 없다
- **위치**: D05 §1·§2·§3·§8, ADR-005 대안, D09 §2, D04 §8, D03 Actuator.
- **내용**
  1. `store()`는 main이 UI를 거쳐 호출한다. 사용자가 입력한 비밀이 renderer DOM, JS 문자열, IPC 직렬화, main 힙을 지난다. 타입드 IPC 검증이 실패하면 그 메시지가 로그로 갈 수도 있다.
  2. BYOK 키는 "금고 → `net/egress` 헤더 주입(엔진 미경유)"으로 적혀 있지만, `net/egress`는 engine 프로세스 안의 모듈이다(D01 §2.1·§7). 계정 bearer 토큰도 게이트웨이를 호출할 때마다 엔진 안에 있다.
  3. `@napi-rs/keyring`은 문자열 API 중심이다(R3 §2.1: 바이너리 API 미확인). 금고에서 꺼내는 순간 지울 수 없는 JS 문자열이 생기므로, D05 §8의 "Uint8Array로만, 문자열 금지"는 이 라이브러리로는 1일차부터 지킬 수 없다. CDP JSON 메시지(`{"text":"a"}`)도 글자마다 힙 문자열을 남긴다.
  4. D03 Actuator는 "금고 타이피스트의 타이밍 허가"를 엔진이 집행한다고 쓴다. 키마다 허가를 받으면 엔진은 비밀의 **길이**를 알게 된다. D05 §4-4("길이·타이밍을 받지 않는다")와 모순이다.
  5. ADR-005 대안의 "엔진에 짧게 평문 전달 — 폴백으로만"은 D01 §3("예외는 human 스텝뿐")과 모순이다. 모듈이 CDP 입력을 거부하는 칸이면 엔진의 CDP 입력도 똑같이 막히므로 폴백으로서 쓸모도 없다.
  6. `ignoreDefaultArgs: true`로 Playwright 기본 인자가 모두 빠지므로, 전용 프로필에서 **비밀번호 저장 말풍선과 자동완성**이 일반 Chrome처럼 뜬다. 사용자가 "저장"을 누르면 포털 비밀번호와 인증서 비밀번호 대화상자의 값이 Chrome `Login Data`로 가고, 프로필에 Google 로그인이 되어 있으면 동기화까지 된다.
- **수정**
  - D05 §1의 목표를 "평문이 **우리 코드 안에서** 머무는 곳을 금고로 최소화"로 바꾸고, 위 경로를 표로 명시한다.
  - store 입력은 renderer에서 금고로 직접 가는 MessagePort로 보낸다(main 라우터를 거치지 않고, 로깅하지 않음). 입력 즉시 `TextEncoder`로 Uint8Array를 만들고 입력란을 비운다. 검증 실패 시에는 스키마 경로만 기록한다.
  - BYOK 키와 계정 토큰은 "엔진 메모리에 존재"로 정정하거나, egress를 별도 프로세스로 뺀다.
  - 키체인 바이트 API는 Phase 1부터 Rust N-API 헬퍼로 확보한다. 그렇게 하지 않으면 한계를 문서에 적는다.
  - 타이밍 허가는 금고가 실행 시작 때 받은 정책으로 스스로 집행한다.
  - ADR-005의 엔진 평문 폴백은 삭제한다.
  - 기동 전에 전용 프로필 `Preferences`에 `credentials_enable_service=false`, `profile.password_manager_enabled=false`, `autofill.profile_enabled=false`, `autofill.credit_card_enabled=false`를 기록한다. 포털이 볼 수 있는 값을 바꾸지 않는 사용자 측 설정이므로 위조·은폐가 아니다.

### A-5 [중간] `type=password`·`secretSlot` 게이트에 남은 우회 경로
- **위치**: D05 §4 제약 3, D02 §2.1 `secretSlot`, D03 "타이피스트는 키 입력마다 `activeElement`와 `type` 재확인"(일부 반영됨).
- **내용**
  1. 보안카드 칸은 보통 `type=text|tel`이라 `secretSlot` 플래그 하나가 근거다. 이 플래그는 서명자가 정하므로, 서명키가 유출되거나 패키지가 악성이면 공격자가 정한다.
  2. 금고가 셀렉터 사전의 서명을 스스로 검증하는지, 엔진이 "secretSlot:true"라고 넘기면 그대로 믿는지가 정해져 있지 않다.
  3. 로케이터가 여러 요소, 다른 프레임, 열린 shadow root 안의 요소를 가리킬 수 있다.
  4. 대상 프레임의 origin을 검사하지 않는다(G-3).
  5. "보기" 토글로 `type`이 바뀌는 경우를 막는 규칙이 키 입력 중 재확인뿐이고, 입력이 끝난 뒤의 변화는 다루지 않는다.
- **수정**: 금고가 직접 다음을 확인한다.
  - (a) 서명된 `selectors.json`을 자기가 가진 공개키로 검증한 뒤 stable_id로 `secretSlot`을 조회한다.
  - (b) 로케이터가 **정확히 1개** 요소에만 일치한다.
  - (c) 그 요소가 `<input>`이고 `type=password`다. secretSlot으로만 허용된 칸은 `type∈{text,tel}`, `maxlength≤4`, `autocomplete≠on`(보안카드 프로파일)이어야 한다.
  - (d) 프레임 origin이 **금고에 내장된 비밀 종류별 허용 목록**에 있다.
  - (e) 매 키 입력 전, iframe과 shadow DOM까지 따라간 `activeElement`의 backendNodeId가 같다. 다르면 즉시 중단하고 그 칸을 비운 뒤 `secret.aborted`를 감사 로그에 남긴다.
  - 입력 후 type이 바뀐 노드는 실행이 끝날 때까지 스냅샷·스크린샷에서 뺀다.

### A-6 [중간] 포커스 경쟁 방지가 "엔진은 입력 중지"라는 협조 약속뿐이다
- **위치**: ADR-005 결과.
- **내용**: 경쟁 주체는 엔진만이 아니다. 헤드풀 창을 클릭하는 사용자, 포털 스크립트의 자동 포커스 이동(보안카드 2자리를 넣으면 다음 칸으로 넘어가는 동작이 흔하다), 갑자기 뜨는 모달도 있다. 12자를 90~260ms 간격으로 치면 2~3초가 걸리는데, 그 사이 포커스가 바뀌면 남은 글자가 검색창이나 아이디 칸 같은 **평문 입력란**에 들어가 화면에 보이고 서버로 전송될 수 있다.
- **수정**: A-5(e)의 키별 확인, `Input.setIgnoreInputEvents(true)`(타이핑 구간에만, 끝나면 해제), 금고에 의한 엔진 명령 보류(A-1 권장안). 보안카드는 칸마다 별도 `secret_fill`로 나눈다.

### A-7 [중간] 크래시 덤프 차단 방법이 없고, 누출 스캐너는 글자 단위 누출을 못 본다
- **위치**: D05 §8, D11 §4·§5, D13 §6.
- **내용**
  1. "금고 크래시 덤프 비활성화"를 어떻게 하는지가 없다. Electron crashpad는 앱 단위로 utility 자식 프로세스에도 붙는다. Windows WER 제외는 실행 파일 이름 기준이라, main과 같은 exe인 금고만 따로 뺄 수 없다.
  2. 스캐너는 평문이 통째로 일치하는지만 찾는다. 타이피스트는 글자 단위 메시지를 보내므로 로그에 비밀이 **한 줄에 한 글자씩** 흩어진다. Chrome 쪽은 UTF-16이고, base64·hex·JSON 이스케이프·URL 인코딩 형태도 있다.
  3. 금고의 CDP 클라이언트에서 디버그 로깅(`DEBUG=pw:protocol` 같은 것)이 켜지면 모든 입력이 기록된다.
- **수정**: 금고는 Electron 밖의 별도 실행 파일(Rust, Bitwarden 방식)로 두거나, 적어도 자체 예외 처리로 덤프를 막고 S6에서 실측한다. 스캐너에 인코딩 변형, 연속 key 이벤트 재조립, UTF-16LE 검색을 넣는다. 금고 CDP 클라이언트의 로깅 경로는 빌드에서 제거하고, 금고 프로세스 환경 변수에서 `DEBUG`·`NODE_OPTIONS`를 지운다.

### A-8 [중간] "하네스는 개인키 파일을 열지 않는다"와 S1b의 충돌, 인증서 파일과 비밀번호의 동거
- **위치**: D05 §2·§6, D13 S1b(`setInputFiles`로 브라우저 인증서 가져오기), 02-product-spec(인증서 비밀번호 저장 여부 질문), R3 §2.6.
- **내용**: S1b는 하네스가 `signCert.der`·`signPri.key`를 전용 프로필의 사이트 저장소로 옮기는 경로를 시험한다. 이 경로를 쓰면 암호화된 개인키(PBKDF1/SEED)의 **새 사본**이 전용 프로필에 생긴다. NPKI 폴더를 노리는 국내 인포스틸러는 흔하며, 같은 사용자 계정에 "개인키 파일 + 키체인에 저장된 비밀번호"가 함께 있으면 인증서가 통째로 넘어간다. 데몬 `auto`가 보류(D10 갱신)되어 압력은 줄었지만, 저장 옵트인은 남아 있다.
- **수정**: S1b 경로를 채택하면 문구를 "사용자의 지시로 인증서 파일을 브라우저 저장소에 넣는다(내용은 읽지 않음)"로 고치고, 사본의 위치와 삭제 절차를 적는다. 인증서 비밀번호 저장은 대화형 등급에서만 허용한다. 저장 화면에 "인증서 파일과 비밀번호가 같은 PC에 함께 있으면 악성코드 한 번에 인증서 전체가 넘어갑니다"를 그대로 쓴다.

### A-9 [낮음] 모바일 쪽 비밀 입력 위생이 정의되지 않았다
- **위치**: D08 §6 `human.response.sealedForVault`, D01 §2.2.
- **내용**: RN 입력창의 키보드 학습(서드파티 키보드, 제조사 키보드의 예측), 스크린샷·화면 녹화, 클립보드, 지울 수 없는 JS 문자열. 숫자 키패드를 쓰는 보안카드 칸은 `secureTextEntry` 없이 구현되기 쉽다. 잠금화면 알림에 문서명과 금액이 보일 수 있다.
- **수정**: 비밀 입력 화면과 문서 뷰어에 Android `FLAG_SECURE`와 iOS 캡처 감지를 적용한다. 숫자 칸을 포함해 `secureTextEntry`, `autoCorrect=false`, `importantForAutofill="no"`를 건다. 입력 즉시 바이트로 바꿔 봉인한다. 잠금화면 알림은 일반 문구로 한다(iOS `hiddenPreviewsBodyPlaceholder`, Android `VISIBILITY_PRIVATE`). 생체 인증 없이 알림 액션 버튼으로 승인하는 경로는 두지 않는다.

## B. 마스킹

### B-1 [높음] 주민번호를 체크디지트로 "확실히 아님" 판정하면 2020.10 이후 번호가 그대로 나간다
- **위치**: D06 §4 표(주민·외국인등록번호 검증 = 체크디지트), §4 마지막 줄("확실히 아닌 것만 제외"), §7(유효 체크섬 생성기 코퍼스).
- **내용**: 2020.10 주민등록번호 개편 이후 새로 부여되는 번호(출생, 번호 변경자)는 성별 자리 뒤 6자리가 임의번호라 기존 검증번호 규칙을 따르지 않는다(구현 전 행안부 고시로 재확인할 것). 체크섬 실패를 "확실히 아님"으로 처리하면 등본·자격득실의 아동 세대원과 번호 변경자의 주민번호가 마스킹되지 않는다. 합성 코퍼스는 유효 체크섬만 만들기 때문에 이 결함이 수용 기준(재현율 99.9%)을 통과한다.
- **수정**: 주민·외국인등록번호는 `YYMMDD` 날짜 유효성과 성별 자리(1~8, 9·0을 포함할지 결정)만으로 판정한다. 체크디지트는 **신뢰도 가중치**로만 쓰고 배제 근거로 쓰지 않는다. 코퍼스에 체크섬이 무효인 번호와 부분 마스킹형(`900101-1******`)을 넣는다.

### B-2 [높음] 정규화 없이 돌리는 정규식은 한국 화면과 PDF에서 쉽게 빗나간다
- **위치**: D06 §2·§4, D07 §8(pdfjs가 공백을 U+0001로 내는 사례).
- **내용**: 전각 숫자와 하이픈(`０１０－`), 대시 변형(U+2010~2015, U+2212, U+FF0D), 제로폭 문자(U+200B~D, U+FEFF), soft hyphen(U+00AD), 특수 공백(U+0001, U+3000, NBSP), 숫자 사이의 공백이나 마침표.
- **수정**: 탐지 앞에 정규화 단계를 둔다. NFKC → 제로폭·soft hyphen 제거 → 대시 통일 → 공백 통일. 원문 위치 매핑을 유지해 치환은 원문에 적용한다. 코퍼스에 변형 생성기를 추가한다.

### B-3 [높음] 스냅샷의 값 제거는 열거된 칸에만 적용되고, 해석에 실패하면 열린 채로 지나간다
- **위치**: D06 §4("type=password 값은 스냅샷에서 제외"), D03 스냅샷 필터("type=password 또는 secretSlot 또는 최근 타이피스트 대상 요소", 일부 반영됨), D06 §3("DOM 보조: 라벨·placeholder"), D06 §5.
- **내용**
  1. 사용자가 `human:secret`으로 `text/tel` 칸에 직접 넣은 보안카드 숫자는 "최근 타이피스트 대상"이 아니다. 사전에 `secretSlot`이 빠져 있으면 다음 `decide` 스냅샷에 그대로 실린다. 2~4자리 숫자는 엔티티로 탐지되지도 않는다.
  2. secretSlot의 stable_id→노드 해석이 실패하면 제거도 함께 실패한다(fail-open).
  3. "DOM 보조"가 `value` 속성까지 끌어올 수 있다.
  4. L2 이미지 경로가 가상키패드나 `human:secret` 입력 중에 스크린샷을 찍으면, 눌린 키의 강조나 평문 표시가 들어갈 수 있다.
- **수정**: **기본 거부**로 바꾼다. 스냅샷에서 모든 입력 요소의 값을 제거하고, `fieldKey`가 있으면서 비민감으로 표시된 readback 필드만 값을 넣는다. 비밀 입력 대상이었던 노드는 실행이 끝날 때까지 값과 자식 텍스트를 뺀다. secretSlot 해석에 실패하면 스냅샷을 중단한다(fail-closed). `human:secret`이나 `secret_fill`이 진행 중인 탭은 스냅샷과 스크린샷을 금지한다.

### B-4 [중간] 브랜드 타입은 컴파일 단계의 장치일 뿐이다
- **위치**: D06 §8, D04 §1, D01 §3, D03 L2 "후보 형태만" vs D12 §3-4 "후보 자동 집계".
- **내용**: `as RedactedText`, `as unknown as`, `any`(JSON.parse 결과나 SDK 응답 타입) 한 번이면 우회된다. `function_call_output`(로컬 도구 `get_a11y_subtree`·`find_candidates`가 돌려주는 페이지 텍스트)과 `replay[]`가 브랜드를 거치는지 규정이 없다. 역치환한 모델 출력(셀렉터 제안 안의 `[NAME_1]`이 실명으로 돌아온 것)이 텔레메트리, 핫픽스 후보, 다음 요청으로 다시 흘러갈 수 있다. D12 §3-4는 셀렉터 문자열을 서버로 올리는 것처럼 읽히고, D03은 "형태만" 올린다고 해 서로 맞지 않는다.
- **수정**
  - redaction 패키지 밖에서 브랜드 타입으로 단언하는 것을 막는 커스텀 lint 규칙과 `no-unsafe-*`.
  - `egress.toModel()` 직전 **런타임 트립와이어**: 같은 탐지기를 한 번 더 돌려 체크섬이 맞는 사업자번호, 주민번호 형태, 카드번호가 남아 있으면 송신을 막고 카운트만 텔레메트리로 보낸다.
  - 도구 결과는 `RedactedText`일 때만 `function_call_output`이 될 수 있게 타입을 정의한다.
  - 역치환 결과는 UI 전용 타입으로 분리해 업로드를 금지한다. 셀렉터 수리 텔레메트리는 `proposedKind`만 보내는 것으로 확정한다(D12 정정).

### B-5 [중간] 오류 메시지, URL, 파일 경로는 마스킹을 거치지 않는다
- **위치**: D06 전반, D03 텔레메트리 `code`, D11 §4 크래시 리포트, D12 §5 진단 내보내기, D07 `runs.checkpoint`.
- **내용**: Playwright 오류 메시지는 셀렉터와 일치한 요소의 텍스트 미리보기를 담는다(엄격 모드 위반 시 요소 목록까지). Node의 `ENOENT` 같은 오류는 `C:\Users\홍길동\…\민원\등본\홍길동_….pdf` 같은 경로를 담는다. Windows 사용자 폴더 이름이 실명인 경우가 흔하다. 홈택스 URL 쿼리에는 내부 식별자가 실릴 수 있다. L2 복구 프롬프트에 실패 원인으로 오류 문자열을 넣으면 그대로 모델로 간다.
- **수정**: 엔진의 모든 예외를 경계에서 `{code, stableId, stepId}`로 바꾼다. 원문 메시지는 로컬 디버그 로그(DB 키로 암호화)에만 둔다. URL은 저장·전송할 때 항상 origin+path로 자르고 쿼리와 프래그먼트를 버린다. 크래시 리포트와 진단 내보내기에는 경로 정규화(`%USERPROFILE%` 치환)와 탐지기를 적용한다.

### B-6 [중간] 빠졌거나 약한 한국 식별자 패턴
- **위치**: D06 §4 표. 아래 정규식은 초안이며, 앞뒤 숫자 경계 `(?<!\d)…(?!\d)`를 모두에 적용한다.
- 운전면허번호(없음): `\d{2}-?\d{2}-?\d{6}-?\d{2}`. 구형 지역명 접두(`서울 12-345678-90`)도 포함한다.
- 여권번호(없음): 구형 `[MSRODG]\d{8}`, 차세대(2021.12~) `[MSRODG]\d{3}[A-Z]\d{4}`.
- 건강보험증번호(없음): 11자리 숫자 + 문맥어("건강보험증", "증번호").
- 사업장관리번호(없음): `\d{3}-?\d{2}-?\d{5}-?\d`. 경계 처리가 없으면 사업자번호 패턴이 앞 10자리만 먹고 끝자리를 남긴다.
- 외국인등록번호: B-1 원칙을 따른다(체크디지트 배제 금지). 성별 자리 5~8.
- 계좌번호(구분자 없음): 현재 "은행별 길이 패턴"은 모호하다. 문맥어(계좌·입금·예금주·은행명 사전) 근처의 10~14자리 연속 숫자, 주요 은행 하이픈 형식, 가상계좌 14자리로 구체화한다.
- 카드 마스킹형(현재 Luhn 전용): `\d{4}[- ]?\d{2}[\d*xX]{2}[- ]?[\d*xX]{4}[- ]?\d{4}`. BIN 6자리와 끝 4자리가 노출되는 형태도 치환한다.
- 법인등록번호: 주민번호 패턴과 겹친다. 13자리 숫자는 7번째 자리와 관계없이 무조건 치환한다.
- 전화번호(현재 "국내 형식"): `(\+?82[- ]?)?0?1[016789][- .]?\d{3,4}[- .]?\d{4}`, 지역번호, `070`·`050x` 안심번호, 괄호형 `(010)`.
- 이메일(현재 ASCII 간이): 한글 로컬파트, 한글 도메인(`.한국`), `xn--` 퓨니코드, `[at]`·`(골뱅이)` 변형.
- 주소: 도로명 사전(행안부 도로명주소 DB), `\d+동\s?\d+호`, `지하`, 5자리 우편번호, 시도가 빠진 부분 주소.
- 차량번호(없음): `\d{2,3}[가-힣]\d{4}`(지방세 자동차세 서류에 나온다).
- 주민번호 부분 마스킹형(없음): `\d{6}-?[1-8]\*{6}`. 생년월일과 성별이 드러난다.
- 정부24·홈택스 증명서의 문서확인번호·발급번호(없음): 16자리 `\d{4}-\d{4}-\d{4}-\d{4}` 등. 진위확인 서비스로 원문 대조가 가능한 번호이므로 접근 토큰처럼 취급하고, 모델·메타데이터·파일명에 넣지 않는다.
- 지방세 전자납부번호(19자리)와 고지서 번호(없음): 길이 + 문맥어.
- 이름 문맥: "님", "대표", "성명", "예금주" 뒤의 2~4자. 외국인의 라틴 대문자 이름.

### B-7 [낮음] 로컬 미리보기와 감사 로그로 낮은 수준의 재식별이 가능하다
- **위치**: D06 §6(마스킹본을 tmp에 평문 24시간), D03 §8(사람 응답 로그는 길이만, 갱신됨), D03 `run.started.inputsHash`, `artifact.saved.path`.
- **내용**: `inputsHash`가 키 없는 해시라면 사업자번호·금액·날짜 조합으로 사전 대입할 수 있다. `artifact.saved.path`는 상호·실명·승인번호가 든 파일명을 감사 로그에 남기는데, 감사 로그는 내보내진다.
- **수정**: 해시류는 `HMAC(K_audit_local, …)`로 바꾼다. 감사 로그에는 `docId`만 남기고 경로는 DB 문서 테이블에서 참조한다. tmp 미리보기는 암호화된 DB 행으로 옮긴다.

## C. 리모트 프로토콜

### C-1 [높음] 봉투 스키마가 승인 서명을 실을 수 없고, 본문과 어긋나는 곳이 많다
- **위치**: `schemas/remote-envelope.schema.json` vs D08 §6 표·§7, D02 §7.
- **내용**: `gate.response` 스키마는 `{runId, stepId, approved, nonce}`이고 `additionalProperties:false`다. 본문은 `sig = Sign_Vm("SAX-approve-v1"‖pair_id‖reqId‖challenge‖actionHash‖decision)`을 요구한다. 검증기를 엄격하게 돌리면 서명된 응답이 거부되고, 스키마에 맞춰 고치면 서명 검증이 사라진다. 스키마의 `nonce`는 R4 이전 설계(D11 T7 "nonce")의 흔적이다.

| 항목 | 스키마 | 본문 | 조치 |
|---|---|---|---|
| 메시지 ID | `id`, ULID 패턴 | inner `id: UUIDv7` | 하나로 통일. D02의 intentId와 맞추려면 ULID |
| 공통 필드 | `v, type, id, ts, replyTo, body` | `t, id, seq, ts, ttl, body` | `seq`, `ttl`(만료 강제), `pair_id`, `from/to` 추가 |
| gate.response | `nonce` | reqId, challenge, actionHash, decision, sig | 본문대로 |
| gate.request | 스키마 없음 | fields, actionHash, challenge(32B), exp | 스키마 추가, `fields` 크기 상한 |
| hello, cmd.abort/resume, run.event, file.offer, query.* | 스키마 없음 | 정의됨 | 전부 스키마화 |
| rotate.static, close | enum에 없음 | 정의됨(인증된 CLOSE) | enum 추가 |
| file.chunk, query.documents/result | enum에 있음 | 정의 없음 | 정의하거나 삭제 |
| cmd.run | `idempotency`(길이 무제한) | `cmd_id`(D02 §7) | 이름 통일, ULID 패턴 |
| human.request.image | 최대 280,000자(약 210KB) | Noise 메시지 상한 65,535B, 64K 버킷 | 청크 규격을 정하거나 블롭 경유 |
| human.request kind=secret | image 허용 | "secret은 이미지 없음" | 조건부 금지 |
| 문자열 상한 | runId, stepId, playbookId, replyTo, sealedForVault, idempotency 모두 무제한 | — | 모두 `maxLength`·패턴 |
| 바이너리 | base64 문자열 | 결정적 CBOR | CBOR byte string. JSON Schema 대신 CDDL(RFC 8610) 권장 |

- **수정**: 본문을 기준으로 스키마를 다시 쓴다. 가능하면 CDDL로 쓰고, 모든 type 분기에 `unevaluatedProperties:false`를 둔다. 회귀 테스트에 "서명이 빠진 gate.response 거부"를 넣는다.

### C-2 [높음] `sealedForVault`(crypto_box_seal)는 발신자 인증도 문맥 결속도 없고, 쓰는 키가 정의되지 않았다
- **위치**: D08 §6 human.response, D05 §5·§3 `fillFromRemote(req:{sessionId, stepId, element})`, D08 §3 키 계층.
- **내용**
  1. 키 계층(Sx·Vx·Qx·Lx)에 "금고 공개키"가 없다. Sx(Noise 정적키)나 Qx(HPKE inbox 키)를 재사용하면 프로토콜 간 키 재사용이 된다(R4 §4.0-5가 금지한 것).
  2. `crypto_box_seal`은 발신자가 익명이고 AAD가 없다. 봉인문이 어느 실행·스텝·요청·필드를 위한 것인지 묶여 있지 않다. 침해된 엔진은 지난 세션의 봉인문을 쌓아 두었다가 언제든 `fillFromRemote`로 재생하고, 대상 요소도 자기가 고른다.
  3. `fillFromRemote`의 인자에 봉인문 자체가 없다. 누가 금고에 봉인문을 건네는지 불명이다.
- **수정**
  - 금고 전용 키 `Kv`(X25519, 금고가 생성, 기기 밖으로 내보내지 않음)를 정의한다. `Vd`로 서명해 PAIR_OK·HELLO로 배포하고 회전한다.
  - 봉인은 인증 방식으로 바꾼다. HPKE Auth 모드(폰 쪽 전용 키) 또는 `crypto_box`를 쓰고, AAD에 `{pair_id, runId, stepId, reqId, vaultChallenge, exp, origin, secretKind}`를 넣는다.
  - `vaultChallenge`는 **금고가** 만들어 `human.request`에 실어 보내고, 한 번 쓰면 폐기한다. 금고는 origin과 secretKind가 자기 허용 목록 및 현재 프레임과 맞을 때만 입력한다.
  - 시그니처를 `fillFromRemote(req:{sealed, reqId})`로 고친다.

### C-3 [높음] 기기를 폐기해도 분실 폰이 우편함과 블롭에 계속 접근한다
- **위치**: D08 §9, D08 §7 드레인 검사 목록, D09 §5(블롭 API는 계정 단위 확인), D08 §3(폰이 KEK_N·K_meta·K_audit을 받음).
- **내용**
  1. 분실 폰은 `tok_read`·`tok_write`를 계속 가진다. Q_D를 회전해도 번들 슬롯에서 새 Q_D를 읽어 다시 봉인할 수 있고, 드레인 검사 목록에는 "발신 기기가 폐기되지 않았는지"가 없다.
  2. 블롭·메타데이터 API는 계정 토큰으로 접근하므로, 분실 폰의 토큰이 살아 있으면 모든 암호문과 wDEK를 내려받아 이미 가진 KEK_N으로 오프라인 복호화할 수 있다. KEK N+1로 재래핑해도 **이미 복사된 wDEK**는 보호하지 못한다.
  3. K_meta(대칭 키)로 만드는 인덱스 무결성 태그는 분실 폰이 위조할 수 있다.
  4. R4 §4.6에 있던 "서버 측 토큰·푸시·블롭 권한 즉시 무효화"와 "기기 인증서 90일 만료"가 D08에 빠졌다.
- **수정**
  - (a) 폐기할 때 남은 기기와 라이브 세션을 맺어 **새 우편함과 토큰을 다시 발급**하고, 옛 우편함은 삭제한다.
  - (b) 드레인과 IK 수락 단계에서 `Vm`·`Sm` 폐기 목록을 검사하도록 명시한다.
  - (c) 계정 토큰을 **기기 범위 토큰**으로 바꾸고 폐기 즉시 무효화한다(블롭, 메타데이터, 릴레이 남용 방지 계층 모두).
  - (d) 인덱스 레코드는 R4 §6.2처럼 `Vd` Ed25519 서명으로 보호하고, 폰에 K_meta를 주지 않는다. K_audit은 회전한다.
  - (e) 기기 인증서 `not_after`를 90일로 둔다.
  - (f) 문서에 "분실 전에 복사된 wDEK로 열 수 있는 기존 블롭은 재암호화하지 않으면 보호되지 않는다"고 적고, 선택형 전체 재암호화 기능을 둔다.

### C-4 [높음] PC 분실이나 복구 문구 유출 시, 키 회전이 실제로는 아무것도 회전하지 않는다
- **위치**: D08 §3(`KEK_N = HKDF(RK, "kek/blob/vN")`, RK는 데스크톱 키체인에 보관), D08 §9 PC 분실 절차, D07 §6.
- **내용**: KEK_N+1도 같은 RK에서 결정적으로 나온다. RK를 가진 사람(분실 PC의 키체인을 연 도둑, 유출된 문구를 가진 사람)은 앞으로의 모든 KEK, K_idx, AIK를 계산할 수 있다. PC 분실 절차는 "복구 문구로 RK 재생성 → 새 인증서 발급"뿐이라, 도둑도 같은 AIK로 기기 인증서·폐기 목록·기기 목록을 **동시에 서명**할 수 있다(신뢰 체인이 갈라진다). R4 §4.8의 "문구 유출 → RK 교체 + 재암호화"가 D08에 반영되지 않았다. RK가 키체인에 늘 있으므로, 같은 사용자 악성코드가 한 번만 실행돼도 백업 전체와 계정 신원이 넘어간다.
- **수정**
  1. PC 분실·문구 유출 절차를 **새 복구 문구(RK′) 발급 → AIK′ 전환 선언**으로 정한다. 폰은 새 PC와 IK 세션을 맺은 상태에서 사용자가 생체 인증으로 승인해야만 핀을 갱신한다. 도둑이 내미는 경쟁 전환은 폰 승인이 없으므로 무효다.
  2. 모든 DEK를 재래핑하고, 위험이 크면 블롭을 재암호화한다.
  3. 키체인에는 운영 키(KEK_N, K_idx)만 두고, AIK 개인키는 Hello 결박으로 보관한다. RK는 회전할 때만 문구에서 다시 유도한다.
  4. 선택안: 계정 로그인 후에만 받을 수 있는 서버 지분을 섞어 `RK = HKDF(entropy ‖ server_share)`로 만드는 2SKD 변형을 검토한다. 문구만 훔친 사람을 막고, 서버 지분은 단독으로는 쓸모가 없다.

### C-5 [중간] "릴레이는 계정과 우편함의 연관을 모른다"는 근거 문서(R4)와 모순된다
- **위치**: D08 §1·§8, D09 §4("토큰 → 기기 매핑만, 우편함 ID 미포함"), ADR-007 제목("무지식 릴레이"), D11 LINDDUN.
- **내용**
  1. 페어링 룸은 계정 토큰으로 발급된다(D08 §4-1). 룸이 끝난 직후 같은 IP에서 새 우편함에 첫 접속이 오므로, 시각과 IP만으로 둘을 잇기 쉽다.
  2. 내용 없는 푸시를 보내려면 릴레이가 "우편함 X에 메시지가 왔을 때 어느 기기를 깨울지"를 알아야 한다. 우편함↔푸시 토큰 매핑이 반드시 필요한데, D09는 이를 두지 않는다고 적어 구현이 불가능한 명세가 됐다. 푸시 토큰은 기기에, 기기는 계정에 연결된다.
  3. R4 §5.1과 §5.5는 레지스트리에 계정 참조를 두며 "연결 가능성은 남는다"고 명시한다.
  4. 접속 IP는 30일 보관된다.
- **수정**: 문구를 "릴레이는 내용과 키를 보지 못한다. 계정과 우편함의 연결은 분리 저장, 접근 통제, 짧은 보존으로 최소화하지만 운영자가 상관 분석하면 가능하다"로 고친다. 처리방침과 투명성 페이지도 같다. 푸시 매핑은 실제 구조대로 명세한다(우편함 → 암호화된 푸시 토큰, 저장 키 분리). 장기 과제로 Privacy Pass 방식의 비연결 토큰을 검토한다. ADR-007 제목에서 "무지식"을 뺀다.

### C-6 [중간] 큐에 쌓인 의도와 원격 명령은 "시작 전"에 승인받아야 한다. 승인 키의 기본값도 약하다
- **위치**: D08 §1·§7, R4 §4.4-3("(비가역 단계)"), D08 §2(Vm 소프트웨어 키 기본, Px는 선택), D10 `semi_auto`(시작 동의 + 커밋 게이트, 좋은 선례).
- **내용**: 드레인 후 만드는 "새 gate.request"가 실행 시작 전에 오는지, 비가역 스텝 직전에 오는지 정해져 있지 않다. 후자라면 PC를 켜자마자 사람 없이 로그인(저장된 비밀번호 타이핑)과 화면 조작이 시작된다. 이는 "무인 데몬은 폰 승인 반자동만"이라는 결정을 우회한다. 승인 서명 키 Vm은 소프트웨어 키라, 폰의 악성코드나 잠금이 풀린 분실 폰은 생체 인증 없이 서명할 수 있다. 폰이 PC가 보낸 `actionHash`를 그대로 받아 서명하면, 그 서명은 사용자가 본 내용과 묶이지 않는다.
- **수정**: 큐 의도와 원격 `cmd.run` 모두 **시작 게이트**(새 챌린지, 카드에 `iat`과 "N시간 전 요청" 표시)를 먼저 거치고, 비가역 게이트를 나중에 거친다(D10 `semi_auto`와 같은 구조). 승인 서명은 사용자 존재를 요구하는 SE/StrongBox 키를 기본으로 하고, 지원하지 않는 기기에서만 Vm을 쓴다. 폰은 표시한 `fields`를 JCS로 정규화해 `actionHash`를 직접 계산하고, 받은 값과 같을 때만 표시하고 서명한다.

### C-7 [중간] 페어링: QR·SAS의 화면 노출, 사회공학, 낡은 ADR
- **위치**: D08 §4, D11 T6, ADR-007.
- **내용**
  1. QR 안의 `ps`와 대체 경로의 단어 코드는 원격 지원 도구의 화면 공유, 스크린샷, Windows Recall에 남는다.
  2. 계정 기기 목록 대조는 이메일 매직링크 보안 수준만큼만 강하다. "지원 상담원"을 사칭한 사람이 화면 공유로 QR을 보고 자기 폰의 6자리를 불러 주면, 사용자는 그 숫자를 PC에 입력한다.
  3. PAIR_OK가 페어링 즉시 KEK_N을 넘기므로, 속아서 맺은 페어링 한 번이면 모든 백업이 열린다.
  4. ADR-007("지문 단어 일치 확인", 큐 7일)과 D11 T5·T6·T7은 현재 설계(PSK + PC 입력 SAS, 72시간 큐, 패딩 적용)와 다르다. 구현자가 금지된 "일치 버튼"을 만들 위험이 있다.
- **수정**: QR, SAS, 복구 문구, 비밀 저장 창에 `BrowserWindow.setContentProtection(true)`를 건다(Windows `WDA_EXCLUDEFROMCAPTURE`, macOS 공유 제외). 폰이 붙으면 즉시 QR을 숨긴다. SAS 입력 화면에 폰의 기기 이름, 플랫폼, **계정 등록 시각**("3분 전 등록")과 "통화 중인 상대가 숫자를 불러 주면 입력하지 마세요"를 보여 준다. KEK_N 전달은 PC의 Hello 확인이 있는 별도 단계("이 폰에서 서류 열람 허용")로 분리한다. 새 기기를 등록하면 기존 기기와 이메일로 알린다. ADR-007과 D11 T5·T6·T7을 갱신한다.

### C-8 [낮음] 프레이밍, 재키, 상태 영속의 세부
- **위치**: D08 §5·§6·§10.
- **내용**
  1. 시간 기반 `Rekey()`(1시간)는 송신 측과 수신 측이 서로 다른 순간에 키를 바꾸게 만든다. Noise Rekey는 n을 유지하고 키 세대를 표시하지 않으므로, 전송 중이던 메시지가 복호 실패한다.
  2. IK msg1 타임스탬프 최댓값을 디스크에 저장한다는 명시가 없다.
  3. 폰을 재설치해 `seq`가 초기화되면 정상 의도가 윈도 밖으로 버려진다.
  4. Vx 서명 용도(의도 봉투, 체크포인트, Qx 번들, ROTATE_STATIC)마다 컨텍스트 문자열이 정해져 있지 않다. 승인 서명만 정해져 있다.
- **수정**: 재키는 `ctr`가 2^20의 배수가 될 때 양쪽이 결정적으로 하거나, outer 헤더에 1비트 epoch를 두고 AD에 포함한다. 타임스탬프와 seq 상태는 pair별로 영속하고, 재페어링하면 epoch를 올린다. 서명 용도별 `"SAX-<용도>-v1"` 접두를 표로 고정한다.

## D. 데이터

### D-1 [높음] 보관함 기본값이 평문 PDF + 실명 파일명 + 동기화·색인되는 폴더다
- **위치**: D07 §1·§4, D02 §8 `nameTemplate`.
- **내용**: 기본 위치 `문서/소버린AX/`는 많은 신규 Windows 11 PC에서 OneDrive '문서 백업'(알려진 폴더 이동)으로 동기화된다. 그러면 주민번호가 모두 찍힌 등본, 자격득실, 지방세 서류가 **평문으로 해외 클라우드에 올라간다**. 이는 "본인 데이터는 본인이"라는 모토와 E2EE 백업의 의미를 무력화하고, 국외이전 고지 범위도 벗어난다. Windows Search 색인(PDF 필터가 있는 환경), 최근 항목, 파일명 자체(`홍길동_20261027.pdf`, `㈜거래처_…_승인번호.pdf`)도 노출면이다.
- **수정**: 기본 위치를 `%LOCALAPPDATA%\SovereignAX\vault`(동기화·색인 대상 아님)로 바꾼다. 사용자가 문서 폴더를 고르면 OneDrive, Dropbox, Google Drive, iCloud 동기화 루트인지 감지해 경고한다. 기본 파일명 템플릿은 `{docType}_{yyyyMMdd}_{shortId}.pdf`로 하고, 표시 이름은 DB에 둔다. `FILE_ATTRIBUTE_NOT_CONTENT_INDEXED`를 설정한다. 중기적으로는 보관함을 at-rest 암호화(파일별 DEK, 키체인 KEK)하고 "내보내기"로 평문 사본을 만든다.

### D-2 [중간] 메타데이터 인덱스만으로 추론할 수 있는 것이 많다
- **위치**: D07 §5, D09 §2(slot 1 = 개인, 2 = 사업자), D09 §7, D11 LINDDUN("프로필 종류조차 없음").
- **내용**
  1. "서버는 종류(개인·법인)도 모른다"는 사실이 아니다. D09 §2가 슬롯 번호에 의미를 고정했고, `doc_type`만 봐도 드러난다(`tax_invoice`, `sme_cert`면 사업자).
  2. 추론 예:
     - 같은 주에 `national_tax_cert`, `localtax_cert`, `insure4_cert`, `sme_cert`가 함께 올라오면 공공 입찰 서류 묶음이다. 시점을 특정 공고와 맞춰 볼 수 있다.
     - `localtax_item_cert`, `building_register`는 부동산 보유·거래 정황이다.
     - `nhis_eligibility`가 반복되면 고용 상태 변동이다.
     - `insure4_cert`가 있으면 직원이 있다.
     - `tax_invoice`의 월별 건수와 `bytes`(품목 수에 비례)로 거래량과 매출 리듬이 보인다.
     - 납세증명은 체납 상태에서는 발급되지 않으므로, 정기 갱신이 끊기면 체납 정황이 된다.
  3. `bytes` 정확값(R4 §6.2는 크기 필드 없이 Padmé 버킷을 권고), 초 단위 `client_updated_at`(사용 시각), UUIDv7 `doc_id`(생성 시각 내장).
  4. 조회 에이전트가 이 행들을 Terra(미국·EU 처리)로 보낸다(D09 §7). 그런데 D11 §6의 국외이전 항목에는 "메타데이터"가 없다.
- **수정**: 서버 필드를 `doc_type`, `expires_on`, `issued_month`(월 단위), `rev`(정수), `sig`로 줄이고 `bytes`와 `client_updated_at`은 삭제한다. 블롭은 Padmé로 패딩한다. `tax_invoice`는 기본적으로 업로드하지 않는다(만료 개념이 없고 조회 가치가 낮다). doc_type별 옵트인을 둔다(R4 §6.2). 서버에서 슬롯 번호의 의미를 없앤다(무작위 번호). 국외이전 고지에 "조회 시 메타데이터 행"을 넣는다. 관련 문구를 정정한다.

### D-3 [중간] 블롭 봉투 형식 결함: AAD에 wrappedDEK가 들어가 재래핑이 불가능하다
- **위치**: D07 §6(`header = {…, wrappedDEK, kekId}`, `ciphertext = AEAD(DEK, nonce, pdf, aad=header)`), 같은 절의 "KEK 회전은 재래핑", "wDEK 레코드를 먼저 지우고".
- **내용**: 재래핑하면 헤더가 바뀌어 AEAD 검증이 실패한다. 그러면 KEK를 회전할 때마다 **모든 블롭을 재암호화**해야 하고, C-3·C-4의 회전 절차는 사실상 쓸 수 없다. wDEK가 블롭 헤더 안에 있으니 "wDEK 레코드를 먼저 지운다"는 키 우선 삭제도 불가능하다. AAD에 `blob_id`가 없어 서버가 같은 계정의 두 블롭을 맞바꾸면 "납세증명" 항목이 다른 문서를 연다. 단일 AEAD라 큰 파일에서 메모리를 많이 쓰고, 패딩도 없다.
- **수정**: R4 §6.1 형식을 따른다. 키 객체를 분리해 `wDEK = AEAD(KEK_N, DEK, ad="SAX-dek-v1"‖blob_id‖kek_ver)`로 만든다. 데이터 객체는 청크 STREAM 방식(청크 AD = 헤더 해시‖청크 번호‖final)으로 한다. 헤더 AAD에는 바뀌지 않는 필드(`v, alg, blob_id, doc_id`)만 넣는다. 인덱스 레코드 서명에 `blob_id`와 평문 해시의 HMAC을 포함한다. Padmé로 패딩한다.

### D-4 [중간] 엔진과 메인의 크래시 덤프에는 DB 키, 토큰, PII가 있다
- **위치**: D05 §8("엔진·메인은 비밀이 없으므로 덤프해도 안전"), D11 §4(크래시 리포트는 옵트인).
- **내용**: 엔진 힙에는 DB 키(`getDbKeyOnce`), 계정 bearer 토큰, BYOK 키, 마스킹 전 스냅샷, 포털 쿠키와 응답이 있다. main도 스케줄러 때문에 DB를 연다면(D10 §3) DB 키를 갖는다. 덤프 업로드에 동의한 사용자의 DB 키가 우리 서버로 온다.
- **수정**: 엔진과 메인의 미니덤프는 업로드하지 않는다. 로컬 덤프도 사용자가 명시적으로 요청할 때만 만든다. 크래시 리포트는 힙 없이 스택 심볼과 오류 코드만 구조화해 보낸다. "비밀이 없으므로 안전" 문구를 지운다. DB 키를 누가(엔진, main) 몇 번 받는지 표로 명시한다.

### D-5 [중간] 전용 Chrome 프로필과 로컬 임시 폴더에 평문이 남는다
- **위치**: D03 Chrome 기동(세션 쿠키 유지), D07 `profiles.keep_session DEFAULT 1`, D07 §1 tmp(평문).
- **내용**: 전용 프로필에는 포털 세션 쿠키(기본으로 유지), HTTP 캐시(발급 PDF와 조회 화면), 방문 기록(URL 쿼리), 자동완성 기록(A-4)이 남는다. 프로필 경로가 정해져 있지 않아 로밍 프로필 경로에 생기면 도메인 서버로 복사될 수 있다. tmp의 마스킹 미리보기와 캡차 크롭은 평문 파일이다.
- **수정**: 프로필 경로를 `%LOCALAPPDATA%`로 고정한다. `keep_session` 기본값을 0으로 하거나 짧은 TTL을 둔다. 종료 시 캐시와 방문 기록을 정리한다(`Network.clearBrowserCache`, `Storage.clearDataForOrigin`). 이것은 사용자 데이터 정리일 뿐 흔적 은폐가 아니며, 감사 로그는 그대로 남는다. 미리보기는 암호화된 DB 행으로 옮기고, 캡차 크롭은 메모리에만 둔다.

### D-6 [낮음] HMAC dedup 토큰은 필요가 없거나 정의가 덜 됐다
- **위치**: D07 §2·§5·§6.
- **내용**: 다시 발급한 서류는 발급일과 발급번호가 달라 해시가 거의 겹치지 않는다(이득이 작다). 반면 "같은 계정에서 같은 서류를 다시 올렸다"는 사실은 드러난다. 도메인 문자열(`"SAX-idx-v1"`)이 빠졌고, 로컬 `user_index_key`와 `K_idx`가 같은 키인지도 적혀 있지 않다.
- **수정**: R4 §6.3-3대로 서버 태그를 삭제하고, 로컬 `sha256 → blob_id` 매핑으로 중복을 판단한다. 남긴다면 `HMAC(K_idx, "SAX-idx-v1"‖sha256)`을 128비트로 잘라 쓴다고 명시한다.

### D-7 [낮음] 로컬 SQLite 키 처리의 세부
- **위치**: D07 §1·§2, D05 §3.
- **내용**: `inputs_json_enc`·`context_json_enc`를 같은 DB 키로 한 번 더 암호화해도 이득이 없다. SQLite3MC는 WAL과 저널을 암호화하지만, 정렬용 임시 파일은 `temp_store` 설정에 따라 디스크에 평문으로 남을 수 있다. `PRAGMA key`는 SQL 문자열이라 키가 JS 문자열로 남는다.
- **수정**: `PRAGMA temp_store=MEMORY`, 암호 알고리즘과 raw key(`x'…'`) 사용을 명시한다. 재개용 컬럼은 금고 키로 따로 봉인하거나 평문 컬럼으로 단순화한다.

## E. 클라우드·게이트웨이

### E-1 [높음] `/v1/respond`의 `messages`와 `replay[]`는 화이트리스트로 검증할 수 없는 자유 구조다
- **위치**: D09 §3(갱신본: "replay는 이전 response.output·function_call_output 항목만"), D04 §4·§7, D04 §6(월 한도 100% 후 L1 유지).
- **내용**: 게이트웨이는 무상태라 replay 항목이 **실제로 모델이 낸 출력인지** 확인할 수 없다. 변조된 클라이언트가 할 수 있는 일:
  1. `assistant` 메시지나 `function_call` 항목을 날조해 맥락을 주입한다.
  2. `function_call_output`에 임의 장문(마스킹되지 않은 PII, 정책 위반 콘텐츠)을 넣는다.
  3. 툴셋에 없는 함수 이름의 호출을 넣는다.
  4. `messages`에 `developer` 역할, 외부 URL `input_image`, `input_file`, 캐시 브레이크포인트를 넣는다.
  5. 수십만 토큰짜리 입력으로 비용을 폭주시킨다.
  정책 위반 콘텐츠가 우리 조직 키로 반복 전송되면 공급사 조치가 **조직 전체**(모든 사용자)에 걸린다. `cacheKey`와 `runId`가 클라이언트 값이라 캐시 네임스페이스 조작과 실행당 예산 우회(runId 교체)가 된다. 월 한도 이후의 "L1 유지"에는 상한이 없다.
- **수정**
  1. 게이트웨이가 응답 `output`에 `HMAC(gw_key, accountId‖runId‖items)` 태그를 붙여 돌려준다. replay는 태그가 맞는 항목과, 그 항목의 call_id에 대응하는 `function_call_output`만 받는다. 무상태는 유지된다.
  2. `messages`는 `role=user`와 `input_text`만 허용하고, 툴셋별 전체 바이트 상한을 둔다(예: L1 16KB, L2 64KB). 이미지는 base64 PNG/JPEG만, 크기 상한을 두고 받는다. 캐시 관련 필드는 제거한다.
  3. `cacheKey`는 무시하고 서버가 계산한다. `runId`는 게이트웨이가 발급하고 서명한 run 토큰으로 바꾼다.
  4. L1에 하드 상한(플랜 한도의 N배)을 두고, 넘으면 안전 판정 번들만 낮은 속도로 허용한다.
  5. 정책 위반이나 거절이 급증한 계정은 자동 정지한다.

### E-2 [중간] 계정 간에 공유하는 `prompt_cache_key`는 오라클 위험에 비해 얻는 것이 적다(문서 간 모순 포함)
- **위치**: D04 §2.1·D09 §3(`pb:<playbookId>:v<major>:shard<n>`, 계정 접두 없음), ADR-009("캐시 키는 계정별 격리").
- **내용**: 명시 모드에서 게이트웨이의 고정 접두만 캐시된다면 안전하다. 하지만 다음 중 하나만 생겨도 사용자 화면 텍스트가 공유 네임스페이스에 캐시된다. (a) 회귀로 명시 모드가 빠짐, (b) 클라이언트가 넣은 브레이크포인트, (c) 암묵 브레이크포인트(Decisions는 공유 입력의 끝에 둔다). 응답의 `usage.cached_tokens`가 클라이언트에 보이므로, 다른 계정이 추측한 텍스트로 적중 여부를 확인하는 오라클이 된다. D04 스스로 "캐시는 최적화 항목이지 핵심 변수가 아니다"라고 쓴다.
- **수정**: `acct:<HMAC>:` 접두로 계정별로 격리한다(ADR-009와 맞춤). 게이트웨이가 명시 모드와 브레이크포인트 위치를 강제하고, 클라이언트 입력의 캐시 필드는 제거한다. 세 문서를 하나로 맞춘다.

### E-3 [중간] "본문 무저장"을 검증할 수단이 없고, 오류 경로로 새기 쉽다. 공급사 보존과 충돌하는 문구도 있다
- **위치**: D09 §3·§10("모델 프롬프트·응답 보존 0"), ADR-009, README 원칙 3, D04 §7(ZDR 승인 전 최대 30일).
- **내용**: 흔한 누출 경로: 검증 라이브러리 오류가 받은 값을 되풀이하는 경우(ajv `verbose`, zod), `JSON.parse` 오류에 들어가는 입력 조각, APM·Sentry가 기본으로 수집하는 요청 바디와 예외 컨텍스트, 공급사 SDK 오류 객체, 엣지·WAF의 바디 로깅, 코어 덤프. 투명성 표의 "0"은 우리 쪽 저장만 센 것이다. ZDR 승인 전에는 공급사가 최대 30일 보존하는데, 사용자는 "어디에도 남지 않는다"로 읽는다.
- **수정**: 허용된 필드만 쓰는 구조화 로거(기본 거부)를 쓰고, 검증 오류는 스키마 경로만 기록한다. APM은 `sendDefaultPii:false`, 바디 수집 끔, `beforeSend` 스크럽. `RLIMIT_CORE=0`, `PR_SET_DUMPABLE=0`. 엣지 바디 로깅을 금지한다. 게이트웨이 소스와 이미지 다이제스트를 공개하고 외부 감사를 받아 검증할 수 있게 한다. 보존표에 "공급사: ZDR 승인 전 남용 모니터링 최대 30일" 행을 추가한다.

### E-4 [중간] 계량 레코드는 사실상 호출 단위의 활동 로그다
- **위치**: README 원칙 3("토큰 수만 계량"), D09 §3 계량·§10(13개월 보존), D04 §7 `X-Device-Id`.
- **내용**: 호출마다 계정, 기기, 번들·툴셋, **플레이북 ID**, 지연, 시각을 13개월 동안 보관한다. 이것으로 "누가 언제 세금계산서를 몇 건 발급했는지"를 재구성할 수 있다. "토큰 수만"이 아니다.
- **수정**: 호출 단위 레코드는 결제 대사에 필요한 최소 기간(예: 35일)만 두고, 그 뒤에는 계정·일 단위 합계로 줄인다. 플레이북 ID 통계는 계정과 분리된 익명 통계로 둔다. 문구를 정정한다(F-5).

### E-5 [중간] 계정을 탈취당하면 백업이 전부 즉시 삭제된다. 디바이스 플로우는 피싱에 취약하다
- **위치**: D09 §2(매직링크, 디바이스 플로우, 계정 삭제 "즉시"), D09 §5 `DELETE /v1/blobs/{id}`.
- **내용**: 이메일만 뚫리면 블롭과 메타데이터를 즉시, 되돌릴 수 없게 지울 수 있다. 기기 목록 조작으로 페어링 방어도 약해진다(C-7). OAuth 디바이스 플로우는 공격자가 만든 코드를 사용자가 정식 페이지에 입력하게 만드는 피싱에 취약하다. 데스크톱 앱에는 RFC 8252 루프백 리디렉트 + PKCE가 맞다.
- **수정**: 삭제에는 기기 서명(`Vd`)을 요구하고, 7~30일 유예(복구 가능)를 두며, 모든 기기에 알린다. 계정 삭제도 유예한다. 데스크톱 로그인은 루프백 + PKCE로 바꾼다. 토큰은 요청마다 기기 키로 서명(DPoP 방식)하거나 TTL을 짧게 한다. 패스키를 기본으로 권장한다.

### E-6 [낮음] 사업자번호 진위확인 프록시
- **위치**: D09 §4.1.
- **내용**: 거래처 사업자번호 조회는 계정의 **거래처 그래프**(공급망, 고객)를 드러낸다. 개인사업자의 사업자번호는 다른 정보와 결합하면 개인정보로 볼 여지가 있다. 게이트웨이 접근 로그(계정 해시, 시각)가 남는다. GET 쿼리로 구현하면 모든 계층이 사업자번호를 기록한다.
- **수정**: POST 바디로만 받는다. 이 경로는 접근 로그에서 바디·쿼리·계정 해시를 모두 빼는 무로그 프록시로 둔다. 처리방침에 수탁·제공 구조를 적는다. BYO 키 선택지를 설정 첫 화면에 보여 준다.

## F. 준수 입장과의 정합성·대외 문구

### F-1 [높음] 후처리 모드가 포털을 자동화 프로필 Chrome으로 열면, 사용자가 매크로 이용자로 제재받을 수 있다
- **위치**: 05 §7("포털 URL 열기(사용자 Chrome)"), D02 §9, D03 §12(portalMode), ADR-011.
- **내용**: 여기서 "사용자 Chrome"이 CDP 파이프로 띄운 전용 프로필이라면, 아무 자동화를 하지 않아도 그 세션은 `navigator.webdriver=true`다. 갱신본처럼 디버깅 포트까지 열려 있으면 더 나쁘다. 정부24 약관 제14조④9호의 매크로 제재(1개월, 3개월, 영구)는 탐지 결과로 집행된다. 허락 전에 약관을 지키려고 만든 후처리 모드가 오히려 사용자의 계정 정지로 이어진다.
- **수정**: `postprocess` 포털은 **`shell.openExternal`로 사용자의 일반 기본 브라우저**에서 연다. 그 모드에서 엔진은 Chrome을 띄우지 않고 CDP 연결도 없다는 것을 테스트로 고정한다. 파일 감시는 G-4의 제한을 따른다.

### F-2 [중간] 캡차를 폰으로 넘겨 푸는 흐름을 약관 10호, 공문, 정책과 맞춰야 한다
- **위치**: 05 §3-1, D01 §5.4, D08 `human.request(kind=captcha)`, ADR-004.
- **내용**: 정부24 약관 10호는 "캡차를 외부 솔루션으로 우회·무력화"하는 행위를 금지한다. 계정 주인이 직접 푸니 우회가 아니라고 해석하는 것이 자연스럽다. 하지만 구조만 보면 "PC는 사람 없이 자동으로 진행하고, 사람은 다른 기기에서 문제만 푼다"는 캡차 중계 서비스와 모양이 같다. 공문(05 §4.2-3, "캡차는 사용자 직접 수행")에 이 방식을 적지 않으면 약속과 다르게 읽힐 수 있다.
- **수정**: 공문의 기술 방식에 "캡차 이미지를 사용자 본인 폰에 E2E로 보내 본인이 입력한다"를 명시해 승인받는다. 서명 정책에 포털별 `captchaRelay: allowed|desktop_only`를 두고, 회신 전 기본값은 `desktop_only`로 한다. 원격·데몬 트리거는 `postprocess`·`assisted` 포털에서 거부한다.

### F-3 [중간] "사람 수준" 키 간격과 지터는 스스로 금지한 '모사'와 같은 것이다
- **위치**: 05 §2 표("글자당 90~260ms(중앙값 약 170ms, 사람 평균 238ms 수준)", "사람 수준 지연(지터 포함)", 표 제목 "탐지 신호 | 일반 봇 | 우리", "피할 수 있는 신호는 피한다"), D03 §7(`keyEventDelayMs [90,260]`, "타이핑 모사는 쓰지 않는다"), D05 §4("사람 속도로"), 05 §6("차단을 막고").
- **내용**: 보안 모듈과 행위 분석이 바로 들여다보는 칸(keyEvents, 비밀 입력)에 사람 분포를 흉내 낸 지터를 쓴다. 공문 첨부에서 이 표와 문구는 '탐지 회피 설계'로 읽힌다.
- **수정**: 키 간격은 모듈 호환에 필요한 **고정값**(예: 50ms, 지터 없음)으로 하고, 근거도 "모듈 호환"으로만 적는다. 스텝 간격과 데몬 시각 분산은 근거를 "운영기관 부하 상한, 사용자 간 시각 분산"으로 바꾼다. "사람 평균 238ms" 비교는 삭제한다. 05 §2 표 제목은 "운영기관이 보는 접속 특성"으로, §6 문구는 "운영기관과 약속한 속도로 동작합니다"로 바꾼다.

### F-4 [중간] "명시적 불허 → 반자동"과 `assisted` 모드의 화면 읽기는 9호 위반 소지가 있다
- **위치**: 05 §4.3("명시적 불허 → 반자동 … 하네스는 입력값 준비·검증·결과 파일 정리"), 05 §7 `assisted`("화면 상태 판정, 결과 수집"), R5 §3-A(9호는 "인증정보로 로그인 후 개인정보 수집"까지 포함).
- **내용**: 불허 회신을 받은 포털에서 CDP로 화면을 읽어 "검증"하거나 결과를 수집하면, 로그인 후 자동 수집에 해당할 수 있다.
- **수정**: 불허 회신은 `postprocess`(CDP 없음)로 매핑한다. `assisted`는 허락 문서가 "로그인 후 자동 입력·화면 판정"을 명시적으로 허용할 때만 켠다. 정책 변경 로그에 문서 번호(D12 §4에 이미 있음)와 허용 범위 필드를 남긴다.

## G. Electron·공급망

### G-1 [중간] `utilityProcess`는 샌드박스가 아니다. 금고의 네트워크 금지는 린트 규칙뿐이다
- **위치**: D05 §3("코드 수준 + 프로세스 샌드박스"), D01 §2.1, D11 §4, R3 §2.3.
- **내용**: utilityProcess는 Node가 켜진, 샌드박스 없는 자식 프로세스로 가정해야 한다. 금고의 의존성(키체인 바인딩, sodium-native, CDP 클라이언트) 하나만 오염돼도 `net`, `fs`, `child_process`를 전부 쓸 수 있다.
- **수정**: 금고를 Rust 별도 실행 파일로 만들고(Bitwarden 방식, Windows 제한 토큰이나 AppContainer 검토), 그렇게 못 하면 최소한 다음을 지킨다. 의존성 3개 이하로 벤더링·고정, 시작 시 `net`·`http`·`child_process` 로드를 막는 훅, Node 권한 모델(`--permission`, 지원 범위 확인). 문서에서 "샌드박스"를 지운다.

### G-2 [중간] 퓨즈 목록이 불완전하다. macOS 키체인 ACL 주장은 퓨즈에 달려 있다
- **위치**: D11 §4("fuses로 runAsNode·nodeOptions 등"), D05 §7(macOS "코드서명 기반 접근 제어").
- **내용**: `EnableNodeCliInspectArguments`, `EnableEmbeddedAsarIntegrityValidation`, `OnlyLoadAppFromAsar`, `GrantFileProtocolExtraPrivileges`(R3 §4.1)가 빠졌다. 이 퓨즈가 열려 있으면 같은 사용자 공격자가 우리 서명 바이너리 안에서 코드를 실행해(`--inspect`, ASAR 교체) 서명 기반 키체인 ACL을 통과한다. "코드서명 기반 접근 제어"의 전제가 무너진다. Windows 사용자 단위 설치 경로는 사용자가 쓸 수 있어 무결성 경계가 원래 없다는 점도 적혀 있지 않다. `@napi-rs/keyring`이 macOS에서 데이터 보호 키체인과 `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`를 실제로 쓰는지는 확인되지 않았다(레거시 키체인이면 이 속성은 무시된다).
- **수정**: R3 §4.1의 퓨즈 전체를 D11에 표로 고정하고, 빌드 순서(퓨즈 → ASAR 무결성 → 서명)를 CI로 검증한다. `utilityProcess.fork`의 `execArgv`를 고정한다. 프로덕션에서 `devTools=false`, `setPermissionRequestHandler`로 전부 거부, `will-navigate`와 `setWindowOpenHandler` 기본 거부를 D11 체크리스트에 넣는다. macOS 키체인 속성은 Phase 3 전에 Rust 헬퍼로 직접 지정해 확인한다.

### G-3 [높음] 레지스트리: 롤백·동결 방어가 미완이고, 서명키 유출 시 피해 반경을 제한하는 장치가 없다
- **위치**: D09 §8, D07 `playbook_packages`·`policy`(`signature_ok`만 있음), D02 §2 `domains[]`, D03 `portalMode`.
- **내용**
  1. D09에는 만료(freshness)만 있고, **단조 증가 버전과 패키지별 최저 버전**이 없다(R3 §4.3 P1은 둘 다 요구한다). 만료 전이라면 옛 인덱스, 옛 패키지, 옛 정책을 다시 내려보낼 수 있다. 정책 롤백은 준수 문제다. 제재 후 `gov24: postprocess`로 내린 정책을 옛 `auto` 정책으로 되돌리면 제품이 약관 위반 상태로 동작한다.
  2. `signature_ok` 플래그를 저장해 두고 이후에는 그 값을 믿는다.
  3. 서명키가 유출되면 공격자는 `domains[]`에 자기 도메인을 넣은 플레이북으로 프로필과 거래처 값을 자기 페이지에 `fill`해 빼 갈 수 있다(코드 실행 없는 유출). 자기 도메인의 `<input type=password>`를 `secretSlot`으로 지정해 **저장된 비밀번호를 타이피스트로 받아 갈 수도 있다**. 엔진과 금고에 패키지와 무관한 내장 허용 목록이 없기 때문이다.
  4. 플레이북과 정책이 같은 키로 서명되는지 불명이다. 인덱스 만료에 상한이 없어 먼 미래 만료로 서명할 수 있다.
- **수정**: 인덱스 `version`을 단조 증가시키고 클라이언트가 최고값을 저장해 더 낮은 것을 거부한다. 패키지, 정책, 핫픽스마다 최저 버전을 둔다. 인덱스 `expires` 상한(예: 14일)을 강제하고, 만료되면 **가장 보수적인 정책**(모든 포털 `postprocess`)으로 돌아간다. 정책 서명키를 플레이북 서명키와 분리해 각각 핀 고정한다. 엔진에는 포털 eTLD+1 내장 허용 목록(`hometax.go.kr`, `gov.kr`, 간편인증·서명 모듈 도메인 등)을, 금고에는 비밀 종류별 origin 허용 목록을 두고, 둘 다 앱 업데이트로만 바꾼다. 서명은 로드할 때마다 다시 검증한다.

### G-4 [높음] PDF 파서와 OCR이, 금고를 빼면 가장 권한이 많은 프로세스에서 비신뢰 파일을 자동 처리한다
- **위치**: D07 §8(pdfjs-dist, tesseract.js), D02 §9·05 §7(후처리 모드의 파일 감시: 다운로드 폴더), D01 §7(engine이 docparse에 의존).
- **내용**: 후처리 모드는 다운로드 폴더에 생긴 PDF를 자동으로 파싱한다. 웹사이트는 `Content-Disposition: attachment`로 사용자 클릭 없이도 파일을 내려보낼 수 있다. 그러면 DB 키, CDP, 계정 토큰을 가진 엔진이 악성 PDF를 처리하게 된다. pdf.js에는 `isEvalSupported` 기본값에서 임의 JS가 실행되는 취약점 이력(CVE-2024-4367, 4.2.67에서 수정)이 있고, Node 위에서 JS가 실행되면 곧 프로세스 장악이다. A-2의 엔진 침해 시나리오가 사용자 클릭 없이 열린다.
- **수정**: `docparse`와 OCR을 DB 키, CDP, 네트워크가 없는 별도 프로세스로 분리하고 구조화된 필드만 돌려받는다. 가능하면 Chromium 렌더러 샌드박스를 쓰는 숨김 창을 쓴다. pdfjs는 `isEvalSupported:false`로 두고 버전을 고정해 자동 감사한다. 파일 감시 대상은 포털 origin에서 시작된 다운로드(Chrome 다운로드 이벤트로 확인)나 사용자가 직접 고른 파일로 한정한다.

### G-5 [낮음] 앱 업데이트 체인: DN 문자열 핀과 동결 공격
- **위치**: D11 §4, R3 §4.2.
- **내용**: electron-updater 6.x는 서명 주체의 DN 문자열과, 같은 서버가 내려주는 `latest.yml`의 sha512만 본다. 업데이트 서버를 장악하면 "업데이트 없음"을 계속 보여 주는 동결 공격은 막지 못한다.
- **수정**: `latest.yml`을 별도 Ed25519 키로 서명하고(만료 포함) 앱에서 검증한다. electron-updater 7.0이 안정화되기 전까지는 자체 구현한다. 발급 CA 핀을 함께 걸고, 업데이트 확인 실패가 N일 이어지면 사용자에게 알린다.

### G-6 [낮음] 개발·지원 산출물과 클립보드로 비밀이 샌다
- **위치**: D13 §3(HAR 녹화), D02 §9(후처리 복사 버튼, 30초 후 비움).
- **내용**: HAR에는 요청 바디, 쿠키, `Set-Cookie`가 담긴다. "비밀 입력 단계 녹화 제외"는 입력 스텝만 빼고, 그 뒤에 오는 로그인 POST(포털 비밀번호, 세션 토큰)는 남긴다. 복사 버튼으로 넣은 값은 30초 뒤 클립보드를 비워도 Windows 클립보드 기록(Win+V)과 클라우드 클립보드에 남는다. guide 변환에서 `secret_fill`이 복사 버튼으로 바뀌는 것을 막는 규칙도 없다.
- **수정**: HAR을 저장하기 전에 인증 경로의 바디, 쿠키, Authorization을 제거하고, HAR은 암호화해 저장한다. 클립보드에 쓸 때 같은 트랜잭션에 `ExcludeClipboardContentFromMonitorProcessing`, `CanIncludeInClipboardHistory=0`, `CanUploadToCloudClipboard=0` 형식을 함께 기록한다(필요하면 네이티브 헬퍼). guide 변환에서 `secret_fill`과 `human:secret`은 복사 버튼으로 만들지 않는다는 검증 규칙을 넣는다.

### G-7 [낮음] 보안 모듈·확장과 공존하는 데서 오는 잔여 위험
- **위치**: 05 §2("보안 모듈: 설치 안내 후 공존"), D03(확장 허용).
- **내용**: 국내 서명·보안 모듈은 원격 코드 실행 취약점이 실제 공격에 쓰인 이력이 있다(예: 2023 MagicLine4NX 관련 국가 배후 공격 경보). 전용 프로필은 확장을 허용하므로, 사용자가 설치한 임의 확장도 비밀번호 칸을 읽을 수 있다. 사용자가 전용 창에서 메일 같은 다른 사이트를 열면 엔진의 CDP가 그 탭에도 닿는다.
- **수정**: 설치 안내는 운영기관 공식 배포처의 최신 버전으로만 하고, KISA 보안 공지 추적을 운영 절차에 넣는다. 전용 프로필의 확장 목록을 점검해 허용 목록 밖의 확장이 있으면 경고한다. 엔진은 자기가 만든 탭에만 붙고, 사용자가 연 탭은 자동화 대상에서 뺀다.

## 유지할 것 (Keep)

- 우리 서버가 포털에 접속하지 않는 로컬 실행 모델, 사용자 IP와 실제 Chrome 사용, 헤드리스·UA 변경·지문 조작·`webdriver` 조작을 하지 않는 것(05 §1, ADR-010). 정책은 강화만 가능하고, `portalMode`는 허락 문서가 있어야 올린다(D12 §4). 차단 신호가 오면 24시간 쿨다운하고, 이중 로그인 상황에서 자동 재로그인을 하지 않는다.
- 정부24는 허락 전 `postprocess`(ADR-011). 데몬 `auto` 보류와 `semi_auto`의 "시작 동의 + 커밋 게이트" 구조(D10 갱신).
- 비밀은 기본으로 저장하지 않는다. 저장할 때 `ConsentRecord`를 남기고, `secret.used` 감사 이벤트를 기록하며, 동등한 "저장 안 함" 선택지를 보여 준다(D05 §2·§9). 같은 사용자 악성코드에 대한 한계를 정직하게 적었다(D05 §7). Hello/Touch ID를 UI 게이트가 아니라 **키 자료 결박**으로 구현하고 대화형·무인 등급을 나눈 것(D05 §7).
- 하네스가 NPKI 개인키를 복호화하거나 서명하지 않고, 가상키패드를 대신 누르지 않는다는 원칙(D05 §4·§6).
- 타이피스트가 키 입력마다 `activeElement`와 `type`을 재확인하고, 타이피스트 대상의 값을 스냅샷에서 제거하는 것(D03 갱신). `commits`·`secretSlot`·`closeAffordance`는 핫픽스 채널로 바꿀 수 없다(D02 v1.1).
- Noise 설계: 페어링은 XXpsk0 + `rs==Sd` 확인, SAS는 **PC에 입력**("일치" 버튼 금지), 앱 내부 스캐너만 사용, QR은 URL이 아닌 바이너리, 룸은 1회용·120초. IK msg1에는 타임스탬프만 싣고, 실패는 응답 없이 버린다. Noise 안에서는 카운터 논스, 밖에서는 XChaCha 랜덤 논스. 서명 입력에 pair_id와 방향을 넣는다(D08 §2·§4~§6).
- 오프라인 큐에는 비밀과 캡차를 넣지 않고, 큐 → **새 챌린지 승인**, 수신 상태 영속, HPKE + 수신자가 포함된 Ed25519 서명(D08 §7).
- 모바일은 RK와 AIK를 갖지 않는다. 계정 인증과 암호 키를 분리하고, 비밀번호에서 키를 만들지 않는다(D08 §3).
- 랜덤 `blob_id`, 평문 해시 대신 키드 HMAC, 국내 리전, 키 우선 삭제 개념(D07 §6. 형식은 D-3대로 고칠 것).
- 게이트웨이: 서버가 정의하는 번들·툴셋, `store:false`, HMAC으로 만든 `safety_identifier`, 컴퓨터 사용 도구 비노출, 읽기 전용 도구, 모델이 어떤 경로로도 비가역 행위를 일으킬 수 없다는 것, Rule of Two(D04 §4·§5, D11 T4).
- 마스킹: 단일 egress 모듈 + import 금지 lint, 공격적 패턴 + 재현율 수용 기준 + CI 코퍼스 회귀, 스크린샷 기본 비전송, 캡차는 모델에 보내지 않음(D01 §3, D06).
- Electron 기본값: contextIsolation, sandbox, nodeIntegration=false, 렌더러 CSP `connect-src 'none'`, 원격 콘텐츠 금지, electron-updater ≥ 6.3.0-alpha.6, 출시 전 서명 DN 고정(D11 §4).
- 해시 체인 감사 로그 + 폰에 앵커하는 서명 체크포인트(끝부분 절단 탐지)(D08 §10). 텔레메트리 허용 필드 + 송신 전 스키마 검증(D12 §1).

## 구현 전 반드시 고칠 것 Top 7

1. **CDP 소유권과 엔진 신뢰 모델 재설계** (A-1, A-2, A-5, A-6, G-4): `--remote-debugging-port`를 폐기한다. 금고가 Chrome 파이프의 단독 소유자가 되고, 엔진에는 토큰으로 보호된 CDP 중계를 준다. 타이핑 구간에는 엔진 명령을 보류하고 `Input.setIgnoreInputEvents`를 쓴다. 엔진이 넘기는 `cdpEndpoint`를 삭제한다. 기동 시 `webdriver===true` 자기 점검. T2와 D08 §11의 문구를 정정한다. PDF·OCR은 권한 없는 프로세스로 분리한다. S6에 "다른 OS 사용자에서 접속 불가" 시험을 넣는다.
2. **원격 봉투 스키마와 비밀 봉인 재정의** (C-1, C-2): 스키마를 CDDL로 다시 쓴다(gate.response의 서명·챌린지·actionHash, seq/ttl/pair_id, 모든 타입 정의, ULID 통일, 청크 규격). 금고 전용 키 `Kv`를 두고, 인증 + AAD 결속 봉인(`vaultChallenge`, origin, secretKind)으로 바꾼다.
3. **모델로 가는 바이트 바로잡기** (B-1, B-2, B-3, B-4, B-6, E-1, E-2): 주민번호 체크섬 배제 폐지, NFKC 정규화, 입력값 기본 거부 + fail-closed 스냅샷, egress 직전 런타임 트립와이어, 누락 패턴 보강. 게이트웨이는 replay에 HMAC 태그, `messages` 역할·형식·크기 제한, 서버 계산 `cacheKey`, 서명된 runId, L1 하드 상한, 계정별 캐시 격리.
4. **비밀 저장 경계와 레지스트리 피해 반경** (A-3, A-4, G-3): 보안카드는 금고 전용 키 또는 칸 단위 키체인으로 옮긴다. 전용 프로필의 비밀번호 저장과 자동완성을 끈다. 금고에 비밀 종류별 origin 허용 목록, 엔진에 포털 도메인 허용 목록을 내장한다. 인덱스·패키지·정책에 단조 버전을 두고, 만료되면 `postprocess`로 돌아간다. 정책 서명키를 분리한다.
5. **폐기·복구·키 회전과 블롭 형식** (C-3, C-4, D-3): 기기 범위 토큰 + 폐기 시 우편함 재발급, 드레인 단계 폐기 검사. PC 분실·문구 유출 시 RK/AIK를 회전하고 폰 승인으로 전환한다. RK는 키체인에 상주시키지 않는다. 블롭은 키 객체 분리, 불변 필드 AAD, blob_id 결속, 패딩으로 바꾼다.
6. **로컬 평문 줄이기** (D-1, D-4, D-5): 보관함 기본 경로를 `%LOCALAPPDATA%`로 옮기고 동기화 폴더를 감지해 경고한다. 파일명에서 PII를 뺀다. 엔진·메인 덤프 업로드를 금지한다. `keep_session` 기본값 0, 종료 시 캐시 정리, tmp를 DB로 옮긴다.
7. **준수 모드의 구멍 막기** (F-1, F-2, F-3, F-4): 후처리 모드는 사용자의 기본 브라우저로 연다(CDP 없음). 캡차 중계를 포털별 정책(`captchaRelay`)으로 묶고 공문에 명시한다. 불허 회신은 `postprocess`로 매핑한다. 키 간격은 고정값으로 하고 "사람 수준" 표현을 모두 걷어낸다.
