# ADR-016 계정 신뢰 앵커(AIK)와 원격 비가역 승인의 하드웨어 키

상태: 채택(SP-1·SP-2 조건부) · 2026-10-28 (하드웨어 키 커버리지는 스파이크 SP-2, 모바일 저장은 SP-1 결과에 조건부, 재감사 E-10·E-11·E-12 반영) · **복구 문구 경로는 ADR-020으로 대체(폰 승인·PASS, 2026-10-30). v2([ADR-029](ADR-029-remote-recovery-data-minimization.md) 결정 1, 2026-11-03): 복구 문구·`K_chk` 경로 삭제, RK·AIK 래핑 사본은 폰·두 번째 PC에만(서버·HSM 사본 없음), PASS는 계정 회복·AIK 폐기 선언까지만이고 백업은 열지 않는다. 아래 본문의 복구 문구 서술은 v2가 우선한다(AUDIT-D N-09)**
근거: 공격표면 감사 C-01·C-02·C-03·C-04·C-05·C-06·C-20·C-21·C-22·C-30(research/AUDIT-C-remote-cloud-sovereignty.md), design/19-attack-surface.md
관련: D08 §1·§3·§4·§6.1·§9, D09 §2·§5·§6·§7, ADR-007

## 맥락
v1.2의 리모트·계정 설계는 "서버가 정직하고 이메일 계정이 안전하다"는 전제에 기대고 있었다.
1. **페어링 신뢰 앵커**: 폰과 PC는 서버가 준 무서명 기기 목록으로 상대를 확인했다. 이메일을 장악한 공격자는 디바이스 플로우로 자기 PC를 등록한 뒤, 피해자에게 그 PC의 QR을 스캔하게 하고 6자리를 피싱 페이지에서 받아 내면 포털 비밀번호·보안카드 칸 값까지 받아 갈 수 있었다. 내부자는 서버 응답만 바꾸면 됐다.
2. **계정 작업**: 기기 추가는 이메일 단일 요소였고, "기기 서명이 있으면 즉시 삭제"는 방금 등록한 기기의 서명으로 우회됐다. 블롭·메타데이터·조회 에이전트는 계정 세션만으로 열렸다.
3. **원격 비가역 승인**: 승인 서명은 소프트웨어 Ed25519였다. 잠금이 풀린 분실 폰이나 탈옥 폰에서 키를 빼면 사용자 명의 세금계산서를 발급할 수 있었고, 밖에 있는 사용자가 PC 없이 막을 방법이 없었다.

## 결정
- **신뢰 앵커는 복구 문구에서 파생되는 계정 신원 키 AIK다.** (v2, ADR-029: AIK는 첫 PC가 무작위로 만들고 복구 문구 파생은 없다.) AIK 개인키는 데스크톱 금고에만 있고 Windows Hello/Touch ID 결박 래핑 키로 암호화하며, 쓸 때마다 사용자 존재를 확인한다(Phase 2, Phase 1은 무인 저장을 잔여 위험으로 둔다). 무인 데몬은 AIK를 쓰지 않는다.
  - 기기 목록의 모든 항목은 AIK 서명 `DeviceListEntry{device_id, role, Sx, Vx, registered_at, list_version}`이다. 서명이 없거나 버전이 낮은 목록은 거부한다.
  - 계정 `AIK_pub`는 첫 데스크톱 설치 때 1회 고정한다. 교체는 옛 AIK 서명 + 7일 지연(`pairing.aikChangeDelayDays = 7`) + 전 기기·이메일 알림.
  - 폰은 서버가 준 `AIK_pub`와 `PAIR_OK`의 `AIK_pub`가 같을 때만 페어링을 진행한다. 등록 24시간 이내 데스크톱은 전면 경고(`pairing.newDesktopWarnHours = 24`). `KEK_N` 전달은 Hello 확인이 있는 별도 단계다. QR·SAS 창은 `setContentProtection`으로 가리고, 폰의 6자리 옆에 "PC 화면에만 입력" 경고를 둔다.
  - 기기 인증서 90일, `deviceListVersion` 불일치 시 비가역 승인·비밀 요청 보류, 30일 미갱신 경고.
- **계정 작업은 AIK로 묶는다.** 즉시 삭제는 AIK 서명만. 7일 미만 기기·계정 세션만의 요청과 1일 10건 초과 대량 삭제는 7일 유예. 새 기기 등록은 AIK 인증 기기 승인 또는 이메일 확인 + 72시간 + 전 기기 알림이며, 패스키 계정은 이메일만으로 추가할 수 없다. 블롭·메타데이터·조회 에이전트는 AIK 인증 기기의 기기 범위 토큰(요청마다 기기 키 서명, DPoP 방식)만 받는다. 데스크톱 로그인은 RFC 8252 루프백 + PKCE이고 디바이스 플로우는 없앴다. 이메일 로그인은 6자리 코드(10분, 5회 잠금)가 기본이다.
- **복구 문구로 복구한 새 기기는 72시간 보류**(v2, ADR-029: 같은 보류·거부·재생성 AIK 서명 거부 규칙을 폰 `Px` 승인 경로와 PASS 경로에 적용한다): 블롭 다운로드와, 그 문구에서 재생성한 AIK의 **어떤 서명**(기기 추가·폐기·삭제·긴급 정지 해제·AIK 교체)도 서버가 받지 않는다. 기존 AIK 인증 기기가 승인하면 즉시 해제한다. 기존 기기가 **거부**하면 서버는 복구 시도를 폐기하고 새 기기 키를 영구 차단하며, 전 기기·이메일에 알리고 사용자에게 새 복구 문구(RK′) 발급 절차를 안내한다(Phase 2, E-11). AIK 교체 7일 지연의 기준 시각은 서명 안의 시각이 아니라 **서버 수신 시각**이다. 문구 입력은 앱 안에서만 받는다.
- **원격 비가역 승인은 하드웨어 키만.** `issue_document`·`send`·`sign`(그리고 `pay`) 효과의 원격 승인은 SE/StrongBox P-256 키 `Px`(사용자 존재)로만 한다. `gate.response.sigAlg`는 비가역 카드에서 `p256` 필수이고, `gate.request.effects`가 필수라 스키마가 이를 강제한다. Android는 등록 시 **Key Attestation 인증서 체인**(StrongBox/TEE, 사용자 인증 필요)을 서버 경유로 받아 PC가 검증하고, 검증 못 한 기기는 비가역 원격 승인을 받지 않는다. iOS는 App Attest로 **앱 무결성만** 확인할 수 있다(E-10). 하드웨어 키가 없는 폰은 조회·캡차·시작 동의만 한다. 정책 `remote` 블록: 원격 비가역 일일 상한 5건, 처음 쓰는 거래처는 PC 로컬 승인, 원격 비가역 시 PC·이메일 알림.
- **계정 웹 '기기 긴급 정지'**: 서버 측 정지만 하고 재활성화는 AIK. 폰 앱은 진입 시 생체 인증, 백그라운드 30초 후 재잠금.
- **모바일 저장**: 모든 키·토큰은 `WHEN_PASSCODE_SET_THIS_DEVICE_ONLY` + `requireAuthentication`, 백업·기기 이전 제외, 재설치 잔존 키 삭제. App Attest·Play Integrity는 신호로만 쓴다.

## 대안
- **서버 기기 목록 신뢰 유지 + 이메일 2차 확인 강화**: 이메일 2차 확인은 로그인과 같은 요소라 추가 요소가 아니고, 내부자 변형을 막지 못한다. 기각.
- **서버 지분을 섞는 키 유도(2SKD 변형)**: "문구만 훔친 사람"을 막지만 계정 서버를 신뢰 경로에 넣는다. 별도 ADR 검토 후보로 남긴다.
- **소프트웨어 Ed25519 승인 유지 + 앱 무결성 검사**: 탈옥·백업 복원 폰에서 키 추출을 막지 못한다. 기각.
- **비가역 원격 승인 전면 금지**: 안전하지만 "밖에서 폰으로 발급 승인"이라는 핵심 사용 사례를 없앤다. 하드웨어 키 + 상한 + 새 거래처 제한으로 대신한다.

## 결과
- 하드웨어 키가 없는 폰 사용자는 비가역 승인을 PC에서 해야 한다. 국내 기기 커버리지가 90% 미만이면 미지원 기기 UX를 확정한다(SP-2).
- 계정 탈취자(이메일 장악)는 기기 목록에 서명할 수 없으므로 원격 페어링 피싱·즉시 삭제·메타데이터 열람 경로가 닫힌다. 남는 것은 계정 세션 권한(구독·기기 관리 화면·긴급 정지 오남용)이다.
- 잔여 위험(TOFU, E-12): 새 폰은 **첫 페어링마다** 서버가 준 `AIK_pub` 외에 독립 앵커가 없다. 서버(내부자)와 공격자 PC가 공모해 같은 가짜 `AIK_pub`를 주면 `PAIR_OK` 대조로도 막지 못한다. 계정 키 투명성은 Phase 3 후보다. PC 자체가 침해되어 AIK가 사용자 존재 확인 중에 악용되는 경우는 D05 §1의 범위다.
- 잔여 위험(v2에서는 PASS 경로, ADR-029. PASS 범위는 보류이며 아래는 잠정안): PASS로는 계정만 되찾고 백업은 열지 못한다. 연결된 기기가 0대이고 72시간·7일 안에 거부하지 못하면 공격자가 새 AIK를 등록할 수 있다. 아래 v1 문장은 기록으로 남긴다. 잔여 위험(복구 문구, E-11): 문구 = 계정 신원이므로 문구 보유자는 결국 AIK를 만들 수 있다. 기존 기기의 거부권과 알림이 유일한 방어이며, 기존 기기가 없거나 72시간 안에 거부하지 못하면 막지 못한다.
- 잔여 위험(하드웨어 키 증명, E-10): iOS에는 Secure Enclave 키 생성 자체를 증명하는 수단이 없어, 변조 앱이 소프트웨어 P-256 키를 `Px`로 신고하면 PC가 구별하지 못한다. Android도 키 증명 체인을 검증하기 전(구형 기기·TEE 미지원)에는 같다.
- 새 기기 추가 지연(72시간)과 복구 보류(72시간)는 정상 사용자에게도 불편이다. 기존 AIK 인증 기기의 승인으로 즉시 해제하는 경로를 온보딩에서 안내한다.
