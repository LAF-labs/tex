# ADR-014 docparse 렌더러 샌드박스 격리와 main 승인 창 기반 로컬 비가역 승인

상태: 채택(S13b 조건부) · 2026-10-28 (docparse 성능은 스파이크 S13b 결과에 조건부, 승인 입력은 재감사 E-06 반영) · **§2(main 승인 창)는 ADR-020으로 대체(2026-10-30), 로컬 승인 근거는 ADR-021(main 소유 승인 바, 2026-10-31)** · docparse 창 `disableDialogs: true`와 공용 하드닝은 [ADR-022](ADR-022-poc3-real-account-safety-baseline.md) 결정 8(2026-11-03, AUDIT-D N-68)
근거: 공격표면 감사 A-14, A-15(research/AUDIT-A-local-desktop.md), A/C-06, design/19-attack-surface.md

## 맥락
두 곳에서 "권한 없음"·"main이 검증"이라는 문서 서술이 OS·프로세스 수준으로 뒷받침되지 않았다.
1. **docparse**: 악성 PDF를 여는 프로세스가 Electron `utilityProcess`였다. utilityProcess는 Node가 켜진 무샌드박스 사용자 권한 프로세스이므로, pdf.js 계열 취약점으로 코드가 실행되면 DB 파일과 키체인(같은 사용자는 조용히 읽을 수 있다)에 닿는다. 사실상 같은 사용자 악성코드와 같다. 게다가 후처리 모드가 다운로드 폴더의 새 PDF를 자동으로 파싱해, 사용자 클릭 없이 열리는 경로였다.
2. **로컬 비가역 승인**: 데스크톱에서 커밋 게이트를 승인할 때 main은 렌더러가 보고하는 `isTrusted`와 렌더러가 계산한 카드 해시를 검증했다. 제3자 텍스트(거래처 상호, 포털 오류 문구, 그것을 반영한 모델 대화 응답)를 표시하는 렌더러가 침해되면, 렌더러는 올바른 값을 **보고만** 하고 실제로는 다른 내용을 보여 주거나 승인을 자동으로 누를 수 있다. 결과는 비가역 발급이다.

## 결정

### 1. docparse는 Chromium 렌더러 샌드박스에서 돈다
- 숨김 `BrowserWindow`: `sandbox:true`, `contextIsolation:true`, `nodeIntegration:false`, `devTools:false`.
- 전용 `session` 파티션: 모든 네트워크 요청 취소, 권한 요청·확인 전부 거부, 탐색·새 창 거부.
- preload는 MessagePort 수신 하나만 노출한다. 그 안에서 pdf.js와 tesseract.js(wasm)가 돈다.
- 입력은 main이 읽은 **바이트**(파일 핸들·경로 아님), 출력은 main이 JSON Schema로 검증한 `{text, pages, hasTextLayer}`(또는 인증서 `{subject, issuer, notBefore, notAfter}`)뿐이다. 스키마 밖 출력은 버린다.
- pdf.js `isEvalSupported:false`, 버전 고정, 월 1회 공지 점검. 작업마다 새 창, 끝나면 파기. 처리 시간·메모리 상한 초과 시 파기.
- 같은 샌드박스에서 NPKI `signCert.der`(공개 인증서)를 파싱한다(D05 §6).
- **자동 파싱 축소**: 자동 파싱 대상은 staging(금고가 정한 다운로드·인쇄 경로)과 사용자가 고른 파일뿐이다. 다운로드·인쇄·사용자 지정 폴더는 "작업 시작 후 생성 + 사용자 확인" 후보만 만든다(D17 §1.3).

### 2. 로컬 비가역 승인은 main이 만드는 별도 승인 창에서만 한다
- 일반 렌더러(대화창·카드 화면)의 승인 신호는 **'승인 창 열기' 요청일 뿐**이다. 그 신호로는 어떤 게이트도 통과하지 않는다.
- main은 엔진에서 받은 **신뢰 계획값(readback 값)**으로 승인 창의 정적 HTML을 직접 만든다. 텍스트는 `textContent`로만 넣고, 스크립트는 없다. CSP는 `default-src 'none'; style-src 'self'`. 창은 `sandbox:true`, preload 없음, 탐색·새 창·권한 요청 거부, `devTools:false`.
- 승인 입력은 main이 그 창(`BrowserWindow`)의 입력 이벤트로 **직접 관찰한 마우스 클릭**으로 인정한다(E-06). Electron에서 main이 클릭을 관찰하는 수단은 M4-2 착수 전에 확인하고, 불가하면 `before-input-event`로 관찰한 **비타이핑 조합키**(예: Alt+Y)만 인정한다. **Enter 단독 승인은 금지**한다(대화창에 입력하던 Enter가 승인이 되는 사고 방지).
- 승인 창은 **포커스를 빼앗지 않는다**(작업 표시줄 표시만, 사용자가 창으로 이동). 창이 표시·활성화된 뒤 **600ms** 동안의 입력은 무시한다. 렌더러가 보고하는 `isTrusted`·카드 해시는 승인 근거가 아니다.
- 원격 승인의 폴백(하드웨어 키 없는 폰, 처음 쓰는 거래처, 원격 일일 상한)으로 로컬 승인이 필요해지면 PC 승인 창은 **자동으로 뜨지 않고** 실행은 "PC에서 승인 필요" 상태로 대기한다. 사용자가 PC 앞에서 승인 창을 연다(무인 PC에서 지나가는 사람·원격 지원 세션이 승인하는 것을 막기 위해).
- 승인되면 main은 `LocalApproval{runId, gateStepId, actionHash, exp}`를 발급한다. 서명 키는 기동 시 main↔금고 사이에 교환한 키다. Phase 2에 커밋 가드가 금고로 옮겨 가면(D05 §3.3, 감사 A A-03) 금고가 이 값을 직접 검증한다.
- **선택 옵션(설정)**: 비가역 승인에 Windows Hello `UserConsentVerifier` 확인을 추가로 요구할 수 있다. 기본은 꺼짐이다.
- 승인 창의 표시 문자열(라벨·카드 템플릿)은 앱 내장 문자열이고, 서명 패키지에서 온 문자열을 템플릿으로 쓰지 않는다.

### 3. 대화창의 모델 출력은 sanitizer를 거친다
- 대화창의 모델 출력 렌더는 마크다운 → 허용 태그 화이트리스트 sanitizer 순서로 하고, **원시 HTML은 금지**한다. 링크는 표시만 하고 열지 않으며, 여는 동작은 main의 키 기반 `openExternal` 규칙(D17 §1.1)을 따른다.
- Terra 출력 중 사용자에게 보이는 것은 구조화 슬롯뿐이다(D04 §4). 이 sanitizer는 그 규칙이 깨졌을 때의 2차 방어다.

## 조건(스파이크)
- S13b: pdf.js + tesseract.js(wasm)를 샌드박스된 숨김 렌더러에서 돌릴 때 한글 추출률·처리 시간·메모리. 기준에 못 미치면 대안 (b)를 비교한다.

## 대안
- (a) 기각 — utilityProcess 유지 + "코드상 접근 없음": OS 경계가 아니다. 같은 사용자 권한으로 DB·키체인에 닿는다.
- (b) 보류 — 별도 실행 파일을 AppContainer 또는 Low IL 제한 토큰으로 기동: 경계는 더 강하지만 Electron 밖 빌드·서명·배포가 늘어난다. S13b 결과가 나쁘거나 Phase 3 엔진 격리(ADR-005 대안의 고수준 브로커)와 함께 검토한다.
- (c) 기각 — 렌더러 `isTrusted` + 카드 렌더 해시를 main이 검증: main은 렌더러가 보고한 값을 검증할 수단이 없다.
- (d) 기각 — 모든 비가역 승인을 폰으로만: 로컬 사용 흐름이 끊긴다. 폰 승인은 그대로 두고, 로컬 승인 경로를 승인 창으로 좁힌다.

## 결과
- 무클릭 PDF 경로가 사라지고, docparse 침해가 키체인·DB·네트워크로 이어지지 않는다(같은 사용자 악성코드에 대한 의미 있는 완화 중 하나, D05 §1).
- 렌더러가 침해되어도 비가역 승인은 main이 만든 창의 실제 입력 없이는 일어나지 않는다. 다만 엔진이 침해된 경우 엔진이 main에 주는 계획값 자체가 오염될 수 있으므로, 이 결정은 렌더러 침해(R)에 대한 것이고 엔진 침해(E)에 대해서는 폰 승인·`verify` 조회·커밋 가드(R-C1 금고 대조, Phase 2 무장 근거 금고 검증)에 기댄다.
- **합성 OS 입력은 실제 입력과 구분되지 않는다.** 같은 사용자 권한의 악성코드(M)나 침해된 엔진(E)이 `SendInput`으로 보내는 클릭·키는 막지 못하므로 M·E에 대해서는 경계가 아니다. PC 앞에 있는 제3자도 승인할 수 있다(선택 옵션 Windows Hello 확인을 켜지 않은 경우).
- M1-8(docparse)에 +2일, M4-2(로컬 승인)에 +2일(승인 창)이 더해진다(D14).
- D01 §2·§3, D11 §4, D03 §3, D17 §3의 서술은 이 ADR을 따른다.
