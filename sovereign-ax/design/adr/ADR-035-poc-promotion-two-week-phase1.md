# ADR-035. PoC 코드를 Phase 1 기반으로 승격, 2주 병렬 개발, 출시 게이트 재정의

## 맥락

### 왜 폐기 전제였나

- ADR-017(2026-10-28)은 1개월 안에 수요검증과 기술 검증을 끝내려고 PoC를 4주(10-29~11-26)로 잡았다. 속도를 위해 PoC 코드는 스파이크 코드와 같은 지위(폐기 전제)로 두고, 나중에 끼워 넣는 비용이 가장 큰 셋(금고 경계·커밋 게이트·원장)만 설계대로 넣었다(ADR-017 결정 4).
- G1은 PoC-12(11-27)에서 06 §5의 Go 조건으로 판정하고, 통과해야 Phase 1 제품 코드를 쓰기 시작하는 착수 게이트였다(ADR-017 결정 7, 04 §1). 보드 프로젝트 규칙 3이 이것을 "G1 전 제품 코드 금지"로 적었다.

### 무엇이 바뀌었나

- **PoC 코드가 설계를 따르는 코드가 됐다.** `poc/` src 14,345줄 중 ADR-017 결정 4의 셋(vault 2,174 + gate.ts 221 + runs.ts 426 + db 780)이 3,601줄(25%)이다(RETRO B-05). AUDIT-D 확정 53건(High 3·Medium 33·Low 17, 그중 PoC-3 전 16건) 가운데 48건을 ADR-025~029가 처리했고(adr/README, D19 §3.5), PoC-3 전 항목은 PR #23에서 코드에 들어갔다. 버리고 다시 쓰면 감사가 확인한 통제와 그 시험을 다시 만들어야 한다.
- **G1 조건은 코드만으로 판정할 수 없다.** 11-02 회고 시점에 G1 조건 5개 중 측정된 것은 0이었다(RETRO 요약, B-06). 그 뒤 PoC-3은 맥 사전 관찰(실발급 0건, 발급 화면 입력·제출 0건)까지 했다(PoC-3-mac 결과 한 줄). S8 50회 실측은 하지 않았고, 하루 40회·세션 15회 상한 때문에 하루에 끝나지도 않는다(PoC-10 §1). 남은 조건은 실계정·인증수단·Windows 실기기·사람 일정에 묶여 있다. 코드 착수를 그 일정에 묶으면 코드는 이유 없이 기다린다.
- **공수와 인력이 맞지 않는다.** Phase 1 공수는 약 247일(폰 승인 M7-7을 넣으면 약 254일)이고 3인 × 12주(180일)를 약 67~74일 넘는다(D14 §2.7, 04 R-18). R-18은 G1에서 17주(3인) 또는 13주(4인)를 고르라고 했다.
- **2026-11-05 yulmu 결정**: PoC 코드를 Phase 1 기반으로 승격하고, 오케스트레이션 세션(팀장)이 트랙별 Opus 세션을 병렬로 돌려 2주(2026-11-19)까지 Phase 1 완료를 목표로 한다.

## 결정

### 1. PoC 코드를 Phase 1 기반으로 승격한다. 승격은 패키지 단위이고, 조건을 통과한 패키지만 "Phase 1 코드"다

1. `poc/`의 패키지와 앱을 Phase 1 코드의 출발점으로 쓴다. 새로 쓰지 않는다. ADR-017 결정 4의 "폐기 전제"는 이 결정으로 대체한다.
2. **폐기 전제 부분을 먼저 식별한다.** 위 표 W-1~W-11이 1차 목록이다. 트랙은 자기 패키지에서 더 찾으면 표에 더한다(이 ADR 개정 또는 decisions.tsv 행). 정리 전의 파일은 첫 줄에 `// PoC 폐기 대상`을 단다(RETRO B-05 초안).
3. **승격 조건**(패키지마다 모두 충족):
   - (가) **AUDIT-D 확정 통제가 코드에 있다.** D19 §3.5에서 단계가 PoC인 16건과 그 패키지에 배정된 P1 건의 통제가 코드에 있고, 통제마다 그것을 이름으로 가리키는 동작 시험이 있다. 소스를 grep하는 시험은 통제의 증거로 세지 않는다(RETRO B-11). PR 본문에 "D-xx → 시험 이름" 표를 둔다(제안).
   - (나) **시험이 녹색이다.** build·lint·test가 macOS와 Windows에서 통과한다. CI(M1-1, RETRO B-01)가 들어온 뒤에는 CI 기준이다. 건너뛴 시험은 이유와 함께 PR 본문에 적는다(RETRO 머리말 기준선: 282건 중 1 실패·5 건너뜀).
   - (다) **금고 경계가 유지된다.** 비밀은 금고 프로세스 밖으로 나가지 않는다(D05). 단일 송신·비밀 직렬화 금지 린트(M1-1)가 그 패키지에 걸려 있고, 누출 스캐너가 0건이다(06 §5 S6 기준).
   - (라) **폐기 표지가 없다.** 승격된 파일에 `// PoC 폐기 대상` 표지가 없고, 표지가 남은 파일은 Phase 1 빌드가 import하지 않는다(린트로 집행, 제안).
4. 조건을 통과하기 전의 패키지도 쓸 수 있지만, 실계정 시험은 ADR-025의 PoC 상한(하루 실행 20·실발급 1·누적 3) 안에서만 한다.

### 2. 2주 병렬 개발: 트랙과 파일 경계, 조정은 팀장 경유

1. 기간은 2026-11-05~11-19(영업일 11일)이다. 이 기간의 목표는 결정 3의 **통합 판정**이다. 출시 판정이 아니다.
2. **1차 트랙과 파일 경계**(공수는 D14 엔지니어 1인 영업일 가설, 결정 4 참고):

| 트랙 | 소유 경로 | M 항목 | D14 공수 |
|---|---|---|---|
| 엔진 | `packages/engine` | M1-4, M2-1~M2-5 | 44일(15+5+5+9+6+4) |
| 금고 | `packages/vault` | M1-3 | 11일 |
| 데스크톱 | `apps/desktop` | M4-1~M4-4, M6-16 | 28일(4+12+4+5+3) |

| 클라우드 | 새 `services/*` | M4-5~M4-7, M7-3 | 26일(8+6+7+5) |

| **합계** | | | **172일** |

   1차 172일 + 2차(결정 5) 74일 + 사람 실측 M6-0 1일 = 247일이며 D14 §2.7의 합계와 같다. 폰 승인 M7-7(7일)은 제안이라 어느 배분에도 넣지 않았다.
3. **트랙은 자기 소유 경로만 고친다.** 다른 트랙의 파일이 필요하면 팀장에게 요청하고, 팀장이 소유 트랙에 배정한다(보드 규칙 5).
4. **트랙 사이 계약은 소유 트랙만 바꾼다.** 계약은 패키지 공개 타입, IPC 메시지(`ipc/*.schema.json`), DB 스키마(D07), 원격 메시지(D08), 설계 스키마(`design/schemas/`)다. 계약을 바꾸려면 팀장에게 먼저 알리고, 팀장이 보드에 공지한다(보드 규칙 4 "트랙 간 인터페이스 변경"). (제안) 계약 변경은 코드와 다른 작은 PR로 먼저 머지하고, 쓰는 쪽 트랙은 그 뒤에 따라간다. 공유 파일(`pnpm-lock.yaml`, `pnpm-workspace.yaml`, `tsconfig.base.json`, `eslint.config.mjs`)도 팀장 경유다.
5. **PR은 작게.** 패키지당 PR 하나를 상한으로 하고, 코드+시험 / 보고서+원자료 / 스크린샷을 나눈다(RETRO B-15). PR 본문에 Windows 실행 해시 칸을 둔다(RETRO B-07). Bugbot에 대응한 뒤 review로 올린다. 머지는 yulmu가 한다.
6. 설계를 바꾸는 구현은 ADR로 남긴다(보드 규칙 3). 절대 규칙(정부24 자동화 금지, 캡차 자동 해결·탐지 회피 금지, 비밀은 금고 밖으로 안 나감, 승인 없는 비가역 실행 없음)은 이 ADR이 완화하지 않는다. D14 §4 원칙 1(비밀 경계 M1-3과 정적 검증기 M1-4가 다른 무엇보다 먼저)은 병렬이어도 유지한다. 다른 트랙은 그 둘의 계약에 대고 시험 대역으로 먼저 만든다.

### 3. G1을 "11-27 PoC-12 판정"에서 "Phase 1 통합 시점의 출시 게이트"로 바꾼다

1. **G1은 더 이상 제품 코드 착수 조건이 아니다.** 제품 코드는 2026-11-05부터 쓴다. G1을 두 단계로 나눈다.
   - **G1-a 통합 판정**(2026-11-19 목표): 아래 표의 "코드로 닫는 부분"과 결정 1의 승격 조건. 통과하면 "Phase 1 통합(코드)"이라고 부른다. 출시 가능이라고 부르지 않는다.
   - **G1-b 출시 판정**(M5-2 라이브 검증 뒤, 베타 초대 M5-3 전, 날짜는 실측 일정이 정한다): 표의 "실측이 필요한 부분" + 대외 조건 + 지불의사. 06 §5의 중단·피벗 기준 K1~K4도 이때 판정한다.
2. **06 §5 Go 조건을 둘로 나눈다.** 팀장 지시는 S6·S7·S8을 코드로, S1 자동 구간·S1a·S1b·S16을 실측으로 나누는 것이다. S7과 S8은 기준 자체가 실화면·실호출이라 코드로 닫는 부분과 실측 부분이 함께 있다. 아래 표처럼 나눈다(S7·S8을 쪼갠 것은 제안).

3. S3(정부24 수동 실측)는 ADR-017 결정 7대로 출시 조건이 아니고 정부24 후처리 착수 전 조건이다.
4. **PoC 태스크의 남은 일은 이렇게 옮긴다.** 코드 작업은 해당 M 항목으로 흡수한다. 실측(PoC-3 S1·S1a·S1b·S2, PoC-6 실발급, PoC-8 S16, PoC-10 S8 50회)은 M5-2 라이브 검증으로 옮긴다. PoC-11 인터뷰는 사람 일 그대로다. PoC-12의 "설계 v1.4"는 G1-a 산출물이 되고, "G1 판정"은 G1-a·G1-b로 나뉜다.

### 4. 공수 247~254일과 2주의 간극을 숨기지 않는다

1. D14의 공수는 "엔지니어 1인 기준 영업일(가설)"이다(D14 머리말). 2주 동안 에이전트 세션 여러 개가 병렬로 일하는 것과 같은 단위가 아니다. 그래서 D14 공수는 **범위의 상대 크기와 순서**를 재는 데 쓰고(이름: 에이전트 병렬 공수의 기준량), 달력 일정은 트랙별 세션 병렬로 잡는다.
2. **이 재정의는 2주 완료의 근거가 아니다.** 에이전트 세션의 처리량을 D14 공수로 바꾸는 환산 계수는 없다. 참고할 실적은 PoC다. PoC-1~10이 PR #1~#17(2026-10-28~11-02)로 src 14,345줄을 만들었다(RETRO 머리말·B-05). 그러나 이 실적에는 CI가 없었고 Windows에서 돌지 않은 PR이 4,500줄 이상이었다(RETRO 요약). 그대로 늘려 잡지 않는다.
3. (제안) 2026-11-12에 중간 점검을 한다. 트랙별로 머지된 M 항목의 D14 공수 합을 세어 남은 범위를 본다. 모자라면 R-18이 이미 정한 순서로 뒤로 미룬다: 폰 승인 M7-7, 근무표 M6-15, M6-7·M6-14, M4-4 설정 화면 일부. 코어 출시 조건(ADR-018)은 줄이지 않는다.
4. **사람이 해야 하는 일은 2주 밖이다.** 2주 목표에 넣지 않고, 끝났다고 말하지 않는다.
