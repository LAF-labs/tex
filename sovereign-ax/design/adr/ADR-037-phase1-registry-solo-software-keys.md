# ADR-037. Phase 1 레지스트리 서명 키 단독 보유·소프트웨어 키 모드

> 상태: 채택(사용자 결정 2026-11-06, 팀장 지시로 문서화. 2026-11-06 개정: 조건 확인됨, 호스팅·로그 쓰기 권한 분리 없음과 완화 (가)~(다) 추가) · Phase 1 한정. Phase 1 동안 D09 §8.2의 키 보관·보유자 규칙을 대신한다. 서명 형식(SIGNING.md)과 클라이언트 검증 규칙은 그대로다.
> 관련: [ADR-013](ADR-013-registry-threshold-signing-transparency.md), [ADR-028](ADR-028-supply-chain-update-signing-roles.md), D09 §8.2·§8.3·§8.4·§8.5, [schemas/SIGNING.md](../schemas/SIGNING.md), D19 B-22·C-27·§8

## 맥락

- D09 §8.2는 레지스트리 서명 키를 이렇게 둔다.
  - 오프라인 루트: 2-of-3, HSM 또는 스마트카드.
  - 패키지·정책: 각 키 3개, 2-of-3. 서로 다른 사람이 하드웨어 슬롯을 하나씩 갖는다.
  - 타임스탬프: 서버 HSM.
  - 1인 긴급: 스마트카드.
  - 앱 릴리스 매니페스트: 하드웨어 토큰, 비운영자 1인.
- 2인 승인은 하드웨어 쿼럼으로 강제한다(ADR-013, ADR-028).
- Phase 1에는 키를 나눠 가질 사람이 사용자 1인뿐이다. 하드웨어 토큰·HSM도 아직 고르지 않았다(SP-4).
- 하지만 앱은 지금부터 루트·패키지·정책 키를 핀 고정하고, 서로 다른 핀 키 서명 2개를 요구한다(D09 §8.2, SIGNING.md §3). 형식을 지금 바꾸면 나중에 되돌릴 때 클라이언트 검증 코드가 다시 바뀐다.

## 결정

1. **Phase 1에는 사용자 1인이 모든 서명 키를 갖는다.** 대상은 루트·패키지·정책·긴급·릴리스 키다. 하드웨어 토큰은 쓰지 않는다.
2. **2-of-3 형식은 유지한다.**
   - 산출물은 `signatures[]`를 갖고, 클라이언트는 서로 다른 핀 키의 유효 서명 2개 이상을 요구한다(D09 §8.2, SIGNING.md §3).
   - 그래서 2-of-3 역할(루트·패키지·정책)은 역할마다 키 3개를 따로 만든다.
   - 긴급 키 1개, 릴리스 키 1개는 지금 규칙대로다.
   - 역할 사이에 키를 다시 쓰지 않는다.
3. **보관**
   - 키는 macOS 키체인에 둔다. 서명할 때마다 Touch ID를 받는다.
   - 디스크에 평문 키를 두지 않는다.
   - 강한 암호로 잠근 오프라인 백업 1개를 둔다.
   - 타임스탬프 키는 서버 비밀값으로 둔다(서버 HSM 대신). 하는 일은 D09 §8.2·§8.4 그대로다: 신선도 재서명, 트리 헤드.
4. **잃는 성질(정직하게 적는다)**
   - 2인 승인이 없다. 2-of-3 서명은 형식일 뿐이다. 같은 사람·같은 장치가 키 3개를 다 가지므로 한 사람의 실수나 강요를 막지 못한다.
   - 단일 장치 또는 비밀번호가 침해되면 전체를 위조할 수 있다. 대상은 패키지·핫픽스·정책·`status.json`·루트 목록(`keyEpoch`)·`revoked_keys.json`·앱 릴리스다. 그 Mac이나 오프라인 백업의 암호 하나로 충분하다.
   - 키가 소프트웨어 키다. Ed25519 키는 하드웨어 안에서 서명되지 않는다. 서명하는 동안 서명 프로세스 메모리에 풀린다. 그 시점의 같은 사용자 악성코드는 키를 읽을 수 있다. 참고로 macOS Secure Enclave는 P-256만 지원하므로 Ed25519 키를 그 안에 둘 수 없다.
   - **호스팅·로그 쓰기 권한과 서명 키가 분리되지 않는다.** 같은 1인이 Supabase·Vercel·레지스트리 게시 관문·로그 DB를 운영한다(조건 절, 확인됨). D09 §8.2의 "레지스트리 호스팅·CDN·투명성 로그·미러의 쓰기 권한자는 서명 키를 갖지 않는다"를 Phase 1에는 지키지 못한다.
   - **완화**
     - (가) 클라이언트가 로그 일관성 증명을 검증한다. 그래서 서버는 클라이언트가 이미 본 트리 헤드를 몰래 고쳐 쓰지 못한다. 이미 구현되어 있다(엔진 `verifyConsistency`, SIGNING.md §9, D09 §8.3).
     - (나) 서명 1건마다 로그 항목을 대조한다. 서명 도구가 남긴 서명 기록과 투명성 로그 항목을 맞춰 본다. 기록에 없는 로그 항목은 키 침해로 다룬다(D09 §8.2 "사용 감사"를 이 방식으로 한다).
     - (다) 승격 때(결정 5) 호스팅 권한자와 서명 보유자를 처음으로 분리한다.
     - 그 밖에 투명성 로그를 감시한다(D09 §8.3). 미러 헤드 비교와 포함 증명은 그대로 한다.
     - 클라이언트 쪽 상한은 패키지가 바꿀 수 없다: 버전 `+1000`, 정책 신선도 72시간, eTLD+1·origin 허용 목록(D09 §8.4).
5. **승격 경로**(사람이 늘거나 하드웨어를 들일 때)
   - 새 보유자는 자기 키를 **새로 만든다**. 기존 키를 복사하지 않는다.
   - 기존 루트 키로 `keyEpoch + 1` 키 목록에 서명한다.
   - 앱 업데이트로 그 목록을 고정한다. 이 릴리스는 ADR-028 결정 3에 따라 2-of-3 서명을 로그 항목에 동봉한다.
   - 그 뒤 이전 키를 `revoked_keys.json`에 올린다.
   - 하드웨어 토큰(스마트카드·HSM)은 이때 들인다. 장치 선정은 SP-4다.

## 대안과 기각 이유

- **Phase 1에 1-of-1 형식으로 바꾸기**: 키는 줄지만 클라이언트 검증 규칙과 SIGNING.md가 바뀐다. 승격할 때 다시 바뀐다. 형식을 지키는 비용(키 11개 관리)이 더 작다.
- **처음부터 하드웨어 토큰**: 장치 선정(SP-4)이 끝나지 않았다. 1인이 토큰 여러 개를 갖는 것도 2인 승인을 주지 않는다.
- **클라우드 KMS**: D09 §8.2가 이미 기각했다. 공급사 의존과 Ed25519 미지원 때문이다.

## 영향

- D09 §8.2 표의 보관·보유자 열은 Phase 1에 이 ADR이 대신한다. 역할·쿼럼 수·검증 규칙은 그대로다.
- 1인 긴급 키 산출물을 "다른 키 보유자에게 자동 알린다"(D09 §8.5)는 Phase 1에 받을 사람이 없다. 투명성 로그 감시가 그 자리를 대신한다.
- D19 §8 잔여 위험에 이 모드를 적는다. B-22·C-27의 Phase 1 상태는 "형식만 2-of-3"이다.

## 조건

- Phase 1이 끝나기 전, 또는 키 보유자가 늘어나는 즉시 결정 5로 승격한다.
- **확인됨**(팀장 답, 2026-11-06): 레지스트리 호스팅·CDN·투명성 로그의 쓰기 권한자도 같은 1인이다. 사용자가 Supabase·Vercel·레지스트리 게시 관문·로그 DB를 모두 운영한다. 그래서 D09 §8.2의 "쓰기 권한자는 서명 키를 갖지 않는다"는 Phase 1에 지켜지지 않는다. 잃는 성질과 완화 (가)~(다)는 결정 4에 있다. 분리는 결정 5 승격 때 처음 한다.
