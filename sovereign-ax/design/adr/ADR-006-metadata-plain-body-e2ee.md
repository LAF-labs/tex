# ADR-006 메타데이터 평문 최소 + 본문 E2EE 분리

상태: 채택 · 2026-10-28 · 개정 메모 v1.3(아래) · **KEK·복구 문장은 ADR-016 v2([ADR-029](ADR-029-remote-recovery-data-minimization.md) 결정 1, 2026-11-03)가 우선한다: 복구 문구는 없고, KEK는 기기에서 만들어 폰·두 번째 PC에만 E2EE 사본을 둔다. 백업은 연결된 기기로만 되찾고, 무지식 원칙(서버는 KEK를 모른다)은 그대로다(AUDIT-D N-09)**

## 맥락
"PC가 꺼져 있어도 '납세증명 언제 만료돼?'에 답한다"는 요구와 "서류 본문은 우리 서버도 못 본다"는 요구를 동시에 만족해야 한다.

## 결정
- 서버는 문서 **메타데이터**만 평문으로 보관한다. v1.3부터 그 범위는 서버 색인을 켠 종류의 `doc_type` 열거값, **발급 월**, 만료일, 그리고 키 객체(wDEK)·`rev`·서명이다(D07 §5). ~~크기, 발급일, HMAC dedup 토큰~~은 v1.3에서 삭제했다(아래 개정 메모). 상호·사업자번호·금액·파일명은 받지 않는다(스키마가 거부).
- 본문 PDF는 클라이언트에서 파일별 DEK로 암호화하고 DEK는 사용자 KEK로 봉인한다. KEK는 복구 문구에서 파생되며 서버는 모른다.
- 조회 에이전트는 메타데이터만으로 답하고, 본문이 필요하면 폰에서 복호화한다. 메타데이터 행은 모델로 보내지 않는다(D09 §7).

## 대안
- 전부 E2EE: 조회 에이전트가 불가능하거나 폰이 항상 켜져 있어야 한다.
- 서버가 본문 보관(서버 측 암호화): 침해 시 전부 노출, 모토와 충돌.

## 결과
- 복구 문구 분실 = 백업 복구 불가. 온보딩에서 강하게 안내하고 기존 기기 승인으로 KEK 공유 경로를 둔다.
- 메타데이터만으로 답할 수 없는 질문은 솔직히 "폰에서 열어 보세요"로 답한다. 색인을 끈 종류는 "PC가 켜져 있을 때 물어보세요"로 답한다.

## 개정 메모 (v1.3, 공격표면 감사 반영)

- **정보량 계산 원칙** (감사 C C-09): 서버 평문 필드는 "그 필드가 없으면 답할 수 없는 질문"이 있을 때만 둔다. 필드마다 답하는 질문과 그 필드로 추론되는 것을 같이 적고, 추론 위험이 질문의 가치보다 크면 필드를 빼거나 거칠게 만든다(일 → 월, 정확한 크기 → 패딩).

  | 필드 | 답하는 질문 | 추론되는 것 | v1.3 처리 |
  |---|---|---|---|
  | `doc_type` | "납세증명 있어?", "몇 종류 갖고 있어?" | 세대·고용·부동산·체납 정황(종류별) | 종류별 서버 색인 설정(2026-11-02 용어 정리: 기본값이 켬인 종류가 있으므로 '옵트인'이라 부르지 않는다). 기본 켬: 만료 추적 대상 4종(`national_tax_cert`, `localtax_cert`, `sme_cert`, `biz_registration_cert`), 나머지 기본 끔. 꺼진 종류는 인덱스 행 없음 |
  | 발급일 | "가장 최근 발급은?" | 사용 시각·생활 사건 연표 | **월 단위**(`issued_month`) |
  | 만료일 | "언제 만료돼?" | 갱신 리듬 | 유지(핵심 기능) |
  | 크기(`bytes`) | 없음 | 세대원 수(등본 쪽수), 품목 행 수 | **삭제**, 블롭은 Padmé 패딩 |
  | 갱신 시각(`client_updated_at`) | 없음(동기화용) | 초 단위 사용 시각 | **삭제**, 충돌은 `rev`로 |
  | dedup 토큰 | 없음(중복 업로드 절감) | 키 유출 시 "이 파일 갖고 있나" 확인, 저엔트로피 대입 | **삭제**, 중복 판단은 로컬 `sha256 → blob_id` |
  | `profile_slot` 번호 | 없음 | 슬롯 2 = 사업자 | 계정별 무작위 `slot_token`으로 교체. 단 사업자 프로필 HMAC(B-28)이 있으면 '사업자 보유'는 안다고 공개 |

- **dedup 삭제** (C-13): 서버 `dedup_token`을 없앴다. `K_idx`는 남기되 용도를 업무 키 표시 HMAC(`"SAX-bizkey-v1"`, B-30)과 프로필 사업자 HMAC(`"SAX-bizno-v1"`, B-28)으로 바꿨다(D08 §3).
- **레코드 서명 `Sign_Vd`** (C-12): 대칭 `K_meta`를 없애고 데스크톱 `Vd` 서명 + 문서별 단조 `rev`로 바꿨다. 폰은 `Vd`로 검증만 하므로 폐기된 폰이 레코드를 위조할 수 없고, 서버의 만료일 변조·롤백이 드러난다.
- **wDEK 백업과 암호적 삭제** (C-08): wDEK 테이블은 DB 정기 백업에서 제외하거나 ≤ 7일만 보존한다. 문서 삭제의 암호적 완료 시점은 wDEK 백업 만료 시점이며 투명성 페이지에 표시한다. 키-객체 분리는 회전·삭제의 운영 편의이지 기밀성 분리가 아니다(둘 다 같은 운영자 안에 있다). 기밀성은 클라이언트 전용 KEK에서 온다.
- **접근 단위** (C-03): 메타데이터·블롭·조회 에이전트는 AIK 인증 기기의 기기 범위 토큰만 받는다. 이메일 계정 세션만으로는 열리지 않는다.
- **남는 추론(정직한 서술, E-08)**: Padmé 패딩은 **크기 등급만** 숨긴다. 100KB대에서 약 2KB 단위라 등본·가입자명부의 쪽수 한 장 차이(세대원 수 등)는 패딩 크기로 드러날 수 있다. 블롭 업로드 시각은 발급 직후이므로 색인을 끈 종류도 발급 일자가 근사되며, 업로드 시각 로그는 **7일**만 보존한다. `expires_on`은 만료 알림에 필요해 일 단위로 유지하므로 유효기간이 고정된 서류(예: 납세증명서)는 `expires_on − 유효기간 = 발급일`로 역산된다. 이 세 가지는 잔여 위험으로 D19 §8·D09 §1.1에 적는다. 위 표의 "세대원 수(등본 쪽수) → Padmé 패딩" 대책은 정확한 크기를 숨길 뿐 쪽수 차이를 숨기지 못한다.
- **유용성 확인**: 최소화 뒤에도 02 §8 예시 질문의 80% 이상에 답할 수 있는지 SP-9에서 확인한다. 미달이면 종류별 색인 기본값을 조정하되 크기·초 단위 시각·dedup은 되살리지 않는다.
