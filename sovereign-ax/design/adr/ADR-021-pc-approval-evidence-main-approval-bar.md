# ADR-021. PC 승인의 근거: main 소유 승인 바와 선택 Windows Hello

> 상태: 채택(2026-10-31), 바 배치는 사용자가 대화 열 하단 띠로 정함(2026-11-01) · **개정(2026-11-03)**: 클릭 활성화 예외(앱이 연 핸드오프 복귀 120초 안만)·중복 경고 상태별 표시·작성일 조각·원격 바 표시 조건은 [ADR-027](ADR-027-approval-precision.md), 승인 바 Hello와 금고 Hello 합치기(엄격 모드)는 [ADR-026](ADR-026-human-secret-device-bound-session-vault.md) 결정 4, 바 색 내장 팔레트는 [ADR-028](ADR-028-supply-chain-update-signing-roles.md) 결정 7 · 관련: ADR-005, ADR-014(§2 후속), ADR-016, ADR-019, ADR-020(결정 4·결과 "보안 영향"), D00 §2·§3, D01 §2.1·§4·§5.1, D02 §6·§7, D03 §1·§2·§3·§3.1·§9·§11, D05 §3.3, D07 §2, D08 §6.1, D11 §0·§4·§5, D13 §4·§8, D14 §0·§1·§2.4, D19 §1.1·§2·§3.1·§3.4·§8·§9, schemas/remote-envelope, 02 §3·§4, 08 §1·§2·§3·§5·§6·§9·§11·§12·§13, design-system
> 근거: ADR-020 결과 "보안 영향", [R11](../../research/R11-approval-evidence-electron-hello.md)(Electron 입력 이벤트·WebContentsView·Windows Hello 공식 문서 조사), PoC-4 승인 창 e2e, PoC-1 Windows 측정(PR #9 브랜치 `poc/poc-1-windows-host`의 poc/reports/PoC-1.md), Opus 검수 2회

## 맥락

- ADR-020 결정 4가 별도 승인 창을 없앴다. ADR-014 §2가 주던 보호도 창과 함께 빠졌다. 그 보호는 "대화창 렌더러가 침해돼도 main이 만든 창의 실제 입력 없이는 승인이 없다"는 것이었다. 커밋 가드가 믿는 승인 근거 `LocalApproval`(D03 §3, D05 §3.3)을 무엇이 발급할지 다시 정해야 한다.
- 대화창 렌더러는 거래처 상호, 포털 오류 문구, 모델 응답 같은 제3자 텍스트를 그린다. 렌더러가 침해되면(sanitizer 우회 XSS, 샌드박스 렌더러 RCE) 다음을 할 수 있다고 본다.
  - **R-1 승인 위조**: 사용자가 누르지 않았는데 승인 신호를 보낸다.
  - **R-2 표시 위조**: 카드에 실제 되읽은 값과 다른 값을 보여 준다. 입력 단계에서 사업자번호·금액·이메일을 바꿔 보낸 뒤 원래 값처럼 보여 주는 것도 포함한다.
  - **R-3 클릭 유도**: 승인 버튼의 위치·표시 시점, 창 위치, 커서 모양을 조종해 다른 것을 누르려던 클릭을 승인으로 바꾼다.
  - **R-4 숨기기·방해**: 승인 버튼을 감추거나 클릭을 막는다. 발급이 안 될 뿐이라 안전한 실패다.
- 렌더러가 못 하는 일(R11 Q2·Q4):
  - main의 `before-mouse-event`를 일으키는 것. 렌더러의 `dispatchEvent`는 렌더러 안에서 끝난다. 다만 R11의 확신도는 "중간"이다. 알려진 렌더러 경로가 없다는 뜻이고, Chromium의 입력 처리 인터페이스 전체를 감사한 것은 아니다.
  - main 전용 API(`webContents.sendInputEvent`, `webContents.debugger`)를 부르는 것.
  - 메인 창 `contentView`의 자식 뷰 위에 페이지를 그리는 것. 자식 뷰는 창 자체 페이지보다 항상 위에 그려지고, 자기 영역의 클릭을 모두 가져간다. 다만 `<select>` 목록 같은 브라우저 팝업 창이 자식 뷰를 덮을 수 있는지는 확인하지 못했다.
  - `before-mouse-event`는 OS 입력 전용이 아니다. main의 `sendInputEvent`와 CDP `Input.dispatchMouseEvent`도 이 이벤트를 일으킨다.
- 렌더러가 할 수 있는 창 수준 일: `window.moveTo`·`resizeTo`로 창을 옮기는 것(main이 `content-bounds-updated`를 막지 않으면), `alert()` 같은 대화상자를 띄우는 것, CSS로 커서를 숨기거나 바꾸는 것.
- 발급 인증별로 승인 클릭 뒤에 남는 사람 행위가 다르다(ADR-020 결정 2).
  - 보안카드는 앱이 전부 하므로 **R-1이 곧 발급**이다(발급 사업자의 14%).
  - 간편인증(폰 승인)과 인증서(비밀번호 직접 입력)는 사람 행위가 하나 더 있다. 그러나 사용자는 막 승인하려던 참이라 위조된 서명 요청도 승인하기 쉽다. 이 행위를 승인 근거로 셈하지 않는다.
- PoC 측정
  - PoC-4의 별도 승인 창(정적 HTML, `javascript:false`, main이 `before-mouse-event`·`before-input-event`로 관찰, 600ms 무장 지연)은 Windows 11에서 e2e 14/14를 통과했다. 조건은 OS 배율 150%, 앱 배율 강제 125%·150%다(PR #9). 다만 e2e는 main의 `sendInputEvent`로 이벤트를 넣었으므로 **판정 로직만 확인했다.** 실제 포인터 좌표와 Win32 입력·DPI 변환은 확인하지 않았다. 측정 대상도 별도 `BrowserWindow`이고, 이 ADR의 자식 `WebContentsView`는 아직 측정하지 않았다.
  - PoC 기기의 `UserConsentVerifier.CheckAvailabilityAsync()`는 `DeviceNotPresent`다. 이 계정에 Hello PIN·생체가 설정돼 있지 않다.
- `UserConsentVerifier`는 결과 열거값 하나만 돌려준다. 서명 같은 암호학적 증거가 없어서, 결과는 그것을 부른 main만큼만 믿을 수 있다(R11 Q6). 대화상자에 앱이 넘긴 메시지가 표시되는지는 공식 문서로 확인하지 못했다. 창 핸들 interop은 Windows 11(빌드 22000) 이상이다.
- 사용자 원칙: 안전하게 실패하는 것도 중요하지만 애초에 실패하지 않는 것이 더 중요하다. 후보 비교에서 "Hello가 없는 PC에서 발급이 되는가"와 "누른 클릭이 무시되는 일이 있는가"를 위조 가능성과 같은 무게로 본다.

- **(c′) 승인 바가 카드 위치를 따라다니기**: 카드처럼 보이지만 위치를 렌더러가 보고해야 해서 R-3이 다시 열린다. 스크롤할 때마다 무장 지연이 다시 걸려 누른 클릭이 무시된다.

  - 대화 열 하단 띠: 승인 대기 카드 바로 아래에 붙어 ADR-020의 "카드 버튼"에 가장 가깝다. 패널을 접거나 창이 좁아도 보이고, 최대화해도 Windows 알림이 뜨는 화면 오른쪽 아래와 겹치지 않는다. 대신 입력창 근처라 입력하려고 습관처럼 그 자리를 누르는 클릭이 승인이 될 위험이 있다. 그래서 입력창은 제자리에 두고 바를 그 위에 두며, PoC-9에서 습관 클릭을 시험한다(조건).
  - 작업 패널 하단: 확인 값 목록 바로 아래라 순서는 자연스럽다. 그러나 카드와 눈 위치가 떨어지고, 최대화하면 알림 자리와 겹치며, 패널이 접히거나 좁아지면 자리를 잃는다.
  - 어느 쪽이든 위치는 main이 창 크기만으로 계산하므로 보안 규칙은 같다.
- **(g) Hello 결박 키 서명(`KeyCredential.RequestSignAsync`)으로 `actionHash`에 서명**: 다른 프로세스(금고)가 공개키로 검증할 수 있는 유일한 증거다(R11 Q7). 그러나 Hello가 있는 PC에서만 된다. 서명 대화상자에는 무엇을 승인하는지 표시할 메시지 인자가 없고, 24H2 이전에는 대화상자가 창 뒤에 뜬다. Phase 2 검토 과제로 넘긴다(조건).

판단: (c)만 Hello 유무와 관계없이 R-1을 막고 R-3을 줄이며 흐름을 클릭 1회로 둔다. (a)는 기본값(꺼짐)에서 보호가 없으므로 근거가 될 수 없고, (c) 위에 더하는 선택 단계로 쓴다. (b)는 ADR-014 대안 (c)와 같은 이유로 기각한다. main은 렌더러가 보고한 값을 검증할 수 없다.

## 결정

### 1. 로컬 비가역 승인의 근거는 main 소유 승인 바에서 main이 직접 관찰한 클릭이다

승인 바는 main이 메인 창 `contentView`에 자식으로 붙이는 작은 `WebContentsView`다. ADR-014 §2의 승인 창 규칙을 창 대신 이 뷰에 적용한다.

**뷰 설정**
- `sandbox:true`, `javascript:false`, preload 없음, `devTools:false`, `focusOnNavigation:false`. 바의 확대 배율은 1로 고정한다(`setZoomFactor(1)`, `setVisualZoomLevelLimits(1, 1)`).
- 전용 메모리 세션 파티션: 자기 스킴 밖 요청 취소, 권한 요청·확인 거부, 탐색·새 창 거부.
- 페이지는 main이 만드는 정적 HTML이고 CSP는 `default-src 'none'; style-src 'self'`다. 스타일은 디자인 시스템의 승인 바 명세(`ApprovalBar`)를 앱 내장 CSS로 옮긴다. 뷰 배경색을 지정하고(기본은 흰색), 모서리는 직각, 그림자는 없다. 뷰는 자기 영역 밖에 그릴 수 없고, 둥글게 잘라 낸 모서리도 클릭을 받기 때문이다.
- 뷰는 메인 창을 만들 때 미리 붙여 두고 `setVisible`로 보이고 숨긴다. 보일 때마다 맨 위로 다시 올린다.

**메인 창이 지킬 것**
- `webviewTag:false`. `<webview>.sendInputEvent`는 공식 문서에 있는, 렌더러에서 부를 수 있는 입력 주입 경로다.
- `disableDialogs:true`. 렌더러의 `alert()` 같은 대화상자를 막는다.
- `content-bounds-updated`를 `preventDefault`한다. 렌더러의 `window.moveTo`·`resizeTo`로 창이 움직이지 않게 한다. 전체 화면 권한 요청은 기존 권한 처리기(D11 §4)가 거부한다.
- main은 렌더러 IPC를 받아 `sendInputEvent`나 `webContents.debugger`를 부르지 않는다. `sendInputEvent`로 입력을 넣는 e2e 코드는 제품 빌드에서 뺀다.
- `remote-debugging-port`·`remote-debugging-pipe` 스위치가 있으면 main이 종료한다(기존 D11 §4 기동 자기 점검). CDP로 넣은 마우스 이벤트도 `before-mouse-event`를 일으키기 때문이다. 같은 사용자 악성코드(M)에 대한 경계가 아니라 값싼 차단이다.
- main은 대화 화면 `webContents`의 `cursor-changed`를 본다. 승인 대기 중 커서가 `none`이거나 `custom`이면 바를 무장하지 않는다. 렌더러가 진짜 커서를 숨기고 가짜 커서를 그려 사용자가 엉뚱한 곳을 누르게 하는 수법(커서 위장) 때문이다. 앱 CSS에는 커스텀 커서를 쓰지 않는다(lint로 금지).

**위치: main이 창 크기만으로 정한다**
- 위치는 **대화 열 하단, 입력창 바로 위**다(사용자 결정 2026-11-01). 승인 대기 카드가 타임라인 맨 끝에 있으면 바가 카드의 버튼 줄처럼 붙어 보인다.
- x와 폭은 창 콘텐츠 폭, 레일 폭(토큰 `rail-width`), 패널 폭(`panel-width`), 대화 최대 폭(`chat-max`)으로 계산한다. 대화 열 폭은 `min(chat-max, 콘텐츠 폭 − 레일 폭 − 패널 폭)`이다(08 §5 "남는 폭은 작업 패널이 쓴다"). 패널 폭은 패널이 접혀 있어도 늘 뺀다. 접힘 여부는 렌더러 상태라, 이것을 위치 계산에 쓰면 렌더러가 바를 옮길 수 있기 때문이다. 패널을 접은 동안 바가 대화 열과 조금 어긋나 보이는지는 PoC-9에서 본다. → PoC-9(2026-11-01): 1280 DIP 창에서 170 DIP 어긋났다. 렌더러가 승인 대기 중에는 패널을 접어도 그 폭을 비워 두는 규칙으로 맞췄다(poc/reports/PoC-9.md §4).
- y는 창 콘텐츠 하단에서 **입력창 예약 높이**(앱 상수, 입력창 3줄 높이)와 바 높이를 뺀 자리다. 입력창은 승인 대기 중에 예약 높이 안에서만 늘어나고, 그보다 길면 입력창 안에서 스크롤한다. 입력창 높이를 렌더러가 보고하게 하면 바 위치를 렌더러가 정하게 되기 때문이다.
- 대화 열 폭이 바 최소 폭보다 좁으면 레일 오른쪽부터 창 오른쪽 끝까지의 띠로 넓힌다. 창 최소 폭은 강제하지 않는다(화면 반쪽 배치를 막지 않기 위해).
- 렌더러가 보고하는 좌표는 쓰지 않는다. 렌더러 확대 배율도 계산에 넣지 않는다. 바는 DIP 크기가 고정이고, 렌더러가 자기 배율에 맞춰 그 자리를 비운다. 단위는 DIP다.
- `resize`마다 다시 배치한다(자동 크기 조정은 없다). 승인 대기에 들어갈 때 바가 디스플레이 작업 영역 밖이면 main이 창을 작업 영역 안으로 옮긴다.
- 바와 입력창 사이에 앱 상수 간격(예: 12 DIP)을 둔다. 입력하려고 누르는 클릭이 바에 떨어지지 않게 하기 위해서다. 습관 클릭은 PoC-9에서 시험한다(조건).
- 렌더러가 따를 레이아웃 규칙: 타임라인 아래쪽, 입력창 예약 영역 위에 바 자리를 비운다. 그 아래에 창 끌기 영역(`-webkit-app-region: drag`)을 두지 않는다. 입력창은 예약 높이를 넘지 않는다. 렌더러가 규칙을 어기면 바가 렌더러 화면을 가리거나 클릭이 창 끌기가 될 뿐이고, 승인은 생기지 않는다.

**내용: 요약 줄과 동작이 한 덩어리다**
- 요약 줄은 3줄 이하다. 서류 종류별 앱 내장 표로 정하고, 서명 패키지 문자열을 쓰지 않는다. 표에 없는 서류 종류의 커밋 게이트는 패키지 로더가 거부한다(D03 §3.1).

  | 서류 | 1줄 | 2줄 | 3줄 |
  |---|---|---|---|
  | H-01 세금계산서 | 공급받는자: 상호 · 사업자번호 | 합계금액 · 세액 | 받는 이메일 |
  | H-03 사업자등록증명, H-04 납세증명서 등 민원증명 | 서류명 · 부수 | 발급 대상: 상호 · 사업자번호(개인이면 이름) | 용도·제출처 · 주민등록번호 공개 범위 |

  민원증명 줄에 쓸 `fieldKey`는 아직 D02 사전에 없다. PoC-8(H-04) 플레이북을 쓸 때 사전과 스키마에 함께 넣는다(조건).

  - 상호는 자유 입력이라 증거가 못 되므로 사업자번호를 반드시 함께 보인다.
  - 세액을 함께 보이는 것은 영세율로 바뀐 경우처럼 합계는 같고 세액만 다른 경우를 드러내기 위해서다.
- **처음 거래·처음 보내는 주소**: 이 PC에서 발급이 확정된 적이 없는 사업자번호에는 "처음 거래", 이메일에는 "처음 보내는 주소"를 붙인다.
  - 판정은 엔진이 원장의 `committed` 행(verify로 확정된 것)만으로 한다. 원장에 공급받는자 사업자번호·받는 이메일의 HMAC 열을 더한다(D07 §2). `observed_manual`처럼 렌더러 동작으로 생길 수 있는 상태와, 렌더러가 고칠 수 있는 거래처 장부는 쓰지 않는다.
  - 결과는 엔진이 만드는 예약 `fieldKey`(`$first.bizNo`, `$first.email`)로 `fields`에 넣어 `cardHash`에 묶는다. 폰 승인 시트에도 같은 표시가 보인다. 예약 키는 D02 `fieldKey` 사전과 schemas/remote-envelope의 닫힌 목록에 더한다.
  - HMAC 키는 엔진이 DB 키에서 HKDF로 파생한 `ledgerHmacKey`다. 이메일은 소문자로 바꾸고 도메인은 punycode로 바꾼 뒤 HMAC한다.
- **중복 경고**: D02 §7의 업무 중복 경고(같은 업무 키 기록, 직전 시도 "발급 안 됨" 판정, 다른 PC 기록 있음·확인 불가)도 바에 올린다.
  - 엔진이 예약 `fieldKey`(`$dup.businessKey`, `$dup.priorNotCommitted`, `$dup.otherDevice`)로 `fields`에 넣어 `cardHash`에 묶는다.
  - 경고가 하나라도 있으면 해당 줄에 표시를 붙이고, 동작 글자를 "같은 건 기록을 확인했고 발급"으로 바꾼다. 이 클릭이 D02 §7의 "명시 확인"이다. 카드에만 경고를 두면 침해된 렌더러가 유일한 중복 경고를 지울 수 있기 때문이다.
- **줄이기 규칙**: 줄마다 앱 라벨 칸을 고정하고 값은 한 줄로 쓴다. 한 줄이 길어져도 다른 줄 위치가 바뀌지 않는다.
  - 값은 "줄이지 않는 조각"과 "줄일 수 있는 조각"으로 나눠 따로 그린다. 사업자번호, 금액, 이메일의 `@` 뒤 도메인은 줄이지 않는다. 상호와 이메일의 `@` 앞은 줄일 수 있고, CSS 말줄임(`text-overflow: ellipsis`)으로 줄인다. 스크립트 없이 된다.
  - 국제화 도메인은 punycode로 보인다.
  - main은 줄이지 않는 조각의 폭을 글자 수로 보수적으로 어림한다(한글 등 동아시아 문자는 두 칸으로 센다). 넘치면 무장하지 않고 "창을 넓혀 주세요"와 넘친 칸을 보인다. → PoC-9(2026-11-01): 대화 열 폭(최대 600 DIP)에서는 긴 도메인·"처음 보내는 주소"·10억대 금액이 흔히 넘쳐 첫 발급이 막혔다. 대화 열 폭에서 넘치면 먼저 레일 오른쪽부터 창 끝까지의 띠로 넓히고, 띠로도 넘칠 때만 무장하지 않는다. 띠 여부는 main이 창 크기와 게이트 값으로 정하고 렌더러에는 배치용으로만 알린다.
  - 값에 제어문자·양방향(bidi) 문자·폭 없는 문자가 있으면 무장하지 않고 어느 칸을 고쳐야 하는지 보인다.
- 요약 줄은 해시한 `fields`에서만 고른다. 필요한 필드가 없으면 무장하지 않고 이유를 보인다.
- **모든 상태에서 바 전체가 동작 하나다.** 바 안에 작은 버튼을 따로 두지 않는다. 덮개가 값을 가리면 누를 곳도 같이 가려지고, 좌표로 하위 버튼을 가리는 판정이 필요 없다. 상태는 다음과 같다.
  - 승인: 요약 줄 + "승인하고 발급"(중복 경고가 있으면 "같은 건 기록을 확인했고 발급")
  - 무장 거부: 요약 줄 + 사유("창을 넓혀 주세요", 고칠 칸 이름, 필요한 필드 없음, 값 대조 불일치). 누를 수 없다.
  - Hello 다시 시도: 요약 줄 + "Windows Hello 다시 시도"
  - Hello 면제: 요약 줄 + "이번만 Hello 없이 승인"(결정 3)
  - 폰이 먼저 결정함: "폰에서 이미 승인했어요"(또는 거절). 누를 수 없고 2초 뒤 내려간다.
  - InDoubt 증언: 결정 5
  - Hello 설정: 결정 3
- 거절·중지는 바에 두지 않는다. 대화 카드의 [중지]처럼 렌더러 신호로 받아도 안전한 실패다.

**입력 판정**
- 승인은 main이 바의 `before-mouse-event`로 관찰한, 바 안에서의 왼쪽 버튼 down → up이다.
- **무장 지연**: 아래 사건 뒤 600ms 동안의 입력은 무시한다. 무장 전에 mouseDown이 오면 600ms를 다시 시작한다.
  - 바가 보이기 시작함, 요약 값이나 동작 글자가 바뀜
  - 바 위치가 바뀜(`resize`, 창 `move`·`moved`, 좁은 창 띠로 바뀜)
  - 창이 다시 보임(`show`·`restore`), 디스플레이 배율·배치가 바뀜(`display-metrics-changed`)
  - 앱 창이 활성화됨. 단, 활성화 뒤 100ms 안에 바 안에서 시작된 mouseDown(바를 눌러 창을 활성화한 경우)은 예외로 둔다. 다른 창(예: 인증서 비밀번호를 넣은 Chrome)에서 돌아와 바를 바로 누르는 흐름이 그대로 된다.
  - 대화 화면 커서가 `none`·`custom`에서 기본 커서로 돌아옴
- **머무름**: 다음 둘 중 하나일 때만 mouseDown을 인정한다. 바를 덮던 알림 창이 사라지는 순간, 그 알림을 누르려던 클릭이 승인되지 않게 하기 위해서다.
  - 마지막 mouseLeave와 마지막 무장 사건 뒤에, 바 안에서 처음 실제로 움직인 mousemove(`movementX`·`movementY`가 0이 아닌 것)부터 150ms가 지났다.
  - 마지막 무장 사건이 시작될 때부터 커서가 바 안에 있었고, 그 뒤 mouseLeave가 없었다. 멈춘 커서 아래에 바가 뜬 경우이고, 600ms 무장 지연이 이미 지켜 준다. 이 경우를 빼면 마우스를 움직이지 않은 클릭이 계속 거부된다.
  - 알림 창이 바를 덮으면 바가 mouseLeave를 받고, 창이 사라질 때 OS가 만드는 이동은 움직임이 0이라고 본다. 둘 다 PoC-6에서 OS 수준 입력으로 확인한다(조건).
- 무장 지연 때문에 버린 클릭에는 "잠시 뒤 다시 눌러 주세요", 머무름 때문에 버린 클릭에는 "마우스를 조금 움직인 뒤 눌러 주세요"를 보인다. 이런 상태 문구는 요약 값·동작 글자가 아니므로 다시 무장하지 않는다.
- **무장 표시는 정적 페이지 세 개로 한다.** 무장 전(흐림, 문구 선택), 무장됨, 무장됨 + 문구다. main이 무장을 시작할 때 무장 전 페이지를 불러오고, 600ms 타이머가 끝나면 무장됨 페이지를 불러온다. 애니메이션과 `insertCSS`(`javascript:false` 페이지에서 동작 미확인)는 쓰지 않는다. 무장된 상태에서 문구만 보일 때는 무장됨 + 문구 페이지를 쓰므로 흐려지지 않는다.
- **창 활성화 처리**: main은 활성화 뒤 100ms를 기다린다. 그 안에 바 안에서 mouseDown이 오면 클릭 활성화로 보고, 재무장도 페이지 다시 불러오기도 하지 않는다. 오지 않으면 재무장한다. 활성화 클릭의 down·up이 다시 불러오는 문서에 걸리지 않게 하기 위해서다.
- **키보드 승인은 없다**(Enter·Space·조합키 모두, 08 §5 "승인에는 단축키가 없다"). PoC 코드의 Alt+Y 경로는 지우지 않고 꺼 둔다. main이 메인 창의 `before-input-event`로 직접 관찰한 비타이핑 조합키는 렌더러가 만들 수 없으므로, 접근성 설정(기본 꺼짐)으로 켤지는 Phase 1 접근성 검토에서 사용자가 정한다.
- 클릭 뒤 main은 키보드 포커스를 대화 화면으로 돌려준다(바를 누르면 포커스가 바로 옮겨 가기 때문이다).

**표시 조건**
- 승인 바 자리는 **커밋 게이트(비가역), InDoubt 증언(결정 5), Hello 설정(결정 3)** 세 가지에만 쓴다. 시작 게이트·데몬 동의는 대상이 아니다.
- 우선순위는 게이트 > 증언 > Hello 설정이다. 높은 것이 오면 낮은 것은 내려가고(나중에 다시 요청할 수 있다), 바뀔 때는 재무장한다.
- `trigger=local` 실행: 엔진 상태가 `WaitingGate`가 되면(main이 엔진에서 직접 받음) main이 바를 띄운다. 창이 비활성이면 작업 표시줄만 깜빡이고 포커스는 가져오지 않는다.
- 열린 게이트가 있는 동안 온 다른 게이트 요청은 바를 바꾸지 않는다(PoC-9 구현: `busy`로 거부. 실행은 한 번에 하나라 정상 흐름에서는 생기지 않는다).
- **한 게이트에서 한 번 뜬 바는 게이트가 끝날 때까지 남는다.** 렌더러의 숨김 요청은 무시하고, 레일 화면으로 옮겨 가도 같은 자리에 남는다. 렌더러가 진짜 바를 잠깐 숨기고 그 자리에 가짜 바를 그리는 수법을 막는다. 렌더러가 [중지]나 "수정하기"로 게이트를 끝내고 다시 여는 것은 막지 못하며, 그때는 무장 지연이 방어다.
- `trigger=remote`·`trigger=daemon`과 원격 승인이 거부돼 로컬로 돌린 경우("PC에서 승인 필요"): 자동으로 띄우지 않고 창을 앞으로 가져오지도 않는다. 사용자가 PC에서 그 작업 카드를 열었다는 렌더러 요청이 오면 띄우고, 그 뒤로는 위 규칙대로 남는다.
- 두 채널 중 먼저 도착한 결정이 이긴다(D03 §3). 폰이 먼저 결정하면 바를 "폰에서 이미 승인했어요" 상태로 2초 보인 뒤 내린다.
- 승인 대기 중에 앱 창이 활성이면 이 앱의 OS 알림을 띄우지 않는다.

**값 대조**
- main은 엔진이 보낸 게이트 요청의 `fields`(readback 값과 예약 `fieldKey`의 배열 전체, 순서 포함)와 `cardHashInputs`로 `cardHash`·`actionHash`를 다시 계산한다. 엔진 값과 같을 때만 바를 무장한다. 폰의 규칙(B-29)과 같다.
- 이것은 엔진 버그를 잡는 자기 일치 확인이다. 렌더러·엔진 침해를 막는 장치가 아니다. 렌더러 카드도 같은 `fields`를 main을 거쳐 받아 그린다.

**근거 형식**
- 승인되면 main은 `LocalApproval{runId, gateStepId, reqId, approvalNonce, actionHash, exp, presence}`를 발급한다. HMAC 문맥은 `SAX-local-approval-v2`다. `exp`는 발급 시각 + 120초다(엔진이 받아 게이트 토큰으로 바꾸는 시간).
  - `reqId`는 게이트 요청 ID(`gate_requests.req_id`)다. 같은 실행 안에서 다시 게이트가 열리면(되감기·수정하기·재개) 앞의 근거가 통하지 않는다. 폰 챌린지를 120초마다 갱신해도 `req_id`는 그대로다.
  - `approvalNonce`는 엔진이 게이트 요청마다 만드는 로컬 전용 값이고 `gate.waitMs` 동안 유효하다. 120초마다 바뀌는 폰 챌린지(`gate.request.challenge`)와 분리해서, 챌린지가 바뀌어도 바를 다시 무장하지 않고 근거도 거부되지 않는다. 게이트 토큰 식의 `nonce`(D03 §3)와는 다른 값이다.
  - `presence`는 `click`, `click+hello`, `click+waiver` 중 하나다. `click+waiver`는 Hello를 켰지만 쓸 수 없어 이번만 면제한 경우다(결정 3).
- InDoubt 증언은 `LocalAttestation{intentId, stepId, attestReqId, attestNonce, summaryHash, kind: not_committed, exp}`로 따로 발급한다. HMAC 문맥은 `SAX-local-attest-v1`이다. 증언이 승인 근거로 쓰이지 않게 하기 위해서다. `attestReqId`·`attestNonce`는 엔진이 증언 요청마다 만들고, `summaryHash`는 증언 바에 보인 요약 줄의 해시다. `exp`는 발급 시각 + 120초다.
- 서명 키는 기존대로 기동 시 main↔금고가 교환한 키다.
  - **Phase 1에는 HMAC을 검증하는 쪽이 없다.** 엔진은 이 키를 갖지 않으므로, 근거를 **main↔엔진 전용 포트**(렌더러 명령을 엔진에 중계하는 통로와 분리, D01 §2.1)로 받았다는 출처만 믿는다. 중계 통로에서 온 `answerGate`·`attestNotCommitted`는 거부하고 보안 이벤트를 남긴다. 폰 서명은 지금처럼 원격 채널로 엔진에 들어온다.
  - Phase 2에 커밋 가드가 금고로 옮겨 가면 금고가 HMAC을 직접 검증한다(D05 §3.3).
- 렌더러가 보내는 승인 신호·`isTrusted`·카드 해시는 근거가 아니다.
- 저널(D03 §9)에 남기는 것: `gate.bar_shown`, `gate.bar_arm_refused{reason}`, `gate.approved{presence}`, `gate.hello{result}`, `gate.hello_waived`, `gate.attested`, `settings.hello_changed`, 보안 이벤트 `security.gate_answer_from_relay`.

### 2. 대화 카드에는 승인 버튼을 두지 않는다

렌더러가 그린 버튼은 믿을 수 없고, 스크롤되는 카드 위치를 main이 독립적으로 알 수 없기 때문이다. 승인 대기 카드는 "홈택스 확정" 값과 상태 칩 "승인 대기", 그리고 "아래 [승인하고 발급]에서 값을 한 번 더 확인하고 눌러 주세요" 안내와 [중지]를 보여 준다. PC의 승인 동작은 승인 바 하나다.

ADR-020 결정 4의 "카드·작업 패널의 [승인하고 발급]"을 "main 승인 바의 [승인하고 발급]"으로 좁힌다. 누르면 바로 발급하고 별도 창이 없다는 결정은 그대로다.

### 3. Windows Hello 확인은 승인 바 위에 더하는 선택 단계다

기본은 꺼짐이다(ADR-020 결정 3). Hello가 더 막는 것은 PC 앞의 제3자다. 렌더러 침해는 승인 바가 이미 막는다. 침해된 main은 Hello 호출을 건너뛸 수 있으므로 M·E에 대해서는 경계가 아니다. **발급 근거와 Hello 설정에 쓰는 Hello는 늘 main 소유 바의 클릭 뒤에만 뜬다.** 렌더러가 이 Hello 대화상자를 직접 띄우게 할 수는 없다. 금고 잠금 해제(08 A-02)의 Hello는 별개다.

**켜 둔 경우의 발급 흐름**
- 바 클릭 → main이 `IUserConsentVerifierInterop::RequestVerificationForWindowAsync`를 메인 창 핸들(`getNativeWindowHandle()`)로 부른다. 데스크톱 앱이 일반 `RequestVerificationAsync`를 부르면 대화상자가 창 뒤에 뜨기 때문이다(R11 Q6).
- 메시지는 main이 신뢰 값으로 만든다(예: "A상사 3,630,000원 세금계산서 발급"). 다만 표시 여부가 확인되지 않았으므로 신뢰 표시로 셈하지 않는다.
- `Verified`이면 `LocalApproval(presence: click+hello)`을 발급한다.
- `Canceled`·`DeviceBusy`이면 바가 "Windows Hello 다시 시도" 상태가 되고 승인 대기를 유지한다.
- `RetriesExhausted`이면 "Windows 잠금 화면에서 PIN으로 잠금을 푼 뒤 다시 시도해 주세요"와 함께 다시 시도 상태가 된다. 면제는 주지 않는다. 본인이 아닐 가능성이 크기 때문이다.
- 가용성이 없으면(`DeviceNotPresent`·`NotConfiguredForUser`·`DisabledByPolicy`) 한 번 다시 시도한 뒤에도 같을 때 바가 "이번만 Hello 없이 승인" 상태가 된다. 근거는 `presence: click+waiver`다. 면제하면 Windows 알림과 활동 기록에 남기고, 폰이 연결돼 있으면 폰에도 알린다. 원격 데스크톱 등으로 Hello가 끊긴 순간에 발급이 막히지 않게 하기 위해서다.
- 실행을 시작할 때(홈택스 로그인 전) 가용성을 다시 확인해, 쓸 수 없으면 준비를 시작하기 전에 알린다.

**구현**
- 호출하는 프로세스는 main이다. D05 §2의 Hello 결박 Rust N-API 헬퍼(S10)와 같은 크레이트를 main이 자기 프로세스 안에 올려 부른다. 결과는 부른 프로세스만큼만 믿을 수 있기 때문이다(R11 Q6). 같은 방식(Rust `windows` 크레이트 + napi-rs)을 Electron 앱 Bitwarden이 쓴다.
- NodeRT(방치)와 PowerShell·별도 실행 파일은 쓰지 않는다. 별도 실행 파일은 결과를 main에 알리는 통로를 따로 인증해야 한다.
- 창 핸들 interop이 Windows 11(빌드 22000) 이상이므로, Windows 10에서는 설정 칸을 비활성으로 둔다.

**설정**
- 켤 수 있는 조건: `CheckAvailabilityAsync()`가 `Available`이고, 켜는 순간 Hello 확인 1회에 성공해야 한다.
- `DeviceNotPresent`·`NotConfiguredForUser`·`DisabledByPolicy`이면 설정 칸을 비활성으로 두고 이유("이 PC에는 Windows Hello가 설정되어 있지 않아요")를 보여 준다. PoC 기기는 이 상태다.
- 설정 값은 main이 앱 폴더(사용자 전용 DACL, D07 §1.1)의 설정 파일에 보관한다. 렌더러 명령으로는 바꿀 수 없다.
- **켜기·끄기는 Hello 설정 바로 한다.** 설정 화면에서 켜기·끄기를 누르면(렌더러 요청), main이 승인 바 자리에 "발급 전 Windows Hello 확인 켜기"(또는 끄기) 바를 띄운다. 그 바를 누른 뒤 Hello 확인이 `Verified`일 때만 바꾼다.
  - 끄기에도 Hello를 요구하는 것은, 클릭만으로 끄게 하면 PC 앞 제3자가 끄고 바로 발급할 수 있기 때문이다.
  - Hello를 쓸 수 없는 PC에서는 끄기 바 클릭만으로 끄고, 면제와 같은 알림을 남긴다.
  - 승인 대기 중에는 Hello 설정 바를 띄우지 않는다. 설정 요청은 거부하고 "발급을 마친 뒤 바꿔 주세요"를 보인다.

### 4. 원격 승인과의 관계

폰 승인(`Sign_Vm`, 하드웨어 키, D08 §6.1)은 그대로다. PC 쪽 표시는 결정 1의 표시 조건을 따른다. `trigger=local`이 아닌 실행에서는 바를 자동으로 띄우지 않는다. 먼저 도착한 결정이 이긴다.

D08 §6.1의 "처음 쓰는 거래처·이메일 수신자"(`remote.newCounterpartyRequiresLocal`)도 결정 1의 원장 판정(처음 거래·처음 보내는 주소)을 쓴다. 지금 쓰는 `counterparties.local_approved_at`은 렌더러가 거래처 장부를 고쳐 바꿀 수 있고, 실행 입력의 이메일이 장부와 달라도 사업자번호만 맞으면 통과할 수 있기 때문이다.

### 5. InDoubt의 사용자 증언("발급목록에 없음 확인", D03 §2)도 승인 바 자리에서 받는다

- 증언 바에는 그 건의 요약 2줄(공급받는자 상호·사업자번호, 합계금액)을 보이고, 그 해시를 `LocalAttestation.summaryHash`에 묶는다. "확인 필요" 건이 둘 이상일 때 사용자가 홈택스에서 확인한 건과 다른 건의 증언이 나가지 않게 하기 위해서다.
- 증언 바는 증언을 받거나, 조회로 InDoubt가 풀리거나, 게이트 바가 자리를 가져가거나, 사용자가 그 카드를 닫으면(렌더러 요청) 내려간다. 증언 바를 숨겨도 증언이 안 될 뿐이라 안전한 실패다.
- 증언 바는 승인과 다르게 보인다. 주의 색(황토, `attention`)을 쓰고 동작 글자는 "홈택스 발급목록에 없음을 확인했어요"다. 같은 자리·같은 모양이면 승인하던 습관대로 누른 클릭이 거짓 증언이 되고, 이어지는 재게이트에서 중복 발급이 될 수 있기 때문이다.
- 자동으로 띄우지 않는다. 엔진이 InDoubt이면서 증언을 받을 수 있는 때가 되고(`armed_at`부터 `policy.verify.minElapsedMs`가 지나고 조회 재시도를 1회 더 한 뒤, E-13), 사용자가 그 "확인 필요" 카드를 열었다는 렌더러 요청이 올 때만 뜬다.
- E-13 고정 문구("발급목록 반영이 늦을 수 있습니다")는 증언 바의 정적 HTML에 넣는다.
- 판정 규칙은 승인과 같고 근거는 `LocalAttestation`이다.
- 증언은 발급이 아니므로 Hello를 요구하지 않는다. 증언 뒤 다시 발급하려면 새 게이트 승인(Hello 포함)을 다시 받는다.

### 6. 보호 범위 고지

- 승인 바는 R-1을 막는다.
- R-2는 바의 요약 줄까지만 막는다. 요약 줄은 위조할 수 없지만, 렌더러가 입력 단계에서 바꾼 값은 요약 줄과 "처음 거래"·"처음 보내는 주소" 표시에 드러날 뿐 막지는 못한다. 사용자가 바의 값을 봐야 한다. 카드 본문은 렌더러가 그리므로 침해되면 바뀔 수 있다.
- R-1의 전제는 렌더러가 main의 입력 이벤트를 만들 수 없다는 것이다(R11 확신도 중간). 렌더러 RCE가 브라우저 쪽 입력 처리 버그와 겹치면 이 전제가 깨질 수 있다.
- R-3은 줄인다. 위치는 main이 정하고, 한 번 뜬 바는 남고, 창 수준 사건마다 다시 무장하며, 무장 지연·머무름이 있고, 커서 위장 중에는 무장하지 않는다. 남는 것:
  - 렌더러가 평소 같은 자리에 자기 버튼을 두어 클릭 습관을 들이는 것
  - 브라우저 팝업이 바를 덮는 것(미확인)
  - 렌더러가 게이트를 끝내고 다시 여는 것(무장 지연만 방어)
- 원격·데몬 실행의 "자동으로 띄우지 않음"은 렌더러 요청에 기대므로, 렌더러가 침해되면 이 제한은 사라진다.
- 같은 사용자 권한 악성코드(M)·침해된 엔진(E)이 보내는 합성 OS 입력(`SendInput`)은 실제 입력과 구분되지 않는다(R11 Q3).
- PC 앞 제3자는 Hello를 켠 경우만 막는다. Hello를 쓸 수 없는 순간의 면제("이번만 Hello 없이 승인")는 제3자도 쓸 수 있다. 사후 알림만 남는다.

## 대안과 기각 이유

| 대안 | 기각 이유 |
|---|---|
| (a) Hello 결과만 근거로 | 기본 꺼짐이라 대부분의 PC에 보호가 없고, Hello가 없는 PC는 켤 수도 없다 |
| (b) 대화창 버튼 클릭을 main이 관찰 | 버튼 위치를 렌더러가 보고해야 하므로 침해된 렌더러가 사용자의 다음 클릭 자리를 버튼이라고 보고할 수 있다(ADR-014 대안 (c)와 같은 이유) |
| (c′) 승인 바가 카드를 따라다니기 | 위치를 렌더러가 정하게 되어 클릭 유도가 열리고, 스크롤마다 무장 지연이 걸려 누른 클릭이 무시된다 |
| 바를 작업 패널 하단에 두기 | 사용자가 대화 열 하단 띠를 골랐다(2026-11-01). 카드와 눈 위치가 떨어지고, 최대화하면 알림 자리와 겹치며, 패널이 접히거나 좁아지면 자리를 잃는다 |
| (d) 렌더러 신호를 그대로 근거로 | 보안카드 발급은 클릭 위조가 곧 발급이다. D19 위협 R의 "막는다"가 거짓이 된다 |
| (e) Hello 필수 | Hello가 없는 PC에서 발급할 수 없다(PoC 기기 포함). ADR-020이 선택으로 정했다 |
| (f) 네이티브 확인 대화상자 | 별도 창과 같은 흐름 끊김. 포커스를 가져가고 기본 버튼이 Enter로 눌린다 |
| (g) Hello 결박 키 서명을 근거로 | Hello가 있는 PC에서만 되고, 무엇을 승인하는지 표시할 수 없다. Phase 2 검토 과제 |
| 별도 승인 창 유지(ADR-014 §2) | ADR-020에서 기각 |

## 결과

- 승인 근거가 Hello 유무와 관계없이 모든 PC에서 같다. Hello가 없는 PC도 렌더러 침해에 대한 보호를 잃지 않는다.
- PC 승인 버튼이 대화 카드 안에서 카드 아래 대화 열 하단 띠로 옮겨진다.
  - 02 §3·§4, 08 §1·§2·§3·§5·§6·§9·§11·§12·§13을 맞춘다.
  - 디자인 시스템(README, data-hierarchy, tokens.json, Button·TaskCard·MainScreen·StepList·ApprovalWindow)을 맞추고 `ApprovalBar` 명세를 새로 둔다.
  - D02 §7의 중복 경고 "명시 확인"은 승인 바 클릭으로 받는다. D02 `fieldKey` 사전과 schemas/remote-envelope의 닫힌 목록에 예약 키(`$first.*`, `$dup.*`)를 더한다.
  - 디자인 캔버스(claude.ai 아티팩트)의 승인 대기 카드·대화 하단 화면은 따로 고쳐야 한다.
- 설계 문서를 이 ADR에 맞춘다: D00 §2·§3, D01 §2.1·§4·§5.1, D02 §6·§7, D03 §1·§2·§3·§3.1·§9·§11, D05 §3.3, D07 §2, D08 §6.1, D11 §0·§4·§5, D13 §4·§8, D14 §0·§1·§2.4, D19 §1.1·§2·§3.1·§3.4·§8·§9, README. ADR-005 결정 10·ADR-019 결정 6에는 개정 메모를, ADR-014·ADR-020 상태 줄에는 이 ADR을 단다.
- **PoC 범위**
  - PoC-6(H-01 게이트, 11-12): 게이트 근거를 승인 바로 만든다.
    - `approval-window.ts`의 `BrowserWindow`를 메인 창의 자식 `WebContentsView`로 바꾼다.
    - `approval-gate.ts`의 판정(`ApprovalGate`)·정적 HTML·HMAC은 이어 쓴다. 바꿀 것:
      - 머무름 150ms, 무장 전 mouseDown이면 재시작, 창 수준 사건 재무장(클릭 활성화 예외)
      - Alt+Y 꺼 둠
      - 끝 자르기(`slice(0,120)`)를 줄이지 않는 조각·줄일 수 있는 조각으로
      - `LocalApproval` v2 필드(`reqId`·`approvalNonce`·`presence`)
    - 메인 창에 `disableDialogs`·`content-bounds-updated` 차단·`cursor-changed` 감시를 넣는다.
    - `approval.demo`를 엔진 게이트 요청으로 바꾸고 main이 `actionHash`를 다시 계산한다.
    - `answerGate`를 main↔엔진 전용 포트로 옮긴다. 지금 PoC main은 렌더러 명령을 엔진 포트로 그대로 넘긴다.
    - "처음 거래"·"처음 보내는 주소"는 PoC에서 원장 HMAC 열까지만 만든다. 중복 경고(`$dup.*`)는 바에 올린다.
    - e2e(`sendInputEvent`, 판정 로직)에 더할 것: 렌더러 승인 신호 거부, 렌더러 중계 경로의 `answerGate` 거부, 바 클릭 승인, 무장 지연·재시작, 머무름, 렌더러 숨김 요청 무시, 창 이동·복원 뒤 재무장, 커서 위장 중 무장 거부.
    - OS 수준 입력(별도 프로세스의 `SendInput` 또는 사람의 실제 클릭)으로 따로 시험할 것: 배율 100·125·150%와 모니터 간 이동, 머무름, 알림 창이 사라질 때의 클릭, 클릭 활성화 예외.
    - Hello는 PoC 범위 밖이다(PoC 기기 `DeviceNotPresent`).
  - PoC-9(데모 UI 셸, 11-19): 발급 흐름은 "확인 카드 → 실행 뷰 → 승인 대기 카드 + 승인 바 → 결과"다. 렌더러는 바 자리(입력창 예약 영역 위)를 비워 두는 레이아웃 규칙을 따른다. 바는 대화 열 하단 띠다(사용자 결정 2026-11-01). 입력창 쪽 습관 클릭을 시험한다. 태스크 제목의 "승인 창"은 "승인 바"로 바꾼다.
- 공수: M4-2의 "main 승인 창 +2일"을 승인 바가 대신한다. Hello 확인 옵션은 M1-3의 Hello 네이티브 헬퍼(S10)를 같이 써서 M4-2 안에서 처리한다(공수 변경 없음, 가설).

## 조건

- **PoC-6에서 확인한다**(R11 마지막 절 목록 중 승인 바 항목).
  - 자식 `WebContentsView`의 `before-mouse-event` 좌표가 배율 100·125·150%와 모니터 간 이동 뒤에도 바의 DIP 영역과 맞는지, 그려진 위치와 클릭 판정 위치가 같은지(OS 수준 입력으로).
  - 창이 비활성일 때도 바가 mousemove를 받아 머무름을 셀 수 있는지, 클릭 활성화 예외(100ms)가 실제 순서(활성화 → mouseDown)와 맞는지, 렌더러의 `window.focus()`가 창을 활성화하는지.
  - 창 크기 변경·최소화·복원·최대화 뒤 재배치. 좁은 창에서 바가 창 오른쪽 끝까지 넓어질 때 Windows 알림과 겹침·오클릭.
  - 렌더러가 띄우는 브라우저 팝업이 바를 덮는지: `<select>` 목록, 날짜·색 선택기, `datalist`·자동완성, `title` 툴팁. 덮는다면 잔여 위험으로 D19 §8에 적는다.
  - 페이지 다시 불러오기로 무장 표시를 바꿀 때 깜빡임·포커스 이동이 없는지, 다시 불러오는 동안 down·up 쌍이 온전히 관찰되는지.
  - 알림 창이 바를 덮을 때 바가 mouseLeave를 받는지, 창이 사라질 때 OS가 만드는 이동의 `movementX`·`movementY`가 0인지. 둘 중 하나라도 아니면 머무름 규칙을 다시 정한다.
  - 멈춘 커서 아래에 바가 뜬 뒤(예: 대기열의 다음 건) 마우스를 움직이지 않고 누른 클릭이 600ms 뒤 승인되는지.
  - 머무름·무장 표시가 사용자에게 실패로 보이지 않는지(특히 Chrome에서 인증서 비밀번호를 넣고 돌아온 직후의 클릭).
  - 패키지된 앱에 `--remote-debugging-port`를 붙였을 때 main이 종료하는지.
- **터치 탭**: 터치 입력은 마우스 이벤트 경로를 타지 않아 `before-mouse-event`가 뜨지 않을 가능성이 높다(R11 Q1). PoC-6에서 터치 기기로 확인한다. 뜨지 않으면 main이 볼 수 있는 다른 신호(`input-event`의 탭 계열)로 같은 판정을 할 수 있는지 본다. 둘 다 안 되면 터치 전용 기기는 마우스·터치패드가 필요하다고 안내한다(잔여 제약).
- **PoC-9**: 대화 열 하단 띠에서 입력창 쪽 습관 클릭이 승인으로 이어지는지 시험한다. 문제가 되면 입력창 예약 영역과 바 사이 간격을 늘리거나 작업 패널 하단으로 되돌리는 것을 사용자와 다시 정한다.
- **PoC-8**: H-04 플레이북을 쓸 때 민원증명 요약 줄의 `fieldKey`를 D02 사전·스키마에 넣는다. 넣기 전에는 민원증명 커밋 게이트의 바가 무장하지 않는다.
- **Phase 1 보안 검토**: 렌더러에서 main의 입력 이벤트로 이어지는 브라우저 쪽 입력 처리 경로를 점검하고, Electron·Chromium 보안 공지에서 이 경로의 버그를 추적한다(R11 Q2 확신도 중간).
- **Phase 1(M1-3·M4-2)에서 Hello PIN을 설정한 Windows 11 기기로 확인한다**: PIN만 있을 때 `Available`인지, 메시지(한글) 표시와 잘림, 바 클릭 직후 대화상자가 앞에 뜨고 포커스를 받는지, 원격 데스크톱 세션·잠금 중 동작, `DeviceBusy` 빈도, 로컬 계정 PC에서의 동작. 금고 잠금 해제의 Hello(D05 §2)와 발급 Hello가 연달아 뜨지 않게 합치는 방법도 정한다(보안카드 저장 방식은 ADR-020 결정 3). → 합치는 규칙은 ADR-026 결정 4(엄격 모드에서 한 번의 프롬프트), 저장 방식은 ADR-026 결정 2로 정했다(2026-11-03). 합치더라도 발급 근거가 되는 Hello는 바 클릭 뒤에만 뜬다.
- **접근성**: 키보드·화면 낭독기 사용자의 승인 경로는 미결이다. Electron 30부터 화면 낭독기 마우스 탐색 문제가 열려 있다(R11 Q4). Phase 1 접근성 검토 때 Alt+Y 접근성 설정을 켤지와 함께 정한다.
- **Phase 2**: 커밋 가드를 금고로 옮길 때, Hello를 켠 경우의 근거를 금고가 직접 검증할 수 있는 서명(대안 (g), `KeyCredential`의 `actionHash` 서명)으로 바꿀지 검토한다. 서명 형식(PKCS#1 v1.5인지 PSS인지)과 24H2 창 소유 오버로드는 실기로 확정한다.
