# ADR-051. 대화 하네스: 판정 → 도구 → 답, 기능 표 하나, 평가로 고친다

## 맥락

지금 대화는 길이 여럿이고, 길마다 문장을 읽는 방법이 다르다.

| 길 | 문장을 읽는 것 | 문제 |
|---|---|---|
| PC 사업자 대화(`chat.step`, `chat_agent`) | 생성 모델 한 번, 도구 8개(조회 5, 카드 3) | 도구가 세금계산서와 조회뿐이다. 은행 연결·인증서·폰 연결·설정·거래처 추가는 "할 수 없음"으로 끝난다 |
| PC 민원증명·꾸러미·등본 | `parseRegex`·`packAsk` 정규식(모델 앞에서 가로챔) | 정해 둔 꼴의 문장만 알아듣는다 |
| PC 개인 프로필 | `intent.resolve`(jev, `intent_route_v1`) → 로컬 파서 → `chat.respond`(`chat_reply`) | 사업자 대화와 다른 길이다. 판정 결과가 도구로 이어지지 않는다 |
| 폰 대화(`chat_phone`) | 생성 모델 + PR #427의 `issueIntent` 정규식과 `intentNet` 안전망 | 발급 말투를 정규식으로 늘려 간다. 머리말에 일상 말 예시(점심 메뉴)를 적어 넣었다 |

같은 뿌리에서 나온 증상이다.

- **사용자 문장을 앱 코드가 정규식으로 읽는다.** `issueIntent`, `OLDEST_ASK`, `FUTURE_DATE_SAID`, `/승인\s*번호/`, `parseRegex`, `packAsk`. 실평가에서 모델이 틀릴 때마다 하나씩 늘었다. 새 말투가 나오면 또 늘려야 한다.
- **판정과 실행이 섞여 있다.** 생성 모델 한 번이 "이게 무슨 말인가"와 "어느 도구를 어떤 인자로"와 "뭐라고 답하나"를 같이 한다. 틀려도 어디서 틀렸는지 잴 수 없다.
- **기능이 도구가 아니다.** 앱이 할 수 있는 일 대부분이 화면 버튼으로만 열린다. 말로는 못 연다.
- **평가는 있지만 관문이 아니다.** `tests/chat-eval`(60건)은 손으로 돌리고, 판정·도구 선택·답 품질을 따로 재지 않는다.

지키는 것은 그대로다: 모델에는 토큰·슬롯만 간다(D06), 발급 도구는 없다(승인은 main 승인 바·폰 하드웨어 키), 세무 판단은 고정 문구, 서버는 대화를 저장하지 않는다. 엔진이 토큰 공간을, main·폰이 값 공간을 맡는 지금의 경계도 그대로 쓴다.

## 결정(제안)

### 1. 원칙: 문장은 모델만 읽는다

1. **사용자 문장을 정규식이나 낱말 목록으로 해석하지 않는다.** 뜻을 읽는 것은 판정 모델과 대화 모델뿐이다. 앱 코드는 구조화된 것(판정 결과, 도구 인자, 도구 결과)만 검사한다.
2. 예외는 모델에 가기 전 보안 단계 둘뿐이다: 가림(마스킹)과 비밀 모양 거부(`chatSecretShaped`).
3. **고정 문장은 세 곳에만 쓴다**: 법적 경계(세무 판단), 시스템 오류, 도구 결과의 사실을 옮기는 틀(예: "○○ 앞으로 확인 카드를 만들었어요"). 사용자 문장에 맞춘 고정 답은 두지 않는다.
4. 틀린 것을 고치는 자리는 넷뿐이다: 판정 질문, 도구 설명, 머리말, 평가 사례. 정규식 안전망을 더하지 않는다. 고치기 전에 평가 사례를 먼저 더한다.

### 2. 한 턴의 구조

```
문장 ─ 가림 ─▶ ① 판정(jev, 생성 없음) ─▶ ② 길 고르기 ─▶ ③ 도구 루프 또는 말하기(생성 모델) ─▶ ④ 답 검사·채우기 ─▶ 화면
                     │                                            ▲
                     └──── 판정 결과는 ③의 입력이자 ④의 대조 기준 ───┘
```

**① 판정(`chat_route_v1` 번들, `/v1/decide`).** 입력은 가린 문장과 짧은 상태 줄(열린 카드, 진행 중인 발급, 직전에 되물은 칸, 기기). 질문:

| 질문 | 꼴 | 값 |
|---|---|---|
| `act` | 선택 | `task`(일을 시킴) · `lookup`(내 기록·돈을 물음) · `followup`(앞 되묻기에 답하거나 앞 요청을 고침) · `app_help`(앱 쓰는 법·할 수 있는 일) · `smalltalk`(일상 말) · `tax_advice` · `other` |
| `domain` | 선택 | `invoice` · `records`(발급 기록·매출·받을 돈·낼 돈·돈 흐름) · `cert_doc`(민원증명) · `bank` · `auth`(인증서·간편인증) · `phone_link` · `counterparty` · `pack`(세무사 꾸러미) · `capture`(영수증·현금 매출) · `settings` · `none` |
| `corrects_previous` | 예/아니오 | 방금 만든 카드나 진행 중인 발급을 고치는 말인가 |
| `mentions_tax_advice` | 예/아니오 | `intent_route_v1`과 같은 질문 |

- 결정 모델을 쓰는 이유: 생성하지 않고 선택지 확률만 낸다(지금 운영 값으로 0.4초, 호출당 약 0.15원, `decision_pick` 측정 2026-11-16). 확률이 보정돼 있어 "모르겠다"를 문턱으로 가를 수 있다.
- 문턱(예: `act`·`domain` 각 0.8) 아래면 길은 `unsure`다. 이때 고정 문구로 떨어지지 않고 ③이 도구 전부를 들고 돈다. 판정이 실패(게이트웨이·시간 초과)해도 같다. 판정은 길을 좁히는 것이지 막는 문이 아니다.
- "몇만원 끊어줘"는 `task`·`invoice`다. 거래처가 없다는 것은 판정이 아니라 ③의 `invoice_draft`가 `needs_input`으로 알린다.
- `intent_route_v1`과 `intent.resolve`는 이 번들로 대체한다. 개인 프로필 대화도 같은 길로 들어온다.

**② 길 고르기(코드, 표 하나).**

| 판정 | 길 | 모델에 주는 도구 |
|---|---|---|
| `task`·`lookup`·`followup` + 도메인 | 도구 루프 | 그 도메인의 도구 + 늘 주는 작은 묶음(`app_status`, 카드 고치기·취소) |
| `app_help` | 말하기 | 없음. 머리말에 기능 표에서 만든 "할 수 있는 일" 목록 |
| `smalltalk`·`other` | 말하기 | 없음 |
| `tax_advice`(작업 없음) | 모델을 부르지 않고 고정 문구 | 없음 |
| `unsure`·판정 실패 | 도구 루프 | 전부 |

**③ 도구 루프·말하기.** 도구 루프는 지금 `chat.step` 구조 그대로다(엔진이 가림·역치환·답 검사, main·폰이 실행과 값). 말하기는 새 툴셋 `chat_talk`(도구 없음, 1턴, 짧은 머리말)다. `chat_reply`를 대체한다. 머리말에는 성격과 경계만 적고 문장 예시를 늘어놓지 않는다.

**④ 대조.** 판정이 `task`를 높은 확률(예: 0.9 이상)로 냈는데 ③이 도구를 하나도 부르지 않고 잡담으로 답하면, 도구 호출을 요구해 한 번만 다시 부른다. 그래도 아니면 모델 답을 그대로 보인다. PR #427의 `intentNet`이 하던 일을 정규식 없이 한다.

### 3. 기능 표 하나(`@sax/chat-core`)

지금 `tables.ts`의 도구 표를 넓혀 **앱이 대화로 할 수 있는 일의 유일한 원본**으로 삼는다. 한 줄에 적는 것: 이름, 인자 스키마, 도메인, 효과 등급, 되는 기기(PC·폰), 선행 조건, 결과 status, 화면 결과(카드·표·화면 열기). 여기서 만들어지는 것: 툴셋 정의, 머리말의 도구 절, 판정 번들의 `domain` 선택지, `app_help` 목록, 평가의 정답 후보. 손으로 맞추던 것을 생성으로 바꾸고 시험이 대조한다.

효과 등급은 넷이고, 대화 도구는 앞의 셋까지만 가진다.

| 등급 | 뜻 | 예 |
|---|---|---|
| `read` | 읽기 | 조회, 상태 확인 |
| `draft` | 되돌릴 수 있는 준비 | 카드 만들기·고치기·취소 |
| `open` | 흐름·화면을 연다(그 안에서 사람이 진행) | 은행 연결, 인증서 등록 |
| `commit` | 되돌릴 수 없음 | 발급, 신청, 보내기. **도구로 만들지 않는다.** 승인 바·하드웨어 키만 |

더하는 도구(1차):

| 도구 | 등급 | 하는 일 |
|---|---|---|
| `open_flow(flow)` | open | 인자 없는 흐름을 바로 연다: `bank_connect`, `cert_register`, `simple_auth`, `phone_link`, `counterparty_add`, `tax_pack`, `receipt_capture`(폰), `cash_sale`(폰), `settings.*`. 결과 status: `opened`·`already_done`·`needs_setup`·`not_on_this_device` |
| `app_status(topic)` | read | 은행·인증·폰 연결·구독·내 사업장 상태를 열거값으로 돌려준다. "은행 연결됐어?"에 답하고, 흐름을 열기 전에 본다 |
| `cert_doc_request(doc, purpose\|null)` | draft | 민원증명 카드. 지금 `parseRegex`가 하던 일 |
| `counterparty_lookup(name)` | read | 장부에 없는 이름일 때 비슷한 거래처 후보(이름은 토큰으로) |

- 비밀(인증서 비밀번호 등)은 대화에 들어오지 않는다(ADR-019 결정 3). 보안카드 지원은 없애기로 해서(2026-11-19, 은행 연결 스레드가 코드에서 삭제 중) 도구 목록에 넣지 않는다. `open_flow`는 금고 비밀 창이나 전용 화면을 열 뿐이다.
- 폰에서 안 되는 도구는 표의 기기 칸으로 정하고, 결과는 `not_on_this_device`다. 폰은 그 요청을 밀린 일로 넘긴다(ADR-047 결정 6 그대로). PC용·폰용 머리말을 따로 손으로 쓰지 않고, 한 틀에 기기 절만 바꿔 만든다.
- 인자 있는 흐름이 늘면 `open_flow`에 넣지 않고 전용 도구로 만든다.

### 4. 발급은 늘 같은 카드, 정정은 자동 대체

- **불변식 1:** 세금계산서는 어디서 시작하든(PC 대화, 폰 대화, 빠른 실행, 화면 버튼, 폰이 맡긴 일) 같은 확인 카드 하나로 모이고, 발급은 승인으로만 된다. 카드를 만드는 함수는 하나다.
- **불변식 2(정정):** 고치는 말이 오면 고칠 대상의 상태로 정한다. 모델은 `draft_edit`만 부르고 상태 판단은 기기가 한다.

| 대상 상태 | 처리 | 도구 결과 |
|---|---|---|
| 카드(준비 전) | 그 카드를 고친다 | `card_updated` |
| 홈택스에서 준비 중·승인 대기 | 진행을 멈추고, 고친 값의 새 카드로 **대체**해 다시 준비한다. 옛 카드는 "새 카드로 바뀜"으로 접힌다 | `card_replaced` |
| 승인을 눌렀거나 발급됨 | 고치지 않는다. 수정세금계산서 길을 안내한다 | `not_editable` |

- 승인 전에는 홈택스에 아무것도 발급되지 않았으므로 멈추고 다시 하는 것은 되돌릴 수 있는 일이다. 지금은 준비 중인 카드에 `not_editable`을 준다.
- 대체는 같은 흐름의 값이 바뀐 것이므로 승인 대조 값(`draftKey`)을 새로 만든다. 옛 승인 대기는 무효가 된다.
- PC 채팅 스레드가 진행 중인 카드 통일·정정 구현을 이 표의 출발점으로 삼는다.

### 5. PC와 폰은 같은 하네스

판정, 길 고르기, 기능 표, 답 검사, 대조(2절 ④)는 `@sax/chat-core`에 두고 PC 엔진과 폰이 같이 쓴다. 지금 따로 있는 두 루프(`engine/chat-agent.ts` 756줄, `chat-core/phone-chat.ts` 928줄)는 마지막 단계에서 `ChatHarness` 하나와 포트로 합친다. 기기 차이는 포트(장부·사본·카드·화면 열기)와 표의 기기 칸이다.

폰이 판정을 부르려면 게이트웨이가 폰 토큰(`chat` 범위)에 `/v1/decide`를 `chat_route_v1` 번들 하나만 연다. 다른 번들과 실행 범위 판정은 지금처럼 닫혀 있다(ADR-047 결정 2 개정, 대표 결정 2: 열기).

### 6. 평가: 층마다 따로 재고, 고칠 때 관문으로 쓴다

`tests/chat-eval`을 넓힌다. 사례는 가상 장부 위의 문장이고 층마다 정답을 적는다.

| 층 | 재는 것 | 정답 | 채점 |
|---|---|---|---|
| A 판정 | `act`·`domain`·`corrects_previous` | 사례마다 라벨 | 정확도, 분류별 재현율, 보정(ECE), `unsure` 비율 |
| B 도구 | 부른 도구와 인자 | 기대 도구·인자(꼭 필요한 것만) | 일치 |
| C 화면 결과 | 생긴 카드 값, 보인 표, 되물은 칸 | 지금 `cases.ts` 방식 | 일치 |
| D 답 품질 | 자연스러움, 묻는 말에 답했나, 지어낸 값·세무 판단 없음 | 채점 기준표 | 규칙 검사 + 상위 모델 채점 |
| E 여러 턴 | 되묻기 → 답, 정정 → 대체, 조회 → 같은 금액으로 발급 | 시나리오 | C와 같음 |

- **세트:** 대표가 실제로 쓴 문장을 씨앗으로 말투를 넓힌다(금액만, 거래처만, 오타, 줄임말, 사투리, 반말, 정정, 일상 말, 세무 질문, 지시 주입). A층 300건 이상, B~E층 120건 이상으로 시작한다. 대표가 "이 말을 못 알아들었다"고 하면 그 문장이 먼저 사례가 된다.
- **관문(초안 값, 1단계 기준선을 재고 확정):** 발급 요청을 일상 말로 놓치는 비율 2% 이하, 일상 말을 작업으로 잘못 여는 비율 2% 이하, A층 전체 정확도 92% 이상, C층은 지금 통과율(crusoe 59/59)을 내리지 않는다.
- **언제 돈다:** 가짜 상류(`--fake`) 배선 시험은 PR마다 CI에서. 실모델 평가는 머리말·기능 표·번들·모델 설정이 바뀐 PR과 매일 밤. 결과는 `reports/chat-eval/`에 남기고 PR에 앞뒤 차이를 붙인다. 관문 아래면 합치지 않는다.
- **모델 별칭:** `jev-latest`나 대화 모델이 다른 버전으로 풀리면 A층을 다시 돌린다(작업 노트 1.6).
- **비용(짐작):** A층 300건 × 약 0.15원 = 약 45원, B~E층 120건 × 약 3원 = 약 360원. 한 번에 500원 안쪽이다. 1단계에서 실제로 잰다.
- **운영 신호(내용 없음):** 턴마다 길, 확률 구간, 부른 도구 이름, 걸러진 종류, 다시 부름 여부만 남긴다. `unsure` 비율, ④의 다시 부름 비율, 같은 사용자가 바로 고쳐 말한 비율을 본다. 문장·토큰·값은 남기지 않는다.

### 7. 비용과 지연(짐작, 1단계에서 잰다)

- 작업 턴: 판정 약 0.15원이 더해지고, 도메인 도구만 실어 머리말·도구 정의가 줄어든다. 지금 한 번 약 0.7~2.9원(ADR-047 맥락).
- 일상 말 턴: `chat_talk`은 짧은 머리말이라 지금 `chat_agent` 전체를 싣는 것보다 싸다.
- 지연: 판정 약 0.4초가 앞에 붙는다. "생각 중" 표시는 보내자마자 뜬다. 목표는 한 턴 중앙값 3초 안.
- 하루 한도(체험 50원, 구독 300원)는 계정 단위 그대로다.

## 기각

- **생성 모델 한 번에 전부 맡기기(지금 방식에 도구만 더하기):** 가장 단순하다. 그러나 도구가 20개 가까이 되면 싼 모델의 도구 선택이 흔들리고, 일상 말에도 전체 머리말 값을 낸다. 판정과 실행을 따로 잴 수 없다.
- **판정을 생성 모델의 구조화 출력으로:** 보정된 확률이 없어 "모르겠다"를 가르기 어렵고 3~4초가 든다. jev가 한국어 관문을 못 넘으면 이것이 차선이다(판정은 포트 뒤에 있어 바꿔 끼울 수 있다).
- **정규식 안전망을 계속 늘리기:** 말투마다 규칙이 필요하고 규칙끼리 부딪친다. 대표 지시와 반대다.
- **판정이 확실하지 않으면 고정 문구:** 막다른 답이 된다. `unsure`는 도구 전부를 든 대화 모델로 간다.
- **발급·보내기 도구:** 모델 출력으로 되돌릴 수 없는 일이 시작되면 안 된다.
