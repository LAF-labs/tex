## 2. 계정 모델

```text
account(id, email, status, plan, created_at, aik_pub, aik_pinned_at, k_chk_sentinel)
  ├─ subscription(plan: starter|business, period, renew_at, pg_customer_ref)
  ├─ profile_slots: 1..2  (slot_token: 계정별 무작위. 번호·종류 의미 없음 (C-09, C/X-05)
  │                         biz_hmac?: HMAC(K_idx, "SAX-bizno-v1" ‖ bizNo)[:16], biz_bound_at (B-28))
  ├─ device_list: AIK 서명 DeviceListEntry[] + list_version (서버는 보관·중계만, 신뢰 앵커 아님 (C-01))
  ├─ devices(desktop: 1~2, mobile: 1~3): device_id, platform, name, registered_at, attest_signal, state(active|suspended|revoked)
  ├─ aik_change_pending(new_aik_pub, old_aik_sig, effective_at)
  ├─ recovery_hold(device_id, until)
  ├─ usage(month, l1_tokens, l2_in, l2_out, cost)
  └─ consents(version, at)
```

- 프로필 슬롯 상한 2는 서버가 강제한다(슬롯 등록 API가 3번째를 거부). 기기당 로컬 DB에도 `ux_profiles_kind`로 이중 강제.
- 서버가 아는 것(C/X-05): 슬롯 개수와, `biz_hmac`이 있으면 '사업자 프로필 보유' 여부. 사업자번호·상호는 모른다.
- 프로필 사업자 바인딩(B-28): 사업자 프로필 생성·변경 시 데스크톱이 기기 범위 토큰으로 `biz_hmac`을 등록한다. **재바인딩은 90일에 1회**(`PROFILE_REBIND_MIN_DAYS = 90`). RK 교체에 따른 재계산 재등록(D08 §9.4)은 AIK 서명이 있으면 횟수에 세지 않는다.
- 기기 등록·해제 이력 상한(C-32): 30일에 데스크톱 3회·모바일 5회. 결제 수단 단위 계정 수가 많으면 경고한다. 신원 확인 없이 다계정을 막을 수는 없다(잔여 위험).

### 2.1 인증 (C-03·C-04·C-30)

- **로그인**: 이메일 **6자리 일회용 코드**(수명 10분, 5회 실패 잠금)가 기본이다. 링크를 쓰는 경우 요청한 브라우저·앱 세션에 결속해 같은 기기에서만 완료된다. 패스키 등록을 온보딩에서 권한다. 메일 발송은 국내 사업자를 쓰고 수탁자로 공개한다.
- **데스크톱 로그인**: RFC 8252 루프백 리디렉트 + PKCE. **OAuth 디바이스 플로우는 쓰지 않는다**(피싱 표면만 늘린다). 받은 토큰은 금고에 보관한다.
- **토큰 두 종류**:
  - 계정 세션: 구독·결제, 기기 관리(목록 열람·긴급 정지·해제 요청), 동의 관리**만** 쓸 수 있다.
  - 기기 범위 토큰: **AIK 인증서가 있는 기기**에만 발급한다. 요청마다 기기 키로 서명한 증명(DPoP 방식, `SAX-dpop-v1`)을 붙인다. 블롭·메타데이터·조회 에이전트·깨우기·업무 키 표시 API는 이 토큰만 받는다. **Phase 1**에도 데스크톱은 AIK와 AIK가 발급한 자기 기기 인증서를 가지므로, 업무 키 표시 API는 Phase 1부터 데스크톱 기기 범위 토큰으로 연다(계정 세션 불가, E-07). 폰·블롭·조회 에이전트용 토큰은 Phase 2.
  - 이메일 로그인 직후의 새 폰은 페어링(= PC의 AIK가 인증서 발급) 전에는 조회 에이전트·블롭·메타데이터를 쓸 수 없다.

### 2.2 기기 추가·삭제·긴급 정지 (C-01·C-02·C-06·C-21, C/X-18)

- **첫 데스크톱**: 계정에 기기가 없을 때 처음 설치한 데스크톱이 `AIK_pub`를 등록하고 고정한다(D08 §4.1). AIK 교체는 옛 AIK 서명 + 7일 지연(`pairing.aikChangeDelayDays = 7`) + 모든 기기·이메일 알림.
- **새 기기 등록**은 둘 중 하나다. (a) 기존 AIK 인증 기기의 승인(`SAX-acct-op-v1`), (b) 이메일 확인 + **72시간 대기**(`device.emailOnlyAddDelayHours = 72`) + 모든 기존 기기 알림. **패스키가 등록된 계정은 이메일만으로 기기를 추가할 수 없다.** 서버 등록은 신뢰가 아니다. 실제 신뢰는 페어링 때 AIK가 발급하는 인증서에서 온다.
- **삭제**: 유예 없는 즉시 삭제는 **AIK로 서명된 요청**(`SAX-acct-op-v1`)만 허용한다(AIK는 복구 문구에서 파생되어 데스크톱에만 있다). 등록 7일 미만 기기의 서명(`device.newDeviceCoolingDays = 7`)과 계정 세션만 있는 요청은 모두 **7일 유예**(`account.deleteGraceDays = 7`) 대상이다. 블롭·메타데이터의 대량 삭제(1일 10건 초과)도 같다. 유예 중에는 모든 기기·이메일에 알리고 취소할 수 있다. 유예 후 메타데이터·블롭 삭제, 계량 결제 레코드는 회계 보존 기간만 보관.
- **복구 보류**(D08 §9.5): 복구 문구로 복구한 새 기기는 72시간 동안 블롭 다운로드와, 그 문구에서 재생성한 AIK의 모든 서명(기기 추가·폐기·삭제·긴급 정지 해제·AIK 교체)이 거부된다. 기존 AIK 인증 기기가 승인하면 즉시 해제, **거부**하면 복구 시도 폐기·새 기기 키 영구 차단·전 기기와 이메일 알림·새 복구 문구(RK′) 발급 절차 안내(E-11). AIK 교체 7일 지연의 기준 시각은 서버 수신 시각이다.
- **기기 긴급 정지**(D08 §9.3): 계정 웹에서 누르면 해당 기기의 블롭·메타데이터·조회 에이전트·릴레이 우편함 토큰·푸시 토큰·깨우기를 즉시 정지한다. 정지만 가능하고 재활성화는 AIK.
- 상수 `account.*`·`device.*`는 서버가 강제하고 투명성 페이지에 게시한다.

## 3. 모델 게이트웨이 통제 명세

| 통제 | 구현 |

| 번들·툴셋 서버 정의 | 질문·도구 정의는 게이트웨이가 번들/툴셋 ID로 주입. 클라이언트가 임의 질문·도구를 보낼 수 없음 → 프롬프트 변조·비용 폭주 방지 |
| 2차 PII 트립와이어 (B-18) | 게이트웨이가 메모리에서 주민등록번호·사업자번호·카드·계좌 패턴을 검사하고, 걸리면 공급사로 보내지 않고 400 `gateway.pii_tripwire`와 카운트만 남긴다(본문 무저장 유지). **Phase 1에서는 `/v1/decide`·`/v1/respond`의 이미지 입력을 모두 400으로 거부**한다(`GW_ALLOW_IMAGES=false`) |
| 계량 분리 (C-23) | (1) 결제 레코드 `{account, month, tokens, cost}`만 계정에 연결. (2) 운영 통계 `{bundle, playbook, latency, outcome}`은 계정·기기 ID 없이. (3) 호출 단위 계정 연결 레코드는 결제 대사 기간 **35일**만. 처리방침에 항목·보존·목적을 명시 |
| 한도 | 계정 월 토큰 한도, 분당 요청 한도(L1 60/min, L2 10/min), 실행당 예산은 게이트웨이가 서명한 `runToken`으로 서버가 집행. L1 하드 상한(플랜 2배) 이후 안전 판정 번들만. 거절·위반 급증 계정 자동 정지 |
| 공급사 설정 | `safety_identifier = HMAC(K_sid, accountId ‖ yyyymm)[:32]`(**월 회전**, `K_sid`는 KMS, 게이트웨이 외 접근 불가. 공급사의 남용 추적이 월 단위로 끊기는 대가를 감수). `prompt_cache_key = acct:<HMAC(server_secret, accountId)>:b:<bundleId>`(Decisions)·`acct:<HMAC(server_secret, accountId)>:t:<toolsetId>`(Terra)(계정별 격리, 정본은 gateway-request.schema 규칙 (4)와 D04 §2.1이며 여기서는 인용만 한다. C-11·C/X-01). 응답의 `cached_tokens`는 클라이언트에 넘기지 않고 계량에만 쓴다. `store:false`, ZDR 승인 시 전 계정 공통. ZDR 전에는 공급사 남용 모니터링 보존(최대 30일, 법적 보존 예외)이 적용된다(C-29, §10) |
| 무결성의 신뢰 지점 (C-24) | **게이트웨이는 모델 출력 무결성의 신뢰 지점이다.** 클라이언트가 보내는 `bundleDigest`(불일치 409)는 배포 불일치 감지용이지 무결성 장치가 아니다. 악의적 게이트웨이는 비교를 건너뛸 수 있다. 그래서 엔진은 응답을 비신뢰 입력으로 다룬다: 결과 매핑·임계값은 로컬 번들 정의로 계산하고, 로컬 툴셋 정의에 없는 도구 호출은 버린다(D04 §7). 게이트웨이는 공급사로 보낸 질문 목록의 해시를 응답에 실어 클라이언트가 로컬 번들과 대조하게 한다(악의적 게이트웨이는 이것도 속일 수 있다) |
| 장애 | 공급사 5xx·429 → 지수 백오프 2회 → 클라이언트에 `unavailable` → 엔진은 L0만으로 진행 가능하면 진행, 아니면 핸드오프 |
| 키 관리 | 공급사 API 키·`K_sid`·캐시 키 서버 비밀은 클라우드 KMS, 로테이션 90일, 게이트웨이 외 서비스는 접근 불가. 레지스트리 서명 키는 여기에 두지 않는다(§8) |

## 4. 릴레이

- WSS 우편함의 프로토콜·한도는 D08 §8이 정본이다(C/X-03). 이 절은 서버 측 운영만 적는다.
- **정직한 서술(C-14)**: 릴레이는 내용과 키를 볼 수 없다. 계정과 우편함의 연결은 분리 저장·접근 통제·짧은 보존으로 줄이지만, 운영자는 연결 시점·IP 상관으로 언제든 연결할 수 있다. 그래서 '영지식'이라고 부르지 않는다. 우편함 ID·능력 토큰은 PC가 만든 CSPRNG 난수이고 서버는 토큰 해시만 저장한다. 페어링 룸(1회용, 120초)과 영구 우편함의 연관은 기록하지 않는다.
- 큐 디스크는 저장소 레벨 암호화를 추가한다(이미 E2E 암호문). 보존(C/X-02): 큐 본문 72시간, 메시지 크기 버킷·시각 7일.
- 접속 IP: 레이트리밋은 **일 회전 솔트 HMAC**으로만, 평문 IP는 법정 접속기록 대상인 운영자 접근 로그에만(§10).
- WSS의 TLS 종단은 특정 LB 기능에 의존하지 않는다(서버 직접 TLS 또는 L4/TLS 프록시, §9.1).
- 남용 방지 기기 인증의 비연결 토큰화(Privacy Pass 계열)는 Phase 3(SP-10).

### 4.1 사업자등록 진위확인 프록시 (C-25)

게이트웨이 경로의 기능이지만 다른 문서가 이 번호로 참조하므로 위치를 유지한다.

공공데이터포털 국세청 사업자등록정보 API(`api.odcloud.kr/api/nts-businessman/v1/status`, `/validate`)는 서비스 키가 필요하다(키 없이 401). 포털 표기 한도는 1회 100건·일 100만 건이나 서드파티 안내는 일 1만 건으로 불일치한다. 선택지: (a) 우리 게이트웨이가 우리 키로 프록시, (b) 사용자가 자기 키를 발급받아 금고에 저장(BYO 키).

- 설정 첫 화면에 (a)와 (b)를 **동등하게** 노출한다. 기본값은 (a).
- (a)는 **POST 바디로만** 받는다. 이 경로의 접근 로그에는 상태코드·지연만 남기고 계정 식별자도 남기지 않는다(레이트리밋은 메모리 카운터). 요청당 사업자번호 ≤ 10, 계정당 분당 30회.
- 처리방침에 "거래처 사업자번호가 서버를 통과해 공공데이터포털로 전달됨"을 적는다.

### 4.2 깨우기 푸시 (C-15, C/X-04, SP-3)

- PC가 기기 범위 토큰으로 `POST /v1/wake{device_id}`를 호출하면 푸시 디스패처가 해당 기기의 푸시 토큰으로 내용 없는 알림을 보낸다. iOS 알림 푸시(+Notification Service Extension), Android FCM data.
- 저장은 `device_id → 암호화된 푸시 토큰`(별도 키)뿐이고 **우편함 ID는 이 경로에 없다.** 운영자는 깨우기 시각과 우편함 접속 시각으로 둘을 상관시킬 수 있다(정직한 서술).
- 속도 제한: 기기당 분당 3회, 시간당 20회. 기기 폐기·긴급 정지 시 푸시 토큰 즉시 삭제.
- 처리방침에 APNs(Apple Inc., 미국)·FCM(Google LLC, 미국)을 수탁·국외이전으로 기재한다. 국내 공급사로 옮겨도 이 지점은 남는다.

## 5. 블롭 저장소 API (C-02·C-03·C-09)

모든 API는 AIK 인증 기기의 **기기 범위 토큰**(DPoP 서명)만 받는다. 계정 세션으로는 호출할 수 없다(C/X-20).

| API | 설명 |

| `POST /v1/blobs` | 멀티파트 암호문 업로드(Padmé 패딩 후), 응답 `blob_id`(서버 발급 무작위 UUID). 서버는 패딩 크기·계정을 기록하고, 업로드 시각은 접근 로그에만 **7일** 보존한다(E-08). Padmé는 크기 등급만 숨긴다 |

## 6. 메타데이터 인덱스 API (C-03·C-09·C-12, B-30)

- 인증: 기기 범위 토큰만.
- `PUT /v1/docs/{doc_id}`: D07 §5 논리 레코드 필드만 허용(`slot_token, doc_type?, issued_month?, expires_on?, blob_id, wdek, kek_ver, rev, signer_device_id, sig`). 추가 필드 400. 서버는 `rev ≤ 저장값`을 거부하고, 서명자가 AIK 서명 기기 목록의 데스크톱인지 확인한다. 색인이 꺼진 종류는 `doc_keys` 행만 만든다.
- `GET /v1/docs?slot_token&doc_type&expires_before`: 계정은 **토큰에서만** 정한다. 클라이언트는 `Sign_Vd`와 문서별 최고 `rev`로 응답을 검증한다.
- 서버는 `doc_type` 사전(열거형)만 받는다. 자유 텍스트 필드 없음. 크기·초 단위 시각·dedup 토큰 필드는 없다.
- 동기화: 클라이언트가 소스 오브 트루스. 충돌은 `rev` 높은 쪽 우선(같으면 서명 기기의 `list_version`이 높은 쪽).
- **발급 활동 표시**(업무 키 표시, B-30, E-07·E-13): **백업(메타데이터 동기화)을 켠 계정에만** 적용한다(서류 백업·서버 색인을 켜는 것과 같은 계정 스위치). `PUT /v1/bizmarks {hmac, state}`, `GET /v1/bizmarks/{hmac}`. 테이블 `biz_key_marks(account_id, hmac, state, day)`, `hmac = HMAC(K_idx, "SAX-bizkey-v1" ‖ businessKey)[:16]`, `state ∈ {armed, committed, in_doubt, observed_manual}`, `day`는 KST 일 단위(시각 없음). `armed` 행은 **10분 뒤 서버가 삭제**하고(행 존재 = 10분 이내), 나머지는 **보존 90일**. 인증은 데스크톱 AIK 기기 범위 토큰만(Phase 1부터, §2.1). 데스크톱 2대가 같은 업무 키로 중복 발급하지 않도록 게이트 직전에 조회해 카드에 경고한다(차단 아님, 다른 PC의 `armed`면 "다른 PC에서 같은 건 진행 중", D03 §4). 백업을 끈 계정은 기기 간 경고가 없음을 카드에 표시한다. 수 초 단위 동시 게이트는 막지 못한다(잔여 위험).

## 7. 조회 에이전트 (PC 꺼짐) (C-10·C-03, C/X-13, SP-9)

- 인증: AIK 인증 기기의 기기 범위 토큰만. 페어링 전 새 폰은 쓸 수 없다.
- **모델에는 사용자 질문(마스킹본)만 보낸다.** 마스킹은 **폰이 로컬에서** 한다(E-09): D06 정규식 마스킹(숫자형 식별자·이메일·전화)을 폰에 그대로 적용하고, 상호·대표자·거래처 이름 사전은 PC가 페어링 채널로 폰에 동기화(폰 Keychain 보호, 옵트인)한 뒤에만 조회 에이전트를 켠다. 사전 동기화 전에는 이름이 포함된 질문을 보내지 않는다(폰이 한글 2~4자 + 호칭·상호 문맥(님·씨·대표·상사·㈜ 등)을 보수적으로 치환하고, 치환이 일어나면 보내기 전에 사용자에게 보여 준다). 게이트웨이 2차 트립와이어(번호 패턴)는 그 뒤의 백스톱이다. 모델 호출은 D04의 조회 질문 해석(`query_parse`) 하나이며, 모델은 `query_kind`(has_doc, expiry, count_by_type, latest_issued, needs_body, unknown)와 열거형 파라미터(`doc_type` 열거값, 날짜 범위)만 돌려준다. `query_agent` 툴셋과 `list_documents`·`get_expiry` 같은 행 반환 도구는 없다(D04 §4).
- 서버는 **인증 토큰에서 얻은 `account_id`로만** 메타데이터를 결정적으로 조회하고, 결과를 템플릿에 채워 응답한다. **메타데이터 행은 어떤 경우에도 모델 입력에 들어가지 않는다.** 모델이 낸 파라미터에 계정·슬롯 식별자가 들어갈 자리는 없다.
- 색인이 꺼진 종류에 대한 질문은 "이 종류는 서버 색인을 끄셨습니다. PC가 켜져 있을 때 물어보세요"로 답한다.
- 본문이 필요하면 "폰에서 열어 보기"를 안내한다. **본문 요약은 PC가 켜져 있을 때 PC의 마스킹 계층(사용자 사전 포함)을 거쳐서만** 하고, PC가 꺼져 있으면 제공하지 않는다.
- 저장: 대화 로그 본문 비저장. 질문 유형·토큰만 계량(운영 통계는 계정 비연결, §3).
- 할 수 없는 것: 발급 실행, 본문 열람, 메타데이터 밖 필드 추론.
- SP-9: 메타데이터 최소화(월 단위·크기 없음·종류별 서버 색인) 뒤 02 §8 예시 질문의 답변 가능률 80% 이상을 확인한다.

## 8. 플레이북 레지스트리 (B-22·C-26·C-27, ADR-013)

### 8.1 배포 경로

정적 호스팅: `/registry/{channel}/index.json`, `/packages/{id}@{ver}.sxp`, `/policy/{ver}.json`, `/policy/current.json`(현재 정책, `{ver}.json`과 같은 내용, ADR-023), `/registry/status.json`, `/registry/revoked_keys.json`, `/registry/log/`(투명성 로그 트리 헤드·항목·증명).

조회 주기(ADR-023): 앱은 `status.json`·`policy/current.json`·`revoked_keys.json`을 켜져 있는 동안 15분마다, 기동·절전 복귀·네트워크 복구 직후, 실행 시작 직전(마지막 성공 조회가 5분 넘었을 때) ETag 조건부 요청으로 받는다. 레지스트리는 이 세 파일에 `Cache-Control: max-age=60`을 준다. 그래서 배포한 정책·status는 켜져 있는 앱에 20분 안에 닿는 것을 운영 목표로 한다(D03 §7.1 `POLICY_APPLY_TARGET_MIN`). 고정 경로 `current.json`은 서명·단조 버전 검사를 그대로 받으므로 롤백 통로가 되지 않는다.

### 8.2 서명 키와 역할 분리 (TUF식)

| 역할 | 키 | 보관 | 하는 일 |
|---|---|---|---|
| 오프라인 루트 | 루트 키(2-of-3) | 국내 보관 HSM 또는 오프라인 스마트카드 3장 중 2장. 연 1회 의식 | 온라인 서명 키 목록·`keyEpoch` 서명, `revoked_keys.json` 본문 서명 |
| 패키지 서명 | 키 3개, **2-of-3** | 서로 다른 사람이 각자 스마트카드·HSM 슬롯 보유 | 인덱스·패키지·핫픽스 |
| 정책 서명 | 키 3개, **2-of-3** | 위와 같음(패키지 키와 분리) | 운영 정책 |
| 타임스탬프 | 온라인 키 1개 | 국내 서버 HSM(자동) | 정책·`status.json`의 **48시간 주기 신선도 재서명**(내용 불변일 때, E-05), `revoked_keys.json`의 24시간 신선도 재서명, 로그 트리 헤드 |
| 1인 긴급 | 당직 키 1개 | 스마트카드 | **엄격하게 보수적인** 정책·`status.json` 내용 변경만(§8.5, 판정은 D03 §7.1 필드별 표) |

- **서명 알고리즘은 Ed25519를 유지한다.** 서명 키는 클라우드 KMS가 아니라 **우리가 국내에서 운영하는 HSM·스마트카드**에 둔다. 이렇게 하면 클라우드 공급사가 바뀌어도 서명 체계가 그대로다. 근거: 네이버클라우드 KMS의 키 타입은 AES256·RSA2048·ECDSA(P-256)뿐이라 Ed25519를 지원하지 않는다(R7 §0-2, R7 S6). 특정 클라우드 KMS의 Ed25519 지원 여부에 의존하지 않는다(현재 가정 공급사의 지원 발표도 R7에서는 검색 요약 수준, §9.1). 장치 선정·쿼럼 리허설은 SP-4.
- 핀 고정: 앱은 루트 키 3개와 현재 `keyEpoch`의 패키지·정책 키 3개씩을 핀 고정한다. 클라이언트는 `signatures[]`에서 **서로 다른 핀 키의 유효 서명 2개 이상**이 있어야 로드한다.
- 서명 의식: 2인 승인은 CI 기능이 아니라 하드웨어 쿼럼으로 강제한다. CI는 서명 대상 다이제스트를 만들 뿐 서명 권한이 없다(C-26).
- 서명은 **로드할 때마다** 다시 검증한다(`signature_ok` 플래그를 믿지 않음).
- 사용 감사: 서명 장치(HSM·스마트카드)와 클라우드 KMS의 사용 로그는 별도 계정의 추가 전용 저장소로 보내고, 서명 1건마다 투명성 로그 항목과 대조한다(SP-4, SP-6, S18).

### 8.3 투명성 로그 (C-26, C/X-16)

- 모든 서명 인덱스·패키지 다이제스트·정책·`status.json`은 추가 전용 Merkle 로그(RFC 9162 형식)에 **먼저** 기록하고 서명된 트리 헤드를 공개한다. 외부(감사인·고객)가 미러링할 수 있다.
- Phase 1: 클라이언트는 받은 산출물의 포함 증명과 트리 헤드를 확인·기록하고(`registry_state`), 트리 헤드를 레지스트리와 **별도 호스트(다른 도메인·다른 운영 계정)의 미러 1곳**에서도 받아 비교한다. 같은 크기에서 헤드가 다르거나 일관성 증명이 안 되면 `registry.head_mismatch`로 새 패키지·정책·핫픽스 적용을 보류한다(E-14, D03 §3.1). 엄격하게 보수적인 정책·status는 보류 중에도 적용한다(ADR-023 결정 4). Phase 2부터는 폰과 PC가 `hello.registryHeadHash`로 본 헤드를 교환해 다르면 경고한다(D08 §5).
- Phase 2: **포함 증명이 없는 인덱스를 거부**한다. 외부 증인(witness) 1곳 이상이 트리 헤드에 공동 서명한다.
- 자체 운영 대 Sigstore 계열 선택과 클라이언트 검증 비용(100ms 미만 목표)은 SP-6·S18에서 정한다.

### 8.4 버전·만료·폐기

- 인덱스는 **단조 증가 `version`** + 만료(`expires` ≤ 14일)를 가진다. 새 `version`은 저장된 값보다 크고 **`+1000` 이하**여야 한다(유출 키에 의한 버전 인플레이션 잠금 방지). 서명 키 세대 `keyEpoch`가 바뀌면 버전 비교는 새 세대 안에서만 한다. `keyEpoch` 변경은 오프라인 루트 서명으로만.
- **정책 신선도 만료는 ≤ 72시간**(패키지 인덱스는 14일 유지). 내용이 바뀌지 않는 재발행은 타임스탬프 키가 48시간마다 재서명하고(사람 쿼럼 불필요), 내용 변경은 2-of-3이다. `issuedAt`이 현재 시각 + 5분보다 미래면 거부한다. 패키지·정책·핫픽스마다 최저 버전을 둔다. **정책이 만료되면** 즉시 내리지 않고 마지막 유효 정책 유지 + 완화 금지 + 데몬 중지 + 핫픽스 로드 거부로 동작하고, 만료 후 **168시간(7일)** 지나면 전 포털 `postprocess`로 내린다(E-05, D03 §7.1). 약관 위반 상태 방지는 앱 내장 `PORTAL_MODE_CEILING`이 맡는다.
- 키 폐기 채널: 오프라인 루트가 서명한 `revoked_keys.json`을 따로 배포한다. 루트 서명은 목록이 바뀔 때(긴급 의식 포함) 하고, **24시간 만료**는 타임스탬프 키가 그 다이제스트를 재서명해 유지한다. 클라이언트는 폐기된 키의 서명을 즉시 거부하고, 24시간 신선도를 잃으면 새 패키지·정책 로드를 보류한다(설치본은 유지). 엄격하게 보수적인 정책·status는 이 보류 중에도 적용한다(ADR-023 결정 4).
- 서명키 유출 피해 반경: 엔진의 포털 eTLD+1 내장 허용 목록과 금고의 비밀 종류별 origin 허용 목록은 패키지가 바꿀 수 없다(앱 업데이트로만).

### 8.5 긴급 채널 `status.json`과 1인 긴급 키 (B-22, C/X-16)

- `/registry/status.json`(**만료 ≤ 48시간**)에 포털별 `portalModeCeiling`과 `killPlaybooks[]`를 담는다. 내용은 정책 키 2-of-3 또는 1인 긴급 키(하향·킬스위치 추가만)로 서명하고, 신선도는 타임스탬프 키가 48시간마다 재서명한다(E-05). 1인 긴급 키만으로 서명된 하향 status는 **72시간 뒤 자동 만료**되어, 그 안에 2-of-3 재확인이 없으면 클라이언트는 마지막 2-of-3 서명 값으로 되돌린다. 72시간 동안 갱신을 받지 못하면 데몬 실행을 멈추고, 홈택스 `auto`는 실행마다 "최신 운영 정책을 확인하지 못했습니다" 경고를 띄운다. 상수 `STATUS_MAX_AGE_H = 48`, `STATUS_STALE_DAEMON_STOP_H = 72`. 클라이언트는 §8.1의 조회 주기로 status를 받는다. 하향(`portalModeCeiling` 하향·`killPlaybooks` 추가)은 진행 중인 실행도 다음 스텝 경계에서 멈춘다. 커밋 구간 안이면 그 구간과 verify를 마친 뒤 멈춘다(D03 §2·§7.1, ADR-023 결정 5·6). 운영기관 요청에 따라 긴급 키로 한 하향은 72시간 자동 만료 전에 2-of-3으로 다시 서명한다(ADR-023 결정 7).
- 1인 긴급 키로 서명한 정책·`status.json`은 현재 값보다 **엄격하게 보수적인** 경우에만 클라이언트가 받는다. "엄격하게 보수적"은 정책의 **모든 필드**에 대한 방향 표(D03 §7.1, E-04)로 정의되며, 하나라도 반대 방향이거나 표에 없는 필드가 바뀌면 거부한다. 긴급 키 산출물도 투명성 로그에 기록하고 다른 키 보유자에게 자동 알린다(D12의 "당직 1인 + 사후 승인"은 이 범위로 제한된다).
- 잔여 위험: 1인 긴급 키(또는 그 탈취자)는 완화는 못 하지만 `portalModeCeiling` 하향·`killPlaybooks`로 서비스 가용성을 떨어뜨릴 수 있다. 이것은 의도된 킬스위치이며 72시간 자동 만료로 범위를 제한한다.

### 8.6 채널·롤아웃

- 채널: `stable`, `beta`, `hotfix`. 단계적 롤아웃(1% → 10% → 100%) 비율은 인덱스에 명시, 클라이언트가 기기 ID 해시로 자기 비율을 결정.
- 변경 로그는 사용자에게 보임(`strings.ko.json.changelog`).

## 9. 가용성·운영

- 게이트웨이 장애 시 영향: L1/L2 불가 → 플레이북은 L0만으로 가능한 범위까지 진행, 판정이 필요한 지점에서 핸드오프. 발급 자체는 가능(사람이 화면 보며).
- 릴레이 장애 시: 리모트 불가, 로컬 사용 무영향.
- 블롭·메타데이터 장애 시: 백업 보류, 로컬 무영향. 조회 에이전트 불가.
- 모든 서비스 SLO: 가용성 99.5%, 게이트웨이 p95 지연(공급사 제외) 50ms.

### 9.1 배포 가정과 공급사 중립 (R7 §0·§6)

- **현재 가정**: AWS 서울 리전. 이 가정은 이 절에만 적는다.
- **설계는 공급사 중립**이다. 의존하는 것은 (1) S3 호환 API의 하위 집합(PUT/GET/HEAD/DELETE/멀티파트. 버전 관리·Object Lock·버킷 정책에 기대지 않는다), (2) PostgreSQL, (3) TLS·WSS 종단을 특정 LB 기능에 의존하지 않음(서버 직접 TLS 또는 L4/TLS 프록시), (4) 레지스트리 서명 키는 자체 HSM·스마트카드(§8.2)다. 클라우드 KMS는 공급사 API 키 같은 운영 비밀에만 쓴다.
- **네이버클라우드로 옮길 때 바뀌는 것**(R7 §6): S3 호환 API에 버전 관리·Object Lock·`ListObjectsV2`가 없으므로 블롭 삭제 7일 유예와 백업 30일은 앱 레벨 소프트 삭제·별도 버킷 복제로 구현한다. WSS는 Network Proxy LB(TCP/TLS) 또는 서버 직접 TLS로 종단한다(ALB는 WebSocket 문서가 없어 PoC 전 사용 금지). KMS에 Ed25519가 없지만 서명 키를 자체 HSM에 두므로 레지스트리 설계는 바뀌지 않는다. 푸시는 SENS 중계 대신 APNs/FCM 직접 호출을 유지한다.
- 전환 결정은 ADR-015(별도)에서 한다.

### 9.2 사고 대응 연결 (C-31)

시나리오별 즉시 조치 표의 정본은 D11 §7이다. 서버 측에서 바로 쓸 수 있어야 하는 조치 수단은 다음과 같다: 계정 세션 전면 무효화와 신규 기기 등록 동결(계정 탈취), 우편함 토큰 전면 재발급 요청과 큐 폐기(릴레이 침해, 재발급은 라이브 세션에서 PC가 수행), 공급사 API 키 즉시 폐기와 처리 중 노출 범위 산정(게이트웨이 침해), 1인 긴급 키의 보수적 정책·`status.json` 발행(제재·프로토콜 결함), `revoked_keys.json` 긴급 의식(서명 키 유출), 기기 긴급 정지(폰 분실 + PC 꺼짐).
