## 0. 한 줄 요약

홈택스로 발급하려다 **아무것도 발급되지 않았음이 확정된 채** 끝났을 때만, 사장님이 새 승인 카드에서 "팝빌로 발급 · 건당 요금"을 보고 직접 누르면 팝빌 API로 같은 세금계산서를 발급한다. 자동으로 넘어가지 않는다. 공동인증서를 팝빌에 미리 등록해 둔 사장님만 쓸 수 있다. 홈택스 시도와 팝빌 시도는 **같은 의도(intent)의 원장**에 묶여, 어느 쪽이든 발급됐거나 발급 여부를 모르면 다른 쪽을 열지 않는다.

- 이것은 소버린 원칙의 두 번째 **사용자 선택 예외**다(첫 번째는 09의 은행 자동 연결). 켜면 사장님의 **공동인증서 개인키·비밀번호**와 그 세금계산서 데이터가 팝빌 서버에 저장된다. 켤 때 따로 동의를 받는다(§6).
- 우리 서버는 팝빌 연동 키로 **사업자별 30분 토큰만** 만들어 PC에 건넨다. 세금계산서 본문·인증서는 PC → 팝빌로 바로 가고 우리 서버를 지나지 않는다(§6.2). 다만 연동 키를 가진 우리 서버는 등록한 모든 사장님 이름으로 발급을 요청할 수 있는 힘을 갖게 된다. 이 위험을 정면으로 다룬다(§6.3).
- 06 §2에서 "만들지 않기로 한 것"으로 적은 ASP API 연동을 **폴백 한정으로 되돌리는** 기획이다. 01의 차별점 문구와 법률 질의 Q2의 사실관계가 바뀐다(§9, §13).

## 1. 왜, 그리고 어디까지

**왜**
- 2026-11-11부터 실제 PoC 고객이 쓴다. H-01이 끝내 안 되는 경우는 지금도 있다: 홈택스 점검·장애, 로그인 막힘(추가 인증·캡차 반복), 화면 개편으로 플레이북이 깨짐, 차단 신호로 쿨다운, Chrome이 없거나 안 뜸. 지금 끝 카드는 [다시 준비]와 [홈택스에서 직접 발급]뿐이다(PR #276).
- 홈택스 자체가 안 될 때 사장님이 할 수 있는 일이 없다. 발급기한(다음 달 10일) 직전이면 가산세가 걸린다. 팝빌은 홈택스와 별개로 국세청에 전송하는 발급 시스템 사업자라, 홈택스가 막혀도 발급이 된다.
- 대표 기준 "고객 입장에서 가장 좋은 것"(2026-11-12)으로 보면, 끝난 자리에서 한 번 더 누를 길이 있는 편이 낫다. 다만 **중복 발급은 홈택스 실패보다 나쁘다**(수정세금계산서·가산세·거래처 혼란). 그래서 "확정된 실패"에만 연다.

**범위(제안)**
- 넣는 것: H-01 **정발행 당초분 1건**(공급자 = 내 사업장, 영수/청구, 과세·영세·면세는 홈택스 초안 그대로). 팝빌 국세청 전송 전 [발행취소].
- 넣지 않는 것: 역발행·위수탁, 수정세금계산서(H-06), 발급 취소 H-01c의 팝빌판, 대량 발행, 홈택스를 거치지 않고 처음부터 팝빌로 발급하는 기본 경로, 폰 원격 발급. 처음부터 팝빌로 쓰고 싶다는 요구가 쌓이면 따로 기획한다(그때는 ASP와 같은 제품이 된다).

**미확인**(테스트 환경·연동 문의로 확인할 것)
- 같은 `MgtKey`로 `RegistIssue`를 두 번 부르면 거부되는지(문서는 "고유 식별번호"라고만 적는다). §3.4가 이것에 기댄다.
- 발행 안내 메일을 끌 수 있는지, 보내는 사람이 공급자 상호로 보이는지, 메일 발송 성공을 조회할 수 있는지, 다시 보내는 API.
- 국세청 전송 설정(자동/즉시)을 API로 정할 수 있는지, 연동회원마다 다른지.
- `JoinMember`가 파트너 자격(LinkID)으로만 부르는 API인지, 이미 다른 파트너·팝빌 웹으로 가입한 사업자(중복 등록 불가)는 어떻게 붙이는지(`CheckIsMember` 등).
- 등록 팝업(`GetTaxCertURL`)이 브라우저만으로 인증서 파일을 받는지, 별도 프로그램 설치를 요구하는지, macOS에서 되는지.
- 등록한 인증서를 지우는 API가 있는지(해지 때 §5.5).
- 발행취소 때 포인트 환불 여부, 파트너 원가 단가.
- `X-LH-Forwarded`가 IPv6·통신사 NAT에서 맞는지(우리 서버가 본 IP와 PC가 팝빌에 닿는 IP가 다를 수 있다).
- 팝빌 이용약관·개인정보처리방침·파트너 계약의 책임·위탁 조항(공개 약관 페이지를 이번에 찾지 못했다). §8.2.
- 팝빌로 발급한 건이 홈택스 발급목록(H-02 조회)에 언제, 어떤 표시로 보이는지.

## 3. "최종 실패"의 정의와 원장 묶기

### 3.1 폴백을 열 수 있는 상태 (제안)

원칙: **발급되지 않았음을 앱이 확정한 실행만** 팝빌 폴백을 연다. "아마 안 됐을 것"은 확정이 아니다.

| H-01 실행이 끝난 상태 | 원장(ADR-042, 그 의도의 모든 시도) | 홈택스 발급 여부 | 팝빌 폴백 |
|---|---|---|---|
| 게이트 전에 끝남: 로그인 실패·캡차·`step.timeout`·`step.selector_miss`·`portal.unexpected_page`·`chrome.not_installed`·차단 신호 쿨다운·`run.handoff_timeout`(로그인 구간) | 발급 단계 행이 **없음**(무장한 적 없음) | 앱은 발급 버튼을 누른 적이 없다 → 앱 발급 없음 확정 | **연다**. 단 사장님이 Chrome을 넘겨받은 핸드오프가 발급 화면(s10 이후)에서 있었으면 사장님이 직접 눌렀을 수 있으므로 아래 "사람 손이 닿은 경우" |
| 게이트 뒤, verify가 발급목록 조회로 `not_committed`(D03 §5.6: 60초 뒤·조회 2회 이상, 기준선 대비 새 건 없음) | 모든 시도가 `not_committed` | 없음 확정 | **연다** |
| `in_doubt`를 사장님 증언으로 해소("홈택스 발급목록에 없음을 확인했어요", ADR-021 결정 5) | `not_committed`(증언) | 사람 확인 | **연다**. 카드에 "직접 확인해 주신 결과로 진행해요" 한 줄 |
| `armed`·`dispatched`·`in_doubt`(해소 전) | 미종결 행 있음 | 모름 | **절대 열지 않는다.** InDoubt 해소(발급목록 확인)로만 보낸다 |
| `committed`·`observed_manual`(사장님이 직접 발급) | 종결·발급됨 | 발급됨 | **열지 않는다** |
| 사람 손이 닿은 경우: 발급 화면 이후 핸드오프 뒤 [다 했어요] (`run.manualDone`)·시간 초과 | `observed_manual` 또는 verify 대기 | verify 결과를 따른다 | verify가 `not_committed`일 때만 연다 |
| 사장님이 [중지] | — | 없음 | 열지 않는다(실패가 아니라 사장님의 선택). [다시 준비]만 |

**실패 이유로도 거른다(제안)**: 팝빌로 바꿔도 안 되거나, 바꾸면 안 되는 실패에는 열지 않는다.
- 연다(홈택스 쪽 문제): 홈택스 점검·장애·응답 없음, 로그인·인증 단계 실패, 화면 변경(셀렉터·예상 밖 화면), 차단 신호 쿨다운, 캡차 반복, Chrome 문제, 발급 화면 서명 차례 시간 초과 뒤 `not_committed`.
- 열지 않는다(내용 문제): 공급자 사업자번호 불일치(s19c), 공급받는자 사업자번호 오류·휴폐업, 금액·품목 검증 실패, 업무 중복 키 경고를 보고 사장님이 멈춘 경우, 하루 실발급 상한(ADR-025) 도달.
- 차단 신호로 홈택스가 막혔을 때 팝빌로 가는 것은 탐지를 피하는 우회가 아니다(다른 정식 발급 시스템이고, 홈택스 화면에 요청을 보내지 않는다). 그래도 쿨다운 중 홈택스 재시도는 그대로 막는다(ADR-036 결정 2 내려가지 않는 규칙 4).

### 3.2 같은 의도의 원장에 묶기 (제안)

- 팝빌 발급은 **같은 `intent_id`** 의 새 단계 `popbill.issue`로 원장에 남긴다. 플레이북 ID는 `popbill.taxinvoice.issue@1`(앱 내장 절차, 서명된 패키지 아님), `inputs_hash`는 팝빌 요청 본문의 정규화 해시다.
- ADR-042의 불변식은 (intent, step)마다다. 홈택스 `s21`과 팝빌 `popbill.issue`는 step이 달라 서로를 보지 않는다. 그래서 **의도 단위 "발급 묶음" 불변식**을 더한다.
  1. 발급 단계 표지(`role = issue`)를 가진 step들(H-01 `s21`, `popbill.issue`)을 한 묶음으로 본다.
  2. 묶음 안 어느 행이든 `committed`면 새 시도 금지(`ledger_committed`).
  3. 묶음 안 미종결(`armed`·`dispatched`·`in_doubt`·`observed_manual`)이 하나라도 있으면 새 시도 금지.
  4. 묶음 안 모든 행이 `not_committed`이거나 행이 없을 때만 다른 채널의 시도를 허용한다.
  5. 팝빌 시도가 `committed`면 그 의도의 홈택스 재게이트·[다시 준비]도 막힌다. 반대로 팝빌이 `not_committed`로 끝나면(예: 팝빌이 검증 오류로 거부) 홈택스 [다시 준비]는 다시 열린다.
  6. DB: 부분 유일 색인을 `(intent_id, issue_group) WHERE state <> 'not_committed'`로 넓힌다(ADR-042 `ux_irr_live`의 묶음판).
- 업무 중복 키(D02 §7: 같은 거래처·같은 금액·같은 날)와 `$dup.priorNotCommitted`는 팝빌 카드에도 그대로 보인다.
- 실발급 상한(ADR-025 `irreversible/day`)은 채널과 관계없이 합쳐 센다.
- 대안 "팝빌 시도를 새 의도로 만들고 `fallback_of`로 잇기"는 기각(제안): 의도가 둘이면 두 의도가 동시에 열리는 것을 원장이 막지 못한다. 한 의도에 묶어야 DB 불변식 하나로 막힌다.
- 이 불변식은 ADR-042를 넓히는 일이라 설계 때 ADR을 먼저 쓴다(§10).

### 3.3 팝빌 쪽 멱등: 문서번호를 의도에서 만든다 (제안)

- `MgtKey`(24자)는 `intent_id`와 시도 번호에서 만든다(예: 접두 `SAX` + 해시 21자). 같은 시도는 언제나 같은 문서번호다.
- 승인 카드 승인 → 원장 `armed` → `CheckMgtKeyInUse`가 거짓인지 확인 → `RegistIssue` 한 번 → `dispatched`.
- 응답이 끊기거나 시간이 넘으면 **다시 발행하지 않고** `GetInfo(MgtKey)`로 확인한다(verify). 문서가 있고 발행완료면 `committed`, 문서가 없으면 일정 시간(제안 60초) 뒤 한 번 더 보고 `not_committed`. 팝빌은 문서번호로 바로 찾을 수 있어 홈택스 발급목록 비교보다 확실하다.
- 같은 `MgtKey` 재호출이 팝빌에서 거부되는지는 **미확인**이다. 거부된다면 팝빌 쪽에도 중복 방지 장치가 하나 더 생긴다. 거부되지 않아도 위 순서(원장 → 한 번 호출 → 조회)로 앱이 막는다.
- 팝빌 `not_committed` 뒤 같은 의도로 팝빌을 다시 시도하면 새 시도 번호 = 새 문서번호 = 새 승인 카드다(ADR-042와 같다).

### 3.4 남는 위험과 안전망: 국세청 전송 전 다시 보기 (제안)

- 남는 위험: 홈택스 verify가 `not_committed`라고 본 뒤 홈택스 쪽 처리가 늦게 반영되는 경우, 사장님이 다른 PC·홈택스 화면에서 같은 건을 따로 발급한 경우(ADR-024의 PC 간 중복과 같은 종류).
- 안전망: 팝빌은 기본 **자동전송(다음 영업일 15시)** 이고 그 전에는 발행취소가 된다. 그래서
  1. 팝빌 국세청 전송 설정은 자동전송으로 둔다(즉시전송이면 취소할 수 없다). 【결정 6】
  2. 팝빌 발급 뒤 다음 홈택스 로그인 기회(같은 날 다른 실행, H-02 조회)에 홈택스 발급목록에서 같은 거래처·금액·작성일 건이 보이면 즉시 "같은 건이 홈택스에도 있어요"를 띄우고 [팝빌 발급 취소] (= `CancelIssue`, 국세청 전송 전만)를 권한다. 자동으로 취소하지 않는다(취소도 사장님 승인).
  3. 국세청 전송 15분 전쯤 앱이 켜져 있으면 한 줄 알림 "팝빌 발급분이 오늘 15시에 국세청으로 갑니다. 그 전에는 취소할 수 있어요"(제안, 켜고 끌 수 있게).
- 발급일 다음 날까지 국세청에 전송해야 하는 의무(부가세법 시행령 제68조, 발급일 다음 날까지 전송)와 팝빌 "다음 영업일" 전송이 주말·공휴일에 어긋나지 않는지는 세무 확인 대상이다(**미확인**, §9).

## 4. 사장님 승인: 자동 전환 금지, 새 main 승인 카드

### 4.1 실패한 자리에서 고르게 한다

H-01이 §3.1의 "연다" 상태로 끝나면 끝 카드(PR #276의 실패·핸드오프 끝 안내)에 줄 하나와 버튼 하나를 더한다.

> 홈택스에서 발급하지 못했어요. **아무것도 발급되지 않았어요**(발급목록에서 확인했어요).
> [다시 준비] [홈택스에서 직접 발급] **[팝빌로 발급…]**

- 버튼 글자에 "팝빌"을 그대로 쓴다. "다른 방법으로" 같은 흐린 말을 쓰지 않는다.
- 팝빌 등록을 안 한 사장님에게는 [팝빌로 발급…]이 등록 안내(§5.3)로 간다. 보안카드·간편인증·금융인증서 사장님에게는 버튼을 보이지 않고, 홈택스가 계속 안 되면 쓸 수 있는 길로 설정 안내 한 줄만 둔다(§5.1).
- 앱이 먼저 팝빌로 넘어가지 않는다. 대화에서 "팝빌로 해 줘"라고 해도 이 끝 카드 상태에서만 같은 버튼을 띄운다.
- 발급기한(다음 달 10일)이 3일 안이면 끝 카드에 기한을 한 줄 더 보인다(앱이 계산한 날짜, 기존 기한 알림과 같은 문구 원칙).

### 4.2 팝빌 승인 카드 (제안)

[팝빌로 발급…]을 누르면 엔진이 팝빌 요청 본문을 만들고 main이 **새 승인 카드**를 그린다. ADR-021 결정 1·7의 틀(main 소유 뷰, [중지] 기본 포커스, 무장 지연, 마우스 down→up만, 값 대조)을 그대로 쓴다.

카드 줄(위에서 아래로)
1. 머리: **팝빌로 발급** · 홈택스가 아닌 팝빌(전자세금계산서 발급 대행 서비스)이 발급하고 국세청에 전송합니다.
2. 금액: 합계, 공급가액·세액.
3. 값 전체: 공급자(내 사업장, 팝빌에 등록한 인증서의 사업자번호와 대조), 공급받는자(상호·사업자번호), 품목, 작성일자, 받는 이메일, 영수/청구. `$first.*`·`$dup.*`·`$dup.priorNotCommitted`(방금 홈택스 시도) 그대로.
4. 요금: **건당 요금 ○원 · {부담 주체}**. 【결정 5】
5. 비가역 한 줄(앱 고정 문구): "승인하면 팝빌이 바로 발급하고 공급받는자에게 메일을 보냅니다. 국세청 전송 전(다음 영업일 15시 전)까지만 앱에서 취소할 수 있어요."
6. 서명 한 줄: "팝빌에 등록한 공동인증서로 팝빌이 서명합니다(비밀번호를 다시 묻지 않아요)."
7. 버튼: [중지] · [승인하고 팝빌로 발급].

값의 출처가 홈택스와 다르다.
- 홈택스는 엔진이 화면에서 되읽은 값("홈택스 확정")이다. 팝빌은 화면이 없으므로 **엔진이 보낼 요청 본문**이 값이다. main은 게이트 요청 `fields`를 그 본문에서 받고, 엔진은 승인 근거에 묶인 `inputs_hash`와 같은 본문만 보낸다(커밋 가드). 본문이 바뀌면 무장이 풀린다.
- 홈택스 시도에서 되읽은 값(있으면)과 팝빌 본문이 다르면 카드에 다른 칸을 표시한다. 다르게 만들 이유가 없으므로, 다르면 멈추는 쪽이 낫다(제안: 공급받는자 사업자번호·합계·작성일이 다르면 무장 거부).

### 4.3 지켜야 할 규칙

1. 자동 전환 없음. 끝 카드 → 사람이 [팝빌로 발급…] → 승인 카드 → 사람이 [승인하고 팝빌로 발급]. 두 번 누른다.
2. 승인 근거는 승인마다 새로(게이트 토큰·reqId·`LocalApproval`). 한 번 승인으로 여러 건을 보내지 않는다.
3. 홈택스 승인 근거를 팝빌 발급에 다시 쓰지 않는다. 홈택스 카드는 "홈택스에서 발급"에 대한 승인이었다.
4. Windows Hello 엄격 모드를 켠 사장님은 팝빌 승인에도 Hello를 묻는다(ADR-021 결정 3). 팝빌은 발급마다 인증서 비밀번호를 묻지 않으므로, 팝빌을 켤 때 엄격 모드를 권하는 한 줄을 둘지 【결정 12】.
5. 폰 원격 발급에는 열지 않는다(Phase 1은 PC 전용, ADR-036 결정 3.7과 같은 이유로 폰 승인 M7-7 뒤에 다시 본다).

## 5. 대상과 사전 등록

### 5.1 누가 쓸 수 있나

| 발급 인증(ADR-020) | 팝빌 폴백 | 이유 |
|---|---|---|
| 공동인증서(전자세금용·사업자 범용) | **가능** | 팝빌에 등록할 수 있는 인증서. 홈택스 전자세금계산서 발급에 쓰는 인증서와 같은 종류다 |
| 공동인증서(은행 발급 **금융거래용**·인터넷뱅킹용) | 불가 | 팝빌이 받지 않는다. 다만 이 인증서로는 홈택스 발급도 안 되므로 H-01 공동인증서 사장님에게는 드물다(**미확인**: 실제 PoC 고객 인증서 종류) |
| 금융인증서(클라우드) | 불가 | 팝빌 문서에 등록 방법이 없다(파일이 PC에 없다) |
| 보안카드 | 불가 | 인증서가 없다 |
| 사업자 간편인증 | 불가 | 인증서가 없다 |

- 홈택스 발급 인증을 보안카드·간편인증으로 둔 사장님도 공동인증서를 따로 갖고 있으면 팝빌 등록은 할 수 있다. 홈택스 발급 인증 고정(ADR-020 결정 1)과는 별개다(팝빌 인증서는 팝빌 발급에만 쓴다). 이 경우를 열지 【결정 3】의 하위 질문으로 둔다. 추천은 **연다**(인증서가 있는 사장님은 누구나). 인증서가 없는 사장님에게 인증서를 사라고 권하지는 않는다.
- 2026-04 발급 사업자 비중은 공동 83%·보안카드 14%·생체 2%·금융 1%다(ADR-020). 대부분이 대상이다.

### 5.2 언제 등록을 받나

| 안 | 장점 | 단점 |
|---|---|---|
| (가) 온보딩 O-03(공동인증서를 고른 직후)에 "홈택스가 안 될 때 대비" 선택 카드 | 막혔을 때 바로 쓴다(기한 직전에 등록할 여유가 없다) | 쓸지 모르는 기능에 인증서를 미리 맡긴다. 소버린 기본값과 어긋남. 온보딩이 길어진다 |
| (나) 첫 최종 실패 때(끝 카드 [팝빌로 발급…]) | 필요가 보일 때 묻는다. 맡기는 사람이 가장 적다 | 등록(가입 + 인증서 + 확인)에 몇 분이 걸린다. 기한 직전이면 급하다 |
| (다) 설정 > 발급 인증 > "홈택스가 안 될 때: 팝빌" | 원할 때 언제든 | 찾아야 한다 |

**추천: (나) + (다), (가)는 한 줄 안내만.** 온보딩에서는 맡기지 않고 "홈택스가 안 될 때 팝빌로 발급하는 길도 있어요(설정에서)" 한 줄만 둔다. 첫 최종 실패 때 등록을 제안하고, 설정에서 언제든 켜고 끈다. 등록은 홈택스와 무관하게 되므로 홈택스가 막힌 순간에도 할 수 있다. 【결정 3】

### 5.3 등록 흐름: 앱 안에서 끝낸다 (제안)

대표의 은행 연결 결정 "연동 과정 자체는 우리 앱에서 끝내"(2026-11-12, 09)와 같은 원칙이다. 사장님을 팝빌 사이트로 보내지 않는다.

1. **동의 카드**(§6.4): 무엇이 팝빌에 저장되는지, 건당 요금, 우리 회사가 팝빌에 처리를 맡긴다는 안내, 팝빌 약관 보기(카드 안에서 펼침). 필수 체크.
2. **연동회원 가입**: 내 사업장 프로필(사업자번호·상호·대표자·주소·업태·종목)을 채워 보여 주고, 담당자 이름·이메일·휴대폰을 묻는다(내 사업장에 있으면 채움). 팝빌 아이디·비밀번호는 앱이 무작위로 만들어 금고에 둔다(사장님이 팝빌 사이트에 로그인할 일이 없게, 파트너 결제 전제). 이미 팝빌 회원인 사업자번호면 **미확인**(§2) 처리 방식에 따라 기존 회원을 잇거나 안내한다.
3. **인증서 등록**(§5.4).
4. **확인**: `CheckCertValidation` = 정상, `GetTaxCertInfo`의 DN·사업자번호가 내 사업장과 같은지, 만료일. 다르면 등록을 멈추고 "다른 사업자의 인증서예요".
5. 끝: "팝빌 준비가 끝났어요. 홈택스에서 발급하지 못한 건만, 사장님이 고를 때 팝빌로 발급해요." 그리고 막혀 있던 그 건이면 바로 §4.2 승인 카드로.

### 5.4 인증서 등록 방법: 앱은 개인키·비밀번호를 만지지 않는다 (제안)

| 안 | 방법 | D05와의 관계 |
|---|---|---|
| **A. 팝빌 등록 팝업을 앱 창 안에** | PC가 토큰으로 `GetTaxCertURL`을 받아(30초) 앱이 띄우는 격리 창에 연다. 사장님이 그 창(팝빌 페이지)에서 인증서를 고르고 비밀번호를 넣는다 | 앱은 `signPri.key`를 열지 않고 비밀번호를 받지 않는다. D05 §6의 "사용자 파일을 포털에 전달하는 동작"(S1b)과 같은 종류다. 대상 사이트가 홈택스에서 팝빌로 바뀌는 것만 더한다 |
| B. 앱 금고 창에서 받아 API로 | 금고 창이 인증서 파일과 비밀번호를 받아 `RegistTaxCert`(공개키·개인키·비밀번호) 또는 `RegistTaxCertPFX`로 PC → 팝빌에 직접 보낸다 | 금고가 개인키 파일을 **열고** 비밀번호를 **받는다** → D05 §2(인증서 비밀번호를 다루지 않음)·§6(개인키 파일 미열람)의 예외가 필요하다. 09의 CODEF 연결도 이 길이라(인증서 der·key와 비밀번호를 CODEF로) 예외를 한 번에 정할 수는 있다 |

**추천: A.** 앱이 개인키·비밀번호를 한 번도 보지 않으므로 지금의 금고 약속(README 약속 2, D05 §6)을 덜 건드린다. "앱 안에서 끝냄"도 지킨다(사장님은 앱 창을 벗어나지 않는다). 단 팝업이 브라우저만으로 인증서 파일을 받는지, 별도 프로그램을 요구하는지, macOS에서 되는지가 **미확인**이라 팝빌 테스트 환경에서 먼저 본다. A가 안 되면 B로 가고 D05 예외를 ADR로 정한다. 【결정 4】
- A의 창은 전용 Chrome이 아니라 앱의 별도 창이다(제안). 홈택스 세션·프로필과 섞지 않는다. 허용 출처는 팝빌 도메인만.

### 5.5 만료·바꾸기·해지

- 만료: `GetCertificateExpireDate`를 하루 한 번 보고, 30일 전부터 이번 달 판에 "팝빌에 맡긴 인증서가 곧 만료돼요"(09 §4.4 조건 3과 같은 모양). 갱신한 인증서는 §5.4로 다시 등록한다. 만료되면 [팝빌로 발급…]은 등록 안내로 간다.
- 인증서 비밀번호를 바꾸면 팝빌 서명이 실패한다(**미확인**: 실패 코드). 실패하면 그 시도는 `not_committed`이고 다시 등록을 안내한다.
- 끄기(설정 > 팝빌 끄기): 등록 인증서 삭제(삭제 API 유무 **미확인**, 없으면 연동회원 탈퇴 또는 팝빌 문의 절차를 운영 체크리스트에) + 금고의 팝빌 아이디·비밀번호 삭제. 이미 팝빌로 발급한 세금계산서는 국세청에 신고된 것이라 팝빌에 남는다(법정 보관, **미확인**: 팝빌 보관 기간). 동의 카드에 미리 적는다.

## 6. 소버린 원칙 예외와 구조

### 6.1 무엇이 어디에 저장되나

| 것 | 지금(홈택스만) | 팝빌을 켜면 |
|---|---|---|
| 공동인증서 개인키 | 사장님 NPKI 폴더, 앱은 열지 않음 | **팝빌 서버에도 저장**(AES256-GCM). 앱은 계속 열지 않음(§5.4 A) |
| 인증서 비밀번호 | 저장 안 함, 사장님이 서명마다 입력 | **팝빌 서버에 저장**(암호화). 팝빌 발급 때 사장님은 넣지 않는다 |
| 팝빌 회원 정보(사업자번호·상호·대표자·주소·업태·종목·담당자 이름·이메일·휴대폰) | — | 팝빌 서버 |
| 팝빌 아이디·비밀번호 | — | 팝빌 서버 + 이 PC 금고(무작위, 사장님은 몰라도 됨) |
| 팝빌로 발급한 세금계산서(공급받는자 정보·품목·금액·이메일) | — | **팝빌 서버**. 이 PC 원장·문서함에도 |
| 홈택스로 발급한 세금계산서 | 국세청(홈택스)과 이 PC | 변화 없음. 팝빌로 가지 않는다 |
| 우리 서버 | 마스킹된 화면 텍스트·지시만 지난다 | + 토큰 요청(사업자번호, 기기 토큰), 가입 요청 한 번(회원 정보, 저장 안 함, **미확인** §2) |

### 6.2 토큰을 PC에 건넨다: 세금계산서가 우리 서버를 지나지 않게 (제안)

```
PC(엔진 net/egress) ──(기기 토큰, 사업자번호)──> 우리 게이트웨이
우리 게이트웨이 ──(LinkID·SecretKey 서명, access_id=사업자번호, scope=[member,110],
                   X-LH-Forwarded=PC가 게이트웨이에 닿은 IP)──> 팝빌 인증 서버
우리 게이트웨이 <── session_token(30분) ──
PC <── session_token ──
PC ──(Bearer, RegistIssue·GetInfo·GetPDFURL 등)──> 팝빌 API   ← 본문은 여기로만
```

- 연동 키(LinkID·SecretKey)는 앱에 넣지 않는다. 앱에 넣으면 누구나 꺼내 모든 사장님 이름으로 발급할 수 있다.
- 게이트웨이는 그 기기의 계정에 묶인 사업자번호에만 토큰을 준다(ADR-040 기기 토큰의 범위, 계정 프로필의 사업자번호). 다른 사업자번호 요청은 거부한다.
- `X-LH-Forwarded`를 PC IP로 묶어, 토큰이 새도 다른 곳에서 못 쓰게 한다. `*`는 쓰지 않는다. IPv6·NAT로 IP가 어긋나면(**미확인**) 게이트웨이의 이 엔드포인트를 IPv4 전용으로 두는 등 테스트 환경에서 정한다.
- 토큰은 엔진 메모리에만, 30분 안에서 필요할 때 받는다. 디스크·로그에 남기지 않는다.
- 이 구조는 09 §4.4 조건 5(CODEF 요청을 게이트웨이가 중계, 본문이 게이트웨이 메모리를 지남)와 다르다. 팝빌은 사업자별·IP 제한 토큰이 있어 본문을 중계하지 않아도 된다. 은행 쪽에서 팝빌을 쓸 때도 같은 구조가 낫다(09 결정 필요 12와 함께 보길 권함).

### 6.3 우리 서버가 갖게 되는 힘

팝빌을 켠 사장님에 대해 **연동 키를 가진 우리 서버는 그 사장님 이름으로 세금계산서를 발급할 수 있는 토큰을 만들 수 있다.** 인증서와 비밀번호가 팝빌에 있고 발급마다 비밀번호를 묻지 않기 때문이다. 지금 구조(우리 서버는 홈택스에 접속하지 않고 발급할 수 없다)와 가장 크게 달라지는 점이다.

줄이는 방법(제안)
1. 연동 키는 서버 비밀 관리(HSM 또는 KMS)에, 게이트웨이 토큰 발급 함수만 쓴다. 운영자가 키를 꺼내 볼 수 없게.
2. 토큰 발급은 **PC의 요청으로만**, 그 PC의 IP로 묶는다. 서버가 스스로 토큰을 만들어 쓰는 코드 경로를 두지 않는다.
3. 토큰 발급 기록(사업자번호·기기·시각·IP)을 남기고 사장님 활동 기록에도 보인다("팝빌 토큰 발급 · 11:02 · 이 PC").
4. 팝빌 쪽 파트너 IP 제한(토큰 요청을 우리 게이트웨이 IP에서만 받기) 기능이 있는지 확인(**미확인**).
5. 끄면 인증서를 지워(§5.5) 힘이 남지 않게 한다.
6. D19(공격표면)에 위협을 더한다: 연동 키 유출, 게이트웨이 장악, 토큰 탈취, 팝빌 쪽 유출.

### 6.4 동의 문구 초안 (제안)

> **홈택스가 안 될 때 팝빌로 발급하기**
> 홈택스에서 발급하지 못한 건만, 사장님이 고를 때 팝빌(전자세금계산서 발급 대행 서비스, 링크허브)로 발급해요.
> - 사장님의 **공동인증서와 인증서 비밀번호가 팝빌에 저장**돼요. 팝빌은 암호화해 보관하고, 팝빌로 발급할 때 그 인증서로 서명해요. 팝빌 발급 때는 비밀번호를 다시 묻지 않아요.
> - 팝빌로 발급한 세금계산서(거래처 정보·품목·금액·이메일)는 팝빌에도 저장돼요. 홈택스로 발급한 건은 팝빌로 가지 않아요.
> - 저희 서버는 팝빌에 접속할 수 있는 30분짜리 열쇠만 이 PC에 건네요. 세금계산서와 인증서는 이 PC에서 팝빌로 바로 가요. 다만 저희 회사가 팝빌 연동 계약을 갖고 있어, 저희 서버도 사장님 이름의 발급 열쇠를 만들 수 있는 구조예요. 저희는 이 PC의 요청 없이는 만들지 않고, 만든 기록을 활동 기록에 보여 드려요.
> - 팝빌 발급은 건당 요금 ○원이고 {부담 주체}.
> - 언제든 설정에서 끌 수 있어요. 끄면 팝빌에 맡긴 인증서를 지워요. 이미 발급한 세금계산서는 법에 따라 팝빌에 남아요.
> [필수] 위 내용과 팝빌 이용약관(펼치기)에 동의해요 · [필수] 개인정보 수집·이용 및 처리 위탁(또는 제3자 제공)에 동의해요

- "제3자 제공"인지 "처리 위탁"인지는 팝빌과의 계약 구조에 달렸다(§8.2, §9). 문구는 법률 확인 뒤 확정한다.
- 공급받는자(거래처)의 상호·대표자·이메일이 팝빌로 간다. 거래처 쪽 개인정보 처리 근거(세금계산서 발급이라는 법정 의무 이행)도 법률 확인 항목이다.

| 실패 | 팝빌이 검증 오류로 거부(사업자번호 오류 등)하면 `not_committed`, 팝빌 응답 코드를 사람 말로(없는 코드는 일반 문장). 포인트 부족(파트너 결제면 우리 운영 문제)은 "지금 팝빌 발급을 쓸 수 없어요"와 운영 알림 |

## 8. 비용과 계약

### 8.1 비용

- 단가: 웹 종량제 200원/건(R5, 2026-10). 파트너 결제는 원가 제공이라 더 낮을 수 있다(**미확인**). VAT 포함 여부도 계약 때.
- 규모: 폴백 전용이라 적다. 가정: PoC 고객 10명 × 월 1건 = 월 2,000원 수준.
- 누가 내나 【결정 5】
  - (가) **우리 회사(파트너 결제)**: 사장님은 팝빌 포인트를 몰라도 된다. 등록·충전을 위해 팝빌 사이트에 갈 일이 없어 "앱 안에서 끝냄"이 된다. 실패의 원인이 대개 우리 자동화나 홈택스 쪽이라 고객 입장에서도 자연스럽다. 남용 막기로 사장님당 월 상한(제안 20건, 넘으면 카드에 "이번 달 팝빌 발급을 많이 쓰셨어요"와 문의 안내).
  - (나) 사장님(연동회원 결제): 사장님이 팝빌 포인트를 충전해야 한다(최소 11,000원). 팝빌 사이트·결제로 나가야 해 앱 안에서 끝나지 않는다.
  - (다) 구독료에 더해 청구: 결제 대행·정산이 새로 생긴다.
  - **추천 (가)**. 카드의 요금 줄은 "건당 요금 ○원 · 소버린 AX가 냅니다".
- 01 §5 유닛이코노믹스에 변동비 한 줄을 더한다(나중).

### 8.2 팝빌 파트너 계약·약관에서 확인할 것 (계약 전, 모두 **미확인**)

09 §4.5의 CODEF 확인 틀을 그대로 쓴다.
1. 사장님(연동회원)이 팝빌 약관에 직접 동의해야 하는지, 동의를 앱에서 받아 넘기는 방식이 허용되는지.
2. 개인정보 구조: 우리 → 팝빌 **처리 위탁**인지, 사장님이 팝빌의 회원이 되는 **제3자 제공**인지. 위탁이면 위탁계약 표준안, 우리 처리방침에 수탁자 공개(개인정보 보호법 제26조).
3. 책임: 팝빌 귀책(유출·서명 오류·국세청 전송 누락·지연 가산세)의 배상 범위와 상대(우리인지 사장님인지). 파트너 서비스에 대한 면책 조항.
4. 인증서 보관: 보관 방식·기간·삭제 절차, 유출 통지 절차.
5. 파트너 키 보안 요구, 파트너 쪽 IP 제한, 토큰을 최종 사용자 PC에 넘겨 PC가 직접 호출하는 구조가 허용되는지(§6.2의 전제).
6. 발행 메일 발신 표시·끄기, 국세청 전송 설정의 회원별 지정.
7. 해지 때 연동회원·인증서·발급 문서 처리.
8. 요금: 파트너 원가, VAT, 결제·연체 시 서비스 중단 조건(CODEF처럼 연체로 전체가 끊기면 모든 사장님의 폴백이 끊긴다 → 운영 체크리스트).

## 9. 법적 지위: 바뀌는 사실관계와 확인할 것

**outreach Q2 사실관계에서 바뀌는 곳**
- 사실 1 "전자세금계산서는 사용자 PC의 브라우저에서 홈택스 화면으로, 사용자 인증수단의 전자서명으로 발급한다. 국세청 전송은 홈택스가 한다." → 폴백 건은 **발급 시스템 사업자(팝빌)** 가 사용자가 맡긴 공동인증서로 서명하고 국세청에 전송한다. 프로그램은 팝빌 API의 파트너로서 발급 요청을 보낸다.
- 사실 2 "당사 서버는 … 세금계산서 데이터를 저장하거나 국세청에 전송하지 않는다." → §6.2 구조면 문장 자체는 여전히 맞다. 그러나 **당사가 팝빌 연동 계약 당사자이고, 당사 서버가 사용자별 발급 토큰을 만든다**는 사실을 더해야 정직하다.
- 사실 3 "이메일은 … 홈택스가 발급 때 그 주소로 보낸다. … 당사 메일 서버로 세금계산서를 보내지 않는다." → 폴백 건은 팝빌이 보낸다.
- 0.1 "발급 건당 과금은 없다" → 폴백 건은 팝빌 요금이 생긴다(누가 내는지에 따라 문장이 바뀐다).
- 0.5 "서버로 가지 않는 것: 인증서·비밀번호" → 우리 서버로는 여전히 안 가지만 **팝빌 서버로 간다**(사용자 선택).
- Q4 "공동·금융인증서 비밀번호: 사용자 직접 입력 구조의 적법성"의 전제("저장하거나 자동으로 입력하지 않는다")가 폴백 사용자에게는 "팝빌에 맡긴다"로 바뀐다.

**새로 물을 것(제안: Q2 보충 또는 새 Q10)**
1. 당사가 팝빌(발급 시스템 사업자) API를 연동해 사용자의 발급 요청을 보내는 파트너가 되면, 당사가 발급 시스템 사업자 등록·표준인증(국세청 고시 제2026-26호) 대상이 되는가. 당사 서버가 토큰만 만들고 본문을 다루지 않는 구조가 판단을 바꾸는가.
2. 사업자 공동인증서(개인키·비밀번호)를 ASP에 등록하게 하는 것이 인증서 가입자 약관(본인 외 이용 금지, 제3자 이용 시 해지. ADR-036 결정 4에서 본 KB 약관 같은 조항)·전자서명법에 어긋나지 않는가. ASP 등록은 업계 관행이지만 **당사가 등록을 권하고 앱 안에서 받는 것**이 "본인 외 이용"이나 대리로 보일 여지가 있는가.
3. 개인정보: 사장님·거래처 정보를 팝빌로 보내는 것이 처리 위탁인지 제3자 제공인지, 필요한 고지·동의.
4. 같은 거래에 대해 홈택스 시도가 확정 실패한 뒤 ASP로 발급하는 흐름에서, 늦게 드러난 이중발급의 책임과 바른 처리(국세청 전송 전 발행취소 / 전송 뒤 착오 이중발급 수정세금계산서, 시행령 제70조 제1항 제7호).
5. 팝빌 "다음 영업일 15시" 전송이 발급일 다음 날까지 전송 의무와 주말·공휴일에 맞는지(지연전송 가산세 위험), 즉시전송으로 두어야 하는지.
6. 당사가 팝빌 요금을 대신 내는 것(무상 제공)이 문제 되는지(세무대리·광고 표현과의 관계, Q1).
- 회신 전에는 테스트 환경까지만 한다(§10). 실제 고객 발급은 회신(또는 대표가 받아들인 1차 검토) 뒤.

## 12. 열린 질문

- O-1. §2 미확인 목록 전부(테스트 환경·연동 문의).
- O-2. PoC 고객의 실제 발급 인증서 종류(전자세금용·범용·금융거래용·금융인증서 비중). 대상 규모가 이것에 달렸다.
- O-3. 이미 다른 경로로 팝빌 회원인 사업자를 어떻게 붙이나(중복 등록 불가).
- O-4. 홈택스가 막힌 날(장애) 팝빌 발급분의 국세청 전송도 밀리는지, 그때 발급목록 맞추기(§7)를 언제 할지.
- O-5. 국세청 전송 실패(305) 뒤 `SendToNTS` 재전송을 승인 카드 없이 해도 되는지. 새 발급이 아니라 같은 문서의 전송이라 비가역 승인이 필요 없다고 보지만, 사장님 확인 한 번은 두는 쪽이 낫다(제안).
- O-6. 팝빌 발급분의 수정세금계산서를 팝빌로 할지 홈택스 수정발급으로 할지(H-01c·H-06과의 관계).
- O-7. 팝빌을 켠 사장님이 "처음부터 팝빌로 해 줘"를 원하면. 이 기획은 막는다(§1). 요구가 쌓이면 별도 기획.
- O-8. 폰 원격 발급에 팝빌을 열지(공동인증서 사용자가 폰에서 발급할 수 있는 유일한 길이 된다). Phase 2 폰 승인 뒤.
