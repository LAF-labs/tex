# PoC-8 홈택스 민원증명 H-04 맥 선행 보고 (2026-11-01)

범위: 발급 **뒤** 단계(PDF → docparse 샌드박스 추출 → 메타 규칙 → 보관함·만료 표시)를 맥에서 먼저 만들었다. 실물 PDF가 나오면 발급 단계(S16·S3a, PoC-6 뒤)만 붙이면 된다. **범위 밖**: 실제 발급(S16 PDF 확보 경로, S3a 무대화상자 저장), 실물 20건 측정(스크립트만 준비), 셸 문서함 연결(PR #11·#13 머지 뒤 PR #14), `doc_meta_check_v1` 모델 호출.

근거: D14 §0 PoC-8, D13 S16·S3a·S4·S13b, D17 §3, D07 §3·§4, ADR-014. 양식 조사는 국세징수법 시행규칙 별지 제94호(납세증명서), 국세청 민원사무처리규정 별지 제5호(사업자등록증명), 국세징수법 시행령 제96조(유효기간), 홈택스 민원증명 원본확인 화면(발급번호 14자리 4-3-4-3)을 따랐다. 실제 홈택스 출력본이 서식과 글자 단위로 같은지는 실물로만 확인할 수 있다.

## 2. docparse PDF 경로(D17 §3, ADR-014)

- **pdf.js 6.4.299 고정.** CVE-2026-16633(스크립팅 경로, 6.2.108에서 수정) 이후 버전이다. **6.x에는 eval 경로가 아예 없어 `isEvalSupported` 옵션이 없어졌다**(5.7.284에서 PostScript 함수가 Wasm·인터프리터로 바뀜). D17 §3·ADR-014의 "`isEvalSupported:false`"는 "eval 경로가 없는 버전(≥ 5.7)으로 고정"으로 고쳐 적기를 제안한다.
- **워커는 페이지가 직접 띄워 `workerPort`로 넘긴다.** `workerSrc`로 두면 워커를 못 띄울 때 pdf.js가 메인 스레드 가짜 워커로 조용히 넘어가 파서와 MessagePort가 같은 JS 세계에 놓인다. 커스텀 스킴 모듈 스크립트·모듈 워커는 `standard`·`secure`·`supportFetchAPI`만으로 돌았다(`corsEnabled` 불필요).
- **CSP**: 워커는 페이지 CSP를 물려받지 않으므로 pdf.js 워커·tesseract 워커 응답에 CSP 헤더를 따로 붙인다. 페이지 CSP에서 `'unsafe-eval'`과 `worker-src blob:`을 뺐다(pdf.js·tesseract 모두 그대로 돈다).
- **송신 차단**: 세션의 `webRequest`는 WebRTC(STUN·TURN)를 보지 못한다(1차 검수에서 UDP·TCP가 로컬 리스너에 닿는 것을 실측). 창마다 `setWebRTCIPHandlingPolicy('disable_non_proxied_udp')`, 세션에 죽은 프록시(`socks5://127.0.0.1:9`, 루프백 우회 없음)를 걸었다. e2e가 docparse 창 **안에서** fetch·WebSocket·WebRTC를 시도해 리스너에 닿은 수 0/0을 확인한다(보호를 뺀 사본에서는 UDP 8·TCP 2가 닿아 시험이 누출을 잡는 것도 확인). 다운로드(`will-download`)도 막는다.
- 함께 싣는 파일: cmaps(ToUnicode 없는 Adobe-Korea1 CID 폰트 복원), 표준 폰트·wasm 3종(OCR 렌더링용). 스크립팅용 quickjs는 싣지 않는다. 옵션: `useWorkerFetch:false`(커스텀 스킴은 메인 스레드 XHR), `disableFontFace`, `useSystemFonts:false`, `enableXfa:false`, `stopAtErrors:false`, `maxImageSize` 2,500만 화소, 앞 5쪽만.
- **줄 재구성**: 같은 y(글자 크기 절반 허용)끼리 묶고 x 순으로 잇는다. 칸 사이가 벌어지면 공백. NFC, 제어 문자 정리, 폭 없는 문자 제거.
- **텍스트 층 판정**: 쪽당 20자 미만, 깨진 글자(PUA·U+FFFD·제어) 2% 초과, 한글·ASCII·흔한 기호 90% 미만이면 "없음". ToUnicode를 끊은 합성 PDF 19건이 모두 텍스트 층 없음으로 판정돼 OCR로 넘어갔다.
- **스캐너가 덧입힌 글자 층**: 쪽 그림 위에 보이지 않는 글자(렌더 모드 3·7)가 있으면 남의 OCR 결과로 보고 `scanned`로 알린다(그리기 목록을 못 만들어도 `scanned`로 본다). 엔진은 이 층을 원본 텍스트로 믿지 않는다(§4). 흰 글자·쪽 밖 글자·그림에 덮인 보통 글자는 감지하지 않는다(실물 측정의 `scanned` 수로 다시 본다).
- **OCR 전처리**: 서식의 음영 칸·표 선이 tesseract를 크게 흔들었다(첫 측정에서 핵심 칸 11/19, 신뢰도 중앙값 75). 흑백 변환(임계 170, 붉은 직인은 지움) + 글자일 수 없는 긴 가로·세로 선 제거 뒤 19/19가 됐다. 합성 자료에 붉은 직인과 0.6° 기울기를 넣은 뒤에도 19/19(신뢰도 중앙값 82)다.
- **암호 PDF**: 권한 암호만 걸린 PDF는 그냥 열린다. 열기 암호는 `password_required`·`password_incorrect` 코드로 묻고, 사용자가 넣은 값으로 다시 연다(저장하지 않는다, 256자 상한). 그사이 main은 고른 파일의 **바이트**를 최대 2건, 5분 들고 있고(경로가 아님), 취소하면 버린다. 보관함에는 받은 파일을 그대로 둔다. D17 §1의 "복호화 사본 보관"과 열기 암호를 비밀 입력 창으로 받을지는 Phase 1에서 정한다.
- **세션 준비**: 스킴 처리기·요청 차단·권한 거부는 세션에 한 번만 걸고, 죽은 프록시 설정만 비동기로 기다린다. 프록시 설정이 실패하면 창을 띄우지 않고(`session_failed`, 송신 차단 없이 PDF를 열지 않는다) 다음 작업이 프록시만 다시 시도한다(e2e로 확인).
- 실패는 코드로만: `input_size`·`not_pdf`·`read_failed`·`session_failed`·`invalid_pdf`·`parse_failed`·`timeout`·`memory_limit`·`renderer_gone`·`schema`. 파일 내용·경로를 로그·오류에 남기지 않는다(파일은 연 핸들 하나로 확인하고 읽는다).

## 3. S13b 측정(맥, M5 Pro, Electron 45.1.0 / Chromium 156)

`reports/raw/poc-8-docparse.json`. 작업 시간은 창 생성부터 결과 검증까지, 메모리는 docparse 렌더러 프로세스 작업 집합 최고치(pdf.js·tesseract 워커 포함)다.

| 경로 | 건수 | 작업 시간 중앙값 / 최대 | 메모리 중앙값 / 최대 | 핵심 칸(종류·발급일·만료일) | 비고 |
|---|---|---|---|---|---|
| 텍스트 층 PDF | 19 | 92ms / 103ms | 120MB / 122MB | 19/19 | 발급기관·발급번호·사업자번호까지 19/19 |
| ToUnicode 끊은 PDF → OCR | 19 | 1.08초 / 1.42초 | 529MB / 537MB | 19/19 | OCR 신뢰도 중앙값 89 |
| 그림 PDF(약 290dpi, 붉은 직인, 0.6° 기울기) → OCR | 19 | 1.14초 / 1.44초 | 591MB / 614MB | 19/19 | OCR 신뢰도 중앙값 82 |
| 7쪽 텍스트 PDF(앞 5쪽) | 1 | 111ms | 127MB | — | D13 S13b 기준 "5쪽 ≤ 3초" 통과, 추출값도 1쪽과 같음 |

- 기준 "규칙 추출 ≥ 95%"는 합성 자료에서 세 경로 모두 100%다. 실물에서는 다시 잰다(§6). 합성 그림은 실물 스캔보다 깨끗하다(배경 무늬·잡음 없음).
- OCR 경로에서 놓친 부가 칸: 발급번호 첫 칸 T를 1로 읽은 1건(값이 틀린 채 남음), 사업자번호 줄을 통째로 놓친 1건(빈 칸). 그래서 **OCR급 글자(docparse OCR, 스캐너 글자 층)로 읽은 서류는 만료일을 사용자 확인 전에는 확정하지 않는다**(`read_by_ocr`·`scanned_text_layer`). 형식이 맞는 오독은 규칙으로 걸러지지 않기 때문이다.
- 시간·메모리 상한은 OCR 도중에도 작업을 끊고 창을 파기한다(e2e: OCR 중 0.7초 상한 → `timeout`, 300MB 상한 → `memory_limit`). 렌더러 사망(`renderer_gone`) 경로는 자동 시험이 없다.
- docparse 창은 동시에 2개까지 띄운다(OCR 창 하나 약 600MB). 대안 (b) AppContainer/Low IL 실행 파일과의 비교(ADR-014 조건)는 지금 수치로는 필요 없다고 본다. Windows 실측 뒤 확정한다.

## 4. 메타 규칙(S4)과 만료 규칙(D07 §3)

- **종류 판별**: 제목 + 본문 문구(OCR은 글자 사이를 넓힌 제목을 자주 놓친다). 국세 납세증명 = (`납세증명서` 또는 `국세징수법`+`체납`) ∧ (`세무서장` 또는 `국세징수법`). 사업자등록증명 = `사업자등록증명` 또는 (`사업자등록일`+`증명합니다`+`세무서장`). 지방세 납세증명·사업자등록증·휴폐업 사실증명·영문 증명·두 종류가 섞인 PDF는 `docType: null`과 이유로 남기고, 보관은 `other`로 한다(ADR-018 결정 7).
- **라벨**: 공백을 지운 사본에서 찾고 값은 원문의 짧은 창(라벨 뒤 수십 자)에서 읽는다(서식 라벨이 「사 업 장 소 재 지」처럼 띄어 인쇄된다). 라벨은 50번까지만 본다(라벨·날짜를 반복해 채운 1MB 텍스트도 0.25초 안에 끝난다). 날짜는 `2026년 11월 1일`·`2026. 11. 1.`·`2026-11-01`을 받고, 실제 날짜이고 앞뒤에 숫자·영문·자모가 붙지 않아야 한다(OCR의 `3O일`·`3ㅇ일`·`3 0일`을 3일로 자르지 않는다).
- **정하지 못할 때**: 서로 다른 날짜가 둘 이상이거나, 읽히는 날짜 옆에 없는 날짜(`2월 30일` 같은 OCR 오독 흔적)가 섞이면 정하지 않는다. 그때 후보는 **가장 이른 날짜**다(발급일·만료일을 이르게 잡는 쪽이 만료된 서류를 내는 사고를 막는다). 서로 다른 후보 전부(`options`, 최대 8개)도 남긴다. 유효기간은 발급일을 고치면 쓸 수 있는 후보가 달라지기 때문이다(발급일 이후 가장 이른 후보를 쓴다).
- **발급일**: 마지막 `증명합니다` 뒤 맺음 부분의 날짜(담당부서·세무서장 줄). 출력일시·납부기한·개업(연월)일·등록일·접수일·유효기간·서식 개정일 라벨이 붙은 날짜, 시각이 붙은 날짜, **같은 줄에서** 기간 표기(`~ ∼ 〜 - – — 부터`)로 이어진 두 날짜, `부터`·`~`로 끝이 열린 기간의 시작은 뺀다(다음 줄이 쪽 번호 `- 1 -`로 시작하는 것은 기간이 아니다). `증명합니다`와 `발급일` 라벨이 모두 없을 때만 `세무서장` 근처 날짜를 쓰고, 그 값은 **불확실**(`issued_on_uncertain`, 확인 필요)로 둔다.
- **유효기간**(납세증명서만): `유효기간` 라벨 바로 뒤 날짜, `A ~ B`면 끝 날짜. `A부터 30일간`처럼 끝을 못 읽거나, 모르는 구분자(`A ∽ B`, `A 에서 B`)로 날짜가 하나 더 붙어 있으면 정하지 않는다(시작일을 만료일로 잡지 않게, 이때는 후보도 없다). **발급일 ≤ 유효기간 ≤ 발급일 + 30일**이 아니면 쓰지 않는다(시행령 제96조. 지정납부기한으로 짧아지는 것은 정상).
- **발급기관·발급번호·사업자번호**: `○○세무서장`(이름 2~4자, 부서명·날짜 글자로 끝나지 않음 — '잠실'은 세무서 이름, '민원봉사실'은 아님, 붙은 글자·띄운 낱글자·섞인 OCR 모두), 발급번호 4-3-4-3(OCR이 T를 ㅠ·ㅜ로 읽는 것을 되돌림), 사업자번호는 체크섬이 맞아야 값으로 둔다(틀리면 후보).
- **못 뽑은 칸**은 값 없이 이유(`not_found`·`unparseable`·`ambiguous`·`checksum_failed`·`not_applicable`·`unsupported_doc`)를 남긴다. 결과는 JSON Schema(값과 이유는 배타, 형식 패턴, 판별 결과와 종류 일치, 사업자등록증명의 유효기간 칸은 `not_applicable`)를 통과해야 저장한다.
- **텍스트 층이 핵심 칸을 못 줄 때**: 종류를 정했는데 발급일을 못 찾거나, 종류를 못 알아봤는데 글자가 적거나(300자 미만) 증명서 단서(`세무서`·`증명`·`납세`·`사업자등록`)가 있으면 엔진은 저장하지 않고 OCR 다시 읽기를 청한다(보통 문서마다 OCR 1초·600MB를 쓰지 않게). main이 같은 바이트를 `forceOcr`로 다시 읽어 넘기면, 엔진이 두 읽기 중 점수(종류 > 발급일 > 유효기간, 지원 밖이라도 종류를 알아본 쪽)가 높은 쪽으로 저장한다. OCR이 낫지 않으면 처음 텍스트 층을 쓴다. 머리말만 글자이고 본문이 그림인 PDF를 위한 경로다. 실물 측정 스크립트는 같은 규칙(`docmeta/choose.ts`)을 쓰지만 main·엔진 코드를 그대로 부르지는 않는다.

- **`doc_meta_check_v1` 후보**: 날짜 ±40자 문맥(마스킹, 최대 8개)을 만들고 L0 규칙의 그림자 판정을 기록한다. 모델은 부르지 않는다. **지금 L0 규칙은 실제 서식 배치에서 답하지 못한다.** 서식에서 `유효기간`·`발급일` 문구가 여러 날짜 가까이 있어 ±40자 문맥이 겹치고, 규칙은 "문맥에 라벨이 있는 후보가 정확히 하나"일 때만 답하기 때문이다. Phase 1 제안: 후보 문맥을 "날짜 앞 문맥"으로 바꾸거나, 라벨 바로 뒤 날짜를 고르는 이 PoC의 규칙 추출기를 1차 판정으로 쓰고 `doc_meta_check_v1`은 추출기가 정하지 못한 칸에만 부른다(D04 §3 변경, PoC-12에서 결정).

## 5. 보관함(D07 §1.3·§4)

- 엔진이 파일을 `vault/{docType}_{yyyyMMdd}_{shortId}.pdf`로 쓴다. 임시 파일에 쓰고 fsync한 뒤 하드 링크로 이름을 붙인다(같은 이름이 있으면 덮어쓰지 않고 다른 shortId). 하드 링크를 못 거는 파일 시스템이면 `COPYFILE_EXCL` 복사. 권한 0600. DB 등록이 실패하면 쓴 파일을 지운다. 이름을 붙인 뒤 임시 파일을 못 지워도(백신 잠금 등) 가져오기는 성공이고, 남은 임시 파일(일반 파일만)은 다음 실행에 지운다.
- 가져오기는 한 번에 하나씩 돈다(같은 파일 동시 가져오기·임시 파일 정리 경쟁 방지). 같은 파일(sha256)은 다시 쓰지 않고 기존 항목을 돌려주며, 보관함 파일이 지워졌으면 그때 되살린다. 같은 서류의 다른 파일(그 서류를 스캔한 PDF 등)은 따로 보관된다. 발급번호가 같으니 Phase 1에서 "같은 발급번호 서류가 이미 있음" 안내를 더한다.
- DB는 v1 `documents` 행 그대로다(스키마 변경 없음 → PoC-6의 v2 마이그레이션과 겹치지 않는다). `meta_json`에는 추출 칸·이유·만료 출처·읽은 글자 출처만 두고 원문 텍스트는 두지 않는다. 렌더러 보기에는 파일 경로가 없다.
- 사업자 프로필에 붙이고, 대상 사업자번호가 다르면 "다른 사업자 서류"로 표시한다. 사업자 프로필이 없으면 `profile_required`.
- `document.import`는 main 전용이다(렌더러 허용 목록에서 뺐다). 렌더러는 바이트·텍스트를 지어 보낼 수 없고, main은 사용자가 고른 파일만 docparse로 넘긴다(D17 §1.3).
- **사용자 확인·수정**(`document.update`): 화면은 바뀐 칸만 보내고, 엔진도 저장값과 같은 값은 바뀌지 않은 것으로 본다.
  - 만료일을 바꾸면 그 값(확인함). 납세증명서는 발급일 + 30일을 넘으면 거부, 비우면 확인 필요로 남긴다. 사업자등록증명 만료일은 지울 수 있다(법정 유효기간 없음).
  - 종류·발급일만 바꾸면 만료일을 규칙으로 다시 정한다. 다시 정한 값이 화면에 보였던 값과 다르면 `expiry_recomputed`로 확인 필요(보여 준 뒤 한 번 더 확인받는다). OCR급 글자에서 읽은 유효기간을 되살렸거나 OCR이 읽은 발급일이 그대로면 `read_by_ocr`도 남긴다. '그 밖의 서류'로 바꾸면 만료일은 그대로 두고 확인한 것으로 본다.
  - 아무것도 바꾸지 않으면 지금 값을 확인한 것(추정 → 확인함, 대상 사업자 확인 포함). 종류를 정한 서류에 발급일이 없으면 `issued_on_missing`으로 남긴다(만료 경고가 영영 안 뜨지 않게).
  - 대상 사업자 이유는 수정해도 남고 '아무것도 바꾸지 않은 확인'에서만 지운다. 발급일이 오늘보다 뒤면 거부.
  - 확인 화면은 정하지 못한 칸의 후보를 값 칸에 넣지 않고 "후보 …(PDF에서 확인하세요)"로만 보여 준다. 사용자가 '후보 넣기'를 누르거나 직접 입력해야 들어간다.
  - **본 값(`seen`)**: 화면은 보여 준 종류·발급일·만료일을 함께 보내고, 엔진은 저장값과 다르면 `stale`, 없으면 `seen_required`로 거부한다(셸 2차 검수 High). '바꾸지 않음 = 확인'이라, 확인을 두 번 눌러 같은 수정이 다시 오면 두 번째가 사용자가 본 적 없는 재계산 값을 확인함으로 만들 수 있었다. 옛 화면으로 확인하는 것도 같이 막힌다.

  - `document.file`(새 RPC, main 전용): 보관함 파일 경로. main이 사용자 기본 뷰어로 열 때만 쓰고 렌더러에는 경로를 주지 않는다. 파일이 없으면 `file_missing`.

- main(`shell-app.ts`):
  - 가져오기는 한 번에 하나다(겹치면 `busy`). 파일 대화상자는 렌더러가 `pick`을 보낼 때만 연다. 이 값은 렌더러가 주장하는 값이고, 사용자 클릭인지 main이 확인하는 것은 Phase 1이다.
  - 'PDF 열기'는 보관함 경로가 `.pdf`일 때만 연다.
  - 문서함 오류(목록·시작 화면 포함)는 알려진 코드만 렌더러로 보낸다. 그 밖의 오류(fs 오류 등, 경로가 들어 있을 수 있다)는 `failed`로 바꾸고, main 로그에는 코드만 남긴다.
  - 남는 것: 외부 뷰어가 보관함 원본을 고칠 수 있다(Preview 자동 저장 등. sha256과 어긋날 수 있다). 읽기 전용으로 여는 방법은 Phase 1에서 정한다.
- 화면:
  - 'PDF 가져오기'(앱 창에 붙은 모달 대화상자), 열기 암호 줄. 읽는 동안 가져오기·열기·그만두기를 막는다. 암호를 묻는 중에 새로 가져오면 묻던 파일은 그만둔다. 읽는 동안 다른 화면으로 가면 끝나도 끌고 오지 않고 알리기만 한다.
  - 목록: 확인 필요 표시(맨 위), 만료 칸에 출처(문서·추정·확인함, 확인 필요인 값은 출처와 상관없이 추정), 발급일 없는 서류 처리.
  - 문서 패널: 서류 카드(유효 칸에 데이터 위계 확실성 표시), 발급기관·발급번호·읽은 곳, 확인 필요 이유, 종류·발급일·만료일 확인, 'PDF 열기'(사용자 기본 뷰어).
    - 바뀐 칸만 보내고 보여 준 값(`seen`)을 붙인다(§5). 만료일을 지우려면 '만료일 없음'을 고른다(납세증명서 제외. 종류를 납세증명서로 바꾸면 꺼진다).
    - 저장값이 있는 날짜 칸을 비우거나 입력하다 만 채로는 보내지 않는다. 빈 칸을 '바꾸지 않음'으로 보내면, 사용자는 빈 칸을 보고 눌렀는데 예전 값이 확인되기 때문이다. 입력하다 만 날짜는 다시 그리면 빈 칸이 된다.
    - 확인 요청은 한 번에 하나다. 확인 구역을 (다시) 만든 뒤 0.7초 동안은 확인 버튼을 꺼 둔다(패널을 열 때, 저장 뒤, `stale` 뒤 새 값으로 다시 그릴 때). 두 번 누른 두 번째 클릭이 새로 그린 버튼에 닿아 보지 않은 값이 확인되지 않게 하려는 것이다.
    - `stale`이면 알리고, 목록을 다시 읽은 뒤 새 값으로 확인 구역을 다시 만든다.
    - 저장된 만료일이 없는 사업자등록증명·그 밖의 서류는 '만료일 없음'이 켜진 채로 열린다.
    - 후보(정하지 못한 칸의 가장 이른 날짜. 유효기간은 발급일 이후 것)는 칸 값과 다르면 칸이 차 있어도 보여 주고, '후보 넣기'로만 칸에 들어간다.
    - 개발 콘솔 보관함 구역도 같이 고쳤다: 후보 표시, `seen`, 입력하다 만 날짜, 두 번 보내기, `stale`이면 목록 다시 읽기, 확인 필요인 만료일은 '추정(확인 필요)'.
    - 1차 검수 High: 유효기간 줄이 둘인 납세증명서는 만료일 칸이 30일 규칙 날짜로 차 있어 문서 후보가 보이지 않았다. 2차 검수에서는 엔진이 잠정 만료일을 더 이른 문서 후보로 두도록 바꿨다(§4 표).
    - 입력 중인 값은 같은 서류를 보는 동안 다시 그려도 남는다. 패널을 닫거나 다른 서류로 옮기면 버리고, 다른 서류의 저장 응답이 지우지 않는다.
- 셸 진입점이 docparse 스킴도 특권 스킴으로 등록한다(`registerShellSchemes`).
- 시험: 공급자 단위 4건(`tests/shell-docs.test.ts`, 실제 DataService를 RPC로), 엔진 `seen`·잠정 만료일·후보 전부 단위 시험(`tests/documents.test.ts`·`tests/docmeta.test.ts`), 셸 문서함 e2e 41항목(`apps/desktop/src/shell-docs-e2e.ts`, 셸 엔진 fixture 모드 → `reports/raw/poc-8-shell-docs.json`·`reports/raw/poc-8/shell-docs.png`), 개발 콘솔 스모크, PoC-6 셸 e2e 51/51.

## 6. 실물 20건 측정(준비됨, 미실행)

1. 발급받은 납세증명서·사업자등록증명 PDF를 **git 작업 폴더 밖** 폴더에 둔다(스크립트가 작업 폴더 안이면 거부한다). 실물은 저장소에 커밋하지 않는다.
2. `pnpm build && electron apps/desktop/dist/poc8-measure.js <폴더> --draft` → `<폴더>/labels.draft.json`(파일 목록만 든 빈 정답 틀). PDF를 직접 보고 종류·날짜·번호를 채워 `labels.json`으로 저장한다. 추출값은 종류까지 미리 채우지 않는다(정답이 추출기 쪽으로 쏠리지 않게). 종류가 빈 표본이 있으면 측정을 시작하지 않는다.
3. `electron apps/desktop/dist/poc8-measure.js <폴더>` → 앱과 같은 규칙(OCR 다시 읽기 포함)으로 읽어 순번별 결과를 낸다. **합격**: 두 종류가 모두 있고, 두 종류 표본 중 95% 이상(20건이면 19건)이 종류·발급일·유효기간(납세증명서는 **문서에서 읽은 값**이 맞아야 함. 규칙 추정이 우연히 같아도 맞음으로 세지 않는다) 모두 맞고, **확인 없이 확정했는데 틀린 건(silent wrong) 0건**. 파일을 못 읽은 표본도 실패로 센다. `other` 표본은 분모에서 빼고 분류 정확도만 따로 센다. 저장소에는 값 없는 요약(`reports/raw/poc-8-real.json`: 순번·참거짓·이유 코드·시간·L0 그림자 답 여부)만 쓴다. 열기 암호는 `--password-stdin`으로 한 줄 넣는다(셸 기록에 남기지 않는다). 콘솔에는 파일명 대신 순번만 쓴다. 오래된 표본은 `SAX_POC8_TODAY`로 기준일을 줄 수 있다.
4. 합성 21건(텍스트 15·그림 6)으로 스크립트를 돌려 21/21을 확인했다(결과 파일은 지웠다).

## 7. 검수

- **Opus 1차(2건, 보안·경계 / 정확성·실패 경로)**: High 2·Medium 6·Low 다수. 모두 반영했다.
  - 화면이 세 칸을 다 보내 "규칙으로 다시 계산"에 갈 수 없어 틀린 만료일이 확인함으로 굳던 것 → 바뀐 칸만 보내고 엔진도 같은 값은 무시, 다시 계산한 값의 확인 필요 유지.
  - 스캐너가 덧입힌 OCR 글자 층을 원본 텍스트로 믿던 것 → 보이지 않는 글자 감지(`scanned`), 확인 필요.
  - 텍스트 층이 핵심 칸을 못 줘도 OCR로 넘어가지 않던 것 → 엔진의 다시 읽기 요청과 두 읽기 비교.
  - 라벨 없는 대체 창 날짜를 확정하던 것 → 불확실 표시.
  - WebRTC 우회 → 창 정책 + 죽은 프록시, 창 안 송신 시험.
  - 발급번호 추출의 제곱 비용 → 창 길이·라벨 수 상한.
  - 그 밖: 측정 스크립트가 `other`를 분모에 넣고 조용한 오답을 세지 않던 것, 임시 파일 삭제 실패로 가져오기가 실패하던 것, 동시 가져오기 중복 행, 다운로드, 워커 CSP, 오류에 경로, 확인 뒤 파일 바뀜, 동시 작업 상한, 기간 표기·날짜 경계·세무서장 이름 규칙, 스키마 조건, 폭 없는 문자, 붉은 직인, 측정 정답 초안의 쏠림.

- **Opus 2차(2건, 1차 반영 확인 / 처음 보는 눈으로 전체)**: 1차 지적은 대부분 해결로 판정. 새 지적 High 1·Medium 5·Low 다수를 반영했다.
  - 수정 경로가 OCR 유효기간을 문서 값으로 되살려 확정하던 것 → 다시 계산한 값이 보였던 값과 다르면 확인 필요, OCR 이유 유지.
  - 다른 사업자 서류를 그대로 만료 추적하던 것 → 확인 필요(`subject_mismatch`·`subject_unverified`).
  - 화면이 후보를 값 칸에 채워 한 번 저장으로 확정하던 것, 후보가 늦은 날짜이던 것 → 후보는 표시만, 가장 이른 날짜.
  - 발급일 없는 서류를 확인하면 만료 경고가 사라지던 것 → `issued_on_missing`.
  - 측정이 규칙 추정을 유효기간 맞음으로 세고, 정답 틀에 종류를 미리 채우던 것 → 문서 값만 맞음, 종류도 비움, 두 종류 모두 필요, 읽기 실패도 실패로.
  - 그 밖: 같은 줄 기간 표기만 보기(다음 줄 '-'로 발급일을 놓치던 회귀), '잠실세무서장', 날짜 경계(`3ㅇ일`·`3 0일`), 모르는 기간 구분자, 오독 흔적이 섞인 날짜, 지원 밖 종류를 알아본 OCR 우선, 보통 문서의 불필요한 OCR, 납세증명서 조정 일수 상한, `scanned` 판정 실패 처리, 세션 준비 실패 뒤 재시도, 폴더 fsync, OCR 도중 상한 시험, 앱 스모크 판정화.
  - 반영하지 않고 남긴 것(§9): 엔진이 이름 붙이기와 DB 등록 사이에 죽으면 남는 고아 파일(sha256 재연결 스캔 없음), 수정 뒤 파일명 갱신, 렌더러 사망 시험, main `rpc()` 시간 상한·단일 인스턴스 잠금(기존 코드, PR #9 범위).

- **Bugbot·CodeSolar(PR #12 1차)**: Bugbot Medium 1·Low 1, CodeSolar Medium 1.
  - 세션 준비 재시도가 같은 파티션에 스킴 처리기를 다시 걸어 영구 실패하던 것(Electron에서 재현 확인) → 동기 설정은 한 번만, 프록시만 재시도.
  - 너무 긴 암호가 들고 있던 바이트를 버리던 것 → 입력 검사를 먼저.
  - 창을 띄운 뒤 메시지 채널 생성이 실패하면 창이 남던 틈 → 채널을 정리 구간 안에서 만든다. CodeSolar가 말한 "창 생성 실패 시 finally가 정의되지 않은 값으로 돈다"는 창 생성이 `try` 밖이라 일어나지 않는다.
